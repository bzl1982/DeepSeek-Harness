## 二、第 1 轮 · 立论（互相看不见）

这一轮每个模型收到的 prompt 里**只有自己的角色 + 议题**，没有任何其他人的信息。
这是有意的：先各自独立表态，避免一上来就互相锚定。

### DeepSeek API（正方）

**它收到的 prompt（逐字）**

```text
【你的角色】
你是这场辩论的正方。你的立场是：主张「切换到微软 MAF 框架」。
请给出你方最强的论证：2 条核心理由，每条一句话。
禁止和稀泥、禁止说"要看具体情况"。

【本轮任务】
议题：通辽会议的多 AI 编排层，应该切换到微软 MAF/AutoGen 框架，还是继续自研？
请发表你方立论。
```

**它的回复**

**正方立论：**

1. **MAF 提供开箱即用的多 Agent 编排原语（GroupChat、Handoff、Magentic 等），自研团队重复造轮子的时间成本足以拖垮通辽会议的交付节奏，而微软的持续迭代让这些原语只会越跑越稳。**
2. **押注微软生态意味着零成本继承 Azure AI Foundry 的可观测性、安全护栏和企业级兼容性，自研方案在审计、合规和长期维护上必然被越拉越远。**

## 三、第 2 轮 · 对辩（只看别人的，不看自己的）

这一轮的关键差异：prompt 里**换成了对方的立论**，而**自己的立论被摘掉了**。
机制上用的是 `selectSlice(OTHERS)` —— 过滤条件是 `senderId !== selfId`。

| 席位 | 切片内容 | 注入字数 |
|---|---|---|
| DeepSeek API | others | 209 |
| Google API (Gemini) | others | 216 |

### DeepSeek API（正方）

**它收到的 prompt（逐字）**

```text
【你的角色】
你是这场辩论的正方，立场是：主张「切换到微软 MAF 框架」。
下面【现场发言】里是对方刚刚发表的立论。
你的任务：**逐条反驳它**——指出对方论证里的漏洞、被忽略的事实或站不住的前提。
要求：用 1./2. 编号；不要复述自己的立场；不要写"我同意某部分"。

【Google API (Gemini) 说】
我方坚决主张**「继续自研，不切框架」**。立论如下：

1. **业务契合与性能可控：** 自研多 AI 编排层已深度绑定通辽会议特有的复杂业务逻辑与高并发响应需求，盲目切换到 MAF/AutoGen 会引发不可控的迁移成本与架构阉割。
2. **核心技术自主与长远演进：** 编排层是系统的核心“大脑”，唯有坚持自研才能避免被微软第三方框架锁死技术演进路线，确保数据合规与绝对的技术自主权。

【本轮任务】
请反驳【现场发言】中对方提出的论点。
```

**它的反驳**

1. “深度绑定业务逻辑”不是继续自研的理由，而是切换成本被高估的借口。通辽会议特有的复杂业务逻辑应当沉淀在领域服务或工作流定义里，而不是和编排引擎耦合在一起；如果现有自研层真的把业务逻辑写死在编排内核中，那恰恰说明它的架构已经不可维护。MAF 提供的是编排原语、状态管理、工具调用和可观测性，业务规则仍可由我方代码承载。对方把“需要适配”直接等同于“架构阉割”，却没有说明哪些具体能力 MAF 无法表达，这是以迁移成本替代可行性论证。

2. “避免被微软框架锁死”是一个方向正确但对象错误的恐惧。继续自研同样会被锁死，而且锁死在自己的隐性知识、离职风险和无人维护的内部代码上。MAF 作为开源框架，其编排协议、工具接口和模型接入层可以隔离；真正需要自主的是数据、提示词、业务规则和部署控制权，而不是每一行调度循环。对方没有证明 MAF 会剥夺这些控制权，只把“第三方”等同于“不可控”，这是把技术选型问题偷换成主权口号。

3. “性能可控”忽略了一个事实：自研编排层在高并发下的性能问题往往来自状态一致性、重试、超时和可观测性缺失，而不是框架本身。MAF 已经把这些做成可配置能力，自研则要重复实现并自行承担缺陷。对方假设自研一定更快，却没有给出压测数据、瓶颈位置或 MAF 的性能基准，这是把未经验证的假设当成前提。

4. “数据合规与绝对技术自主权”并不由是否自研编排层决定。合规取决于数据流向、存储位置、访问控制和审计能力；这些在 MAF 上可以通过自托管、私有化部署和自有工具层实现。相反，自研编排层如果缺乏成熟的安全审计和权限模型，反而更容易产生合规盲区。对方把“自研”与“合规”直接画等号，却没有说明 MAF 具体违反哪一条合规要求，这是用情绪化安全感代替事实论证。

2. **押注微软生态意味着零成本继承 Azure AI Foundry 的可观测性、安全护栏和企业级兼容性，自研方案在审计、合规和长期维护上必然被越拉越远。**

**它的反驳**

1. **对方所谓的“开箱即用”忽视了真实业务逻辑的适配成本，且将外部框架迭代等同于“稳定”是严重的逻辑谬误。** 通用的编排原语（如 GroupChat、Handoff）看似省时，但在复杂业务场景下极难直接落脚，团队不得不花大量时间去绕过框架的黑盒限制，甚至被迫修改框架源码，这引发的调试与排错成本反而会彻底拖垮交付节奏。此外，微软开源或商业框架的历史（如 Semantic Kernel 或 AutoGen 的频繁破坏性更新）表明，巨头的“持续迭代”往往伴随着高昂的 API 断层升级成本，绝非对方预想的“越跑越稳”。

2. **所谓的“零成本继承生态”是以放弃数据自主权与架构弹性为代价的“隐性高昂成本”。** 绑定 Azure AI Foundry 意味着彻底被微软生态锁定（Vendor Lock-in），在私有化部署、跨云架构或敏感数据不出域的严格合规要求下，云端集成的“开箱即用”反而会变成最大的合规阻碍。自研的可观测性与安全护栏能够精准贴合自身业务的审计需求，而依靠外部框架不仅无法做到真正的深度审计，还会让企业在长期的 API 计费和云资源捆绑中失去议价能力与技术自主性。

## 四、这两轮的差异说明了什么

同一场会里，同一个模型的 prompt 在两轮之间发生了变化：

| 轮次 | 切片 | 它看得到什么 | 它看不到什么 |
|---|---|---|---|
| 第 1 轮 立论 | `TASK` | 只有议题 | 其他所有人的发言 |
| 第 2 轮 对辩 | `OTHERS` | 对方的立论 | **自己的立论**（防自我复述） |

这就是「互动」在工程上的确切含义：**不是把几个 AI 放在一起各问一遍，**
**而是每一轮的 prompt 都由「前面谁说过什么」动态组装出来。**

如果哪一天互动断了，症状会非常明确：第二轮 prompt 里切片为空 ——
那说明 `messages` 没被写进会议状态，或者 `selfId` 传错了导致过滤掉所有人。
