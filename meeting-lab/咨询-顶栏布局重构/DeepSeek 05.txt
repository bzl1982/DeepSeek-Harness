## Q1（向 A 派）— 通义三轮刀，正面接

**我上轮立场：A。本轮：接受逃生舱，但理由不是"被驳倒"，而是"刀 3 在 T1 确实成立"。**

### 刀 1（剪贴板解耦可见性）：我承认 60%，反驳 40%

通义说"粘贴那一刻源窗口内容已在剪贴板，不需同屏"。这**在手抄场景下成立**——用户选中→Ctrl+C→开抽屉→Ctrl+V，确实不需要同屏。

但反驳点：**剪贴板解耦的是"粘贴动作"，没有解耦"选择动作"。** 用户要 Ctrl+C 之前，必须先决定"抄哪一段"。transparent 模式下 web3 的回答里引用了 web1 的论点，用户要判断抄哪段，必须**同时看到 web1 和 web3**。这个判断发生在"选中"那一刻，而不是"粘贴"那一刻。B 派把"选择"和"粘贴"混成一个动作，刀 1 只切了后者。

**但——** 这个反驳只在"答案有交叉引用"时成立。如果 9 席答案彼此独立（broadcast 退化形态），刀 1 完全成立，A 的并排优势归零。**所以刀 1 部分成立，取决于工作流形态，不是无条件成立。**

### 刀 2（A 在 running 自吃 96px）：我承认，但这是设计债不是方案债

通义说"running 中手动抄答案要先手动展开甲板→网格底行被压矮"。**这是事实，我承认。** 修正版 A 的 `data-editing=true` 只冻结自动折叠序，不阻止用户手动展开——手动展开时确实吃 96px。

但这不是 A 方案本身的缺陷，是**修正版 A 没把"编辑态"和"展开态"解耦**。解法：`data-editing=true` 时 topdeck 用 `flex-basis:28px` 但 `max-height:40vh` 的**overlay 子层**展开，不占布局高度：

```css
body[data-editing="true"] .topdeck{
  flex-basis:28px;  /* 布局高度不变 */
  position:relative;
}
body[data-editing="true"] .deck-body{
  position:absolute;
  top:28px; left:0; right:0;
  max-height:40vh;
  z-index:100;
  background:#fff;
  box-shadow:0 4px 12px rgba(0,0,0,.15);
}
```

编辑时甲板**不占布局高度**，overlay 浮在网格上方，网格不缩。**刀 2 被这个补丁中和。** 但代价：overlay 会盖住网格顶部，用户抄答案时看不到顶行席位。这是**纵向遮挡换横向遮挡**，比 B 的右侧遮挡更轻（顶行通常不是回收目标）。

### 刀 3（自动回收让手抄归零）：我承认，这是 A 翻 B 的合法判据

通义说"T1 下 A 成本无正当性"。**我承认。** 如果自动回收可靠率 ≥80% 且用户手动占比 <20%，A 的顶甲板确实过度设计。**我接受这个阈值作为 A 翻 B 的判据。**

但刀 3 有个前提：自动回收**必须真跑通**。当前 R5 还是待建功能，T1 不存在。用 T1 的假设否定 T0 的设计，是**用未来赌现在**——除非有可测遥测。

**所以我的最终立场：A 在 T0 成立，但接受"跑 N=10 次后按遥测翻 B"的决策规则。刀 3 我接，但接法是"接受遥测判据"，不是"现在翻 B"。**

## Q2（向 B 派）— 修正版 A 是否消灭了你们的攻击？

### 对 Agnes "态冲突正交论"

Agnes 说"overlay=布局树零占位，折叠序/密度/logdock 全照常，甲板补丁面=0"。修正版 A 加 `data-editing=true` 硬锁后，**态冲突确实被中和**——编辑中自动折叠序 early-return，手动折叠仍可用。Agnes 的"甲板跟折叠序打架"前提**因此失去**。

但 Agnes 的更深论点是"甲板补丁面=0"——修正版 A 加了 `data-editing`、加了 overlay 补丁、加了 max-height，补丁面从 0 变 3。**这不是态冲突，是复杂度税。** Agnes 若说"B 补丁面 0 因此更优"，这个论点**在修正版 A 下仍部分成立**。

### 对通义 "纵向税"

豆包算账"日均<35px"。我修正版 A 的 overlay 补丁后，running 中编辑**不占布局高度**，纵向税趋近 0。**通义"纵向税"攻击在 overlay 补丁后基本失效。** 但 overlay 补丁本身是新增复杂度，不是免费。

### micro 密度（50+ 席）

Kimi 说"micro 下卡内抽屉展不开"。B 的 overlay 在 50+ 席**仍可用**——因为 overlay 不占布局宽，micro 卡片 56px 高不影响右侧抽屉。**B 在 micro 下优势不打折。** 但 A 在 micro 下也不差——顶甲板 overlay 补丁后同样不占布局高。**micro 不是区分点。**

## Q3（向双方）— 逃生舱：接受

**我接受"先 ship 默认 A + 可切换 + 遥测翻 B"。**

理由：Q3 胜负 = 未验证的自动回收率。硬定一个 = 用布局直觉赌未来。逃生舱不是和稀泥，是"默认 A + 明确决策规则 + 可测遥测"——**比"我觉得 A 好"硬，比"定死 A"诚实。**

**但我加一条修正：遥测指标不只回收率，还要加"编辑态频次"。** 如果用户 90% 时间在 running 中编辑，overlay 补丁的顶行遮挡会成为新痛点，此时 B 的右侧遮挡可能更优。指标：

```js
const Q3_METRICS = {
  autoRecoveryRate: 0.0,    // 自动回收可靠率
  manualRatio: 1.0,         // 手动占比
  editingInRunningRatio: 0.0, // running 中编辑占比
  topRowObstructionMs: 0,   // overlay 遮挡顶行累计时长
};
// 翻 B 条件：autoRecoveryRate >= 0.8 && manualRatio < 0.2
// 或：editingInRunningRatio > 0.5 && topRowObstructionMs > 阈值
```

## Q4（向双方）— 人工咨询"双半"补设计

### 最终态度：hybrid 是合理分工，不是 muddle

**分发半在顶甲板，回收半在右滑抽屉。** 理由：

- **分发半是"写+发"，属于配置/操作**，与 topdeck 的 mode-params、toolmatrix 同节奏，放顶甲板顺。
- **回收半是"读+抄+汇总"，属于监控/审计**，与 tooldock 的日志/工具时间线同节奏，放右滑抽屉顺。
- 两者共用 `DispatchJob` 三态（分发态/回收态/文件态），但**不共用面板**。

### 分发半线框

```text
┌─ .topdeck > .dispatch-panel ──────────────────────────────┐
│ 咨询稿: [contenteditable 多行]                             │
│ 附件: [选择文件] 已选 3 个  [预览]                         │
│ 席位: [全选] [web1] [web2] ... [api1] ...                 │
│ 发送: [一键发全部] [逐席复制]                              │
│ 进度: 已发 2/9  失败 1 (web3: setFileInputFiles 静默失败)  │
│ 失败兜底: [web3 复制稿] [web3 选文件] [标记已发]           │
└────────────────────────────────────────────────────────────┘
```

### 回收半线框

```text
┌─ .tooldock > .collect-panel ──────────────────────────────┐
│ [对话] [工具] [回收] [权限]                                │
│ ┌ web1 ✓已答 ──────────────────────────────────────────┐  │
│ │ <回答内容预览>                          [落盘] [重抄] │  │
│ └──────────────────────────────────────────────────────┘  │
│ ┌ web2 ○未答 ──────────────────────────────────────────┐  │
│ │ [粘贴回答] [标记未答]                                 │  │
│ └──────────────────────────────────────────────────────┘  │
│ 汇总: 已答 5/9  缺失: web6 web7 web8 api2                 │
│ [生成 R5-共识提炼.md]                                      │
└────────────────────────────────────────────────────────────┘
```

### 分发半 CDP 失败兜底

`setFileInputFiles` 静默失败 → DispatchJob 降级链：

```js
async function dispatchFile(seat, filePath){
  try {
    await cdpSetFileInputFiles(seat.webviewId, filePath);
    if(!await checkUploadOk(seat)) throw new Error('upload not confirmed');
    return { ok:true };
  } catch(e) {
    return { ok:false, fallback:'manual', reason:e.message };
  }
}
// 降级 manual：显示 [复制稿] [选文件] [标记已发] 三按钮
```

**成本：** 分发面板 +1 DOM；回收面板 +1 DOM；DispatchJob 三态已定。  
**反例：** 如果用户只做回收不做分发（纯人工咨询），分发面板可折叠隐藏。
