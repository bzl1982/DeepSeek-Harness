## §2 第 1 轮共识基线（已锁定，作为本轮设计前提，不要重新发明）

> 以下为 9 家中 ≥7/9 一致、且经我方核对源码确认可行的结论。**除非你能推翻，否则视为已定。**

1. **删固定右栏 `.side`（380px）**，`.main` 只剩 `.grid`，占满整宽。（9/9）
2. **顶部 `.topdeck` 控制甲板**（可整段折叠、真腾纵向空间）+ **底部 `.logdock` 日志停靠条**（展开 `flex:0 0 32%` ↔ 折叠 `flex:0 0 28px` 只留标题行）。（8/9）
3. **外部 AI 回答 = 顶甲板内折叠表单**（间歇录入），max-height 限高防撑爆；**会议日志 = 底部停靠**（持续滚动）。（7/9；通义千问的"右侧 overlay 抽屉"少数派方案记录在案，若你支持它请给出比 7 家共识更强的理由）
4. **主持人栏常驻**（广播/发文件双态可用）；⏸暂停/⏹停止随"开会中"阶段显隐或灰显（细节分歧：display:none vs opacity 灰显，本轮 Q4 映射表里一并定）。（8/9）
5. **模式 × 阶段双键**（`data-mode` + `data-phase`）驱动 CSS 显隐，替代零散 if；倾向**固定 DOM + hidden 属性**（不重渲染、事件不重绑、测试友好）。（7/9）
6. **折叠机制统一两条规则**：无 webview 容器 → `display:none` 或 `height:0+overflow:hidden`；含 webview 的 `.grid`/`.cell` → **永不 `display:none`**，只被动响应兄弟容器 flex 尺寸变化（resize 会发生、会不卸载，登录态不丢）。（8/9）
7. **顶部最多两层**：`.header`（一行常驻）+ `.topdeck`（可折叠）；现有 `.flow`/`.scene` 降级为 modezone 子成员。（Kimi 提出，多数隐含接受）
8. **可加分项（第 1 轮独占硬货，欢迎认领或改进）**：deck-summary 收起态一行摘要（ChatGPT）；日志自动滚动跟随暂停/恢复（豆包）；广播按钮文案随态切换（Kimi）；窗口高度阈值自动折叠（豆包）；"resize 不可避免"诚实表述（DeepSeek）。

## §3 本轮新增需求（第 1 轮没写，是设计前提的变更）

### 3.1 席位规模化：12 只是起点，50+ 是常态，无上限

**现状证据（已核源码）**：
- 角色组下拉直接显示固定席位数：`o.textContent = \`${s.label}（${s.seats} 席）\``（`shell/index.html:1680`）——角色库 14 角 6 组，**按固定席位数设计**，第 13 个 API 接入点加进来就溢出。
- 每排窗口数下拉只有 3/4/5/6（`index.html:186-191`）；列数 `relayout()` 按参会数自适应的分支最多算到 4 列。
- 上下文成本 O(N²)：9 人专家会诊一轮注入 153 份材料（实测）——50 席不分组就是 2500 份/轮。
- API 接入点从客户端 `settings.yaml` 动态读入（`getRedacted()`），**数量由用户的 API key 决定，会持续增长**。

**要你设计的**：
- 网格在 50+ 席位时的组织方式（分组页签？虚拟滚动？密度档位缩小卡片？搜索定位席位？）；
- 「每排 N 个」下拉如何升级（自动按席位数+视口算？档位扩展？）；
- **角色组去固定席位化**：任意 N 人怎么分配角色（超编时角色怎么合并/轮替/分组，组长怎么选）；
- 每个方案的成本与反例（尤其 webview 数量有实际上限：9 个网页 + N 个 API div，API 是轻 div 可以多，网页 9 个封顶——这个不对称你要利用）。

### 3.2 能力对齐：网页席位获得工具箱（对标 WorkBuddy）

**背景**：DeepSeek Harness 桌面壳内置 **200+ 工具**（文件、shell、检索、多模态生成等，对标 WorkBuddy 的工具箱能力）。目前：
- API 席位走 OpenAI-compatible chat（纯文本）；
- 网页席位走 webview `insertText` + 页面发送按钮（纯文本）；
- **两者都还没有工具调用通道**。

**目标**：让网页席位经壳层获得与 API 席位一致的工具能力（网页 AI 说"我要查文件 X"，壳层执行 Harness 工具，结果回注给该席位），最终**网页和 API 在能力与 UI 上无区别**。

**要你设计的（只做 UI/交互层，工具执行引擎不在本轮范围）**：
- 席位卡片的信息架构怎么统一（现在 API 名牌带 `-API` 后缀标签，网页是公司+模型名——拉平后怎么标识/要不要标识）；
- **工具面板放哪**：席位卡片内抽屉？⧉弹出窗里加工具页？全局工具台？——注意 12 个 webview 里是网页本体，工具 UI 只能做在我们壳层；
- 工具调用的呈现：调用中（哪个工具、参数）/ 结果（成功/失败/内容预览）/ 结果回注（自动带给下一轮 vs 用户确认后发）；
- **权限控制**：200+ 工具不可能全开，按席位配置工具白名单的 UI 放哪、默认给谁开什么；
- 开会中多席位并发调用工具时，用户怎么不被工具输出刷屏（聚合？按席位隔离？）。

### 3.3 模式清单（Q4 映射表的对象）

8 种模式：`transparent`（透明广播）/ `panel`（专家会诊）/ `build`（工程交付）/ 顺序接龙 / 辩论 / 质证 / 分组会诊 / 开放讨论。每种模式的「开会前配置组 / 开会中控件组」你给出完整映射（模式细节可合理假设，但表要覆盖全部 8 种 + phase 键）。

## §4 交付格式要求（不合格标准写在最前）

1. **必须有 ASCII 线框图**（展开态 + 收起态；席位卡片带工具面板的也画）。纯架构论述 = 不合格。
2. 每个设计决策附**"为什么"**（对照 §3 的真实约束说，不写教科书理由）。
3. 字段级：容器 class / 状态键 / 尺寸值 / 映射表条目。
4. 每个建议：成本（DOM/状态/重排/测试影响）+ 反例（什么时候不该这么做，要针对本台真实约束）。
5. 关键 CSS/HTML 片段可以给，**不要整文件代码**（我方落地后跑 `node --test` 400 用例验证）。
6. 结尾一句话：你对 §2 共识基线的态度（无推翻 / 推翻哪条+理由）。
