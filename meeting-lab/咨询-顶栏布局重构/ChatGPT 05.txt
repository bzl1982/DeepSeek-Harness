这一轮我会明确收口，不再因为“两个方案都有道理”而继续拖。我的判断是：**Q3 不应该靠 AI 的布局直觉永久定死，应该改成“默认 A、同时把 B 做成可切换布局，并用真实使用数据决定默认值”**。但这不是和稀泥，而是把一个尚未存在的 T1 能力，转化成可验收的产品实验。

# Q1：A 派还能不能守住纯 A？

## 我的上轮立场：A；本轮翻转为“**A 默认，但不再坚持纯 A**”

原因不是被某一刀彻底击倒，而是三刀叠加后，**“纯 A 永久正确”已经没有足够证据支持**。

### 刀 1：剪贴板解耦

通义的原话：

> “粘贴那一刻源窗口内容已在剪贴板，不需同屏。”

我承认这击中了 A 派上一轮“对照式回收”论证中最脆弱的一环。

真正的人工动作是：

```text
窗口 7
↓
选择答案
↓
Ctrl+C
↓
打开回收面板
↓
Ctrl+V
```

从纯操作路径看，**复制完成之后，源窗口确实不再是必须可见对象**。

所以我不能再把“9 窗并排可见”说成手动回收的刚性需求。

但也不能反过来说它完全没有价值，因为：

```text
粘贴
↓
核对是否完整
↓
发现复制错位置/少段落
↓
返回源窗口重新选取
```

这个时候同屏仍然降低往返成本。

因此这项优势从：

> “人工回收必须同屏”

降级成：

> “人工回收有时受益于同屏，但不是决定性需求”。

**这一刀 A 派应当让分。**

---

### 刀 2：running 下的 96px 纵向税

通义的原话：

> “A 在 running 自吃 96px，用户 manual 抄答案若发生在 running，要先手动展开甲板。”

这一刀也成立。

但修正版 A 已经不是“展开后永久 96px”。

我们现在应该把它定义成：

```text
topdeck collapsed
≈ 28px

topdeck expanded
= min(28vh, 220px)
```

并且：

```text
manual capture
editing
dirty
attachmentPending
```

任何一个状态成立：

```text
auto-collapse = false
```

用户结束当前回收：

```text
commit
↓
extState = idle
↓
可以自动回到 28px
```

因此真正的纵向成本不是：

> “每天持续占 96px。”

而是：

> **只有人工编辑/回收窗口存在期间占空间，完成后回到摘要行。**

但这里必须承认一个事实：

**T0 当前人工模式下，这个状态很可能经常被用户打开。**

所以“只有短时成本”现在还只是设计意图，不是实测事实。

---

### 刀 3：T1 自动回收

通义的原话：

> “自动回收让手抄归零。”

这个方向没有争议。

如果自动回收成熟，T1 的核心工作就从：

```text
人工抄 9 次
```

变成：

```text
等待自动回收
↓
检查异常席位
↓
确认最终结果
```

那么为了一个低频动作长期给它顶部操作空间，确实可能是错误的。

所以这一刀我不再硬扛。

---

## 因此我的最终结论

**纯 A，我不再坚持。**

我接受：

```text
V1 默认 A
V1 同时实现 B 切换
T1 用真实遥测决定默认值
```

这不是退缩，而是因为 Q3 的争议核心已经从“哪个布局逻辑更正确”变成了：

> **未来自动回收成熟后，用户还会不会经常手动操作这个面板？**

这是可测问题，不应该继续靠想象。

# Q2：如果站 B，本轮我会怎么评价修正版 A？

这里我认为 B 派上一轮的两个主要攻击，已经**不再足以要求 A 彻底失败**。

## 1. “态冲突”已经基本消失

Agnes 的原话：

> “甲板跟折叠序打架。”

修正版加入：

```text
data-editing="true"
```

并规定：

```text
editing
dirty
capturing
attachmentPending
```

均阻止自动折叠。

所以：

```text
自动折叠
      ↓
用户进入编辑
      ↓
锁住自动折叠
```

不再出现：

```text
展开
↓
系统又收回
↓
用户再展开
```

因此我认为：

> **这个攻击在修正版 A 上已经失去决定性。**

它变成一个普通状态机实现问题，而不是架构缺陷。

---

## 2. “纵向税”也已经大幅削弱

28px 摘要态其实把长期成本压得很低。

而且这里还有一个以前没充分利用的事实：

**人工咨询是“一个任务写一次，多个席位分发；多个席位回收”。**

所以顶部空间最值得保留的其实不是“答案正文”。

而是：

```text
分发状态
回收状态
异常状态
```

例如：

```text
人工咨询   已发 9/9   已回收 7/9   ⚠2
```

这 28px 就已经非常有价值。

---

## 3. micro 密度下 B 也不是无条件占优

Kimi 的原话：

> “50+ 席位 micro 下卡内抽屉展不开。”

这个判断我完全保留。

所以 B 如果说：

> “右侧 overlay 永远解决问题”

也不成立。

50 席时：

```text
SeatCard = 56px
```

卡内根本不适合放工具历史。

所以 B 最终也必须演化成：

```text
卡片
  ↓
状态摘要
  ↓
全局 Dock
```

也就是说：

**真正成熟的 UI 已经不是“A vs B 的纯形态竞争”，而是各自承担不同信息密度。**

# Q3：我接受你的“逃生舱”，但我要修改一个关键地方

## 接受：

```text
默认 A
+
B 可切换
+
10 次真实人工咨询遥测
+
根据数据改变默认
```

### 不接受只用一个“可靠率 ≥80%”

因为：

> **自动回收最怕的不是漏，而是错收。**

例如：

```text
真实回答漏收：
Claude → 未回收
```

用户还能手工补。

但：

```text
把上一轮旧回答误当成新回答
↓
写进 WorkBuddy 送审包
↓
被后续 AI 当成真实新观点
```

这个错误会污染最终分析。

所以我的正式验收指标应该是两个：

### 自动回收 Precision

```text
错误提交次数 = 0
```

在试运行阶段，我甚至建议：

> **任何 1 次错误自动提交，都不能直接把它判定为“自动回收成熟”。**

### Recall

```text
正确自动回收 / 所有应该被回收的回答
```

目标：

```text
≥ 80%
```

### 人工介入率

```text
需要人工确认/补回收的席位
÷
全部已完成回答
```

目标：

```text
< 20%
```

---

## 因此我的 T1 切换规则

### 翻 B 为默认：

```text
10 次真实人工咨询
+
自动回收 Precision = 100%
+
Recall ≥ 80%
+
人工介入率 < 20%
```

### 保持 A 默认：

只要：

```text
Precision < 100%
```

或者：

```text
Recall < 80%
```

或者：

```text
人工介入率 ≥ 20%
```

满足任意一个，就不翻。

---

## 还有一个必须补充的记录项

不要只记录“用户最终用了哪个布局”。

还要记录：

```text
externalPanelOpenCount
externalPanelEditDuration
manualRecoveryCount
autoRecoveryCount
manualCorrectionCount
dockSwitchCount
```

这样半年后都可以重新算。

# Q4：人工咨询的“双半”到底怎么落？

这一题我的最终态度是：

# **Hybrid 可以做，而且我认为这是合理分工，不是 muddle。**

但前提是：

> **不是把同一个面板拆成两半乱摆，而是把两个完全不同的工作对象拆开。**

---

# 一、顶部负责“咨询任务”

顶部：

```text
Consult Composer
```

负责：

```text
咨询稿
附件
席位选择
投递策略
分发进度
```

例如：

```text
┌──────────────────────────────────────────────────────────────┐
│ 人工咨询                                      已发 7 / 9      │
├──────────────────────────────────────────────────────────────┤
│ 咨询稿                                                       │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ 请分析……                                                │ │
│ └──────────────────────────────────────────────────────────┘ │
│                                                              │
│ 附件：[需求.pdf] [截图.png]                                 │
│                                                              │
│ 席位：☑ Claude ☑ GPT ☑ Gemini ☑ Qwen ...                   │
│                                                              │
│ [复制给当前席位] [发给全部]                                 │
└──────────────────────────────────────────────────────────────┘
```

---

# 二、自动/人工分发统一成 DispatchJob

```text
DispatchJob
├─ prompt
├─ attachments[]
├─ seats[]
├─ transport
│   ├─ auto
│   └─ manual
└─ status
```

每席：

```text
pending
sent
failed
```

文件：

```text
not-needed
pending
sent
failed
```

所以 CDP 上传静默失败时：

```text
auto
↓
fileState = failed
↓
attention
↓
[手动选择文件]
```

而不是：

```text
按钮点了
↓
假装成功
```

---

# 三、右侧 Dock 负责“回收/观察”

这里就可以和 ToolDock 合并成：

```text
ContextDock
├── 工具
├── 回收
└── 当前席位
```

但注意：

**“回收”不是编辑器。**

只显示：

```text
当前席位
回答状态
自动检测结果
原始回答预览
[确认回收]
[重试]
[标记已回答]
```

例如：

```text
┌───────────────────────────────┐
│ 回收 · Claude                 │
├───────────────────────────────┤
│ 自动检测：✓ 新回答           │
│ 置信度：高                    │
│                               │
│ ┌───────────────────────────┐ │
│ │ Claude 的完整回答……      │ │
│ │                           │ │
│ └───────────────────────────┘ │
│                               │
│ [确认回收] [重新检测]         │
└───────────────────────────────┘
```

这样不会把“编辑长咨询稿”和“查看某席回收结果”混到同一交互焦点里。

---

# 为什么这个 Hybrid 不属于 muddle？

因为它们服务的是两种不同对象：

```text
TopDeck
对象 = Consultation Job

ContextDock
对象 = Seat/Task/Event
```

一个操作：

> **我要把什么东西发出去？**

另一个操作：

> **这个席位现在回来了什么？**

所以这是**数据对象分离**，不是 UI 随便拼盘。

---

# 这也解决了 A/B 的最终争论

实际上最后形成的是：

```text
顶部
└─ 咨询任务/分发

右 Dock
├─ 工具活动
└─ 回收检查

网格
└─ 9 个网页 + N API

底部
└─ 系统日志
```

外部 AI “回答正文编辑器”才是：

```text
TopDeck
```

而不是右 Dock。

# Q2 透明广播：最终 21 条意外因素应该如何落地

前面 21 条分析里，我再强调几个必须进 P0 的，不只是“以后补”。

## ① 单席超时

不要让：

```text
等待第 7 席
```

把整轮锁死。

轮次状态：

```text
7 / 9
```

最后两个：

```text
⏱ timeout
```

汇编：

```markdown
### DeepSeek
> [本轮超时，未形成可用回答]
```

而不是静默消失。

---

## ② 发送失败自动降级

真实链路：

```text
AUTO
 ↓
send
 ↓
FAILED
 ↓
MANUAL
```

用户看到：

```text
DeepSeek
⚠ 自动投递失败
[复制到剪贴板]
```

而不是需要自己判断为什么没发出去。

---

## ③ DeepSeek 提前完成

这项我建议明确成：

```text
suspect_complete
```

而不是：

```text
completed
```

状态层：

```text
GENERATING
SUSPECT_COMPLETE
COMPLETED
```

只有：

```text
候选内容存在
+
内容稳定
+
结束证据
```

才可以 `COMPLETED`。

这和你现在的“增量比较”事实是兼容的，但不能继续把一个过早的 provider 信号当最终真相。

---

## ④ 验证码/登录弹窗

这是典型的：

```text
attention=blocking
seat=degraded
phase=running
```

三者同时成立。

不要为了一个席位验证码把整场会议状态莫名其妙切成 paused。

---

## ⑤ O(N²)

这一条我会比普通“提示框”更硬：

```text
预计上下文注入：
N = 24
预计开轮传播量 = ...
```

超过安全阈值：

```text
⚠ 当前会议规模可能造成上下文爆炸

[按广播域拆分]
[继续承担成本]
```

但如果引擎自己明确规定某模式必须广播全体，就不能 UI 私自改语义。

---

# 还必须补两个透明广播真机意外

## 22：网页席位被用户手动点击，破坏自动操作焦点

比如广播正在向 ChatGPT 投递：

```text
页面获得焦点
↓
用户点了别处
↓
输入框状态变化
```

修复：

```text
自动发送前
→ 检测目标输入容器
→ 重新定位
→ 确认当前页面仍属于该 provider
```

失败：

```text
seat = manual_intervention_required
```

不要盲点。

---

## 23：网页回答中“重新生成”导致双版本

例如模型第一次：

```text
Answer A
```

用户点：

```text
重新生成
```

出现：

```text
Answer B
```

如果只看“最后一条 assistant 内容”，可能把 A、B 混成一次回答。

必须给每次 dispatch 一个：

```text
responseCandidateId
```

并绑定：

```text
dispatchId
attemptId
```

这样：

```text
attempt 1 → A
attempt 2 → B
```

审计关系清楚。

# 其他 10 个模式快检

这里我继续按你列出的模式逐个给**新意外因素**。你这一段实际上列了 10 个非-transparent 模式，我按 10 个检查。

| 模式           | 新意外因素                                  | 修复                                                              |
| ------------ | -------------------------------------- | --------------------------------------------------------------- |
| `broadcast`  | 某个席位返回内容极短但格式合法，系统误以为已经完成高质量回答         | 完成判定和质量判断分离；`completed` 不等于 `usable`，允许 `low_content` attention |
| `review`     | 多份材料之间存在不同版本，AI 实际审阅的不是同一批材料           | 建立 immutable `materialSetId`，每个席位记录实际使用的材料集合                    |
| `assist`     | 用户执行后得到的真实结果与 AI 建议不同                  | `execution_result` 独立作为人类输入回合，不允许系统自动把原建议当执行结果                  |
| `iterate`    | 修订后只是换措辞，实质问题没变，却因为 critique 文本变化而继续循环 | 增加结构化 critique fingerprint，区分“文字变化”和“问题集合变化”                    |
| `debate`     | 一方因为格式异常没有生成可解析论点，下一阶段却把空结果当成真实立场      | 立论产物必须 `argument.valid=true`；无有效论点只能标缺失                         |
| `panel`      | 20 席中某一位异常慢，导致后面的 19 席长期等待，用户误认为系统卡死   | 当前席位明确显示 `第 7/20 席 · 等待 Claude`，并显示独立 timeout，不允许无状态等待          |
| `chairman`   | 主席连续点名同一个席位，形成重复发言循环                   | 点名历史 `calledSeatIds` 去重/重复阈值；达到重复阈值进入 attention                 |
| `divide`     | 两个分工任务分别修改同一个产出文件                      | 建立 artifact ownership / merge boundary，不能直接覆盖同名产物               |
| `tournament` | Borda 结果出现并列第一，`same-winner` 根本无法判断    | 必须定义 tie-break 规则；无规则时进入 `verdict_pending`，禁止自行拍板               |
| `build`      | 构建成功，但产物目录不是用户预期目录                     | READY 阶段冻结 workspace/output path；build 结果记录绝对路径并回显              |

其中 `tournament` 的并列第一，我认为尤其应该提前定义。否则：

```text
A = 7.2
B = 7.2
```

如果代码直接：

```js
winner = max(score)
```

就会产生一个**看似确定、实际上无定义**的 winner。

这属于引擎契约，不应该交给 UI 临时处理。

# 我给第 5 轮的最终判词

**Q3：我翻转“纯 A”，接受最终形态为“默认 A + B 可切换 + 数据驱动默认值”。**

但不是：

> “A、B 都不错。”

而是：

> **T0 真实用户明显依赖手工分发/回收，因此默认 A；T1 自动回收成熟后，是否继续承担 A 的交互成本必须由真实 Precision / Recall / 人工介入率决定。**

**Q4：双半采用 Hybrid，但按“任务对象”分工：TopDeck 管咨询稿/分发，右侧 ContextDock 管回收/工具，不做一个混合大面板。**

> **第 5 轮之后，不值得再开第 6 轮大范围争 UI/工作流方向了。可以进入实现阶段；先完成“5 家 Provider 自动回收 + ToolDock/WebView 层级”的工程闸门验证，闸门通过就正式改 UI。**
