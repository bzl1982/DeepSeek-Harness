Q1 · phase 状态机：支持"四相 + attention"，但必须补一个正交维度 round

结论（选边）：采纳你的 setup / running ⇄ paused / done 四相 + attention 正交。反对五态（通义）、反对六态（ChatGPT）、反对三态（Kimi）、反对维持两相（豆包系）。但四相要加一条你没写的前提：loop 型模式的"轮"不是 phase，是 running 内部一个正交计数器 round，phase 机对 round 无感知。

为什么四相是闭集（逐个过 11 个真实模式）：
模式   loop   setup 特有   running 里的 round   终止→done   paused 语义
broadcast   否   无   无（单遍）   全员答完即 done   中途收料

review   否   材料门槛   三阶段是 running 内子进度不是 phase   归并完 done   暂停派发

assist   否   无   三阶段子进度   收敛完 done   暂停派发

iterate   ≤5   草稿门槛   round=1..N，判据 no-new-critique   判据达成/耗尽→done   插话补草稿

debate   否   无   两阶段子进度   对辩完 done   暂停派发

panel   否   无   依次发言=顺序游标   归并完 done   暂停派发

chairman   ≤4   API 席位门槛   round=1..N，判据 no-new-question   判据达成/耗尽   主持人改点名序

divide   否   无   三阶段子进度   拼装完 done   暂停派发

tournament   ≤3   无（但有产出契约）   round=1..N，判据 same-winner   连续同 winner/耗尽   暂停改标

build   是   无（有验证档门槛）   round=1..N，判据 buildPass   buildPass/耗尽   暂停改产物

transparent   固定 1-10   议题+资料门槛   round=1..10（硬计数）   轮数跑满 done   插话补料

结论清晰：11 个模式全部塞得进四相。区别只在 running 内部要不要显 round——loop 型（iterate/chairman/tournament/build）显示，单遍型不显示。这不是第五相，因为 round 与 phase 正交：paused 时 round 冻结在原值、恢复后从原 round 续，它永远不是和 running 平级的状态。

为什么不加第五相（configuring）——通义 5 态的反例：通义想把 setup 再拆成"配置中 / 就绪"两相。但"就绪"不是一个用户停留的态，它是 READY Gate 的瞬时校验结果（见 Q6），校验通过就直接跳 running。给它一个 phase 会导致一个尴尬中间态：用户卡在 configuring-ready 里，既不能改配置（配置冻结了）又不能开会（等校验），纯增心智负担。READY Gate 应该是 setup→running 的一条带拦截的边，不是一个驻留节点。

为什么不是三态（Kimi done 版，无 paused）——反例：chairman/iterate/tournament 的 loop 里，主席常要"暂停插话改点名序 / 补一条批评"（§4 chairman 硬约束、§2 定案 17"开会中允许席位停用激活"都依赖 paused）。没有独立 paused，暂停就被塞进 running，控件语义混淆：running 下"开始/暂停/停止"三态互斥关系要靠 disabled 表达，且自动折叠序（定案 14）会误判"还在 running 就收甲板"，可你暂停恰恰是要展开甲板插话。paused 必须是显式态。

成本 / 反例：
成本：data-phase 取值 4 个 + data-round（loop 型才写）+ attention 独立 data-attention。DOM 上就是 body 属性，零重建，400 用例只要不断言 phase 具体串、只断言节点在，全绿。
反例（对四相唯一要防的坑）：loop 模式的"轮间屏障"（一轮结束、准备下一轮）容易被误当成第五相 round-transition。别建。轮间是一个自动发生的瞬时事件，UI 上用"轮结束摘要条"表达即可（见 Q6 漏洞6 的 done-exhausted 区分），不占 phase。

Q2 · 工具面板：支持"全局右滑 tooldock"，但反对"绑定 activeSeat 作主视图"

结论（选边）：采纳你的全局右滑 tooldock；但推翻"绑定 activeSeat"作为主视图。tooldock 的默认视图必须是跨席位事件流（按席位分桶的全局时间线），activeSeat 只能当过滤器的一个 chip，不能当数据源的唯一绑定。

为什么（这是能说服你的那条硬理由）：你自己在题面里出的极端场景"50 席同时 10 个工具在跑"，恰恰是 activeSeat 绑定必然失效的场景——它一次只渲染 activeSeat 一个席位的工具历史，而"10 个工具在 10 个席位上并发"这个监控诉求，本质是跨席位聚合，绑定单席位 = 用户要在这 10 个工具间点 10 次切换才能看全，等于没有聚合视图。§2 定案 11 的"聚合视图"精神，activeSeat 绑定是违背的。

正确形态（回答"10 工具并发长这样"）：
.toolbench (全局右滑 dock, 360px overlay)
 ├─ 顶栏[过滤: 全部▼|席位✕|风险级▼|状态▼]   ← activeSeat 只在这当chip
 ├─ 待回注 3 ▲(红点)                          ← 全局确认队列(定案19)
 └─ 时间线(全局, 每行=1次调用, 带席位色标)     ← 10并发=10行连续滚动,不用切
    ●A公司 shell ⏳ | ✎写 · 中风险 | [批准][丢弃]
    ●GPT    search ✓ | 只读 · 低风险 | 已自动回注
    ●B公司 net   ✗ 越权(高默认关)

"50 席 micro 密度（卡 56px）怎么用"：卡片在 56px 下只留一行 24px 定高状态行（🔧3 · ⏳1 徽标，点它→tooldock 自动把过滤 chip 预置成"该席位"）。即卡内不展面板（豆包/文心的 24px data-tool-state 是对的），详情全在 dock。这样 50 张 56px 小卡各自只占 24px 状态行，不挤 webview，点开才拉全局 dock。
成本：1 个全局 dock（唯一 DOM，O(1) 换绑保留——你/Kimi 这点是对的，我改成"换过滤 chip"而非"换数据源"）+ 1 个全局事件分桶 Map（所有席位的工具事件先进全局 bus，dock 只渲染过滤后的视图）。比 activeSeat 绑定多一个 Map，但少一套"每席切换重载"的抖动。

⧉弹出窗失效场景：多窗在 --disable-gpu 下截图/CDP 定位全乱，且 10 并发 = 用户满屏小窗，Electron 多 BrowserWindow 管理成本高。

Q3 · 外部 AI 回答：我改投 B（右滑抽屉），且理由是 §5 逼出来的新理由

你在 §3-C 说"倾向 A 先跑"，并给 A 加了"编辑时锁折叠"。我先诚实认输：编辑锁把我第 2 轮最强的"焦点契约冲突"论点中和掉了——你正在打字时锁住折叠，甲板确实不会把你输入框收走。所以 A 的致命伤不再是失焦。

但 §5 人工模式暴露了一个你形成"A 倾向"时还不知道的事实，它把天平重新压向 B：

在人工咨询里，"外部 AI 回答"（粘贴回答回来）是整个长会话的主交互，用户要逐个窗口粘 9 次、反复粘。它不再是"录一条就走"的间歇表单，而是全天常驻的高频操作。

这条事实决定成败：
A 的代价：顶甲板常驻吃掉纵向 ~96px 一整天。而人工咨询用户的注意力 90% 时间在 9 个网页窗口（网格）里——webview 高度被永久压矮 96px，是每天每轮都在交的"纵向税"。横向折叠禁令（定案 2）说明你们对 webview 重排极其敏感，A 常驻顶甲板就是持续给 webview 减高。
A 还留一个失效场景没被编辑锁覆盖：编辑锁只保护"已经在编辑时"不被收；但它保护不了"要开始编辑前，得先把它从折叠态展开"这个动作与自动折叠序（定案 14：running 时 topdeck 自动收成一行的 deck-summary）的冲突。用户开会中（deck-summary 态）突然要粘一条回答回来 → 顶甲板要么被迫展开（瞬间吃掉网格空间、打断看网页），要么在收起态里硬塞输入框（与"running 自动收"直接打架）。B 没有这个态冲突，因为它根本不在甲板里。
B 的真正红利：tooldock（Q2）反正要一个右侧 overlay 抽屉，外部回答复用同一套抽屉组件（一个组件两用途，省一套输入容器 DOM 和状态），且用时出现、平时 0 占位，完美贴合"高频但非同时——粘回答时你要么在看网页要么在看工具，不粘时该还空间给网格"。

我是每天用它咨询的用户，我要 B：因为我的主战场是 9 个网页窗口，我要它们多高就多高；回收/工具这两个"用时才看"的输入流，用时右滑出来、平时收干净。

对 A 的公道话：如果你的实际用法以自动会议为主、极少人工回收，A 也够用，"尊重用户挪到上面原话"就成立。但 §5 说明当前真机恰恰以人工为主，所以我押 B。若你坚持先跑 A 过渡，唯一要加的护栏：deck-summary（running 自动收）时，点外部回答输入必须走"临时展开 + 展开期间豁免自动折叠"，而不是只在输入态锁。

Q4 · API 虚拟滚动：支持你的"先原生"倾向，但分界线是"节点数"不是"席位数"，且中间档用"惰性展开"

结论（选边）：支持你——先原生滚动 + 分组/域页签 + 密度档，不预建真虚拟化。但你要的"可测判据、不要拍脑袋"我给三条，并且数量分界线不是席位数的函数，谁给你"50/100/200"谁就是拍脑袋。

为什么席位数不是判据：Chromium 渲染进程画 200 个空壳 div毫无压力（Gemini"50 个轻 div 无压力"完全正确）。真正压垮渲染进程的是累积的消息 DOM 节点和 resize 时的全量 reflow/paint。一个 API 席位展开一段长回答 ≈ 100–500 个文本节点；50 席 × 300 = 15k 节点才到临界。所以分界线是 密度档 × 每席平均活跃消息节点数 决定的总活跃 DOM，不是席位数量。

三条可测判据（都在 --disable-gpu + Runtime.evaluate 下跑，不靠截图）：
节点总量闸：document.querySelectorAll('.grid *').length。经验安全区 < 8000。换算：comfort 档每席~300 节点 → ~25 触顶；compact/micro 档隐藏历史每席~50 节点 → ~150 触顶。这就是"分界线"——它在 25（展开历史）到 150（隐藏历史）之间浮动，取决于密度档。
单帧重排闸：resize 时包一层强制 reflow 测耗时：t0=performance.now(); grid.getBoundingClientRect().width; ...; performance.now()-t0。单帧 layout+paint > 16ms 即触顶。
长任务闸：new PerformanceObserver(e=>e.getEntries().forEach(x=>x.duration>50&&console.log('longtask',x.duration)))，observe ['longtask']。resize/新消息注入时出现 >50ms longtask → 上治理。

务实三档路径（这就是我的落点，比"全虚拟化"和"纯原生"都好）：
档 0（默认可覆盖 90% 场景）：域页签/分组页签天然把可见席位压到 ≤20（一个域 ≤12 席），绝大多数情况判据 1-3 全绿 → 纯原生滚动，Gemini 是对的，什么都不用上。
档 1（中间档，我推荐作为主要治理手段）——"惰性展开历史"而非"虚拟化挂载"：IntersectionObserver 只回收离屏 API 席位的"展开历史文本"，收起为一个占位高度，席位名牌行始终在 DOM 里。这样滚动条高度稳定、scrollIntoView 高亮定位不破（守住定案 23"搜索=高亮不筛选"，因为占位行还在 DOM 可定位）。它是 web/API 不对称的又一次利用：API 格可自由 mount/unmount（轻 div），但"unmount 的是历史文本、不是席位本身"——既省节点又不破搜索。成本：1 个 IO + 每席历史占位高度数组，远比真虚拟化省。
档 2（真窗口化，最后手段）：只有当某单域也逼近 ~80–100 席且全展开时才上窗口化。且只对 API 格，web 格永不进 IO（定案 3 红线，web 格不参与任何 observer）。

你的方案倾向对不对：对。你"先原生+分组页签+密度档、不预建虚拟化"完全正确，我只是把"分界线"从虚的席位数字换成三条可跑的实测判据 + 一个成本更低的"惰性展开"中间档。
直接上虚拟化的失效场景：过早引入 IO，滚动时 API 格频繁挂载/卸载导致文本流闪烁、选中态丢失、scrollIntoView 命中未挂载格失败（搜索高亮直接坏）。这就是 Kimi/Gemini 反对过早虚拟化的真正工程理由。

Q5 · 人工模式：选建模三（通道为底层 + "人工咨询"快捷预设），且它是自动通道的降级 fallback

结论（选边）：建模三。但我要把建模三讲成一个比"两者都要"更锋利的结构——人工通道不是与自动通道平行的第二套系统，而是同一"分发 Job"的降级 executor。 这是让"开会"与"人工咨询"共用最多代码的关键，也是状态机最不别扭的原因。

为什么建模三完胜（三个维度逐个赢）：

① 代码复用最多——因为 auto/manual 是同一 DispatchJob 的降级链。 现状事实（§5）：自动链路（📎发文件 CDP DOM.setFileInputFiles）真机不可靠（File.path 废弃、上传 ok 未检查静默失败、图片/PDF 只 push 占位符）。既然自动会失败，正确架构是把"发给席位 X 的内容+附件"抽象成一个 DispatchJob，executor 有两个实现：
DispatchJob { targetSeat, text, files[], state }
  executor = auto → CDP setFiles + 回报（现状那条不可靠链路）
  executor = manual → 复制到剪贴板 + 标记"待粘贴"（人工兜底）
  auto 执行失败/超时 → 同一 Job 自动降级为 manual（不是重试到死，是顺滑转人工）

人工咨询 = 全席位 executor=manual 的退化配置。它天然复用分发/追踪/回收/落盘全部基础设施（R1~R4 一套代码），因为人工咨询和 broadcast 的"形状"相同（全员并行分发），只是把"AI 生成内容"换成"人粘贴内容"。建模一（独立 mode）做不到这种复用——它得把分发/回收整套在 mode 里重写一遍。

② 状态机最不别扭——复用 Q1 四相，不新增 phase。 人工咨询就是 setup（选席/贴稿/传附件）→ running（人自己分发+回收，可不跑轮次）→ done（汇总落盘），paused 由人自然掌控（中途插话就是人自己操作）。引擎派发器对 manual 席位短路：不调 API/CDP，只 emit"待人工"事件 + 等回收标记。needs 门槛在人工模式天然满足（人工 review 就是人自己把材料贴进去），READY Gate 自动降级。这与建模一"新造一个 phase 走法"相比，零状态机改动。

③ 用户心智最简单——给一个一键入口，同时保留细粒度。 建模二（纯横切通道）的 UX 缺陷是：全 manual 时 mode 下拉该选什么？用户心智里"人工咨询"和"开会"是两码事，纯通道建模缺一个入口。建模三补上："人工咨询"是 mode 下拉旁的一个快捷预设，点它 = 全席 manual + 分发追踪面板 + 引擎旁路。同时保留"某席位临时转 manual"（质证临时拉一个还没 API 的人，正好用 manual），这是建模二独有的细粒度价值，建模三也保住了。

与会议引擎的关系（R3）：人工模式 = 引擎旁路（bypass）。自动轮次调度器、完成检测、上下文自动切片全部不跑（人自己判断完成），但落盘复用 round-N.md / 会议记录.md（R3 要求）。回收侧复用现有"外部 AI 回答"面板（它已能剥标注、参与切片）——这又回到 Q3：正因为人工模式让回收变高频，回收 UI 才更该是 B（用时出现的抽屉/面板），而不是常驻顶甲板吃空间。Q3/Q5 自洽。

R2 回收：[回收] 从该席把回答抓回会议记录（手动勾选 or DOM 自动检测）；未答名单置底红字。
R4 文件：手动档每席文件选择器预填同批；自动档走 CDP setFiles + 逐席状态（成功/失败/重试）。
成本：一个 DispatchJob 抽象（把现有自动广播/发文件重构到它下面，是最大工作量）+ 一张追踪表 + 复用回收面板。反例：别把人工面板做成只读进度条——必须每席带独立"复制/标记/回收"三按钮，因为 9 个窗口的粘贴顺序由人决定，UI 不能假设齐步走。

Q6 · 真实工作流总检：基于 §4 真表重做映射，并揪 4 条工作流漏洞

6.2 工作流漏洞（≥3，附修复 + setup 硬门槛怎么做）

漏洞 1｜chairman 主席位被默认塞进 web 席位 → 静默违反 ADR-001。
§4 明说主席必须走真实 API、绝不能用网页版。但用户默认往往 9 个全 web 席（现状就是 9 网页窗口）。选了 chairman 模式，主席位落在 web 席上，系统不会报错，只是"主席点名质量不可控"——这是静默错误。
修复：READY Gate 从 chairman.needs=API席位 自动推导一条硬门槛——setup 里"主席位指派"控件只列出 API 席位；若无 API 席位，"开始"按钮 disabled 并在 READY Gate 显示 ⚠ 主席模式需至少 1 个 API 席位。"不满足开不了会"就落在这一处。

漏洞 2｜tournament 的产出契约 kind 对网页 AI 不可控 → 评标当候选发出去。
§4 明说产出物必须打 kind（candidate/ballot/verdict/revision/review），否则切片把评标当候选。但网页版 AI 不保证输出结构化 kind 标注——它自由发挥，切片器拿不到 kind 就误路由，结论被污染却不报错。这是"自动严格契约模式 × 不可控网页 AI"的结构性矛盾。
修复：(a) UI 侧日志/席位卡给产出物打 kind 色标（候选蓝/名次金/结论绿），肉眼可审计切片是否正确；(b) 需要严格契约的模式（tournament/iterate 规范化）在 setup 里软提示"建议用 API 席位以强制输出契约"；(c) kind 缺失时切片不猜、进"待人工归类"队列（呼应 Q5 人工通道）。

漏洞 3｜build 第三档"真跑 npm run build" = 执行不可信 AI 代码，缺安全门槛。
§4 第三档会真跑构建（前两档不执行）。真跑 AI 写的代码是高危动作（可触发任意脚本），但当前 UI 可能把它当普通下拉选项，一键就开。
修复：把"产物验证档"做成带二次确认的 setup 硬门槛——默认锁"仅语法"，选到第三档弹确认框"将真实执行 AI 生成代码，确认？"，并在 running 的工具台/日志红标"真构建已启用"。这是 READY Gate 的安全类检查项（与 needs 类并列）。

漏洞 4｜loop 模式跑满上限但未收敛 → done 被误读为"已完成"。
iterate≤5、chairman≤4、tournament≤3、build 都有上限。若跑满上限而终止判据仍未达成（iterate 第 5 轮仍有新批评 / tournament 三轮无 same-winner），当前 done 态无法区分"收敛完成"与"耗尽未收敛"——落盘却长得一样，用户误以为已收敛。
修复：done 分两个终态徽标 done✓（判据达成） vs done⚠exhausted（轮次耗尽·未收敛），落盘 MD 首行标 # status: exhausted，会议记录里红标。这也回答 §6 第 3 点（loop 轮次语义统一又不误导）：loop 模式进度条不要用"第 3/5"假分母（暗示一定到 5），统一显示"第 N 轮 + 终止判据徽章（no-new-critique 待触发 / same-winner 待达成）"；只有 transparent 的固定轮数才用真分母"N/10"。

（附赠漏洞 5）review 第一阶段"只看材料"若可见域实现漏一格 → 锚定污染静默发生。
§4 review 硬约束"第一阶段必须并行 + 只看材料防锚定"。若某席位违规看到他人发言，结论不可信但系统不报错。修复：running 给一个可见性审计视图（每席显示"本阶段可见域 = 仅材料 / 含他人发言"），审计视图一旦有席越域即高亮告警（挂 attention，不改 phase，合定案 15）。
