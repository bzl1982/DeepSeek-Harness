# Q1｜F1 是否足以让我接受默认 A？

**接受。**

F1 已经解决了我上一轮认为最关键的“第三态缺失”问题：

> 追踪表需要展开、需要逐席操作，但展开不能改变主网格垂直几何。

因此，只要实测能同时做到：

**追踪表可点 ∧ 展开可读 ∧ 网格高度/行位零变化**

我接受：

> **R1 默认 A + 可见切换器**

### 但这里还有一个必须写进验收的具体失效场景

`position:absolute` **本身并不等于“真正浮层”**。

最容易出现的假成功是：

```text
DOM 尺寸没变
↓
Grid 行高没变
↓
验收通过
```

但实际：

```text
父容器 overflow:hidden
    ↓
浮层被裁掉
```

或者：

```text
父/祖先形成 stacking context
    ↓
z-index 无法越过 Grid / Header
    ↓
视觉上展开了，但部分区域点不到
```

或者：

```text
浮层展开后内部需要滚动
↓
滚动手势命中了底下 Grid
↓
用户感觉“又点不动了”
```

所以我建议把 F1 的最终验收句从：

> “展开不挤压网格”

升级成：

> **“展开态不改变 Grid 几何布局；浮层不被祖先裁剪；浮层内部鼠标/触摸/滚轮/键盘焦点均独立闭环；浮层关闭后原 Grid 几何恢复零漂移。”**

满足这个条件，**我不再反对默认 A。**

# Q2｜R1 三触发器 + 六指标 + N≥20，是否可以直接冻结？

## 这里我会明确打一个“暂缓冻结”。

最大问题不是指标数量，而是：

> **现在三个触发器并不在测同一件事。**

### ① Precision=100% ∧ Recall≥80% ∧ 手动<20%

这是**自动回收质量指标**。

它回答的是：

> “自动回收值不值得信？”

但它不直接回答：

> “A 甲板布局是否应该切到 B 抽屉布局？”

因此存在一个逻辑反例：

```text
自动回收：
Precision 100%
Recall 90%
手动 10%

同时：
A 下操作极少
B 下也没有明显收益
```

① 仍然会强制触发 B。

也就是说：

**数据质量达标 ≠ B 布局优于 A。**

这属于变量错位，不是统计误差。

---

### ② 分发半手动操作日均 >30min

这个比①更接近布局决策，但仍有一个边界：

```text
用户每天确实手动 40min
但这 40min 集中发生在某一种特殊任务
```

于是全局默认布局被切成 B。

这时候真正应该观察的是：

> **高频任务是否持续造成 A 的纵向税。**

所以至少要给这个触发器一个“连续观察窗口”，否则一天异常任务就可能翻转默认值。

---

### ③ 通义判据：浮层挡住逐席操作目标且无法消除

**这个才是真正的布局触发器。**

因为它直接证明：

> A 的空间模型与真实工作流发生结构性冲突。

因此三个触发器现在实际上是：

| 触发器 | 实际测量对象  |
| --- | ------- |
| ①   | 自动化准确性  |
| ②   | 工作量     |
| ③   | 布局结构性失败 |

它们可以同时发生，也可以彼此完全独立。

所以对“互斥/覆盖完备性”的回答是：

**不互斥；也不完备。**

---

## 我认为还缺一个触发器

### “短时间反复 A⇄B 切换”触发器

F3 的核心问题其实不是“有没有开关”，而是：

> 用户是否在真实任务中被迫寻找更合适的落位。

现在只有：

```text
dockSwitchCount
```

还不够。

例如：

```text
A
→ B
→ A
→ B
```

如果 30 秒内就发生两三次，这不是正常偏好切换，更像：

> 当前落位无法稳定支撑任务。

所以应把**连续短窗口切换/回切**视为异常行为。

不需要把它做成新的复杂指标体系，单纯把：

> **短时间重复 A⇄B**

设为一个机械触发条件，就足以堵住 F3。

---

## 可见切换器是否足以消解 F3？

**不完全足够，但已经是必要条件。**

可见切换器解决的是：

> “用户不知道 B 存在。”

它没解决：

> “用户虽然知道 B 存在，但长期默认不切。”

所以真正消解 F3 的不是：

```text
可见切换器
```

而是三者共同作用：

```text
可见切换器
+
dockSwitchCount
+
短时间反复切换行为
```

这个组合我认可。

---

## N≥20 也还缺一个统计边界

这里的：

> **N≥20 动作级计数**

必须明确 N 到底是什么。

否则可能出现：

```text
N = 20
其中 18 次来自正常席位
2 次来自异常 provider
```

总体 Precision 仍然漂亮。

但那个 provider 已经足以污染最终送审包。

因此建议保持你现有架构不变，只把统计单位写死：

> **总 N≥20，同时失败不能被总体平均值掩盖；provider / 席位异常必须保留逐席记录。**

这和 R3 已经存在的“失败席位显式点名”是兼容的，不需要开新架构。

# Q3｜R2 是否真的收敛 hybrid 之争？

**是，我接受 R2。**

我现在不支持重新把“分发半”和“回收半”拆成两个物理位置。

因为你已经解决了上一轮 hybrid 最大的实际疑问：

```text
逻辑组件只有一个
状态只有一份
物理落位可以变
```

这是正确的收敛方式。

---

## 但 R2 有一个必须补死的具体工作流问题

场景：

```text
1. 分发 Tab
2. seat 47 发送失败
3. 切到“回收”
4. 找到 seat 47 的返回内容
5. 手动修正
6. 切回“分发”
7. 对 seat 47 执行 L2 / L3 重试
8. 再切回“回收”确认
```

如果双页签只是：

```text
切 Tab → 重新挂载 View
```

或者：

```text
切 Tab → scroll/filter/search 全部恢复默认
```

那么这个工作流会凭空增加：

> **多次重新定位席位的操作成本。**

尤其 50+ 席时非常明显。

### 所以 R2 不需要改布局，只需要加一条状态约束：

**“分发”和“回收”各自保留自己的视图状态，同时共享同一个 `DispatchJob/dispatchTrack` 数据状态。**

至少应保持：

```text
当前筛选条件
当前滚动位置
当前搜索词
当前选中席位
```

这样：

```text
Dispatch → Recovery → Dispatch
```

才是真正意义上的“同一个工作面切页”。

否则 R2 虽然架构正确，但操作体验会出现一种非常隐蔽的：

> **“我没有丢数据，但每切一次页签都得重新找人。”**

这不是 hybrid 成立的理由，只是 R2 的实现验收项。

# Q4｜R3/R4 之外还有没有 L 级遗留？

**有，两个。**

这两个我认为必须在“开工闸门”之前冻结。

---

## L1｜READY Gate 必须是“不可变快照”，不能只是按钮状态

现在 R4 有：

> READY Gate

但必须把它解释成：

```text
草稿
↓
READY
↓
生成不可变 dispatch snapshot
↓
DispatchJob 执行
```

否则存在一个致命时序：

```text
咨询稿进入 READY
↓
开始自动分发
↓
用户修改原稿
↓
部分席位收到旧版
部分席位收到新版
```

最后回收包看似完整，但实际上：

> **9 席回答不是来自同一份问题。**

这比漏收严重得多。

因此 READY 至少要绑定：

```text
artifact/version
+
content hash
+
生成时间
```

不需要新组件，但必须是 Gate 的语义。

---

## L2｜L1/L2/L3 必须逐席幂等，否则“自动降级”可能变成重复发送

现在 R3 写的是：

> 已发 k/N + 失败席位显式点名

还差一个非常关键的执行条件：

```text
seat A 已经成功
seat B 失败
↓
L1 → L2
```

这时 L2 绝不能重新处理全部 N 席。

否则：

```text
A 已成功
B 失败
C 已成功

进入 L2

A 重发
B 重试
C 重发
```

就会出现重复咨询。

因此 `DispatchJob` 至少必须具备：

```text
per-seat status
+
attempt
+
idempotency / delivered marker
```

这样 L1→L2→L3 才是真正的**降级**，而不是“重新跑一遍”。

这个属于我认为必须在开工前锁死的 L 级条款。

# 23 条透明广播兜底：我的排序意见

我这里不重新增加条目，只谈**实现先后**。

你当前上下文中明确提到的 **22/23 号意外**，我认为：

> **“用户手点破坏自动投递焦点”应提前。**

原因很直接：

```text
自动分发
→ 用户介入
→ 焦点被手点改变
→ 自动流程继续
→ 后续席位状态错误
```

这是会直接污染 DispatchJob 状态的行为，不是单纯 UI 小问题。

因此它应该进入：

> **分发自动化真机验证之前/同时**

而“重新生成双版本”更适合放在：

> **artifact 输出与送审包验证阶段**

即：

**先防止用户操作破坏执行链，再验证产物双版本。**

# 最终裁决

### Q1

**接受 R1 默认 A。**

F1 已经补足“第三态”，但验收必须加入“不裁剪、不抢焦点、浮层内部独立交互”。

### Q2

**暂不建议原样冻结。**

最关键的漏洞是：

> **① 的自动回收质量指标与 A/B 布局选择不是同一个因变量。**

三个触发器不互斥，而且没有覆盖“用户因为真实工作流反复 A⇄B”的情况。

我建议最低限度修正为：

```text
布局结构性失败
+
持续人工时间税
+
短时间反复切换
```

而自动回收 Precision/Recall 继续作为**自动化是否升级**的门槛，不要直接承担“布局翻 B”的因果职责。

### Q3

**接受 R2，不恢复 hybrid 双物理位置。**

但冻结：

> **双页签独立保存视图状态，共享同一 DispatchJob/dispatchTrack。**

否则 50+ 席交叉操作会出现反复找席位的隐形操作税。

### Q4

**有 2 个 L 级，必须提前钉死：**

```text
L1：READY = 不可变输入快照
L2：L1/L2/L3 = 逐席幂等、禁止重复发送
```

除此之外，我没有看到足以重新开启架构争论的 L 级问题。

**因此我的开工闸门意见是：Q1/Q3 可冻结；R3/R4 主体可冻结；Q2 修正这一个逻辑缺口后，我认可进入开工。**
