
这轮我建议**不推翻 Q3 默认 A，也不再重开整体布局方向**。但 R7-1、R7-2 各有一处需要修正文案，否则开工后还会出现“看起来冻结了，实际上没有把最危险的边界钉死”的问题。

# 第 7 轮复审结论

## Q1：R7-1 是否正确？——**方向正确，但应改成“全局 L2 基座 + 按站点条件优先 L1”**

单纯把 L1 全局降成“所有站点都先 L2”其实又走过头了。

根据你给出的 F7-1/F7-2 事实，真正应该冻结的是：

> **产品层不能把成功交付建立在 L1 可用之上。**
>
> 但这不等于 Provider 层不能对少数已证明有可行专属通道的站点先试 L1。

### 站点级落位

| 站点           | 本轮建议               | 原因                                         |
| ------------ | ------------------ | ------------------------------------------ |
| **Gemini**   | **L1 条件优先，L2 硬兜底** | 已有专属菜单/拖放通道，存在真实成功样本，但目前仍是“偶尔成功”，不能当绝对可靠链路 |
| **元宝**       | **L1 条件优先，L2 硬兜底** | 有专属菜单/拖放通道，具备 Provider 特化价值，但仍需成功判定加固      |
| **豆包**       | **L1 条件优先，L2 硬兜底** | 同上                                         |
| **GPT**      | **L2 起手**          | 当前真实链路已证明不稳定，不应该再把自动上传作为默认假设               |
| **千问**       | **L2 起手**          | 同上                                         |
| **文心**       | **L2 起手**          | 同上                                         |
| **谷歌**       | **L2 起手**          | 你给出的三条 attach 策略均未打通                       |
| **Kimi**     | **L2 起手**          | 当前没有可靠专属通道                                 |
| **DeepSeek** | **L2 起手**          | 当前没有可靠专属通道                                 |

因此我会把 R7-1 从：

> “L2/L3 主，L1 尽力尝试”

修成更精确的冻结条款：

> **分发半的可靠性基座是 L2/L3；L1 仅作为 Provider 级 opportunistic fast path。**
>
> **允许 Gemini / 元宝 / 豆包在满足 Provider 能力检查时先尝试 L1；其余席位默认 L2 起手。任何席位 L1 失败必须立即转 L2，不得阻塞整轮广播。**

这样既承认 F7-1/F7-2 把“全局 L1 主路径”打穿了，也没有浪费已经存在的三个可利用通道。

### 还有一个关键点

目前 Gemini / 元宝 / 豆包也不能叫“稳定主路径”。

它们最多叫：

**“站点级优先尝试路径”**

因为你当前的证据是“偶尔成功”，而不是“可重复、可判定、可恢复”。

# Q2：闸门丙是否必要？——**必要，而且我建议保留**

这一点我赞成 R7-2，而且我认为应该把它从“建议闸门”提升成**真正的 ship gate**。

原因很简单：

> 现在最危险的不是“顶栏看起来不好看”，而是**dispatch 被搬进新布局以后，恰好把原本还能工作的 L2 兜底一起搬坏了。**

所以：

**顶甲板布局 ≠ 自动拥有分发能力。**

必须真实走通：

```text
勾选席位
   ↓
生成本轮快照
   ↓
建立席位任务
   ↓
L1 尝试 / L2 起手
   ↓
逐席完成
   ↓
状态落盘
   ↓
k/N 正确
   ↓
失败席位明确列出
```

只要 L2 基座其中一个关键步骤在新布局中断掉，闸门丙就该失败。

---

## 但 R7-2 有一个漏洞：不能接受“dispatch 一撤，甲板变空”

这才是我认为本轮最应该补的一刀。

你现在的表述：

> L2 真机走不通 → dispatch 回退独立浮窗 → 不占网格

本身没问题。

但如果实现成：

```text
TopDeck
└── 空

Grid
└── 9 webview

Floating Dispatch
└── 真正能发送文件
```

那实际上不是“保留 A”，而是：

**A 的视觉骨架还在，A 的功能中心已经被掏走。**

这会导致一个非常现实的问题：

用户打开会议工作台，最核心的“广播控制”反而跑到另一个浮层去了。

---

## 我建议的修正版

不要把“dispatch”理解成一个单一 DOM 面板，而是拆成：

```text
TOPDECK
┌──────────────────────────────────────────────┐
│ Broadcast Control                            │
│                                              │
│ 席位： ☑1 ☑2 ☑3 ... ☑9                     │
│ 文件： xxx.md   状态：6/9                    │
│                                              │
│ [生成快照] [广播] [打开手动助手]             │
│                                              │
│ 失败：GPT / 千问 / 谷歌                      │
└──────────────────────────────────────────────┘

GRID
┌────┬────┬────┐
│ AI │ AI │ AI │
├────┼────┼────┤
│ AI │ AI │ AI │
├────┼────┼────┤
│ AI │ AI │ AI │
└────┴────┴────┘
```

只有当某个 Provider 进入真正需要人工完成的 L2/L3 文件框操作时：

```text
TOPDECK
   ↓
[打开手动助手]
   ↓

FLOATING HELPER
┌───────────────────────────────┐
│ 当前席位：千问                 │
│                               │
│ 1. 复制文件                   │
│ 2. 点击上传                   │
│ 3. 粘贴/选择文件              │
│ 4. 确认后点 [已发送]           │
│                               │
│              [下一席]          │
└───────────────────────────────┘
```

这样：

**A 没被推翻。**

只是：

> **控制面板留在 TopDeck，必要时把重操作面板临时浮出去。**

这比“dispatch 整块退回浮窗”更稳。

# Q3：五个缺口到底属于哪里？

这里其实可以非常明确地切层。

| 缺口                             | 必须在哪层解决                                          | 是否与布局本质相关 |
| ------------------------------ | ------------------------------------------------ | --------- |
| **A 成功判定不可靠**                  | **Provider Adapter / Dispatch Transport 层**      | **无**     |
| **B Kimi / DeepSeek 无专属通道**    | **Provider Capability + Adapter 层**              | **无**     |
| **C 谷歌 attach 失败**             | **Google Provider Adapter**                      | **无**     |
| **D 千问 / 文心 / ChatGPT 真实轮挂不上** | **各 Provider Adapter / WebView-CDP Transport 层** | **无**     |
| **E 跨轮残留文件污染**                 | **Dispatch Job State + Provider Adapter**        | **无**     |

### A：成功判定

这是目前最严重的传输层问题之一。

你已经有了最典型的反例：

```text
旧文件还在
↓
hasChip = true
↓
程序判断“成功”
↓
实际上新文件根本没发
```

所以：

> `input.files.length > 0`
>
> 或
>
> `hasChip == true`

都不能再作为统一成功定义。

必须抽象成一个 Provider 无关的结果契约，例如：

```text
DispatchReceipt
├── provider
├── roundId
├── fileId / fingerprint
├── attemptId
├── transport
├── attached
├── submitted
├── confirmed
└── failureReason
```

**成功应该是“本轮新文件被这个席位确认”，而不是“页面看起来有文件”。**

这个问题和顶栏位置无关。

---

### B：Kimi / DeepSeek 无专属通道

完全是：

**Provider Capability Registry + Adapter**

例如：

```text
ProviderCapability
├── canDirectInput
├── canDrop
├── canMenuAttach
├── canCDPUpload
├── requiresManual
└── fallbackMode
```

这样以后再增加第 10、第 11 家时，不需要重新修改 TopDeck。

---

### C：谷歌 attach 失败

这是纯 Google Provider Adapter 问题。

顶栏最多负责：

```text
dispatch(provider="google")
```

它不应该知道：

```text
Google 要找哪个 input
Google 要不要点哪个按钮
Google 为什么清空 input.files
```

否则 UI 和 Provider DOM 立刻耦合，后面改一次谷歌页面，TopDeck 一起跟着坏。

---

### D：千问 / 文心 / ChatGPT

也是 Provider Adapter / WebView-CDP Transport。

尤其不要因为 dispatch 搬到顶栏，就在顶栏 JavaScript 里开始写：

```js
if (provider === 'chatgpt') ...
if (provider === 'qwen') ...
if (provider === 'wenxin') ...
```

这是本轮最该避免的错误架构。

正确关系应该是：

```text
TopDeck
   ↓
DispatchController
   ↓
ProviderAdapter
   ↓
WebView/CDP
   ↓
站点 DOM
```

而不是：

```text
TopDeck
   ↓
ChatGPT DOM
   ↓
Qwen DOM
   ↓
Google DOM
```

---

### E：跨轮残留污染

这个我认为必须单独强调：

**不能把“本轮上传了什么”存在 DOM 里。**

否则 TopDeck 一折叠、重渲染、切换模式、重新挂载 dispatchdeck，就可能重置状态。

应该由：

```text
DispatchController / JobStore
```

保存：

```text
roundId
fileFingerprint
selectedSeats
seatStatus[]
attempt[]
receipt[]
```

DOM 只是显示状态。

这是**传输状态与布局彻底解耦**的关键。

---

# Q2 里真正新增的布局耦合风险是什么？

不是“上传技术本身变复杂”。

真正新增的是这几个：

### 1. z-index / WebView 层级

Electron `<webview>` 和普通 DOM overlay 的层级关系非常特殊。

所以 F1 浮层、TopDeck、LogDock、普通 DOM 的层级要提前定契约。

否则最危险的不是按钮点不到，而是：

> 看得到浮层，实际上点击落到了 WebView。

---

### 2. focus 被顶栏夺走

例如：

```text
TopDeck input
    ↓
用户点击
    ↓
焦点留在 TopDeck
    ↓
“下一席”
    ↓
原本应该操作 WebView
    ↓
键盘事件还被 TopDeck 吃掉
```

这个是典型“布局改完后才出现”的问题。

---

### 3. 折叠导致 dispatch 重挂载

如果：

```text
TopDeck collapse
```

直接：

```text
display:none
```

然后再展开重新创建 dispatchdeck DOM，就可能把：

* 当前 k/N
* 当前席位
* L2 当前步骤
* 当前文件
* retry 状态

全部弄丢。

所以：

> **UI 可销毁，任务状态不能销毁。**

---

### 4. 滚动容器改变

TopDeck 内部如果再出现自己的：

```css
overflow:auto
```

会导致：

* 焦点滚动
* 点击坐标
* 快捷键
* 自动定位
* 浮层锚定

出现一系列二次问题。

所以我建议：

**TopDeck 是“控制面”，不是“大滚动工作区”。**

---

# Q4：还有没有 L 级遗留？

这里我不建议回答“完全没有”。

但也**不需要再开第 8 轮大辩论**。

我只看到两个真正值得在开工前补进冻结稿的 L 级条款。

---

## L-1：L2 基座必须定义“完成”而不是只有“点了文件框”

现在的：

```text
逐席复制 / 模拟点击 / k/N
```

还差半步。

必须明确：

```text
READY
↓
FILE_SELECTED
↓
SUBMITTED
↓
CONFIRMED
```

而不是：

```text
我帮你打开了文件框
↓
+1
```

否则又会出现第二种“假成功”。

例如：

```text
千问文件框打开
↓
程序 k = 7
↓
用户实际上取消了
↓
UI 显示 7/9
```

所以：

> **k/N 只能在“该席位达到本轮确认态”后递增。**

这应该直接进 P0。

---

# L-2：L2 “模拟点击文件框”不能成为唯一可靠手段

这也是我认为必须补的一条。

因为你现在明确把 L2 提升成地基，就不能再让地基依赖另一种“其实也可能不稳定”的自动化。

所以应该定义：

```text
L2
├── 自动辅助点击        ← accelerator
└── 人工明确完成        ← guaranteed fallback
```

而不是：

```text
L2 = 自动模拟点击
```

例如模拟点击失败：

```text
[继续自动尝试]
[切人工]
```

人工路径必须一直存在。

否则你实际上只是把：

> “L1 不可靠”

换成：

> “L2 也偷偷变成半自动不可靠”。

---

# 关于你提到的 #19：**应该提前到 P0**

这个我明确赞成。

而且不是简单地：

> “发送前清空”

而应该升级成：

### P0：发送前清空 + 发送后新文件回读校验 + 本轮身份绑定

至少逻辑上形成：

```text
本轮任务建立
   ↓
记录 roundId + fileFingerprint
   ↓
清空旧 attachment/input
   ↓
验证旧状态已消失
   ↓
执行 attach
   ↓
确认出现“本轮新文件”
   ↓
提交
   ↓
确认提交态
   ↓
seat = CONFIRMED
```

这样才能同时解决：

* F7-1 的假成功
* F7-1 的假阴性
* F7-1 的旧文件污染
* F7-2 的“程序说发了，实际上没发”

所以 **#19 从普通兜底条目提升为 P0 是合理的。**

---

# 最终裁决

我的建议是把第 7 轮冻结为下面这个版本：

### R7-1′

**全局可靠基座 = L2/L3。**

但不是“9 家一律 L2”。

实际策略：

```text
Gemini / 元宝 / 豆包
    → Provider 条件检查
    → L1 优先尝试
    → 失败立即 L2

GPT / 千问 / 文心 / 谷歌 / Kimi / DeepSeek
    → L2 起手
```

同时：

**L1 永远不能成为整轮成功的单点依赖。**

---

### R7-2′

**闸门丙保留，而且必须是真机 ship gate。**

`dispatchdeck` 进入 TopDeck 后：

```text
9站点真实 DOM
+
L2 基座完整流程
+
状态落盘
+
k/N 正确
+
失败席位显式列出
```

任何关键项失败：

**允许把“重操作 Dispatch Helper”退回独立浮层。**

但：

> **TopDeck 不允许因此变成空壳。**

TopDeck 仍保留：

* 广播控制
* 席位状态
* 快照
* 进度
* 失败列表
* 打开手动助手

---

### R7-3

冻结稿其余条款继续保持，不重开 Q3 已冻结决策。

---

### P0 新增两条

**P0-A：#19 升级**

> 发送前清空 + 回读验证 + 本轮文件身份校验 + 提交态确认。

**P0-B：L2 必须具备真正人工可完成的 guaranteed fallback**

> “模拟点击”只能是加速器，不能成为可靠性的唯一组成部分。

---

# 开工闸门结论

**可以开工顶栏。**

但开工前请把冻结稿补上这四个词，否则后面实现的人很容易把架构做歪：

> **全局 L2 基座**
>
> **站点级 L1 优先**
>
> **Provider 状态与 UI 解耦**
>
> **L2 确认态才计入 k/N**

我认为这四句话一旦钉死，第 7 轮就已经解决了真正的核心问题：**不是“dispatch 放不放进顶栏”，而是无论它放在哪里，广播都不能再依赖一个脆弱的上传成功假象。**
