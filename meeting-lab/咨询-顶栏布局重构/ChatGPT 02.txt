这一轮建议不要再从“按钮怎么摆”开始，而是先把**会议工作流定义成一套状态机**，然后让 UI 去表达状态。你现在的第 2 轮稿已经把“删右栏、顶栏控制甲板、底部日志、模式×阶段”作为共识基线，但我认为其中“开会前 / 开会中”这一维还不够严谨，尤其当加入 50+ 席位和 200+ 工具以后，会出现大量状态无法归类。

下面我按“工作流 → UI → 席位 → 工具 → 8 模式 → 落地代码结构”的顺序继续往下设计。

# 一、先改一个根本问题：不要再把“阶段”定义成只有前/中

你现在稿子的 Q4 是：

```text
模式 × 开会前
模式 × 开会中
```

这对第一版够用，但进入真正的会议控制台后不够。

例如：

```text
会议暂停了
```

它到底属于“开会中”还是另外一种状态？

再比如：

```text
会议已经结束，但用户正在查看结果
```

也不是“开会中”。

再比如：

```text
某个席位工具调用失败
```

这甚至不应该改变会议主状态。

所以建议正式定义成：

```text
mode       = 会议模式
state      = 会议生命周期状态
attention  = 当前需要用户关注的问题
selection  = 当前用户正在查看哪个席位/工具
```

这四个维度不要混。

# 二、我建议的正式会议状态机

```text
                         ┌────────────┐
                         │   DRAFT    │
                         │ 会议配置中 │

              │          └─────┬──────┘          │
              │                │                 │
            暂停              结束               │
              │                │                 │

        │  已暂停   │     │ 收尾确认   │          │
```

# 二十、我建议的 8 模式工作流

下面的具体语义，因为你上传的稿子只给出了模式名称而没有完整业务定义，因此这里属于**产品设计假设**，不是从现有源码事实直接得出的。

| 模式          | 会前重点             | 运行中核心动作        | 最重要状态  |
| ----------- | ---------------- | -------------- | ------ |
| transparent | 议题、资料、广播规则、轮数    | 主持人广播→所有席位响应   | 当前轮/广播 |
| panel       | 专家成员、角色、议题       | 并行回答→主持人查看→下一轮 | 回答完成率  |
| build       | 任务、工作区、工具权限、验收标准 | 执行→工具→产物→验证    | 任务/产物  |
| sequence    | 顺序、每席超时、跳过规则     | A→B→C          | 当前发言席  |
| debate      | 正方/反方、轮次、发言顺序    | 陈述→反驳→再反驳      | 当前阵营   |
| examination | 询问方、被询问方、问题队列    | 提问→回答→追问       | 当前问题   |
| group       | 分组、组员、组间汇总       | 组内讨论→组总结→总汇    | 当前组    |
| open        | 主持人规则、发言策略       | 自由发言→主持干预      | 活跃席    |

# 二十一、每个模式最好只有自己的“一个特殊控制区”

例如透明广播：

```text
┌─────────────────────────────────────────────┐
│ 透明广播                                    │
│                                             │
│ 议题：________________________              │
│ 轮数：8                                     │
│ 资料：3                                     │
│ 广播：○全部  ○选中组                       │
└─────────────────────────────────────────────┘
```

顺序接龙：

```text
┌─────────────────────────────────────────────┐
│ 顺序接龙                                    │
│                                             │
│ ① Claude → ② GPT → ③ Gemini → ...         │
│ 每席：120秒                                 │
│ 超时：[跳过 ▼]                              │
└─────────────────────────────────────────────┘
```

工程交付：

```text
┌─────────────────────────────────────────────┐
│ 工程交付                                    │
│                                             │
│ 项目：[project ▼]                           │
│ 工作目录：/workspace                        │
│ 验收：[测试 / 构建 / 人工 ▼]                │
│ 工具权限：工程开发模板                      │
└─────────────────────────────────────────────┘
```

**每次最多展示一块模式专属区。**

这样顶部不会重新膨胀。

# 二十二、真正的“会前检查”应该有一个 READY Gate

这是我认为你现在 UI 最应该补的一块。

用户点：

```text
开始会议
```

不要马上开跑。

先显示：

```text
┌─────────────────────────────────────────────────┐
│ 开会前检查                                     │
│                                                 │
│ ✓ 模式：专家会诊                               │
│ ✓ 12 个席位已准备                               │
│ ✓ API 连接 3 / 3                                │
│ ✓ Web 席位 9 / 9                                │
│ ✓ 工具策略已配置                                │
│ ✓ 议题已填写                                    │
│ ⚠ 2 个席位尚未登录                              │
│                                                 │
│ [返回修改]                         [开始会议]  │
└─────────────────────────────────────────────────┘
```

否则大量错误都会变成：

> 开会后才发现配置不完整。

成本非常低，却能明显降低事故。

# 二十三、RUNNING 状态应该“冻结配置”

会议开始以后：

可以：

```text
广播
文件
暂停
查看席位
查看工具
查看日志
调整密度
筛选
```

不应该随便：

```text
删除席位
改变模式
重定义角色
批量重排参与者
修改核心工具权限
```

UI 上直接锁：

```text
🔒 会议配置已锁定
```

要改：

```text
结束当前会议 / 新建会话
```

这是非常重要的状态边界。

---

# 二十四、暂停也应该重新定义

当前按钮叫：

```text
⏸暂停
```

但是实际上用户必须知道：

> “暂停到底暂停了什么？”

建议明确规定：

```text
PAUSED
=
停止继续派发新一轮任务
+
保持已有席位状态
+
保持工具历史
+
允许检查/浏览
```

而不是：

```text
所有外部请求瞬间停止
```

因为正在执行的 HTTP、Shell、网页动作到底能否取消，是另一个执行引擎问题。

所以 UI 不应该承诺：

> “所有任务已停止”。

只显示：

```text
⏸ 已暂停派发
```

更严谨。

---

# 二十五、“停止”这个词建议改掉

我会建议把：

```text
⏹停止
```

改成：

```text
结束会议
```

然后二级菜单：

```text
结束并保存
结束并导出
强制中止
```

因为：

```text
停止
```

很容易被理解成：

> 立刻 kill 所有模型和工具。

实际上“会议结束”和“强制终止执行”是两个完全不同的语义。

# 三十二、状态控制不要散落到几十个 `if`

统一：

```js
document.body.dataset.mode
document.body.dataset.state
document.body.dataset.attention
```

例如：

```js
document.body.dataset.mode = 'panel';
document.body.dataset.state = 'running';
document.body.dataset.attention = 'tool';
```

CSS：

```css
body[data-state="draft"] .running-only {
    display: none;
}

body[data-state="running"] .setup-only {
    display: none;
}

body[data-state="paused"] .run-only {
    display: none;
}

body[data-mode="transparent"] .panel-only {
    display: none;
}
```

这样非常适合你现在：

> 原生 JS + 原生 CSS + 固定 DOM + 400 个测试

的技术约束。

# 三十三、但是 WebView 要特别处理

这一点继续沿用第 1 轮共识：

```text
.topdeck        可以 display:none
.logdock        可以收缩
.attentionbar   可以 display:none
.deck-panel     可以隐藏

.grid            不销毁
.cell            不 display:none
.webview         不重建
```

也就是：

```text
UI 层折叠
        ↓
兄弟容器改变大小
        ↓
Grid 被动 resize
        ↓
WebView 继续存在
```

不是：

```text
折叠
 ↓
重新生成 grid
 ↓
重新生成 webview
```

这一点与你第 2 轮基线一致。

# 三十四、对 50+ 席位我还有一个工程上的底线建议

这里需要利用 Web 和 API 的“不对称”。

你现在的真实约束是：

```text
WebView：最多 9 个
API：理论上 N 个
```



所以不要做：

> “统一虚拟化所有席位。”

因为 9 个 WebView 不适合这样搞。

更合理是：

```text
Web Seat
→ 永远保持挂载

API Seat
→ 普通 div
→ 数量极大时再做 DOM virtualization
```

UI 上完全统一：

```text
SeatCard
```

底层实现可以不同：

```text
SeatCard<WebViewSeat>
SeatCard<ApiSeat>
```

这就是：

> **视觉统一，渲染策略不必强行统一。**

这是 50+ 扩展必须利用的结构优势。

# 三十五、最后给你一个完整“会议工作流”

以后用户进入程序，不应该感觉自己是在“操作一个 UI”。

而应该感觉：

```text
创建会议
   ↓
选择模式
   ↓
选择/编排席位
   ↓
设置角色
   ↓
设置工具权限
   ↓
输入议题/资料
   ↓
预检
   ↓
READY
   ↓
开始
   ↓
第 N 轮
   ↓
席位工作
   ↓
工具调用
   ↓
结果回注
   ↓
主持人干预
   ↓
下一轮
   ↓
……
   ↓
结束
   ↓
收尾
   ↓
日志 / 摘要 / 产物
   ↓
COMPLETED
```

而 UI 只是始终告诉用户：

> **现在在哪一步、谁在干什么、什么需要我处理、下一步可以做什么。**

这比“把按钮都摆合理”高一个层次。

# 三十六、我对第 2 轮共识基线的最终态度

**不推翻大骨架，但推翻“阶段只有开会前/开会中”的简化。**

保留：

```text
删除 380px 右栏
        ↓
Header
        ↓
TopDeck
        ↓
Seat Board
        ↓
Log Dock
```

保留：

```text
mode × state
```

但升级成：

```text
mode
+
meetingState
+
attention
+
selection
```

同时把：

```text
固定席位角色组
每排 3/4/5/6
Web/API 两套席位 UI
工具输出全部进入日志
停止 = 结束
```

这些旧思路逐步淘汰。

我认为下一版真正应该冻结的是一份 **《通辽会议 UI/工作流规范 V1》**：先把 `DRAFT → READY → RUNNING → PAUSED → FINISHING → COMPLETED` 的每个状态，逐项列出“允许操作 / 禁止操作 / 顶栏显示 / Seat 卡显示 / Log 显示 / 工具状态 / 8 种模式差异”，然后让 AI 按这份规范改 `index.html`。这样后面就不是反复争论“这个按钮放上面还是下面”，而是有一套可以直接验收的产品规则。
