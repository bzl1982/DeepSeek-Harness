Q1 · phase 状态机几态
结论

四相 setup → running ⇄ paused → done + attention 正交‌ —— 支持 §3-A 的推荐，但必须同时钉死第二条铁律：

phase 是"会议级生命周期"；mode 内部的"阶段(stage)"与"轮(round)"是 running 的子状态，绝不进主状态机。‌

四相之所以对，恰恰是因为有这层分层；‌不分层的话，四相也装不下‌。

说服理由（三条）
paused 是刚需，不是可选‌：已定案 17 要求 RUNNING 冻结核心配置、"要改先结束或暂停"。若没有 paused，改配置的唯一出口就是"结束会议"→ 已跑轮次全丢。‌paused 是"配置冻结"这个约束的唯一合法解药‌。
done 是刚需‌：五类终止判据（single-pass / no-new-critique / same-winner / buildPass / 固定轮数）必然产生"收敛完成"终态。
但绝不能加第 5、第 6 相‌：一旦把 mode 内阶段当 phase，phase 数量就随模式数膨胀——tournament 5 阶段、review/assist/divide 各 3 阶段、build 4 阶段，各不相同。‌phase 必须"粗"才能统一，stage 必须"细"才能保真。‌

对方方案的失效场景
反对"两相"（我上轮的错误立场）‌：开会中质证要临时拉人 / 改角色，两相下‌没有出口‌——只能结束会议，已跑轮次全丢。这就是两相会坑用户的现场。
反对"六相+attention 进主状态机"‌：一旦"工具失败"是一个 phase，它就会‌覆盖掉 running‌，进度条、轮次显示全要跟着切 → UI 要维护 N×M 的状态组合；正交的 attention 只需一个 badge（已定案 15）。
反对"把 mode 阶段升为 phase"‌：phase 数随模式数增长，新增模式要改状态机 → 直接违反已定案 13（新增模式=加一行配置）。

成本‌：引擎仅需 4 值 phase 枚举 + 每 mode 一个 stage/round 描述符；UI 由 body[data-phase] + 描述符驱动。
反例‌：别把 done 拆成"正常收敛 done / 强制中止 aborted"两个 phase——续会逻辑会分叉。正确做法是 done 带 doneReason 字段，不进 phase 数量。

Q2 · 工具面板放哪
结论

全局右滑 tooldock 绑定 activeSeat；卡内只留 24px 定高状态行‌（支持 §3-B）。并补一条硬规则：

tooldock 是 overlay，不改 grid 宽度 → 它不属于"横向折叠"，不受已定案 2 约束‌（定案 2 管的是"占位尺寸变化"，overlay 不占位）。

说服理由
卡内抽屉在 micro 密度下是"物理不可用"‌：50 席 micro 卡片高 56px，抽屉可用高度 = 56 − 32(头部) = ‌24px‌，连一行工具参数都放不下。这不是"体验差"，是根本画不出来。
卡内抽屉靠展开卡片腾空间 → 展开即改行高/列宽 → 触发相邻 webview 重排‌（横向甚至有卸载风险），违反已定案 3。
全局 dock 是唯一 DOM，O(1) 换绑‌（Kimi）：50 席切换只是改 activeSeatId，DOM 数量恒定。
工具历史天然是纵向时间线‌，右滑竖条容器形状天然匹配。
密度极限推演：50 席 micro + 10 工具并发
卡片级（50 张）‌：每张底部 24px 状态行，只显示"最近 1 条"。10 个在跑 → 那 10 张显示 🔧调用中 转圈 + 头部徽标计数；其余 40 张显示 —。‌状态行定高 + overflow:hidden，绝不撑高卡片。‌
分组级‌：group-tabs 聚合计数 🤖API组 🔧10。
全局级‌：logdock 的"工具"Tab 按席位分桶；头部全局指示器 🔧10（通义三级架构）。
dock 本体‌：点任一卡的状态行 → dock 滑出并绑该席位；dock 顶部有一行"并发 10"的活跃席位列表，可在 10 个席位间 O(1) 跳转，‌不用回网格找卡‌。
自动滑出策略‌：只有 confirm 态（高危待批）自动滑出；calling/success/error 只在状态行显示，不抢焦点 → 50 席并发不会满屏弹窗。
对方方案的失效场景
卡内抽屉‌：micro 下 24px 不可用；真去展开卡 → 横向重排，disable-gpu 下开销是纵向的 6~8 倍。
⧉弹出窗‌：10 并发 = 10 个 Electron 窗？或 1 窗反复换绑（重挂 DOM）；且可能被 webview 盖住（z-index 坑）；50 席还要解决"哪个窗属于哪个席位"。
入 deck‌：topdeck 已 200~280px，再塞 10 个工具面板撑到 600px+ → 挤压网格 → 9 个 webview 高度剧烈变化。

成本‌：新增 1 个固定 dock DOM + 每卡 1 个 24px 状态行（50 卡 = 50 div，可忽略）；状态键 data-tool-state + activeSeatId；引擎零改动。
反例（我方案何时坑人）‌：若未来开启 GPU 加速，webview 可能升为独立合成层盖住 dock → dock 失效。‌本方案成立的前提正是你强制 --disable-gpu（webview 走软件合成，是普通 DOM 层，z-index 生效）‌；放开 GPU 需回归验证，兜底改成"底部整行抽屉"（纵向、全宽）。

Q3 · 外部 AI 回答落位：A 还是 B
结论

选 A（顶甲板表单 + 编辑锁 + 限高）。作为每天用它咨询的人，我要 A。‌
理由不是"尊重原话"，而是一条功能性硬理由：

回收这个动作天然要"对照网格里的网页原文"——任何覆盖网格右侧的抽屉都会挡住我正在复制的那几个窗口。‌

说服理由
回收 = 对照式操作‌：我从 Web1 复制回答 → 要粘回来。此时视线在网格（上）、手在粘贴框。右滑抽屉宽 360px，覆盖右侧一列 = ‌正好盖住我要复制的那 3 个窗口‌；顶部甲板不遮挡任何网格。
工具面板遮挡无所谓，回收面板遮挡致命‌——这条差异直接否掉 B 的"一套两用"：工具执行细节不需要对照网格（工具在跑时我看的是日志/dock），所以工具适合右滑 dock；‌回收必须对照网格，所以回收适合顶部‌。两者形状可以都是"面板"，但落位必须分开。
批量"先粘贴后归属"‌：顶部单表单支持"粘贴 → 下拉选归属席位 → 提交"，可连续回收多席位；B 必须先选席位再开抽屉，多席位回收要"选-开-粘-关"循环 9 次。
原话零解释成本‌：用户说"挪到上面"，A 直接满足。
A 必须配的三条硬化（否则 A 会坑人）
编辑锁‌：focusin 给 body 加 data-editing，禁自动折叠；focusout 解除。否则用户打字时甲板被收走。
限高‌：max-height:96px; overflow-y:auto，内部滚动，绝不撑高甲板挤压网格。
默认归属 = activeSeat‌：提交默认记到当前 activeSeat，可下拉改 → "选中卡片→粘贴→提交"两步完成，把 B 的席位绑定优势吸收进来。
B 的失效场景（什么时候 B 会出事）
遮挡对照窗口‌（最高频场景直接坏掉）：见上第 1 条。
与工具台抢同一容器‌：工具在跑时你要回收 → 同一 dock 两个用途，要么 Tab 切换（丢工具时间线），要么叠两层（更乱）。
长回答核对‌：对着 9 个窗口逐个核对时，B 每次开合都盖住右侧，效率低于顶部常驻小框。
唯一 B 更优的场景是"单席位长回答、且不需要看网格"——在"9 窗口人工咨询"里占比很低，‌列 v2 即可‌。

成本‌：extbox 从 .side 搬进 .topdeck（DOM 几乎不变）+ 2 条 CSS + 1 个 focus 监听。
反例‌：若外部回答常超 500 字需长时间编辑，96px 限高会难受 → 兜底是 extbox 提供"⧉放大到弹层"（不遮挡网格中部的大编辑层，仍不占布局）。

Q4 · API 席位要不要虚拟滚动
结论

先原生滚动 + 分组页签 + 密度档；不预建虚拟化。‌ 分界线：‌单组 150 席 / 总 200 席‌，依据是三个‌可测指标‌，不是拍脑袋。

说服理由（"不虚拟化"是安全，不是偷懒）
真正的重排风险不在节点数，在"行高自适应"‌：若 API 卡高度是内容自适应（grid-auto-rows:auto），任意一卡流式输出变长 → 整网格重排。‌只要把行高钉死（grid-auto-rows:var(--api-cell-h) + 内容 overflow:hidden），50/100/200 席的差别就只是节点数，不是重排量。‌ 固定行高是"免虚拟化"的前提条件。
分组页签 = 天然的"分组级软分页"‌：非当前分组可 display:none（‌API div 可以 display:none，只有 webview 不行‌，定案 3 只禁 webview 卸载）。同屏 DOM = ‌单组席位数，不是总数‌ → ‌分界线由"单组席位数"决定‌。200 席分 5 组，同屏仅 40 席。
原生滚动本身就等于"离屏保留"‌（滚出视口的节点不销毁，只是不绘制），所以"先原生滚动"已经拿到 .offscreen 的全部好处。

对方方案的失效场景
直接上虚拟化‌：① 虚拟化要求预知/固定高度，与"卡片内容预览"冲突；② 席位卡滚出视口被回收 → 正在流式的对话、未提交输入、滚动位置全丢，用户滚回来发现"对话没了"；③ 虚拟化引入高频 scroll 计算，在 disable-gpu 软件渲染下滚动本身就更重，JS 开销叠加‌可能反而掉帧‌。
离屏保留 .offscreen‌：节点数与内存不减（只是移出视口），对"节点多导致的内存/layout 压力"‌无效‌；而原生滚动已拿到它的全部好处。

成本‌：固定行高 1 条 CSS、分组页签复用 group-tabs、密度档 3 个 CSS 变量；引擎零改动。
反例‌：若某分组真超 150 席，届时‌只给该分组加虚拟化（按组开关）‌即可，不必全量改。

Q5 · 【新需求】人工模式
建模选边：‌选建模三，但去掉"第 12 种模式"这层‌

通道（per-seat auto|manual）是引擎层一等公民；"人工咨询"是"全 manual + 强制打开咨询台"的投递预设(preset)，不占 mode 位、不进 mode 下拉。‌

为什么不是建模一（第 12 种 mode）‌：① 它把"人工"绑成模式 → ‌无法表达混合通道‌（9 个网页走 manual、同时用 panel 让 API 席位自动会诊）——而混合恰恰是你真机上最可能的用法（网页广播不可用、API 广播可用）；② 它会污染 phase 语义（人工模式的 running 是"人驱动"，与 broadcast 的 running 不同）。
为什么不是纯建模二‌：纯通道没有"工作台"——用户不知道去哪看"已发 k/M / 未发清单 / 已回答"，R1~R4 需要一个会议级视图承载。
为什么建模三最优‌：
代码复用最多‌：per-seat 投递状态机 pending → sent → answered 是 auto/manual ‌共用‌的；auto 的 sent/answered 由 CDP 检测驱动，manual 由人工勾选/辅助检测驱动。引擎‌只换驱动源，不换状态机‌。
状态机零新增‌：人工咨询照走 setup/running/done，只是 running 内不自动派发，派发动作从"引擎调 CDP"变成"提示用户去复制"。
用户心智最简单‌：一个"人工咨询"按钮，点开就是工作台，不用理解"通道"。
⚠️ 关键发现（直接修正 R1 的定义）

§4 真表说明，‌多个模式的"每席位该看到的内容"是不同的‌：review 第一阶段"只看材料不看他人"（防锚定）、debate 对辩"不看自己的论点"（防自我强化）、tournament 评标"匿名+定序"、transparent"除自己外所有人上轮发言"。

所以 R1 的"一份咨询稿发往 M 个席位"在 review/debate/tournament/transparent 下是错的‌ —— 那等于把同一份稿发给所有人，‌直接破坏防锚定 / 防自我强化 / 匿名‌。

修复‌：咨询稿是"素材"，引擎按 mode + stage + seat 生成‌每席位视图(view)‌；分发时复制的是"该席位的 view"，不是原稿。人工模式与自动模式‌共用同一个 view 生成模块‌，只是投递通道不同（剪贴板 vs CDP 注入）。这既是 R1 的修正，也是"共用最多代码"的落点。

完整交互设计（R1~R4）

R1 分发‌

咨询台左栏=素材区：咨询稿多行编辑 + 附件列表。
中栏=席位清单：每行 席位名 | 通道(自动/手动) | 状态徽标 | 视图预览(截断) | 操作。

R2 回收‌

每席位"📥收"：点卡片/追踪行 → 聚焦顶部 extbox 并预选该席位 → 粘贴 → 提交（‌复用已有"剥标注 + 参与上下文切片"‌）→ 状态置 answered。

未答名单：追踪表按状态排序，answered 沉底，sent 高亮置顶。

R3 与会议引擎的关系‌

人工预设下 deliveryChannel = manual for all，引擎的"自动派发"被替换为"生成 view + 提示用户复制"，不调 CDP、不依赖完成检测。

可混合‌：通道是 per-seat 的，"panel 模式 + 网页 manual + API auto"合法；人工咨询只是"全 manual"的预设。

R4 文件‌

手动：咨询台"📎全部预填同一批文件" → 各席位"📎选文件"预填 → 系统对话框确认 → 卡片置 file-sent。

6.2 工作流漏洞（给 7 条）+ 修复建议

漏洞 1 · 前置条件缺"来源"与"降级路径"‌（review 材料 / iterate 草稿 / chairman API主席 / transparent 资料）

现象：没材料就开不了 review，但材料常不是文件（可能是某网页内容或上一轮产物）；硬门槛只认"文件"会把用户卡死。
修复‌：前置条件支持三种来源 —— ①文件 ②粘贴文本 ③引用历史会议产物；并区分‌硬前置‌（不可降级：chairman 的 API 主席）与‌软前置‌（可降级：iterate 无草稿 → 自动先跑一轮"生成草稿"；review 无材料 → 引导选来源）。硬前置不满足 → "开始"置灰并指向缺失项；软前置不满足 → 黄字警告 + "一键补齐/跳过"。

漏洞 2 · loop 型模式的"轮"语义互不可比，统一"N/M 轮"会误导‌（iterate 2 阶段/轮、chairman 动态点名、tournament 5 阶段/轮、build 4 阶段/轮）

现象：都是"第 3/5 轮"，但一轮干的事完全不同；tournament 一轮含 5 个阶段，用户按 iterate 的"轮"理解会误判进度。
修复‌：主进度用‌阶段步‌、轮次作副标签：第 2/3 次评审 · 定标阶段 (3/5)。由 mode 描述符提供 roundNoun（tournament=次评审、build=次构建、chairman=轮点名），‌UI 不硬编码"轮"字‌。

漏洞 3 · 产出契约(kind)在 UI 不可见 → 用户会把评标当候选‌（tournament 的 produces/kind）

现象：tournament 要求产出打 kind（candidate/ballot/verdict/revision/review），否则切片把评标当候选发出去；用户在 UI 上看不到类型，无法察觉错切。
修复‌：① 席位卡/日志行加 ‌kind 徽标‌（色块+文字）；② logdock 支持按 kind 过滤；③ setup 展示"本模式产出契约表"；④ kind 缺失 → attention 告警。

漏洞 4 · chairman 的"分歧"没有来源‌（真表只说"每轮按分歧动态点名"，没说分歧从哪来）

现象：没有初始观点时，主席无从判断分歧 → 第一轮点名是空的/随机的。
修复‌：① setup 增加"首轮立论"（并行先出观点）或允许"引用上一轮结论/其他模式产出"作为分歧来源；② 分歧视图可视化（哪些席位观点冲突），让用户能干预点名；③ READY Gate 增查"分歧来源已指定"。

漏洞 5 · build 第三档会执行 AI 写的代码‌（真跑 npm run build）

现象：在用户本机 D 盘执行 AI 生成代码 = 任意代码执行风险；已定案 12 说 shell/写类默认需确认，但"构建"容易被漏掉确认闸。
修复‌：① build ‌默认第二档‌（语法+引用完整性，不执行代码）；② 选第三档强制弹确认闸（明示"将执行 AI 生成代码"）+ 建议独立目录；③ build 阶段条上‌标红"真执行"档位‌。

漏洞 6 · 人工模式会破坏"防锚定/防自我强化/匿名"‌（见 Q5 关键发现）

现象：review 第一阶段"只看材料"、debate"不看自己论点"、tournament 评标"匿名+定序"——若人工分发是"同一份稿复制给所有人"，约束全废。
修复‌：per-seat view 生成（Q5）+ ‌按阶段锁死可发内容‌：review 第一阶段的分发按钮只能发"材料 view"，任何"他人回答"不可发；debate 为每辩手生成"只看他人"的 view；tournament 评标 view 去作者标识 + 固定顺序。

漏洞 7 · transparent 的 O(N²) 没有 UI 侧护栏‌

现象：9 人一轮 153 份注入；席位加到 20，一轮 380 份，成本爆炸但用户无感。
修复‌：模式选择/席位调整时‌实时显示"预计每轮注入 = N×(N-1) 份"‌，超阈值（如 >200）红字警告 + 建议改用 panel 分组降本；或硬上限（席位 >12 禁选 transparent），直到已定案 21 的广播域落地。

成本‌：漏洞 1/2/3/4/7 是 UI 侧（配置驱动 + 徽标 + 护栏），‌不动引擎‌；漏洞 5/6 需引擎配合（沙箱档位、per-seat view 生成）。
反例‌：若把"前置条件"做成纯提示而不拦截，用户仍会硬开 review 无材料 → 跑出无意义结果 → ‌硬前置必须在"开始"按钮层拦截（READY Gate）‌，而不是事后报错。

结尾

对 §2 已定案 23 条：无推翻。‌ 两条澄清（是补定义，不是推翻）：① 定案 2"横向折叠禁令"针对的是‌占位尺寸变化‌（会触发 webview 重排），‌overlay 型抽屉（右滑 tooldock、咨询台）不占位、不改宽度，不受此禁令约束‌——否则 Q2 的推荐会自相矛盾；② 定案 5"外部AI回答=表单"需补"编辑锁 + 限高"两条硬化，否则与自动折叠打架。
