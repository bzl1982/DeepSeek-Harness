基于《第3轮咨询案-拍板轮与人工模式-20260923.md》，以下是针对 6 个问题的明确选边与论证。

### Q1：phase 状态机几态？（悬案 A）

**结论：坚决支持你的推荐 —— `setup / running ⇄ paused / done` 四相 + attention 正交状态。**

**逐模式检验与说服理由：**

* **`setup`（准备期）**：完美契合 §4 要求的“前置条件硬门槛”。例如 `review` 模式必须在这里校验是否有**材料**输入，`chairman` 必须校验是否分配了 **API 席位**。不满足则死锁在 `setup`，`READY Gate` 亮红灯，无法进入 `running`。


* **`running`（运行期）**：承载 `iterate` (≤5轮)、`chairman` (≤4轮)、`tournament` (≤3轮) 的自动化 Loop。


* **`paused`（干预/挂起期）**：极其关键。当 `build` 模式执行到第三档（真跑 npm run build）失败时，或者 `tournament` 模式由于 AI 输出未严格遵循 `candidate/ballot` 产出契约导致解析失败时，系统必须切入 `paused`，让人工接管修正，然后 `⏵续会`。


* **`done`（完成期）**：用于 `broadcast`、`panel` 等 single-pass 模式的自然结束，或 loop 模式触达终止判据（如 `tournament` 的 same-winner）。


* **`attention`（正交）**：某 API 席位短暂掉线或某个只读工具执行报错，不应该改变主状态机，仅挂出 Attention Bar，保障 `running` 不被打断。



**反例（二态或三态的失效场景）：**
如果只有 `setup/running/done`，当 `iterate` 跑到第 3 轮发现 AI 陷入死循环报错时，你只能强行 `done`（强制中止并结算）或者退回 `setup`（重置整个会议配置），无法实现“暂停修 bug 后继续当前轮次”。

### Q2：工具面板放哪？（悬案 B）

**结论：坚决支持全局右滑 `tooldock` 绑定 activeSeat。**

**密度极限场景推演（说服理由）：**
在 50 席 `micro` 密度下，为了在一屏内挤下更多网格，每个 `.cell` 卡片可能被压榨到仅剩 56px 高度（仅够显示卡头和一行状态）。如果采用“卡内抽屉”，当工具返回一个 200 行的 JSON 或复杂的文件树目录时，根本无法在 56px 内展开。全局 `tooldock` 保证了无论网格如何缩放，工具界面始终享有稳定的右侧纵向 400px+ 宽度和完整屏幕高度，且 O(1) 换绑性能极佳。

**反例（卡内抽屉的失效场景）：**
当 50 席中有 10 个席位并发调用工具时，如果用卡内抽屉，这 10 个卡片会突然各自纵向膨胀 300px。这会瞬间摧毁 CSS Grid 布局，引发极度昂贵的纵向重排（正如第 2 轮豆包和文心指出的 6-8 倍开销），并把用户正在盯着的其他关键席位挤出视口外。

### Q3：外部 AI 回答落位（悬案 C）

**结论：选择 A方案 —— 顶甲板 `.topdeck` + 编辑锁折叠 + max-height 限高。**

**说服理由：**
首先，必须尊重用户原话“挪到上面”。其次，从交互流向看，“从上到下”符合人类认知：顶部输入（外部 AI 回答表单），中间运算（12 个席位），底部输出（会议日志）。编辑锁（输入时禁止触发折叠）和 max-height（防止长文本撑爆）足以控制其空间占用。

**反例（右滑抽屉的失效场景）：**
如果外部 AI 回答与工具面板共用右滑抽屉，会产生**焦点互斥冲突**。日常工作流中，用户极有可能需要“一边看着某个席位跑出的工具结果（工具抽屉），一边将这个结果总结写进外部 AI 回答框里”。如果两者同在一个右侧抽屉且互斥，用户将面临“打开工具就关了外部 AI，打开外部 AI 就看不见工具结果”的灾难级坑点。

### Q4：API 席位要不要虚拟滚动（悬案 D）

**结论：坚持原生滚动 + 分组页签 + 密度档，拒绝虚拟滚动。数量分界线定在 200 席。**

**依据与说服理由：**

* **判据 1：DOM 渲染成本**。Electron 的底层是 Chromium。在不携带复杂 iframe/webview 的前提下，渲染 200 个结构简单的轻量 `.cell` div 节点，内存占用不到 10MB，重排开销在亚毫秒级，毫无压力。
* **判据 2：生态破坏**。一旦引入虚拟化，就意味着 DOM 树被阉割。第 2 轮已定案“搜索=高亮 scrollIntoView，不筛选”，如果节点被虚拟滚动卸载，原生的 `document.querySelector` 和用户的 `Ctrl+F` 统统失效。



**反例（盲目上虚拟化的坑）：**
为了区区 50-100 个轻 div 引入 `react-window` 级别的复杂逻辑（即使手写原生虚拟滚动），会导致你在执行 `CDP DOM.setFileInputFiles` 传文件时，发现目标席位的 DOM 根本不在可视区内、节点不存在，文件直接发送失败。

### Q5：【新需求】人工模式设计与建模

**建模选边：选“建模三”（两者都要：底层通道 + 顶层快捷模式）。**

**说理：**

* 底层必须是“投递通道（auto/manual）”的解耦，因为在 `panel` 等真实模式中，用户完全可能遇到 9 个网页 API 坏了 1 个，需要对那 1 个临时切手动兜底的情况。
* 顶层暴露“人工咨询模式”作为第 12 种 mode。用户心智最简单（一键进入纯手工发报机状态），复用 `setup/running` 状态机，产出依然走 `round-N.md`，完美兼容底层引擎。



**线框图（人工模式面板）：**

```text
+-------------------------------------------------------------------------+
| .header   [模式: 人工咨询 ▾] [🚀开始分发]                               |
+-------------------------------------------------------------------------+
| .topdeck (人工模式专属 Dispatch 面板)                                   |
| [文本输入区: 咨询稿内容...]                                             |
| [📎全局文件: a.pdf, b.jpg (统一预填)]                                   |
| 分发追踪: 🟢已发 3/9  🟡未答 6/9       [一键复制所有未发席位内容 📋]    |
+-------------------------------------------------------------------------+
| .grid                                                                   |
| +--------------------------------+ +--------------------------------+   |
| | .cell (Web) [🟢已发] [⚪未答]  | | .cell (API) [🟡未发] [⚪未答]  |   |
| | [粘贴回答入库 ↵]               | | [粘贴回答入库 ↵]               |   |
| | (若 CDP 发文件失败, 显警报图标)| | (API通道走原生接口, 静默处理)    |   |
| +--------------------------------+ +--------------------------------+   |
+-------------------------------------------------------------------------+

```

**交互流 (R1-R4)**：
用户在 `.topdeck` 写好总稿。点击席位卡片上的快捷复制按钮（带文本和文件路径）。用户手动在网页框操作后，点击卡片上的 `[粘贴回答入库 ↵]`，将结果录入并触发该席位的“已答”标记，自动计入主会议记录 (R2/R3)。如果 CDP 自动发文件 (`setFiles`) 回报失败，状态灯标红，转人工通道 (R4)。

### Q6：真实工作流合理性总检（基于 11 种真模式）

**重做「模式 × phase」关键映射（基于 §4）：**

* `review` [setup]: 强制校验 `docs.length > 0`，激活 `#doc-upload-panel`。
* `iterate` [setup]: 强制校验 `#draft-input` 非空。
* `chairman` [setup]: 检查当前参会席位，若无 API 席位 (`count(api) == 0`)，`READY Gate` 阻断。
* `tournament` [running]: 界面冻结，进入全盲（匿名）状态，开启 Borda 计分表 UI。

**挑出 3 条真实工作流本身的漏洞与修复建议：**

1. **漏洞 1：`debate` 模式的“只看他人”违背历史常识**。


* **问题**：§4 要求 `debate` 每人只看别人的论点，不看自己的。但在有长期上下文的会话中，如果不给 AI 喂它自己上轮说的话，它极有可能在下一轮自相矛盾（幻觉）。
* **UI 修复**：在 `setup` 期提供一个 Toggle：`[✓] 辩论时附带自身历史摘要`，在底层将自身的历史压缩为前提注入，既防强化又防失忆。


2. **漏洞 2：`tournament` 模式的“匿名+定序”易造成格式崩溃**。


* **问题**：要求 AI 并行盲评并输出契约 (`candidate/ballot`)。但大部分网页 AI 拒接结构化输出，只要它寒暄一句“好的，我的评价如下”，判定器就会切片失败，导致死循环。
* **UI 修复**：进入 `paused` 相，为 `tournament` 配置一个 **人工解析干预弹窗**。如果 AI 输出非法，截获并展示给主持人：“请从以下大段文本中圈选出第 1 名、第 2 名”，人工转录补齐契约后继续。


3. **漏洞 3：`iterate` 模式的“规范化比对”死锁**。


* **问题**：`no-new-critique` 依靠文本规范化比对判断终止。但 AI 极其喜欢在每次回答末尾加上“此外，您还可以参考...”导致两次比对永远不同，5 轮跑满。
* **UI 修复**：`running` 期的进度条旁增加 `[强制收敛]` 按钮。当主持人肉眼判定核心矛盾已解决，不需要干等 5 轮跑满，点击直接将状态强推入 `done`。
