这轮我会把前两轮的 UI 讨论进一步“收紧”为一套真正可以落地的产品规则。最重要的结论先说：

> **phase 不应该承载“第几轮”和“当前做哪一步”。**
>
> 我支持你推荐的 **`setup / running ⇄ paused / done` 四相 + attention 正交**，但必须再增加两个独立维度：**`step`（模式内部步骤）**和**`round`（业务轮次）**。
> 否则 `tournament`、`chairman`、`iterate`、`build` 一定会把 phase 搞乱。

这次判断严格基于你勘误后的 11 个真实模式，而不是上一轮那套已经作废的 8 模式。

# Q1：phase 几态？

## 我的结论：四相，支持你的推荐

正式定义：

```text
phase
├─ setup
├─ running
├─ paused
└─ done

attention
├─ none
├─ warning
└─ blocking

step
└─ 当前模式自己的工作步骤

round
├─ index
├─ max
└─ label
```

其中：

```text
READY Gate ≠ phase
```

而应该是：

```text
phase = setup
readiness = blocked | ready
```

这样“配置中”和“已经满足开会条件”不需要再硬造一个 `ready` phase。

---

## 为什么不是 5 态 / 6 态？

因为 `phase` 的职责应该是**会议生命周期**，不能把下面这些东西混进去：

```text
暂停
第3轮
评标阶段
等待 API
工具失败
主席点名
真编译
```

这些都属于不同维度。

例如：

```text
phase = running
step = evaluate
round = 2/3
attention = none
```

这已经完整表达了“招标评审正在第二轮评标”。

如果再造：

```text
running_evaluate_round2
```

状态组合会爆炸。

四相最大的好处是：

> **任何模式都能放进去，而不会为新模式增加 phase。**

## 11 个真实模式逐个过一遍

| 模式            | setup         | running 中的 `step`                                  | round 怎么显示     | done        |
| ------------- | ------------- | -------------------------------------------------- | -------------- | ----------- |
| `broadcast`   | 配置席位/任务       | `answer`                                           | 单轮             | 完成          |
| `review`      | **材料硬门槛**     | `independent_review → cross_exam → merge`          | 单轮             | 完成          |
| `assist`      | 配置任务/席位       | `propose → consult → converge`                     | 单轮             | 完成          |
| `iterate`     | **草稿硬门槛**     | `critique → revise` 循环                             | `修订循环 2/5`     | 达到终止条件      |
| `debate`      | 配置双方/席位       | `opening → cross_debate`                           | 单轮             | 完成          |
| `panel`       | 配置成员/任务       | `consult → merge`                                  | 单轮             | 完成          |
| `chairman`    | **API 主席硬门槛** | `select → speak` 动态循环                              | `第2次点名 · 动态终止` | 无新问题        |
| `divide`      | 配置任务          | `decompose → parallel → assemble`                  | 单轮             | 完成          |
| `tournament`  | 配置任务/候选席位     | `candidate → ballot → verdict → revision → review` | `第2轮/最多3轮`     | same-winner |
| `build`       | 配置交付          | `produce → persist → build → verify`               | **不称“第几轮”**    | buildPass   |
| `transparent` | **议题+资料硬门槛**  | `broadcast`                                        | `第3/8轮`        | 固定轮数        |

这些模式的真实形状、前置条件、循环与终止判据，都是你本轮提供的源码核实定义。

### 这里有一个非常重要的 UI 规则

**不要统一显示：**

```text
第 N / M 轮
```

因为这对 `build`、`chairman` 是误导性的。

统一组件应该是：

```text
.progress-primary
```

显示“当前工作步骤”。

```text
.progress-secondary
```

在确实存在业务轮次时才显示轮次。

例如：

### transparent

```text
第 3 / 8 轮
```

### iterate

```text
修订循环 2 / 5
当前：修订
```

### chairman

```text
第 2 次点名
动态终止
```

### tournament

```text
评审循环 2 / 3
当前：复评
```

### build

```text
阶段 3 / 4 · 真编译
```

这样用户不会产生错误心理模型。

---

## `paused` 也不重置 step / round

例如：

```text
running
step = cross_exam
round = 1
     ↓
paused
step = cross_exam
round = 1
     ↓
running
step = cross_exam
round = 1
```

暂停是生命周期状态，不是重新开始。

这与你们已经定下的“暂停=暂停派发”一致。

---

## 反方方案什么时候会失败？

如果采用“为不同模式建立更多 phase”，最典型的失败是：

```text
tournament_review_round2
chairman_waiting_round3
iterate_revise_round4
build_verify
```

然后每新增一个模式就新增一堆 CSS/按钮状态。

**失效场景：**

50 个席位、工具调用、人工投递同时加入后，一个席位掉线到底属于：

```text
paused？
running-error？
tool-wait？
chairman-api-lost？
```

状态机会迅速变成组合爆炸。

---

## 成本

非常低：

```js
phase
readiness
attention
step
round
```

五个维度，DOM 无新增要求，主要是状态模型变化。

**反而能减少后续状态判断数量。**

## 唯一工程风险

**当前 `<webview>` 与 HTML overlay 的层级必须实机确认。**

如果当前 Electron 版本下 webview 原生层压住 HTML ToolDock，那么不能硬上 CSS `z-index:99999`。

应预留：


作为独立壳层；如果普通 DOM overlay 在当前 Electron 组合下无法稳定盖住 webview，再考虑升级到更合适的壳层承载方式。

这一点必须用你们现有 CDP/真机验证，不应该凭 CSS 猜。

# Q3：外部 AI 回答到底放哪里？

## 我选 A：顶部甲板 + 编辑锁折叠 + max-height

这一题我不会摇摆。

我作为每天使用它的人，会选：

> **A。**

最重要的原因其实不是“顶部方便”。

而是：

> **外部 AI 回答本质是一个“输入工作台”，不是一个“监控面板”。**

而 ToolDock 是：

> **监控/审计工作台。**

两者不应该共享同一个抽屉。

你本轮的真实背景也明确了：用户当前人工咨询就是“写咨询稿 → 各窗口投递 → 回收答案”，而现有外部 AI 面板已经承担回收粘贴与上下文切片。因此它天然靠近“发起咨询”的操作流。

### 编辑时锁折叠

当：

```text
textarea.focus
OR dirty === true
OR attachmentQueue.length > 0
```

自动收起逻辑不能把它折掉。

即：

```js
data-edit-lock="true"
```

不是禁止用户手动关闭，而是：

> **系统自动折叠不能抢走用户的编辑空间。**

# Q4：API 席位要不要虚拟滚动？

## 我的选择：现在不要。

我支持：

> **原生滚动 + 分组页签 + 密度档。**

而不是提前上虚拟化。

但我不会把这个结论写成“以后永远不虚拟化”。

我建议冻结一个**可测的升级门槛**：

```text
≤ 200 API 席位
    ↓
原生滚动

> 200
    ↓
先跑性能检测

性能连续越过阈值
    ↓
才启用 virtualization
```

---

## 为什么我选 200 作为第一道工程门

不是因为“200 是神奇数字”。

而是你的 API 席位是：

```text
轻量 div
```

而不是：

```text
webview
```

这正是你们已经确认要利用的不对称。

假设每个 API SeatCard：

```text
1 card
+ name
+ status
+ role
+ tool summary
+ buttons
```

即使最终有二三十个子节点，200 席也只是几千级 DOM。

这和 50 个 webview 完全不是同一个问题。

因此没有必要为了“可能出现 200 席”提前引入：

```text
virtual viewport
item recycling
scroll anchoring
preserved offscreen state
```

这些都会增加复杂度。

---

## 真正的升级判据

把“200”作为**触发基准**，不是性能真理。

CDP 压测时记录：

```text
seatCount
JS heap
DOM node count
layout time
recalc style time
scroll FPS
1 秒内状态更新数量
```

建议：

```text
> 200 席
且满足以下任意 2 项：

1. p95 layout > 16ms
2. 滚动稳定低于 55fps
3. 连续运行 5 分钟后 heap 持续异常增长
4. 频繁状态更新时出现明显输入延迟
```

再启动 virtualization。

这些是**你们产品的工程验收门槛建议**，不是声称已经从现有源码实测得到的数据。

# Q5：人工模式——我明确选建模二

这是我这轮最明确的选择：

> **人工模式不是第 12 种 mode。**
>
> 它应该是横切所有模式的 `delivery channel`。

即：

```text
Seat
├─ transport = auto
└─ transport = manual
```

我不选“一”和“三”。

---

## 为什么不是第 12 种 mode？

因为人工并没有改变“会议怎么思考”。

它改变的是：

> **任务怎么到达 AI、回答怎么回收。**

比如：

```text
review
```

本身还是：

```text
独立审阅
→ 交叉质证
→ 归并结论
```

人工投递只是：

```text
第一阶段：
用户手动把材料发给每个 AI
```

所以如果把人工变成：

```text
mode = manual
```

你反而丢失了：

```text
review
iterate
panel
tournament
...
```

的真实语义。

---

# 人工模式不是“没有模式”

这是最容易误解的地方。

我建议产品里这样理解：

```text
会议语义
    ↓
mode

任务投递方式
    ↓
deliveryChannel
```

例如：

```text
mode = review
delivery =
    Claude      manual
    GPT         manual
    Gemini      auto
    Qwen        manual
```

这就非常强。

以后自动广播修好了：

```text
同一个会议
某些席位继续 auto
某些席位仍 manual
```

不需要再造模式。

---

# “人工咨询”怎么做到一等公民？

不要让用户自己理解 `deliveryChannel`。

在 UI 里做一个非常直观的入口：

```text
开始会议
开始人工咨询
```

**这是产品入口，不是 mode enum。**

用户点：

```text
开始人工咨询
```

系统内部创建：

```text
session
mode = consultation/broadcast-like task context
delivery = all manual
engine = manual-coordinator
```

这里 `人工咨询` 是一个**工作入口/快捷预设**，不是第 12 个模式。

这实际上取得了你想要的“三”的 UX 优点，同时保留“二”的架构正确性。

# Q6：重新审查 11 种真实工作流

这里我要直接指出：**目前最大的风险不是 UI，而是“模式定义已经有硬契约，但 UI 还没有把契约变成真正的门”。**

你本轮已经明确提出：

* `review` 必须有材料
* `iterate` 必须有草稿
* `chairman` 必须有真实 API
* `tournament` 有 `kind` 产出契约
* loop 模式有不同轮次语义。

我认为至少有下面 **5 个真实工作流漏洞**。

---

# 漏洞 1：前置条件如果只是“提示”，用户迟早会误开

例如：

```text
review
```

没有材料。

如果 UI 只是：

```text
⚠ 未添加材料
```

仍然有：

```text
[开始]
```

这是错误的。

必须：

```text
开始按钮 disabled
```

并明确：

```text
不能开始的原因：
✕ review 要求至少 1 份材料
```

---

## 统一 READY Gate

不要每个模式手写一套。

定义：

```js
modeConfig.requires
```

例如：

```js
review: {
  requires: [
    { type: 'material', min: 1 }
  ]
}
```

```js
iterate: {
  requires: [
    { type: 'draft', min: 1 }
  ]
}
```

```js
chairman: {
  requires: [
    { seat: 'api', min: 1, role: 'chairman' }
  ]
}
```

```js
transparent: {
  requires: [
    { type: 'topic', min: 1 },
    { type: 'material', min: 1 }
  ]
}
```

UI 自动生成：

```text
✓
✓
✕
```

这与你们已经锁定的 READY Gate 完全一致，但这里把 Gate 真正绑定到模式定义上。

### 成本

低，中间加一个 validator。

### 反例

如果继续手写：

```js
if (mode === 'review') ...
if (mode === 'iterate') ...
if (mode === 'chairman') ...
```

新增模式时很容易忘掉 UI Gate。

---

# 漏洞 2：`review` 的“第一阶段只能看材料”容易被 UI 无意破坏

这个约束不是普通流程顺序。

它要求：

```text
第一阶段：
全员并行
↓
只看材料
↓
不能看彼此回答
```

所以 UI 必须把：

```text
阶段1
```

和：

```text
上下文可见范围
```

绑定。

例如：

```text
REVIEW · 独立审阅

上下文：
✓ 原始材料
✕ 其他席位回答

状态：
12 / 12
```

到了：

```text
交叉质证
```

才显示：

```text
✓ 材料
✓ 他人回答
```

否则系统虽然“代码顺序正确”，用户却可能错误理解为什么第一阶段没有互相看到答案。

---

# 漏洞 3：`iterate` 没有草稿版本管理，终止判据很难让用户相信

`iterate` 的真实终止条件是：

```text
no-new-critique
```

而且必须文本规范化比较，否则可能永不停机。

因此 UI 至少应该显示：

```text
原始草稿 v1
↓
批评
↓
修订 v2
↓
批评
↓
修订 v3
```

例如：

```text
反复修正
循环 3 / 5

草稿 v3
批评项：2
新增批评：0

✓ 达到终止条件
```

否则用户看到：

```text
循环结束
```

却不知道为什么停。

### 成本

需要 Artifact metadata：

```text
version
sourceDraft
critiqueCount
normalizedFingerprint
```

UI DOM 很少。

### 反例

没有版本链时：

```text
v3 和 v2 实际只改了空格
```

结果“新批评”判断异常，用户无法审计。

---

# 漏洞 4：`chairman` 的 API 主席是硬依赖，必须变成“结构化门槛”

不是：

```text
主席：DeepSeek API
```

而要明确：

```text
主席席位
● DeepSeek
API
已连接
```

并在 setup：

```text
主席点名模式

✓ 存在 API 主席
✓ 主席身份固定
✓ 点名池 8 席
```

如果用户只剩：

```text
9 个 WebView
```

那么：

```text
✕ 无法开始
需要至少 1 个 API 主席席位
```

因为你的真实约束就是：

> 主席必须走真实 API，不能用网页版。

---

## 更重要的是运行中 API 主席掉线怎么办？

这里建议：

```text
phase = running
attention = blocking
```

如果当前步骤无法继续，再由引擎明确把：

```text
phase → paused
```

而不是 UI 自己看到：

```text
API 掉线
```

就擅自改变 phase。

这样 attention 和 phase 的职责才不会互相污染。

# 漏洞 5：`tournament` 必须把 `kind` 契约做成第一等数据

这个是最容易导致灾难性错误的模式。

你已经明确：

```text

ballot
verdict
revision
review
```

不同产出物不能混。

所以席位卡不能只显示：

```text

```

而应该：

```text

✓
输出：candidate
```

进入评标阶段：

```text
匿名候选
candidate #07
```

评标：

```text
ballot
```

定标：

```text
verdict
Winner = #07
```

复评：

```text
review
```

修改：

```text
revision
```

# `build` 还有一个独特风险

它的三个验证档位行为明显不同：

# 最终的 ControlRegistry 我建议正式冻结成这套

```js
    termination: 'no-new-question'

      'candidate',
      'ballot',
      'verdict',
      'revision',
      'review'

    termination: 'same-winner'
  },

      'produce',
      'persist',

  }
```

# 还有一个很重要的产品原则

你现在实际上已经不是一个“12 个 AI 网页排在一起的测试台”。

随着：

```text
50+ 席位
+
API
+
200+ 工具
+
人工投递
+
```

它已经开始变成一个：

> **AI 多席位会议编排器 / 观察台**

所以以后 UI 设计不要再围绕“哪个按钮在哪”。

应该围绕：

```text
↓

↓

↓

↓

↓

```

这才是能长期扩到几十、上百席位而不重新推翻 UI 的核心。

## 本轮最终裁决

**Q1：四 phase + attention，接受，但增加 `step + round + readiness` 三个正交维度。**

**Q2：全局右滑 ToolDock 绑定 activeSeat，卡内只保留 24px 工具状态摘要。**

**Q3：外部 AI 回答选 A——顶部甲板 + 编辑锁折叠 + max-height；不与 ToolDock 合并。**

**Q4：API ≤200 先原生滚动；>200 进入性能检测，达到实测门槛再启用虚拟化，不提前背复杂度。**

**Q5：人工模式选“横切所有模式的 delivery channel”；产品层提供“人工咨询”快捷入口，但不增加第 12 个 mode。**

**Q6：真正需要冻结的是“模式契约 → READY Gate → step → round → artifact kind → termination”的完整链条，而不是单纯的 UI 显隐。**

对 §2 的 **23 条已定案，我本轮无推翻**；但我建议把“第 13 条 `ControlRegistry`”进一步升级为本次《UI/工作流规范 V1》的核心骨架，并把 `phase / readiness / step / round / attention / deliveryChannel / artifact.kind` 七个字段冻结下来。
