# 第 7 轮咨询案 · 独立顾问席回答（Q1-Q4）

## Q1 R7-1 全局降 L1 vs 按站点分主备
裁决：全局降 L1 为"尽力"正确，采纳 R7-1；但"尽力"层内部按站点排序，基座恒为 L2。
不做主备矩阵的原因：两条控制路径会让 F7-1 的 hasChip 误报（成功却漏发新文件）成为默认故障面；地基必须单一确定性路径。
站点级判断（仅决定尽力层是否值得先试一次）：
- Gemini / 元宝 / 豆包：有专属菜单/拖放通道（F7-1），尽力层优先级最高，可先试专属通道一次，仍须回读校验。
- Kimi / DeepSeek：无专属通道、直塞不稳（F7-1）-> L1 跳过，起手 L2。
- 谷歌：attach 三条策略均未塞进 input（F7-3、缺口 C）-> L1 事实上已死，起手 L2。
- GPT / 千问 / 文心：真实轮挂不上（缺口 D）+ 残留污染（缺口 E）-> 起手 L2。

## Q2 闸门丙是否必要 / 回退浮窗是否推翻 Q3 默认 A
裁决：闸门丙必要，且不构成推翻 Q3 默认 A。
必要性：F7-3 布局从未落地 + F7-2 用户痛点=发不出去；若 dispatch 进甲板却因 L2 逐席交互走不通，甲板成"看着有用不了"的重演。
不推翻甲板：闸门丙只管 dispatch 重交互子面板能否在甲板内闭环，不等于甲板不该存在。
落位：甲板常驻=全局触发器组 + 广播控制入口 + 已发 k/N 全局进度（不依赖逐席交互，窄甲板也稳）；L2 逐席复制/模拟点击重交互放浮层，由甲板触发器唤起，与闸门甲（F1 浮层不压网格）一致。甲板永不空。仅连浮层都真机走不通才整块回退独立浮窗、且不阻塞 ship。

## Q3 五缺口归属层判定
- A 成功判定不可靠（hasChip 误报）：Provider/传输层，布局无关，甲类先解，与 E 联动。
- B Kimi·DeepSeek 无专属通道：Provider 适配层，布局无关，甲类先解，认命走 L2 直塞。
- C 谷歌文件 attach 失效：Provider 适配层，布局无关，甲类先解。
- D 通义·文心·ChatGPT 真实轮挂不上：Provider 适配层，布局无关，甲类先解。
- E 跨轮残留文件污染：传输层，布局无关，甲类先解，L2 基座必选项。
结论：5 缺口全部为 Provider 适配层/传输层，全部与布局无关。移入顶甲板不新增其技术难度；唯一新增布局耦合风险=L2 逐席交互控件需可点击空间，甲板过窄会压没它，这正是闸门丙要拦的那一件事。

## Q4 还有无 L 级遗留 / 兜底优先级
- 除 F7-1~7-3 外无新的必须再辩 L 级遗留。结论：可开工顶甲板。
- 开工顺序必须卡准：1 先在 Provider 适配层落地 E+A 的发送前清空+回读校验，作为 L2 基座第 0 步 -> 2 落四容器骨架 -> 3 过闸门丙真机走通。跳过 1 等于在 F7-1 的沙子上再盖甲板。
- 兜底 #19（发送前清空+回读校验）必须提前到 P0：L1 降为尽力后若不清空，缺口 E（残留旧文件->hasChip 误报成功）会直接击穿手动基座可信度。#19 升格为 L2 基座第 0 步 + 闸门丙验收前置。
