为什么放底部‌：

使用节奏‌：日志是「被动接收型」——用户原话「开会时持续滚动、偶尔瞟一眼」，底部不挡操作路径上操作路径干扰顶部操作动线
真腾空间逻辑‌：折叠成 1 行（28px）几乎不占有效空间，展开时从下往上"涨"，网格从上往下"退，符合阅读习惯
字段级理由‌：.log 是 flex:1; overflow-y:auto 的滚动容器，放在底部天然占满整宽时，长文本行宽更长、换行更少、信息密度更高
和 dragCellHeight 的冲突‌：dragCellHeight 是 cell 内部高度拖拽，logdock 是外层容器，二者不冲突——logdock 撑高时 grid 容器高度减小，grid 内部用 grid-template-rows: repeat(auto-fill, minmax(0, 1fr)) 自动适配，cell 内部 webview 只是高度变小、不卸载

成本‌：低。新增 1 个 flex item，CSS 约 15 行，JS 折叠逻辑复用现有 body.infocollapsed 思路（加 body.logcollapsed）。
反例‌：如果你的用户习惯「边看日志边调外部 AI 回答」（两个都要同时看），日志在底、外部 AI 在顶，上下扫视距离远——此时该把外部 AI 也挪到底部和日志并排或做 Tab。

Q3：模式感知顶栏怎么做不臃肿

推荐方案：分组显隐 + 两阶段（配置期 / 运行期）‌

字段级设计：
html
<!-- 模式键：data-mode="transparent|panel|build|..." -->
<!-- 阶段键：data-phase="config|running" -->
<body data-mode="transparent" data-phase="config">
  <div class="topdeck">
    <div class="seatbar group-global">  <!-- 全局组：所有模式都有 -->
    <div class="chairbar group-global">
    <div class="modezone">
      <div class="ctrl-group group-transparent">  <!-- transparent 模式专属 -->
        <!-- tmbox 内容：输出目录/轮数/议题资料 -->
      </div>
      <div class="ctrl-group group-build">         <!-- build 模式专属 -->
        <!-- 产物验证档位等 -->
      </div>
      <div class="ctrl-group group-panel">         <!-- panel 模式专属 -->
        <!-- 专家会诊设置 -->
      </div>
      <div class="ctrl-group phase-config">       <!-- 仅配置期显示 -->
        <!-- 开会前才需要的：角色组/重排/每排窗口数等 -->
      </div>
      <div class="ctrl-group phase-running">      <!-- 仅运行期显示 -->
        <!-- 开会中才需要的：轮次进度、暂停原因等 -->
      </div>
    </div>
    <div class="extbox group-global">            <!-- 外部 AI 回答 -->
  </div>
</body>


CSS 显隐规则（核心 6 行）‌：

css
/* 默认全藏 */
.ctrl-group { display: none; }

/* 按模式显 */
body[data-mode="transparent"] .group-transparent { display: block; }
body[data-mode="build"] .group-build { display: block; }
body[data-mode="panel"] .group-panel { display: block; }

/* 按阶段显 */
body[data-phase="config"] .phase-config { display: block; }
body[data-phase="running"] .phase-running { display: block; }

/* 全局组恒显 */
.group-global { display: block; }


JS 切换逻辑‌：

js
const MODE_CONTROLS = {
  transparent: ['seatbar', 'chairbar', 'tmbox', 'extbox', 'log'],
  panel:       ['seatbar', 'chairbar', 'group', 'extbox', 'log'],
  build:       ['seatbar', 'chairbar', 'buildlevel', 'log'],
};
// 切换模式时：
document.body.dataset.mode = currentMode;
// 切换阶段时（开始会议 = running，停止 = config：
document.body.dataset.phase = isRunning ? 'running' : 'config';

为什么用「data- 属性 + CSS」而非 JS 逐个 if」
声明式‌：CSS 管显隐，JS 只改一个属性值，状态源单一
易扩展‌：加新模式 = 加一组 class + 一条 CSS 规则
测试友好‌：CDP 读 body.dataset.mode 就能断言模式状态
不臃肿‌：同屏最多显示「全局组 + 1 个模式组 + 1 个阶段组」，控件数量可控

成本‌：中。需要把现有零散的 if (mode === 'transparent') 逻辑统一改成 data-attribute 驱动。
反例‌：如果模式数量超过 8 种、且每种模式控件组之间差异极大（> 80% 控件都不一样），用 CSS class 拼起来会很碎——此时该拆成多个独立 deck 组件、按模式整个替换 render，而不是在同一个 deck 里显隐。

成本‌：低。2 条 CSS 规则 + 1 个 body class 切换。
为什么安全‌：.topdeck 内部全是表单/文本，‌没有 webview‌，`height:0 + overflow:hidden 完全没问题，不会触发任何 webview 重排。

底部日志 .logdock：Flex 高度收缩‌

css
.logdock {
  flex: 0 0 32%;     /* 默认展开占 32% */
  min-height: 28px;
  transition: flex-basis 0.25s ease;
  display: flex;
  flex-direction: column;
}
body.logcollapsed .logdock {
  flex-basis: 28px;  /* 折叠成标题行高度 */
}
.logdock-body {
  flex: 1;
  overflow: hidden;  /* 折叠时内容被裁掉 */
}
body.logcollapsed .logdock-body {
  display: none;    /* 折叠时彻底隐藏 body，避免滚动条残留 */
}

成本‌：低。3-4 条 CSS。
为什么安全‌：logdock 收缩时，.main（grid 容器）的 flex:1 自动补满高度——‌grid 容器只是高度变小，12 个 cell 还在，webview 不卸载、只是高度变矮‌。Electron webview 对高度变化非常稳定（不像宽度变化那样会触发列数重排）。

⚠️ 绝对不能做的‌：

❌ 对 .grid 或 .cell 用 display:none → webview 卸载重建，丢登录态
❌ 对 .grid 用 visibility:hidden → 空间还占着，白折了
❌ 折叠右栏用 width:0 但 overflow:visible → 内容还露着

成本总计‌：CSS 约 15-20 行，JS 约 10 行（两个折叠按钮的 click handler）。
反例‌：如果折叠需要「折叠后 webview 尺寸变化导致某些网页 AI 内部布局错乱（如某些网页对可视区域变化触发重排开销大），此时不该用纵向折叠、改用 overlay 抽屉——但 9 个 webview 高度变化的开销远小于宽度变化，纵向是安全的。

推荐：常驻顶栏 + 阶段驱动可用性
html
<div class="chairbar group-global">
  <input class="chair-input" placeholder="主持人输入...">
  <button class="btn-broadcast" data-phase-active="both">📢 广播</button>
  <button class="btn-file" data-phase-active="both">📎 文件</button>
  <button class="btn-pause" data-phase-active="running">⏸ 暂停</button>
  <button class="btn-stop" data-phase-active="running">⏹ 停止</button>
</div>


CSS 规则‌：

css
/* 默认所有按钮都显示，只是可用性不同 */
.chairbar button { opacity: 1; }
.chairbar button:disabled {
  opacity: 0.4;
  cursor: not-allowed;
}

/* 配置期：暂停/停止按钮灰掉但可见 */
body[data-phase="config"] .chairbar button[data-phase-active="running"] {
  opacity: 0.5;
  pointer-events: none;
}


为什么常驻理由‌：

语义一致性‌：chairbar 是「主持人操作入口」，不管开不开会都在那儿，用户知道去哪儿找
肌肉记忆‌：按钮位置固定，不用找，效率高
实现成本低‌：只是改 disabled 状态，不用动 DOM 结构
空闲时广播/发文件也有用‌：用户原话里空闲时广播=直接发给网页/API，不是没用

两阶段的视觉差异‌：

配置期（空闲）‌：⏸⏹ 按钮半透明（opacity:0.5），视觉上「不可用但可见」，用户知道这是开会后才会激活
运行期（开会中）‌：全部按钮高亮，⏸⏹ 全可用

成本‌：极低。加 data-phase-active 属性 + 2 条 CSS。
反例‌：如果 chairbar 控件超过 8 个按钮、且空闲时大部分都没用，常驻会让顶栏显得拥挤——此时该把「运行期专属」按钮在配置期 display:none 彻底隐藏，开会时才出现（用 phase-running 组）。
