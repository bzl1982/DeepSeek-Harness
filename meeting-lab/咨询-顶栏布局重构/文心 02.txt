Q2：席位规模化（12→50+）落地方案
核心设计原则：利用网页/API席位的不对称性
网页席位：9个封顶（重webview，永不卸载、永不滚出视口、宽度尽量不变）
API席位：轻div，可无限扩展，支持虚拟滚动、动态创建销毁
2.1 网格组织方案：分层网格+分组+虚拟滚动+密度档位

字段级结构：

.grid-web-section {

  width: 100%;

  position: absolute; /* 虚拟滚动定位 */
  /* 按索引计算top/left值 */
}

分组页签‌：固定第一个为「🌐网页组(9)」（永远存在，切换后仅显示9个webview），后面为用户自定义API分组，支持新建/拖拽席位/重命名，溢出时横向滚动
三档密度‌：用data-density="loose/normal/compact"驱动：
宽松（<20席）：API cell最小宽320px，最小高240px
标准（20~40席）：API cell最小宽240px，最小高180px
紧凑（>40席）：API cell最小宽180px，最小高120px
搜索过滤‌：seatbar内搜索框输入时，匹配名称/角色的API席位高亮，不匹配的API cell隐藏，webview永远显示不隐藏

成本‌：虚拟滚动仅作用于API区，9个webview完全固定不动，不会卸载/重排；DOM节点数仅比原来多15%（虚拟列表只渲染可见项，实际内存开销增长<10%）。
反例‌：

❌ 全网格虚拟滚动：会导致webview滚出视口冻结/卸载，违反§2共识6
❌ 网页/API混排：滚动时webview位置变化触发重排，甚至被挤出视口
❌ 分页而非虚拟滚动：切换分页时API席位上下文丢失，操作效率低
2.2 「每排N个」下拉升级：自适应优先+手动覆盖

下拉选项改为：自动 / 2列 / 3列 / 4列 / 5列 / 6列，默认选自动。
自动模式计算逻辑：

js
function calcAutoColumns(containerWidth, density, sectionType) {
  const minWidth = {loose:320, normal:240, compact:180}[density];
  // 网页区固定3列，宽度<600px时降为2列，尽量少变宽
  if (sectionType === 'web') return containerWidth < 600 ? 2 : 3;
  // API区按宽度算，最少2列、最多8列
  return Math.max(2, Math.min(8, Math.floor(containerWidth / minWidth)));
}

手动选择的列数按分组记忆，不同分组可独立配置
窗口resize时自动模式自动重新计算列数，手动模式保持用户选择

成本‌：修改原有relayout()函数加sectionType参数，原有3/4/5/6逻辑保留作为手动档位，不破坏现有测试用例。
反例‌：

❌ 保留原3/4/5/6不扩展：50+席位时6列需要9行，滚动过长
❌ 网页区列数随宽度自动变：webview宽度变化触发重排开销大
2.3 角色组去固定席位化：角色规则引擎

将原有角色组配置从{label, seats}改为{label, requiredRoles, optionalRoles, overStrategy, leaderRule}，实现人数与角色解耦：

表格
字段	说明
requiredRoles	必须存在的角色（如主席/记录员各1个）
optionalRoles	可选角色，人数不足时自动省略
overStrategy	超编策略：轮替（每轮轮换角色）/分组（超8人拆平行小组）/合并（多人共用一个角色）
leaderRule	组长规则：指定/选举/轮值
UI入口：角色组下拉点开后弹出配置面板，支持拖拽分配参会人到角色，超编时自动提示选择策略，确认后生效。	

成本‌：新增一个轻量配置弹层，原有6个固定角色组可平滑迁移，不破坏现有逻辑。
反例‌：

❌ 硬编码每个角色组支持的人数：新增模式/角色组需要改代码，不可扩展
❌ 超编时自动分配不支持干预：辩论等场景正反方人数需要对等，自动分配容易不符合预期
❌ 不支持分组：50人参会O(N²)上下文成本达2500份/轮（实测9人153份），不分组会导致上下文爆炸

3.3 权限控制UI
全局预设‌：设置面板内提供三个权限等级，默认按席位类型分配：
只读：文件读、检索（默认给网页席位，防prompt注入执行危险操作）
标准：只读+文件写+生成（默认给普通API席位）
全权限：标准+shell/网络/系统（默认给工程组等可信席位）
单席位自定义‌：点击cell右上角ⓘ打开抽屉，按类别分组开关工具（文件/检索/生成/Shell/网络/系统6大类，不需要逐个开关200+工具），支持继承全局/自定义模式
临时授权‌：confirm弹窗可选择「本次会话允许」，不需要修改全局配置

成本‌：权限配置仅存几个布尔值，UI为复选框组，开发量极小。
反例‌：

❌ 默认全开：网页席位可能被恶意prompt调用shell执行危险命令
❌ 默认全关：工具能力完全无法使用，失去对齐意义
❌ 200+工具逐个列开关：配置面板过长，用户配置成本极高
3.4 多席位并发防刷屏

三级展示架构：

卡片级‌：每个cell仅显示最近1条工具状态，不堆历史
分组级‌：group-tabs页签上显示该组进行中的工具数（如🤖API组 🔧3）
全局级‌：LogDock新增「工具日志」Tab，聚合所有席位工具调用记录（带席位名、时间、结果），支持过滤；头部全局指示器显示总并发数，>5变黄、>10变红提醒

成本‌：LogDock新增一个Tab页，仅需加事件监听往日志里加行，不改动原有日志逻辑。
反例‌：

❌ 所有工具调用弹toast：并发时toast堆几十个挡住操作
❌ 仅在日志里显示：用户看不到实时状态，以为程序卡死

.seatbar配置期显示，运行期默认隐藏（可临时点按钮展开调整席位）
.chairbar常驻所有模式所有阶段，⏸/⏹按钮配置期opacity:0.5灰显（不隐藏，保持位置固定形成肌肉记忆），运行期高亮可用
.extbox、.logdock所有模式常驻，可折叠
模式专属控件仅在对应模式+阶段显示，用body[data-mode][data-phase] .group-xxx { display:block } CSS规则驱动，不需要JS逐个操作DOM

成本‌：将原有零散if(mode==='xxx')逻辑替换为遍历配置加/去hidden属性，逻辑收敛，测试用例仅需断言data-mode/data-phase正确时对应控件可见即可。
反例‌：

❌ 每个模式写独立显隐逻辑：模式超过8种时if嵌套满天飞，维护成本极高
❌ 运行期彻底隐藏配置控件：开会中想调整参数需要先停止会议，体验差
❌ 所有模式控件全部显示：topdeck塞几十上百个控件，完全无法操作
