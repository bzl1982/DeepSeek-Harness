# 一、工作流批判：现在的流程有 4 处不严谨（先挑刺，再设计）

**当前隐含工作流**（从源码反推）：`选模式 → 选角色组(固定席位) → 填议题 → 开始 → 广播/收集/汇编 → 暂停/停止 → 结束`。问题：

| # | 不合理处 | 为什么是问题 | 修正 |
|---|---|---|---|
| W1 | **角色组绑定固定席位数**（`index.html:1680` 组=席位），但 API 接入点从 `settings.yaml` 动态增长 | 组是"配置时选的"，席位是"运行时探测到的"，两个真相源。第 13 个接入点出现时，"9 人专家组"放不下，溢出无定义 | 解耦：角色组降级为**角色模板包**（label + prompt 模板），选人后按实到人数实例化角色（见 Q2） |
| W2 | **只有开会前/开会中两相** | 停止会议后，摘要、日志、材料包没有"家"——现在摘要是右栏一个孤立区块。8 种模式全部有会后产物（纪要/判决书/交付物） | phase 扩为三相：`setup → running → done`。done 阶段顶栏换"纪要确认/导出/导出材料包"控件组。**这是对第 1 轮共识的推翻/补充，详见 Q5** |
| W3 | **轮次汇编 O(N²)**：每轮把全部 N 份回答注入下一轮提示，50 席 = 2500 份/轮 | 不只是上下文爆炸，是工作流模型在 12 席以上失效：50 个 AI 每轮读 2500 份材料，回答质量反而下降，"透明广播"变"透明噪音" | 工作流层面引入**两级汇总**：席位 → 小组摘要 → 主广播只发各组摘要链。UI 上表现为 logdock 增加"汇总视图"页签（明细/汇总）。UI 改不动这个，必须在汇编逻辑里改，UI 只是暴露开关 |
| W4 | **开会中席位集合冻结** | 质证/开放讨论需要临时拉人（"请第 7 席对质"），顺序接龙中途可能有人掉线要摘除 | running 阶段允许**席位停用/激活**（webview 不卸载，cell 加 `.inactive` 灰显 + 退出汇编），主持人权限 |
| W5 | **停止 = 丢弃现场** | ⏹停止后 9 个 webview 的对话上下文仍在网页里，但本台无任何"续会"概念 | done 阶段加「⏵ 续会（从第 N+1 轮）」按钮，成本只是存 `lastRound` 元数据 |

**工作流定义（修正后，三阶段状态机）**：

```
setup ──▶ running ⇄(暂停)──▶ done ──▶(⏵续会)──▶ running
  │            │
  └─ 席位/角色/议题/工具白名单   └─ 广播/监控/工具审批/席位停用/汇总视图
```

状态键：`data-phase="setup|running|done"`，挂 `body` 上，全局 CSS/控件显隐全部吃这一个键——不新增 JS 状态变量。

# 三、Q2 席位规模化方案

## 3.1 物理承载：webrow / apiscroll 两区制（前述）

```css
.main { display:flex; flex-direction:column; }
.webrow  { flex:0 0 auto; display:grid; gap:6px;
           grid-template-columns:repeat(var(--cols,auto-fit),1fr); }
.apiscroll { flex:1; overflow-y:auto; }         /* <13席时 display:none，席位并入webrow同一grid */
```

**API 席位并入 webrow 的方式**：`<13 席时无 apiscroll`，`.cell.api` 与 webview cell 同 grid 排布——都是 flex/grid item，API cell 是 div 无重排风险，`.grid` 列数自适应即可。成本：`.cell` 加 `.api` 修饰类，无结构分叉。

## 3.2 网格密度与每排升级

放弃「3/4/5/6」下拉，改**双键**：

```js
seatView = {
  cols:  'auto' | 3 | 4 | 5 | 6 | 8,   // auto=按视口宽算, 默认
  zoom:  'comfortable' | 'compact' | 'micro'  // 卡片最小高: 160 / 96 / 56px
};
// auto 列数: cols = clamp(floor(viewportW / cellMinW), 3, 9)
```

**为什么 auto 默认但保留手动**：webview resize 有开销（DeepSeek 第 1 轮已诚实声明"resize 不可避免"）——窗口拖拽时 auto 会连续触发列数跳变，9 webview 连环 resize 会卡。所以 auto 只在**窗口 resize 防抖 300ms 后**重算，拖拽过程不动。成本：1 个防抖 + clamp；反例：双屏拖拽窗口跨屏的瞬间列数闪变，若用户截图验收会抓到——验收脚本里固定 `cols:6` 再断言。

搜索定位：`🔍` 输入 → 匹配名牌的 `.cell` 加 `.spotlight { outline:2px solid var(--accent) }` 并 `scrollIntoView`。只高亮不筛选——**筛选会 display:none 某些 cell，若是 webview cell 就违反红线**。反例：当用户想要"只看组A"时，用页签（逻辑视图）而非搜索过滤（物理显隐），别混。

## 3.3 角色组去席位化（W1 的修正落地）

```js
// 旧: roleGroup = { label:'9人专家组', seats:9 }        ← 席位绑定
// 新: rolePack   = { label:'专家会诊', roles:[
//        {label:'主审', promptTpl:'…', maxShare:1},      // 唯一角色
//        {label:'专家', promptTpl:'…', maxShare:∞},      // 可多人共享
//        {label:'记录', promptTpl:'…', maxShare:1} ] }
```

落座算法（setup 阶段，选完角色包后弹出分配条）：

```
已选 14 席 → 主审×1(点选) 记录×1(点选) 专家×12(自动填满)
超编处理: 专家 maxShare=∞ 无冲突; 若某模式角色均为 maxShare=1 且人数>角色数
         → 自动均分为 ⌈N/k⌉ 小组, 页签出现 [小组1][小组2]… (呼应两级汇总)
```

**成本**：`rolePack` 纯数据改造，`renderSeatbar` 重写约 60 行，400 测试中断言"9 人专家组"文本的用例需改为断言 `rolePack.label`。反例：透明广播模式不需要角色（全员同权），角色包允许为空包 `roles:[]`，UI 走旧的全员同席路径——别强推"每个模式必须配角色"。

## 3.4 为什么不用虚拟滚动包 webview、不用分页移 webview

有人可能想把 9 webview 分页（移动 DOM 节点到另一页）。技术上移动节点 webview 不 reload，但：① 移出视口的页用户看不见任何状态灯，监控断掉；② `--disable-gpu` 下多页合成行为未验证；③ 收益为零（视口外 webview 照样耗内存）。**webview ≤9 是产品约束，写进设置页**：超出的网页接入点排队提示"网页席位已满 9，剩余请走 API 通道"。

# 四、Q3 工具能力方案（壳层 UI）

## 4.1 席位卡片统一 IA

```
.cell
├─ .cell-head   名牌: [模型名] [@渠道徽标12px]    ← 徽标只是溯源, 不是能力标签
├─ .cell-body   webview | API 文本区            ← 两者能力拉平后, body 无差别
├─ .cell-foot   [●状态灯][R3][🔧×n][⚠×m][⠿]     ← 状态条: 轮次/工具/告警/拖拽
└─ .cell-tools  (不存在的节点 —— 工具UI全部外置到 .tooldock)
```

`@Web/@API` 徽标保留的原因：排查问题时要知道"这个席位是壳控制不了的网页"，但这是运维信息，缩成 12px 图标，不再做 `-API` 后缀文本。

## 4.2 工具调用生命周期与呈现

```
席位发言"我要查X" → 壳层解析出工具意图 → 三态分流:
  ① 白名单内+只读类(file.read/search) → 自动执行 → 结果自动回注下一轮汇编
  ② 白名单内+危险类(shell/write)     → 执行前挂起 → ⚠进顶栏审批条+该席位历史
  ③ 白名单外                          → 直接拒绝 → cell-foot ⚠+1, logdock记一行
审批三键: [允许本轮] [总是允许(升白名单)] [拒绝]
```

呈现位置：**三处分层，互不刷屏**——

| 层级 | 位置 | 内容 | 为什么 |
|---|---|---|---|
| 信号层 | `.cell-foot` 角标 | `🔧×2 ⚠1` 纯计数 | 50 席同屏时唯一的概览手段；数字比图标省空间 |
| 详情层 | `.tooldock`（右滑出） | 该席位调用时间线：工具名+状态+折叠的参数/结果 | 时间线是纵向的，右侧滑出空间匹配；绑定 activeSeat |
| 审计层 | `.logdock` | 每调用只记 1 行聚合：`[12:03] 席位#3 file.read ✅` | 主日志永远不被工具输出淹没——**这是开会中防刷屏的底线规则** |

结果预览截断 200 字 + 「⧉ 完整结果进 tooldock」，文件类结果给「📂 在文件夹中显示」（Electron `shell.showItemInFolder`，成本一行）。

## 4.3 权限 UI

```js
seat.tools = { preset:'readonly' | 'standard' | 'custom', allow:[...] };
// 默认: 网页席位 readonly(壳只能insertText, 工具结果回注依赖汇编, 误伤面大)
//       API 席位 standard(文件+检索, 无shell)
// 入口: seatbar 每个席位芯片 hover 出 ⚙ → 弹出该席白名单编辑(分组折叠列表)
```

配置挂在席位芯片上而非全局工具台：**白名单是"这个 AI 被信任到什么程度"的属性**，跟着席位走才符合心智。成本：芯片 hover 弹层 1 个；反例：批量配置 50 席时逐个点芯片是噩梦——加 chips 行尾的「批量设置」钮（对当前页签选中席应用同一 preset），别做全局默认模板，否则"改了默认，老席位静默升权"是安全事故。

**映射表随模式增长不失控的策略**：

1. **组复用**：8 种模式的控件组实际只有 ~10 种（`z-seatbar/z-chairbar-static/z-chairbar-run/z-tmbox/z-flow/z-extbox/z-buildlevel/z-debate-pair/z-breakout-tabs/z-summary`），模式只是**组的排列组合**，新增模式=新一行配置而非新代码。新增第 9 种模式的成本 ≈ 写 1 行映射 + 新增组（若需要）30 行 DOM。
2. **未知组白名单制**：渲染器启动时校验映射表引用的组名都在已注册组列表内，不存在的组直接抛错——防止映射表漂移出幽灵控件。
3. **反例**：如果某模式（如 build）的 running 组超过 6 个，说明该模式工作流本身该拆分阶段（build 的验证移到 done 子相），**不要用映射表硬塞**——映射表是显隐工具，不是流程万能药。

**推翻一条半，其余 8 条共识无推翻**：
