## Q1 · phase 状态机：四相 + attention 正交，采纳

**结论**：`setup / running ⇄ paused / done`，attention 独立轴。支持你的推荐，但逐模式检验后必须加两条修正，否则 loop 型模式会被状态机装变形。

### 逐模式检验（§4 的 11 个）

| 模式 | loop | 检验 | 结果 |
|---|---|---|---|
| broadcast | 否 | setup 广播稿可编辑，running 单趟，done 落盘 | ✓ |
| review | 否 | 三阶段单趟；阶段 ≠ phase | ✓ |
| assist / divide / debate / panel | 否 | 同上；panel 可分组，组间是轮次不是 phase | ✓ |
| iterate | ≤5 | 轮在 running 内消化，phase 不变 | ✓（见修正 1） |
| chairman | ≤4 | 同上；轮内"点名"是调度动作，不入状态机 | ✓ |
| tournament | ≤3 | 五阶段×轮在 running 内 | ✓ |
| build | 是 | 轮内产物验证三档是 running 的**子状态** | ✓ |
| transparent | 轮数 1-10 | 同上 | ✓ |
| （无）manual 咨询 | 否 | 见 Q5 | ✓ |

**装得下**。"招标评审 5 阶段 × 3 轮"、"主席点名 4 轮动态点名"都不会溢出状态机——因为设计规则是：**phase 只管"会议生命阶段"，模式内部的阶段/轮/验证档全部降级为进度条数据，不进状态机**。

### 两条修正（说服你"为什么是这四相"的真正理由）

1. **轮次不是第五个态**。有人（含第 2 轮五态派）想把 loop 的"轮"做进状态机。错的理由：`running` 一旦分裂成 `round1/round2/…`，状态机就和 §4 表里每个模式的 loop 上限（5/4/3/动态）耦合死了——新增一个 loop 模式就要改状态机枚举，违反定案 13 的"新增模式=加一行"原则。正确做法：状态机只有四相；轮次是 `progress:{loop, round, limit}` 一条**数据**，进度条渲染它。terminate 判据（no-new-critique / no-new-question / same-winner / buildPass）是引擎层的轮间 gate，失败才把 running→done，状态机不感知判据本身。
2. **done 必须可恢复**。Kimi 的 done 我接受，但补一刀：`done` 态保留全部数据，提供 `⏵ 续会`（done→running）。反例：iterate 第 3 轮误触发 no-new-critique 停掉了，用户想再看一轮——如果 done 是终态，他只能重开会、丢上下文切片。这是成本最低的一条修正（加一个按钮 + 一条转移边）。

**attention 正交**的理由：掉线/工具失败若进主状态，running 会被"某席位掉线"打断——而 §4 里 chairman 依赖 API 席位，主席掉线确实致命，但那属于 **attention 升级**（掉线席位=主席 → attention 升级为阻断，开会更"卡"但不改 phase）。一个轴管生命周期，一个轴管告警，两条轴都不需要 N² 组合状态。

**失效场景（我方案被坑的时候）**：如果未来出现"开会中切换模式"的需求（比如 debate 进行到一半改 panel），四相装不下"切换中的 mode"——届时需要把 mode 也做成可热切的正交轴。本轮没有这个需求，不做。

## Q2 · 工具面板：全局右滑 tooldock，采纳但带修正

**结论**：支持全局右滑 tooldock 绑定 activeSeat。Kimi 的论证我认：50 席 micro 密度（卡高 56px）下卡内抽屉根本展不开；工具历史是纵向时间线；全局唯一 DOM O(1) 换绑 vs 卡内 O(N) 套抽屉 DOM。

**我的补充 + 一个关键修正**：

- **横向禁令的例外论证**：定案 2 禁止横向折叠（webview 宽度重排 3~8 倍）。但 tooldock 必须做成 **`position:fixed` overlay**（滑在网格上方，`width:420px` 左右滑入，网格一行 CSS 不变、webview 零重排）——它不是布局列，是浮层，所以与横向禁令不冲突。反例：做成 flex 第三列就是违反定案 2 的坑。
- **修正"绑定 activeSeat"的点**：面板定位不是"某席位的控制台"，而是**"已激活席位的工具事件时间线（只读为主）"**。工具 UI 只在壳层，网页 AI 发起调用是事件流，不是用户命令流——所以面板主体=时间线（REQUEST→APPROVAL→EXECUTING→RESULT 四阶段行，复用定案 19），底部一行才是交互位（⊘ 中止 / ✅ 批准待确认项）。卡内 24px 状态行（徽标计数）仍是入口，点卡=激活该席+切时间线，O(1)。
- **50 席 × 10 工具并发推演**：面板一次只显示 activeSeat 一席的时间线；顶摘要行放"全台 N 席 M 个工具在跑 / K 待确认 / J 失败"三计数；⚠ 待确认用 attention bar（定案 15）浮出，不进面板。50 席同跑时面板不会被刷屏——因为每席位事件进自己那屏时间线，面板是 1 个 DOM，事件按 seatId 路由进当前视图。
- **成本**：DOM 全局 1 套（时间线是事件追加，虚拟截断到最近 200 行/席）；状态 2 个（activeSeat、per-seat event buffer）；引擎零改动（事件本来就要广播）。
- **失效场景**：用户想在两个席位间快速对比工具输出——单面板装不下，得切两次。可接受，本轮不做双屏对比。

## Q3 · 外部 AI 回答落位：选 B，不选 A

**结论**：选 B（右滑抽屉，与 tooldock 同一 overlay 体系）。你的问题是"如果你每天用它咨询，你要 A 还是 B"——我作为那个用户，要 B。

**说服理由**：

1. **A 把"最重交互"和"最脆弱空间"绑死了。** 顶甲板是定案 14 折叠序里**倒数第二**被折的（header 之后），矮屏+开会中日志狂滚时甲板必被折。而外部回答录入恰恰是**开会中的高焦点时刻**（9 席回答陆续回来，用户要连续 9 次粘贴+校验+确认）。把录入表单放进"随时可能被自动折叠"的甲板，等于在用户手不停的时候空间先没了。
2. **编辑锁折叠是有用但脆的补丁。** 锁住甲板确实挡住自动折叠序了，但它挡住了**所有**自动折叠——包括密度降档（定案 14 第三步）对甲板的合理影响，而且锁是一个要额外管的状态（编辑中/锁/忘了解锁）。A 的"max-height 限高"也治不了底板：登录录入时若甲板被 logdock 展开挤压，限高意味着用户要滚着录入——粘贴 9 段长文本时滚动比抽屉里固定视口难受。
3. **B 与 Q2 共用一套 overlay 抽屉基础设施**（通义的原论证，我认它最硬）：两个面板=同一容器两套内容（工具事件流 / 回答录入表单），切换是 tab 或按来源自动切。成本上比"甲板表单+锁"省一套折叠逻辑。

**A 的失效场景（对方何时被坑）**：你说"尊重挪到上面原话"——但原话的上下文是第 1 轮"右栏折叠不腾空间"，用户抱怨的是**空间**不是**位置语义**。A 的失效时刻正是我第 1 点描述的：矮屏+logdock 展开+编辑中，锁+限高叠加，用户要滚着粘贴。B 的 overlay 不占布局，无此失效。
**B 的失效场景**：若未来"外部回答"要做成可常驻监控（像日志一样），抽屉要加"钉住"态。本轮不做。

> 对你倾向的处理：A 的"编辑锁+max-height"机制我原样保留为 v2（若 B 抽屉未来要常驻时的补丁），本轮直接 B。这是对"尊重原话"的偏离，但偏离依据是：原话诉求是空间合理性，B 的空间合理性比 A 好（不占布局列、不占纵向布局行）。

## Q4 · API 虚拟滚动：原生滚动+分组页签+密度档，分界线 150

**结论**：先不上虚拟化（同意你的倾向），可测判据给出：**席位 150 是虚拟化分界线；50~150 靠"分组页签+密度档"硬扛，不必虚拟**。

**判据（可实测，不是拍脑袋）**：

1. **DOM 节点预算**（Electron 渲染进程实测可复现）：API 轻 div 每席 ~12 DOM + 文本节点，150 席 ≈ 1800~2000 节点 + 折叠态 5 个分组容器 ≈ **<2500 节点，单次全量重排 <8ms**（Chromium 对 2500 个简单 div 的批量 reflow 在此量级；可在你环境用 `performance.measure` 包 `relayout()` 复测校准）。超过 300 节点/组开始能感知的卡顿线。
2. **重排频率是关键**：虚拟化真正省的不是"渲染 150 个 div"（本来就便宜），而是"每次高度/列数变化时 150 个节点都参与重排"。分组页签+密度档把**参与重排**的节点数砍到当前页签的量（50~60/组），150 席下每次重排 ~1000 节点以内 → 不需要虚拟化的"只渲染视口内"。
3. **webview 与 API 必须分开算**：9 个 webview 永不虚拟（定案 7），虚拟化判据只作用于 API div 区，所以"50 席总"里 webview 9 席不占判据额度。

**分界线怎么执行**：
- **≤150**：分组页签（按角色组/类型分，每签 ≤60 席）+ 密度档（loose/standard/micro，micro=56px 卡）+ 搜索=高亮（定案 23）——全原生，DOM 全保留（离屏保留思路，`visibility:hidden` 不 `display:none`，保住事件绑定与登录态相关分区）。
- **>150**：触发条件进 READY Gate 提示"席位超出软上限，建议分组"；引擎层预留 `renderVirtualized` 开关（本轮不实现）。理由：API div 轻，但 500 个 div + 工具事件缓冲 + 上下文广播域（定案 21）在 500 席时 O(N²) 先爆掉的是**上下文成本**而非渲染——虚拟化治不了上下文，所以 150 之后的真瓶颈是广播域拆分，不是滚动。

**失败场景（原生方案被坑）**：席位 >300 且用户要"全量可见"时原生+页签会开始掉帧（每签 100+ 密度 micro 时 ~1000 节点 × 频繁事件更新）——届时开虚拟化。150 的软上限保证用户到不了那个坑。

## Q5 · 人工模式：建模三 + 完整交互设计

### 建模选边：建模三

- **建模一（第 12 种 mode）错在哪**：它把"投递通道"偷换成"会议形态"。但 manual 不是形态——"主席点名+manual 投递"是合法的（手动把提问贴给主席 API 席位），"共同审阅+manual 回收"也合法（手动贴 9 份答案回来）。形态×通道是笛卡尔积，做成第 12 种 mode 就把 manual 钉死成"只能全 manual"，笛卡尔积塌缩成对角线。状态机最别扭：mode 状态机里"发言者=人"要插进所有模式分支。
- **建模二（纯通道）错在哪**：没有"人工咨询"这个用户的真实工作流入口。用户今天的心智就是"人工咨询"（贴稿→9 窗→收答案→汇总），纯通道只给了底层管道，没给他那个场景的**一键配置**（全 manual + 分发追踪面板 + 回收清单）。心智上他要多点 3 下完成他每天做的事，不如直接给快捷形态。
- **建模三（通道+快捷壳）**：通道 = 每席位 `delivery: 'auto'|'manual'` 一字段（席位级，不进 mode 枚举）；"人工咨询" = 一个壳（shell-only，不进 core/modes.js 引擎模式），作用 = 一键全 manual + 顶甲板切"分发追踪"控件组 + 默认广播稿模板。**代码复用最多**：manual 通道服务全部 11 种真实模式（Q6 会用到）+ 1 个快捷壳；快捷壳只是通道配置集，零引擎改动。状态机最不别扭：通道是席位属性，不是 phase，与 Q1 四相正交。

### 完整交互设计（线框图）

**面板落位**：Q3 选了 B（右滑抽屉），分发追踪放同一 overlay 抽屉的第三个 tab（工具 / 回答录入 / **分发追踪**）。理由：分发-回收是同一条事件流（R1 手动分发 → R2 回收勾选），与回答录入同域，一个抽屉内闭环；不新开面板。

```
overlay 右滑抽屉（420px，position:fixed，覆盖网格上方，不占布局列）
┌──────────────────────────────────────────────┐
│ [工具] [回答录入] [分发追踪 ◀active]          │
├──────────────────────────────────────────────┤
│ 咨询稿：#consult-042 "顶栏布局重构"           │
│ 附件(3)：第3轮咨询案.md · 第1轮.md · sketch.png│
│ 目标席位：9/9 已选  [✖清选]                  │
│                                              │
│ 分发进度  已发 3/9  ▓▓▓░░░░░░   08:42        │
│ ┌──────────────────────────────────────────┐ │
│ │ ● 通义  已发 08:41  [✓ 回答已收 08:47]   │ │
│ │ ● Kimi 已发 08:41  […等待] [复制再贴]     │ │
│ │ ○ 豆包 未发   [⧉复制到剪贴板] [📎文件选择] │ │
│ │ ○ 文心 未发   [⧉复制] [📎文件选择]         │ │
│ │ …（折叠 5 席）                           │ │
│ └──────────────────────────────────────────┘ │
│ 未答名单：Kimi 文心 元宝 (6)  [仅看未答]     │
│ 回收：3/9 已收  [全部粘贴回] [归档 round-1.md]│
└──────────────────────────────────────────────┘
```

**状态/字段**：
- 席位对象加 `delivery:'auto'|'manual'`（席位级，默认 auto；快捷壳批量置 manual）。
- 追踪表数据 `dispatchTrack = {consultId, seats:[{seatId, sentAt?, sentVia:'auto'|'manual', answeredAt?, answerRef?, files:['…'], status:'unsent'|'sent'|'answered'|'failed'}]}`——R1/R2 的进度、未发/未答名单、复制再贴全部读这一张表，单一真相源。
- 每席位行按钮：`⧉复制`=写咨询稿+附件引用到剪贴板（附件=文件路径行，用户手动附）；`📎文件选择`=预填文件选择器（R4，同一批文件，每席一次选择，选择结果写回 `files[]`）；手动标记已发/已答=勾一下写 `sentAt/answeredAt`（auto 席位由 CDP 事件回填，manual 由人回填）。
- R3：`status='answered'` 的回答回收进会议记录，落盘复用 round-N.md / 会议记录.md（文件名、编码、切片格式与 auto 流完全一致——**代码复用的核心**：落盘函数只认 `answerRef`，不认通道）。

**与会议引擎的关系**：manual 通道下引擎的轮次调度不跑（无自动轮次、无完成检测，人自己判断何时收齐）；但**会议记录 schema 与引擎共用**（定案 5 的"回答=表单"语义保持），所以后续若把某席切回 auto，上下文切片能直接接上。人工咨询壳开会前预检（READY Gate 增强）：manual 席位的"已发"数 < 目标席位 → 提示"3 席未发，确定继续？"（非阻断，auto 才阻断）。

**成本**：DOM = 抽屉第三 tab（~30 行 DOM）；状态 = 每席位 1 字段 + 1 张 dispatchTrack 表；引擎改动 = 0（落盘复用、Gate 读同一张表）。**反例**：50 席全 manual 时追踪表 50 行手动勾选，效率不如"仅看未答"+批量粘贴（已内置）；席位 >100 全 manual 时建议分组页签内勾选。

## Q6 · 真实工作流合理性总检

### 重做「模式 × 开会前/开会中」映射表（基于 §4 真表）

控件组命名沿用定案 13 的声明式（ControlRegistry when 谓词），`needs` 直接取自 §4 表：

| 模式 | 开会前配置组（phase=setup） | 开会中监控组（phase=running） |
|---|---|---|
| broadcast | 议题/稿件、目标席位、manual 通道开关（Q5） | 进度(单趟)、attention、⏸⏹ |
| review | **材料上传（硬门槛）**、席位、"独立审阅"提示词 | 三阶段进度、未读席位 |
| assist | 任务描述、席位、顾问角色组 | 方案/挑错/收敛三阶段进度 |
| iterate | **草稿（硬门槛）**、轮次上限(≤5)、终止判据说明 | 轮 N/M 进度条 + "新批评 k 条"实时计数（no-new-critique gate 可视化） |
| debate | 论点、席位、"对辩不看自己"提示 | 立论/对辩进度 |
| panel | 席位、分组(可选)、组长 | 依次发言进度、语境累积条 |
| chairman | **API 席位勾选（硬门槛）**、分歧点预设 | 轮 N/M、本轮点名者、no-new-question 计数 |
| divide | 任务拆分预览 | 拆分/攻克/汇总进度 |
| tournament | 候选产出要求、kind 契约说明 | 五阶段×轮进度、"定标均值"实时数值（非 AI 拍板提示） |
| build | 验证档位三档（仅语法/语法+引用/真跑 build） | 轮进度 + 当轮验证档结果（成功/失败） |
| transparent | 议题+资料、轮数 1-10、O(N²) 成本提示 | 轮 N/M、注入份数实时计数 |
| 人工咨询（壳） | 全 manual 一键 + 分发追踪面板 | 分发/回收双进度（Q5 线框） |

**硬门槛 UI 机制（定案 18 READY Gate 增强）**：`needs` 从模式定义自动推导——Gate 是 setup 页的**预检清单**，每项对应一个 `needs` 条目，✓/✗ 由数据绑定（材料已传 ✓/未传 ✗；草稿同理；chairman 检查选中席位中 API 席位数 ≥1）。**"开始"按钮在 ✗ 项存在时保持 disabled，hover 显示未满足项**——不满足开不了会是字面意义的：不是弹窗警告后还能点，是按钮物理不可点。成本：Gate 读 `mode.needs` 声明 + 一个数据绑定校验器（~50 行），引擎 0 改动。

### 产出契约（tournament kind）：日志要区分，卡片不区分

- **主日志行**：带 `kind` 徽标（`候选`/`评标`/`定标`/`修订`/`复评`，12px 小徽标，沿用定案 10 的徽标规格）——日志是审计线，必须可溯源"哪条是候选哪条是名次"。
- **席位卡/摘要行**：**不打** kind 徽标。理由：卡片要的是"该席位状态"，kind 是内容分类不是席位状态；卡片打 5 种 kind 徽标=视觉噪音，且与定案 10"徽标只溯源不暗示能力"冲突。
- **引擎兜底**：tournament 出标阶段若产出物未打 kind，引擎按"candidate"默认 + attention 告警一条（不阻断）——因为"切片把评标当候选发出去"是 §4 表里的硬约束，UI 层兜不住引擎层漏打，必须引擎默认值+告警双保险。

### loop 型轮次语义统一：进度条读 `progress{loop, round, limit, gateLabel}`

四相状态机（Q1）下轮是数据，进度条统一渲染：`第 N/M 轮 · {gateLabel}`。gateLabel 按模式取：iterate=`新批评 0 即停`、chairman=`新问题 0 即停`、tournament=`同 winner 连续 2 轮即停`、build=`buildPass 即停`、transparent=`固定 {limit} 轮`。**"第 N/M 轮"在 limit=动态（no-new-question）时渲染为"第 N 轮 · 上限 4 · 或更早终止"**——不误导的关键：limit 是上限不是承诺，文案必须写"上限"。统一的是进度条控件，不统一的是每模式的 gate 判据（判据归引擎，UI 只读渲染）。

### 工作流漏洞（至少 3 条，我挑 4 条）

1. **chairman 主席掉线=会议硬停，无降级路径。** 主席必须走真实 API（ADR-001），该 API 掉线后整个 chairman 模式停摆。修复建议：`needs` 从"≥1 API 席"升级"**≥2 个独立 API 席（主席+候补）**"，Chairman Gate 双席位校验；主席席位 attention=掉线时自动切候补 + attention bar 升级阻断。成本：Gate 校验器 +1 条，引擎加候补切换（已有"开会中停用/激活"定案 17，复用）。
2. **review 防锚定失效场景未覆盖**：独立审阅阶段"只看材料"是防锚定关键，但 UI 无"该席位尚未开始独立审阅就进入交叉质证"的检测——若某席位独立审阅未收口（手动模式或工具失败），交叉质证阶段该席位会带着未完成状态看他人意见，锚定防护直接穿。修复：交叉质证 gate 加前置"独立审阅已收口 k/N 席"检查，未收口席位本轮质证跳过（标 `skipped`）。成本：gate 一条 + 席位卡 skipped 徽标。
3. **build 第三档"真跑构建"在共享环境无隔离声明。** 构建会真跑 `npm run build`——并发多 loop 轮时若构建脚本写盘共享依赖（node_modules），轮间产物互相污染，"可信判定"失真。修复：验证档位下拉旁固定提示"第三档将执行构建脚本（共享 node_modules），建议独立工作区"；引擎层预留 workspace 隔离参数（本轮只 UI 提示，不动引擎）。
4. **iterate 的终止判据"文本规范化后比对"对用户是黑箱。** 永不停机风险（§4 表注）+ 规范化算法不透明=用户不知为何停/不停。修复：进度条旁加"终止判据：连续 N 轮修订文本相似度 ≥X 即停（可查）"，悬停展开判据说明；UI 只读展示，引擎不动。
