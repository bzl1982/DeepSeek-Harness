一、先挑不合理（这是你点名要的"现在不合理的可以提出来"）
§处   不合理之处   为什么是坑   处置
P1   §3.1 / §2.2   把"50 席"当成纯网格布局问题   真实矛盾不是"格子排不下"，而是 O(N²) 上下文：50 席一轮 2500 份注入，Harness 壳的 token/时延直接崩。先解耦广播拓扑，再谈网格   新增工作流 WF-2「上下文广播域」，网格按域渲染

P2   §2.6 vs §3.1   "webview 永不卸载" 与 "席位无上限" 直接打架   红线要求 9 个 webview 不能卸载重建；但席位不设上限、还要滚动/虚拟滚动——虚拟滚动的本质就是"进视口挂载、出视口卸载"，对 web 席位是违红线的   新增工作流 WF-3「webview 席位池 + 换席」：web 席位是稀缺常驻池，只有 API 席位可虚拟滚动

P3   §2.3（共识）   外部 AI 回答表单塞进"顶甲板折叠区"   表单需要持续的输入焦点 + 键盘；顶甲板的设计目标是"不用时收 0 腾空间"。一个要常驻输入的表单和一个"随时要收起"的容器是语义对立——用户一边打字，模式/阶段一变，甲板 renderDeck 重排就可能让输入框失焦或丢失草稿   Q5 正式推翻，改右侧 overlay 抽屉（通义派），但给出比 7 家更强的理由（见 Q5）

P4   §3.2   "结果自动带给下一轮"当作默认   网页 AI 一次可能调 5 个工具，50 席并发 → 下一轮注入被工具输出刷屏，等于把 P1 的 O(N²) 从"席位互看"换成"工具输出灌满"。默认必须是人工确认闸，自动是给可信白名单工具的例外   工具回注默认走确认闸（见 Q3、WF-4）

P5   §3.3 + §2.5   Q4 用一张"模式×阶段映射表"扛 8 模式   8 模式 × 2 phase × (配置组+控件组)，加席位数、加工具就是改表，正是第 1 轮 G4"零散 if"的升级版   改声明式控件注册表（manifest），控件自带可见性谓词，模式只声明引用哪些控件（见 Q4）

P6   §3.2   工具权限按"席位"配置   席位 50+ 时逐席配白名单不可维护   权限按角色组 × 工具风险级两级授权，席位继承角色组（见 Q3）

二、工作流总设计（4 条状态机，UI 只是它们的投影）

先把工作流定死，Q1–Q5 的每个 UI 决策都挂到某条状态机上，避免"为布局而布局"。

WF-1 会议生命周期（决定 data-phase，是所有控件显隐的根）
idle ──配置──▶ configuring ──开始会议──▶ running ──暂停──▶ paused
  ▲                │                        │▲              │
  └──停止──────────┴──────停止───────────────┘└──恢复────────┘

data-phase 取值扩为 idle | configuring | running | paused（§2.5 只有 pre/run 两态，不够：辩论/质证的"暂停插话"、会诊的"暂停补材料"都要一个独立 paused 态，否则暂停被塞进 run，控件语义混淆）。
UI 投影：configuring 才展开 .topdeck 配置组；running/paused 甲板收成 deck-summary（一行），把纵向还给网格；idle 隐藏所有 run 控件。

WF-2 上下文广播域（解 P1，O(N²)→O(N)）
topic-domain（话题域）= { seats[], injectPolicy, window }
seat 只能看到 自己所在域 + 被 @ 定向 的历史注入

一个 topic-domain 就是一个"频道"，默认整会 1 个域（等价现状全广播，向后兼容）；分组会诊/辩论正方反方/质证质方答方 = 各自独立域。
域大小是软上限告警线（如 >12 席提示"建议拆域"），把 50 席拆成若干 ≤12 席的域并行跑，上下文从 2500/轮 降到 Σ(域k²)。
UI 投影：网格顶部一条 .domain-rail 域标签页（Q2），每格右上角一个域色点。

WF-3 webview 席位池换出（解 P2，守红线）
webviewPool = 9 个物理 <webview>（常驻，永不卸载）
webSeat: 需要上屏的 web 席位 → 借一个 pool 槽渲染
当第 10 个 web 席位要上屏 → 触发"换席"：
   选一个可回收的 web 席位 → 快照其状态 → 归还 pool 槽 → 新席位借槽

关键取舍：web 席位 ≠ 无限。设计上明确告诉用户"网页席位上限 = 硬件池大小(9)，超出需换席或降级为 API 席位"。这是诚实边界，不是实现缺陷。
换席不是卸载：被换出的 web 席位的登录态由网页自身服务端保持（换回来重新加载即恢复），pool 槽的 <webview> DOM 自始至终没被销毁——只是 src/可见性切换。这守住 §2.6"不销毁 webview DOM"。
UI 投影：web 席位卡右上一个 pool● 指示灯（占池=亮，待换席=橙）；网格对 API 席位用虚拟滚动（轻 div 可随意 mount/unmount），对 web 席位用固定池 + 换席确认，两套虚拟化策略。

WF-4 工具调用生命周期（解 P4）
[席位AI输出工具意图] → parse → gate(白名单&风险级)
   gate拒绝 → 席位卡红标"越权"，不回注
   gate通过 → execute(壳层Harness) → result
        风险级=low 且 auto=true → 自动回注
        否则 → pending 进"回注确认队列" → 用户批准/丢弃 → 回注下一轮

并发聚合：工具事件先进一条全局 .toolevent-bus，按席位分桶，席位卡只显示"● 工具·内部工具 ✓"一行徽标，点开才看参数/结果——防刷屏（见 Q3）。

3.2 折叠优先级规则（屏幕矮时谁先被折）——这是本方案的新增核心

定义折叠优先级序（数字越小越先牺牲）：
collapse-order = [ logdock, topdeck, domain-rail, header ]

屏高阈值（可用 --disable-gpu 下 CDP 读 innerHeight，或监听 resize）：
  h < 900 → 自动收 .logdock（复用豆包"高度阈值自动折叠"，扩展成按序）
  h < 760 → 再自动收 .topdeck（进 deck-summary）
  h < 640 → 网格切 density:compact（Q2 密度档），而不是继续收 header
  .header 永不折叠（它是模式/域/工具授权的全局入口，收了就找不到北）。
为什么是这个序：日志是"可事后回看"（牺牲代价最低）→ 甲板配置在 running 期本就不需要（WF-1）→ 域标签是导航骨架（较难牺牲）→ header 是根。
为什么纵向优先（采纳文心）：9 个 webview 高度变化开销远小于宽度变化，所以"收顶/底"比"收左右"对 webview 友好——这决定了所有折叠都往纵向走。

3.3 区域尺寸 / 状态键（字段级）
.topdeck：data-state="expanded|collapsed"；展开 flex:0 0 auto，收起固定 flex:0 0 36px；收起态不销毁子 DOM（height:0+overflow:hidden），子块 display:none 兜底防负高（通义坑清单）。
.logdock：flex:0 0 32% ↔ flex:0 0 28px；内部滚动条用豆包"手动上滚暂停跟随、回底恢复"。
.grid：flex:1，永不 display:none；.cell 最小高由 density 档决定（Q2）。
成本：新增 2 个状态属性 + 1 个 resize 监听（debounce 120ms，只读阈值、不触发网格 reflow，只切 class）。对 400 测试：只要不断言 .topdeck 的 height 具体值、只断言节点存在，全绿。
反例：不要把 collapse-order 做成"用户手动折叠也走同一自动逻辑"——手动折叠要写 data-user-collapsed 覆盖自动序，否则用户刚展开日志、窗口 resize 又被自动收起，很烦。自动序只在 !data-user-collapsed 时生效。

四、Q2 · 席位规模化（50+，无上限）

核心：两套席位两种虚拟化（利用 web/API 不对称，P2）。
维度   API 席位（轻 div，无限）   web 席位（重，池=9）
虚拟化   虚拟滚动（进视口渲染 div，出视口回收，随便滚）   固定池 + 换席（不能虚拟滚动，见 WF-3）

数量   无上限   硬上限 9，超出提示降级为 API

网格组织方案（推荐组合，非单选）：
域页签（主，来自 WF-2）：.domain-rail 把 50 席切成多个 ≤12 席的域，一屏一个域 → 一屏最多 12 格，网格本身几乎不用滚动。这是最省 webview、最省上下文的正解，优先用它压规模。
域内虚拟滚动（辅，只对 API 格）：某域 API 席位 >20 时，.grid 用 IntersectionObserver 回收 API 格；web 格不参与 observer（常驻）。成本：一个 IO 实例 + API 格占位高度数组；反例：对 web 格用 IO 会触发换席抖动，禁止。
密度档位（.grid[data-density]）：comfort（12 格/屏，卡片含工具徽标）→ compact（24 格/屏，只显示名牌+池灯+工具点，hover 出详情）→ list（表格行，适合纯 API 批跑，web 席位禁用 list——看不到网页本体没意义）。屏高触发自动降档（§3.2）。
搜索定位席位：.header 加 ⌘K 席位搜索，输入命中自动切到该席所在域并 scrollIntoView + 高亮。成本：一个 flat 索引数组，几乎零重排。

「每排 N 个」下拉升级：从固定 3/4/5/6 改为 auto（默认）+ 手动覆盖。
auto：cols = clamp(2, floor((gridWidth - gap) / minCellWidth), 8)，minCellWidth 随 density 变（comfort 280px / compact 160px）。删掉 §现状里"relayout 最多算到 4 列"的硬分支。
反例：auto 下 web 格若被压到 <240px 宽，网页不可读 → 对含 web 席位的域强制 cols ≤ 4（data-has-web="true" 时封顶 4 列）。

角色组去固定席位化（解 §现状 ${s.seats} 席）：
角色改为配额而非定数：role.quota = {min, max} 或 'auto'。14 角 6 组不再写死席位数。
分配算法 assignRoles(seats, roleGroups)：
  先按 min 占位；2. 剩余席位按组权重轮转填到 max；3. 超编 → 触发组长选择（见下）+ 溢出席位进该组"候选席"（有历史注入权但默认不主动发言）。
组长怎么选：chair 位（用户指定）→ 否则组内 role.weight 最高 → 并列则组内投票一轮（复用现有广播通道做一次 mini 投票）。UI：角色组配置块给"组长：自动 / 指定席位"单选。
成本：assignRoles 是纯函数（可单测，400 用例友好）；反例：不要在 running 中途改角色组配额触发全量重分配（会打断接龙/辩论轮次）→ 角色编辑在 configuring/paused 才允许，running 下只读并提示"暂停后可调整"。

┌ .cell .seat ────────────────┐
│ [名牌 A公司·GPT]     ●池  🔧3 │ ← 顶栏：名牌 + 池灯(web) + 工具徽标

标识拉平：不再用 -API 后缀。改为能力等价、来源角标：两栏都用 [名字 · 模型]，来源差异降级为一个极小角标 ⌗API / ◉web（且只在 compact 密度隐藏）。理由：§3.2 目标是"能力与 UI 无区别"，把 API 写进名牌是反向暗示能力不同。web 席位多一个 ●池 灯是资源信息不是能力差异，保留。
工具面板放哪（推荐：⧉弹出窗 + 全局工具台 双层，席位卡内只留徽标）：
  席位卡内不放完整工具面板——12 格里塞面板会把 webview 挤没（反例，且踩"网格里做悬浮窗"高成本坑，Gemini 已证）。
  席位卡底栏 🔧n 徽标 → 点开 ⧉弹出窗的"工具"页签（席位级：该席近 N 次调用、参数、结果、"重新回注"按钮）。
  全局 .toolbench（右侧 overlay 抽屉，复用 Q5 的抽屉机制）：跨席位工具事件流 + 按席位分桶 + 权限快捷入口。开会中多席并发看这里，不被单格刷屏（解 §3.2 最后一条）。
工具调用呈现：徽标态 ⏳调用中 / ✓成功 / ✗失败；⧉工具页里列 工具名 · 参数摘要 · 结果预览(可展开)。
结果回注（解 P4）：默认 pending → 确认队列（.toolbench 顶部一条"待回注 3"红点）；仅"低风险只读工具 + 用户显式开自动"才 auto-reinject。反例：shell/write_file 等写类工具永不默认自动回注（错误结果会污染下一轮所有席位上下文）。
权限控制（解 P6）：授权 UI 放 .header ⚙ 工具授权 面板，两级：
  工具按风险级分 3 档（read/search 低 / write/exec 中 / net/shell 高）；
  按角色组 × 风险级给开关矩阵（不是逐席配），席位继承角色组。默认：只读组全开、执行组开低+中、高危险全局默认关需逐组开。
  WF-4 的 gate 直接查这张矩阵（permCache[roleGroup][tier]），200+ 工具用 tool.tier 归类，不必逐工具配。
成本：1 个 overlay 抽屉 + 1 个事件分桶 Map + 权限矩阵一张表；工具徽标更新走单格局部 DOM，不重渲染 .grid。400 测试：工具 UI 全新节点，不碰既有断言节点。
反例：工具输出绝不注入 webview 内部 DOM（§3.2 明确只能壳层做）——回注走 insertText 到网页输入框，与 API 席位注入文本流同一通道，保证"无区别"。

六、Q4 · 模式 × 阶段 控件组（解 P5：用注册表，不用大映射表）

不写 MODE_PHASE_CONTROLS = {...} 大表（会失控），改声明式注册表：
// 控件自注册：每个控件声明"我在哪些(mode,phase)可见"
ControlRegistry.register({
  id:'roleGroupCfg', el:'#roleGroup',
  when:(mode,phase)=> phase==='configuring'          // 所有模式配置期都有
})
ControlRegistry.register({
  id:'debateSideCfg', el:'#debateSide',
  when:(mode,phase)=> mode==='debate' && phase==='configuring'
})

模式侧只声明引用哪些控件 id + 默认值，renderDeck(mode,phase) 遍历 registry 按 when() 切 hidden（固定 DOM + hidden，守 §2.5"不重渲染"）。
随模式增长不失控：加新模式 = 加一条 manifest（引用现有控件 + 至多补几个专属控件）；加新控件 = 一处 register，不碰任何模式。二者正交，复杂度从 O(模式×阶段×控件) 降到 O(模式)+O(控件)。这正是替代 §2.5"零散 if"的落点。

8 模式 × 4 phase 完整映射（配置期=configuring，运行=running，暂停=paused 附注）
模式   configuring（配置组）   running（监控/控件组）   paused 额外
transparent 透明广播   角色组·每排·密度·工具授权·发言顺序   日志·广播·发文件·暂停⏸·停止⏹   暂停补材料

通用常驻（所有模式 running）：日志、发文件、暂停⏸、停止⏹；idle 隐藏 ⏸⏹（display:none，非灰显——本轮定 §2.4 分歧：选 display:none，因为 400 测试常断"运行态控件在空闲不存在"，灰显反而要额外断 disabled，none 更干净；若你们有"按钮位置不能跳动"的强需求再退回 opacity 灰显）。
成本：registry 是一张 Map<id, {el, when}>，renderDeck 一次遍历 Map.forEach(el.hidden=!when())，无重建。
反例：when() 里不要读写 DOM 做判断（只读 mode/phase 两个入参），否则 renderDeck 变成隐式 reflow 源。

七、Q5 · 推翻表态（对 §2 共识基线）

明确推翻 1 条：§2.3 中"外部 AI 回答 = 顶甲板内折叠表单"。

比 7 家共识更强的理由（不是"抽屉不遮网格"这种通义已给的理由，而是工作流层的硬冲突）：
焦点生命周期冲突：外部回答是"要持续打字"的表单，顶甲板受 WF-1（phase 变）、WF-2（切域）、§3.2（resize 自动折叠）三重自动重排驱动。用户打字中途任一事件触发 renderDeck/自动折叠 → 输入框失焦或草稿丢失。顶甲板的契约是"随时可被收 0"，而表单的契约是"我输入期间你别动我"，二者互斥。
与工具台同构更省实现：Q3 已经要为工具做一个右侧 overlay .toolbench 抽屉；外部回答复用同一套 overlay 抽屉机制（.ext-drawer），一个组件两处用，比"甲板表单 + 独立抽屉"两套输入容器更省 DOM、状态更统一。
webview z-index 坑可控（DeepSeek 警告）：overlay 抽屉盖在 .main 上会压到 webview 原生层——但外部回答/工具台打开时用户本就不在看网格，可接受；且规避方案现成：抽屉打开瞬间对 .main 加 visibility:hidden（不是 display:none，webview 不卸载，只是不绘制），关抽屉复原。这个规避成本 3 行 CSS，远小于"甲板表单丢焦点"的返工成本。

其余 §2 骨架（1/2/4/5/6/7/8）全部保留，其中 §2.3 的另一半"会议日志=底部停靠"保留（日志是只读持续滚动，无焦点需求，放底部没问题，只有"表单"这半被推翻）。
