## Q1 phase 状态机：支持四相 + attention 正交，但"轮"必须拆成 cycle/stage 双层（否则装不下 §4 真表）

**结论**：`setup / running ⇄ paused / done` 四相 + attention 正交（§3-A 推荐成立），但我补一条 §3-A 没说的：**四相只描述"会议生命"，不描述"会议进度"；进度走正交的 cycle/stage 键**。这是 tournament/build 逼出来的。

**11 模式逐个检验**：

| 模式 | 四相检验 | 结论 |
|---|---|---|
| broadcast / assist / debate / divide / panel | setup→running→done 直线走通，⏸=已暂停派发 | ✅ 直接装下 |
| review | 三阶段是**running 内部的 stage**（审阅→质证→归并），不是 phase——若提升为 phase，paused/done 语义要在每个 stage 重定义，状态机爆炸 | ✅ stage 层解决 |
| iterate | running 内 cycle 1~5；done 由 no-new-critique 触发。paused 有效（修订到一半喊停） | ✅ cycle 层解决 |
| chairman | **最刁钻**：主席是人，running 期间引擎实质在等人类输入。这不算新状态——running 的定义应是"**引擎等待下一轮的输入源**"，输入源是 AI 完成检测还是人点"点名"，对状态机无差别 | ✅ 装下，但要接受"running≠机器在忙" |
| tournament | 出标/评标/定标/改进/复评是 cycle k 内部的 stage 序列；same-winner 决定 cycle 是否+1。若按 phase 建，11 模式×各自子阶段，五相六相都打不住 | ✅ 必须 cycle/stage 双层 |
| build | 同 tournament：编译失败→改进→再编译是 cycle 内循环 | ✅ |
| transparent | 固定轮数，cycle 1~10 上限已知，进度条第一次有了准确感 | ✅ |

**字段级**：

```html
<body data-mode="tournament" data-phase="running" data-cycle="2" data-cycle-max="3" data-stage="评标">
```

```css
/* progress 显示由 cycle/stage 驱动，不进状态机 */
.statusbar::before { content: "第" attr(data-cycle) "/" attr(data-cycle-max) "轮 · " attr(data-stage); }
```

**成本**：0 个新状态变量，2 个 data 属性 + 1 条 CSS。**反例**：四相什么时候会坑人？——未来若要加"关窗口明天接着跑"（build 的 npm 跑 10 分钟），有人会想加 `suspended` 相。别加：那是 session 序列化问题，是正交轴，硬塞进 phase 会让"续会"在 setup/running/done 三处都要特判。**失效场景**：如果哪个模式要求"暂停后从第 k 轮精确重放"（ tournament 复评了一半暂停），四相+checkpoint 文件解决，依然不需要新相。

## Q2 工具面板：维持全局右滑 tooldock，补「双页签 + attention 兜底」

支持 §3-B 推荐（也是我第 2 轮方案），本轮补强三个第 2 轮没说的点，然后做你要求的极限推演。

**补强**：
1. tooldock 内分两个页签：`调用历史 | 白名单`——配置和监控的生命周期不同（配置在 setup，监控在 running），混在一个时间线里会互相挤。

**极限推演：50 席、10 个工具并发在跑**：

```
概览层(永远可见):  seatbar 右侧 [🔧10 ⏳4 ✅5 ⛔1]   attention bar: ⚠ 3项待确认
                  logdock 标题行同步计数(折叠≠失联,已定案4)
```

三层各自独立，10 并发不会把任何一层淹没——因为**信号层只有数字，详情层只绑一个席位，审批层只走 attention bar**。

- **卡内抽屉**：micro 密度 56px 高卡片，抽屉展开必然遮挡邻居（grid 是共享的，抽屉不是浮层就是占位——占位触发整网格重排，违反纵向折叠禁令已定案 2）；且 50 套抽屉 DOM = 50 份事件监听，换绑问题变成"没有绑"的问题。

**成本**：tooldock 1 套 DOM（~120 行）+ attention bar（~30 行）；反例：若未来工具调用要**跨席位对比**（"GLM 和 Qwen 都查了同一份文件，结果不同"），单席位绑定的时间线不够用——留 v2 页签"跨席对比"的扩展位，现在不做。

## Q3 外部 AI 回答：我翻转立场，选 B（右滑抽屉，与 tooldock 共容器分 tab）

第 2 轮我支持 A（顶甲板），本轮被通义的「表单焦点契约」论证说服。把理由说透：

**用户原话"挪到上面"的真实动机是消灭 380px 占宽，不是崇拜顶部**。B 方案抽屉不占布局宽，同样满足动机；A 方案在"编辑时锁折叠"的瞬间，恰恰违背了用户的核心诉求——**他为腾空间而来，结果填个表单空间被锁死**。生命周期论证：extbox 是长驻操作面（填一条回答要对照日志、翻材料，可能开 10 分钟），topdeck 是瞬态容器（看一眼就折）——把长驻面放进瞬态容器，每次折叠都要做"锁 or 丢"的选择题，这就是 A 的结构性矛盾。

**共容器分 tab**：

```
右滑抽屉(唯一,与tooldock同容器):
┌───────────────┐
│ [外部回答|工具] │ ← tab: 全局视图 vs 席位绑定视图
│ 外部AI回答      │
│ [多行表单………]  │ ← 回收主功能:粘贴→剥标注→参与切片
│ 席位归属[#3▾]  │
│ [加入会议记录]  │
└───────────────┘
```

**A 方案何时出事**：deck 被快捷键误折（或窗口高度阈值自动折叠，豆包第 1 轮硬货触发）→ 表单要么丢上下文要么锁死空间；且 extbox 在顶、logdock 在底，填回答对照日志=视线纵穿整个屏幕，右抽屉与 logdock 零冲突。

**B 方案何时出事**：开会中同时需要"看工具执行结果 + 填外部回答"——两 tab 互斥。缓解：回收外部回答的高发时段是**会后**（done 阶段），工具调用高发时段是 running，时间正交，撞车概率低；真要并发，logdock 展开时占底、抽屉占右，共存不打架。**兜底**：如果你坚持 A 先跑，最低配必须加"折叠时表单暂存、展开恢复 + 编辑锁期间禁用自动折叠触发"两条，否则就是给用户埋丢稿雷。

**成本**：extbox 从 deckrow 搬到抽屉 = 搬 DOM 不搬逻辑（剥标注/切片逻辑不动）；A 方案的两条兜底规则反而比搬家成本高。**对 §2 定案 5 的态度**：定案 5 特意标注"落位在 Q3 裁决"，本轮裁决为 B，不推翻定案本身。

## Q4 API 虚拟滚动：选「原生滚动 + 页签 display:none」，分界线给可测判据不给拍脑袋

选边：支持 §3-D 倾向（先不虚拟化），并吸收 Gemini 和 DeepSeek 各一半：

- **Gemini 对**：50 个轻 div 确实无压力，虚拟化是过早优化；
- **DeepSeek 的"离屏保留"免费实现**：分组页签切换 = 非当前组 API 席位 `display:none`——API div 无 webview 红线，display:none 只是不参与渲染，**DOM 状态（文本区内容、输入）天然保留**。这就是离屏保留，零代码。

**数量分界线：120 席**，判据三条（全部 CDP 可测）：

| 判据 | 阈值 | 测量方式 |
|---|---|---|
| 滚动流畅度 | 滚动一屏 fps < 45 | CDP `Runtime.evaluate` 包 rAF 计数 |
| 密度/列数切换重排 | 单次重排 > 100ms | Performance API measure layout |
| 搜索 scrollIntoView 延迟 | > 300ms | 高亮定位耗时 |

120 席 ÷ 8 列 = 15 行 × 56px = 840px，与视口同量级——此时可视区外只有 ~7 行，虚拟化省掉的渲染量≈一半，**收益接近零而实现成本固定**（scroll 接管 + 与 dragCellHeight、scrollIntoView 高亮、页签 display:none 三套机制打架）。超过 120 席后成本线性涨，才轮到虚拟化上场。

**依据不是内存**：200 席 × ~50KB DOM+JS 对象 ≈ 10MB，Electron 不在乎。**真正的成本是重排频率 × 节点数**——auto 列数已有 300ms 防抖（上轮定的），频率已被压死，剩下只有滚动合成，而轻 div 滚动走合成器，天然流畅。

**反例**：如果用户把 50 席全塞一个"未分组"页签且从不用分组——滚动行数 = 总席位数，分界线直接失效；所以页签不是可选项，是性能策略的一部分（强制默认按角色包分组）。**失效场景**：虚拟化上太早会把 `dragCellHeight`（cell 底边拖拽）变成噩梦——虚拟列表里被回收的行拖不到，这是"先不虚拟化"最实际的理由。

## Q5 人工模式：选建模三，但精确表述为「delivery 轴 + 工作台，不占 mode 位」

**建模一否决理由**：11 个引擎模式共享一个假设——发言者完成检测 + 终止判据 + 轮次推进。人工模式 R3 明说"不跑自动轮次、不依赖完成检测"，塞进 mode 注册表意味着引擎 1359 行里每个 loop/判据/READY Gate 都要为"发言者=人"开后门。mode 表是"会议怎么推进"的注册表，人工咨询根本不推进会议。

**建模二（纯横切）否决理由**：干净但不够用。用户今天的真实用法**连会都不开**——没有模式、没有轮次，就是"分发 9 份 → 收回 9 份"。纯横切下他得选 broadcast 模式、全席 manual、点"开始会议"、忍受 READY Gate 和轮次仪式——为一次手动咨询伪造一场会，心智成本荒谬。

**建模三（选定）**：三条正交轴，各归各位——

```
mode 轴(11模式):     会议怎么推进(自动引擎)        ← modes.js,不动
delivery 轴(每席位): 材料怎么到达席位(auto/manual) ← seat.delivery='auto'|'manual',广播循环跳过 manual 席
工作台:              全 manual + 不开会的退化体验   ← 不进状态机,不占 mode 位
```

**关键设计**：头部模式下拉多一项「✋ 人工咨询」；选中后 `data-mode="consult"`，**phase 键整个不参与**（没有开会，没有 setup/running），topdeck 换成工作台视图，grid/logdock/席位卡照常复用。

**线框（分发 + 追踪一体，R1/R2/R4）**：

```
┌ topdeck · consult 视图 ────────────────────────────────────────────┐
│ 咨询稿 [┌─────────────────────────┐]        已发 6/9 · 已答 4/9     │
│        [│多行文本域………            │]  附件 [📎需求.docx][📎图.png][+] │
│        [└─────────────────────────┘]                               │
├────────────────────────────────────────────────────────────────────┤
│ 席位投递清单                          [全选] [自动分发▾] [逐席复制] │
│ [✓] #1 Kimi-K2    ●已发 ✓已答  [复制回答]                          │
│ [✓] #2 GPT-4o     ●已发 ⏳未答  [复制回答]  ← 回收后自动✓,可手动改  │
│ [✓] #3 Claude     ⚠自动失败 → [复制][传文件][标记已发]  ← R1 兜底   │
│ [ ] #7 API-GLM    ○未发                                            │
│                                              [归档: round-1.md ▾]  │
└────────────────────────────────────────────────────────────────────┘
席位卡片同步角标:  cell-foot 加 [✓发][✓答] 两个 14px 徽标,与工具角标同排
logdock:           回收的回答以"席位名+时间"进会议记录,复用剥标注管线
```

**四个 R 的落点**：
- R1 分发：双通道。自动通道走现有广播管线（修复 `webUtils.getPathForFile` + 上传 ok 检查，这俩是真机失败源）；失败席位逐行降级为手动三键。**进度 = 清单行内状态，不做全局进度条**——9 行清单本身比进度条信息量大。
- R2 回收：主手动（粘贴进抽屉 tab「外部回答」，§Q3 的 B 方案在此兑现价值——工作台和 extbox 是同一个组件！）；CDP 自动检测标"实验"（网页 DOM 变化启发式，不可靠就明说不可靠）。未答名单 = 清单里 ⏳/○ 的行，一眼可得。
- R3：落盘复用——一次咨询 = `round-1.md`（咨询稿 + 9 份回答 + 时间戳），[归档] 生成会议记录.md。不碰轮次引擎。
- R4 文件：自动 = CDP `setFileInputFiles` + 逐席回报 ✅/⚠（**必须修上传 ok 检测，静默失败是原罪**）；手动 = 每席文件选择器记忆上次的目录，预填同一批文件。

**成本**：`seat.delivery` 是纯数据字段（引擎广播循环加一个 skip）；工作台 UI ≈ 90 行 DOM；回收管线与 extbox 共用（Q3 选 B 的复利——若 Q3 选了 A，工作台和 extbox 就是两套表单，这里每天付一次重复成本）。**反例**：如果广播/发文件修好且稳定三个月，工作台会没人开——但 delivery 轴和单席 manual 降级永远有价值（某网页 AI 掉线时单席切手动），所以**轴必做，工作台可砍**；砍掉工作台只损失"不开会的体验"，横切能力不损失。

**与会议引擎的关系一句话**：引擎管"轮次怎么转"，delivery 管"话怎么到"，工作台是"连轮次都不需要"时的壳——三层从不互相调用，只共享分发/回收/落盘三条管线。

| ✋ consult(工作台) | —（无 phase） | 分发清单 · 已发/已答追踪 | round-1.md 归档 |

**工作流漏洞与修复**：

- **V1 · iterate 终止判据是黑盒**：no-new-critique 靠文本规范化后比对，用户看不到"为什么停/为什么没停"，标点差异导致永不停机时只能干瞪眼。修复：running 面板加终止仪表——显示"上轮批评指纹 / 本轮指纹 / 距离值"，判据从黑盒变仪表盘。**成本**：引擎把内部比对值暴露出来，UI 两行。
- **V2 · chairman 的终止权归属模糊**：no-new-question 若由引擎判定，主席（人）被架空；若全靠人按 ⏹，判据名存实亡。**这是真表里最深的漏洞**。修复：终止判据降级为"建议"——引擎检测到连续 2 轮无新问题，在点名台显示"建议结束"徽章，**⏹ 的最终触发权只在主持人手里**。UI 加 1 个建议徽章，引擎判据输出从命令改建议。
- **V3 · tournament 的 kind 契约无 UI 表达**：产出物不打 kind，切片把评标当候选发出去——更糟的是用户**在 UI 上完全无法分辨**一条消息是候选还是名次。修复：① 卡片消息按 kind 着色角标（candidate=蓝 / ballot=紫 / verdict=金 / revision=灰 / review=绿），一眼可辨；② 引擎侧 kind 校验失败=**硬停止**而非静默继续——契约破坏必须是显式失败。
- **V4 · review 防锚定与外部投递互相污染**：第一阶段"只看材料"是硬约束，但 extbox/工作台可在此时往席位塞别人的观点，防锚定形同虚设。修复：review 第一阶段，对该席位的外部投递内容打"⚠ 锚定污染风险"警示条（不禁止——紧急补充材料是合理需求，但禁止=防死 legitimate 用例），且该内容**默认不进第一阶段的上下文切片**。
- **V5 · transparent 无提前收尾路径**：固定 1-10 轮，第 3 轮已收敛也只能 ⏹ 硬停。修复：⏹ 二级菜单（已定案 16）加"提前收尾：用当前各轮发言汇编摘要"，落盘格式与跑满轮数一致。
- **V6 · build 第三档是模式级代码执行，但权限模型只认工具调用**："真跑 npm run build" 走的不是工具白名单通道，是模式自身行为——意味着工具权限矩阵对 build 模式最大的危险敞口完全无效。修复：① 选第三档时弹确认"将真实执行 AI 生成的代码"，记下确认时间戳；② READY Gate 检查产物目录是独立工作区（非用户主目录）；③ build 运行期间 attention bar 常显"正在执行生成代码"。

**映射表维护**：依旧 ControlRegistry/when 谓词（已定案 13），新增模式=1 行配置；但 V1~V6 说明**有些模式需要的不只是控件显隐，而是专属仪表**——注册表条目加 `instrument` 字段（如 `terminate-gauge`/`borda-table`），仪表组件自注册，映射表不膨胀。
