Q1 · Q3 续辩（外部 AI 回答落位 A vs B）

我上轮立场：B 派（右滑抽屉，与工具台共用同一 overlay 组件）。
本轮立场：仍坚持 B，不翻转。 翻转的门槛是"对方有一条我驳不倒的论点"，而文心那条恰恰是可以正面拆掉的——而且拆掉之后它反向变成 B 的论据。

先逐字引用对方最强论点（文心，A 派）：
"回收是对照式操作——用户在网格里抄 9 个窗口的答案，右滑抽屉正好盖住要抄的窗；工具面板遮挡无所谓，回收面板遮挡致命。"

我正面接它，分三刀，且不复用我上轮说过的"纵向税/复用抽屉"。

第一刀｜"对照"的载体是剪贴板，不是同时可见——抄写天然是两段式，不需要窗口和输入框同屏。
"抄答案"的物理动作是：① 在窗口 7 里选中、Ctrl+C（此刻抽屉是关的，9 扇窗全可见）→ ② 打开右滑抽屉、Ctrl+V。剪贴板就是"对照缓冲区"，它把"读源"和"入框"切成两段，中间根本不需要两者同时在场。文心把"对照"偷换成了"必须同屏可见"，但复制粘贴的定义性特征恰恰是它用剪贴板解耦了可见性。唯一需要同屏的场景是"粘贴后核对有没有粘全"——那是在关着抽屉滚动源窗口来核对，抽屉此时本就应关。所以"右滑抽屉正好盖住要抄的窗"这个致命前提，在标准抄写流里不成立：等你打开抽屉时，源窗口的内容已经进了剪贴板，不需要再看它。

第二刀｜退一万步真要同屏，A 在它自己的 running 态下同样做不到——只是把遮挡从横向换成了纵向，还额外收全天税。
按已定案 14（running 时 topdeck 自动收成 deck-summary 一行），A 方案在 running 中输入框本身就是隐藏的。用户"对照式抄答案"若发生在 running（人工咨询 90% 发生在开会/挂着的 running 期），他要先把顶甲板手动展开才能拿到输入框——这一展开，网格纵向被吃掉 ~96px，3×3 网格的最底一排窗口（7/8/9）被压矮或被挤出视口。也就是说：

B：抽屉盖右侧 1 列（3/6/9），左/中两列 6 扇窗全可见；且只有抽屉开着的那几秒付遮挡成本，平时 0。
A：展开甲板压底部 1 行（7/8/9），且不抄答案时也天天挂着这 96px 纵向税。

结论反直觉但很硬：A 和 B 都没法让你"输入框 + 9 扇窗"同时全见。文心用来打 B 的"遮挡致命"，A 一样犯，而且 A 是横向遮挡（右列）与纵向遮挡（底行）二选一都躲不掉，还叠加了"不抄时也常驻"的税。文心的论点不但没打死 B，反而暴露 A 在 running 态连自己的核心场景都守不住。这条我把它记成论点反噬。

第三刀｜本轮 §0-Q3 的整个主题是"自动回收"，A 是在为一个产品正在亲手消灭的交互长期付费。
用户终极验收原话："结果要自动回收生成，我直接拖到你对话框给你。"这等于宣布：手抄 9 窗是过渡态、是衰减中的工作流，不是稳态。自动回收跑通后，手抄根本不再发生，"对照式操作"这个场景直接归零；跑不通的少数窗口才降级回手抄——而那少数又被第一刀的剪贴板两段式覆盖。所以 A 的真实成本函数是：为"自动回收上线前的一段衰减期"，支付"永久性的 96px/天"。 为一个注定被淘汰的交互做常驻布局优化，是反向优化。B 在两种世界都成立：自动回收成 → 手抄不发生 → 抽屉几乎不打开 → 0 成本；自动回收败 → 降级手抄 → 剪贴板两段式 → 抽屉用完即收。B 严格支配 A。

一句话：文心的"对照式"要的是"输入框与源窗同屏"，而这个需求 A 在 running 下也满足不了（只是纵遮替代横遮还多收全天税），剪贴板又把同屏需求消解掉，自动回收又把整个手抄场景消解掉。三层叠加，B 胜。

对 A 派的公道收尾：若你们实测下来自动回收的可靠率低于 ~50%（第三刀不成立），且用户确实以"边看窗边逐字改抄"为主（第一刀不成立），A 才翻身。这是唯一能让 A 赢的实证条件，请 A 派拿真机回收率来打，别再用布局直觉打。

Q3 · 主力工作流②：人工咨询自动回收 + R5 最终形态

① 自动回收怎么可靠（9 家 DOM 各异）

抽取作用域锁死在单个 webview：per-seat 抽取规则以该席 webview 实例为根查询（webview.executeJavaScript 内查 DOM），绝不用 document 级全局选择器——从根上杜绝跨窗串台、归属错乱。
判定"是这条 AI 的新回答"用三条件与门：(a) per-provider 角色选择器（每家一张 selector 表：消息容器、role=assistant 标志、流式结束标志）；(b) 增量游标 diff——记录上次回收时该席最后一个 assistant 节点的指纹，只取其后新增；(c) 后验稳定窗口（复用 Q2#3，末次变更 3s 无新增才落盘，防流式半截）。三者全真才算"一条可回收的新回答"。
归属天然正确：谁抽的就是谁（webview 即席位身份），不靠猜文本来源。

② 部分回收（9 回 5）的生成策略

已答 5 席正常产出 per-seat txt；未答/未回收的 4 席产出显式占位 txt（内容写 【未回收·原因:额度耗尽/未答/检测失败】），并在索引 MD 的"覆盖度"段红字点名缺哪几席。
铁律：未回收席位绝不作为空字符串混入共识——空内容会被 WorkBuddy 当成"该席没意见"从而虚高共识度。缺就是缺，显式标红。

Q5 · 小分歧快裁（四条硬裁决 + 理由）

① tournament 的 kind 徽标打在哪 —— 裁决：席位卡打一个 kind 色点，日志行打完整 kind 文字。二者不是二选一。
理由：席位卡 56px micro 只加一个不占布局的 6–8px 色点（候选蓝/名次金/结论绿），满足第 3 轮漏洞 2 的"肉眼审计切片路由对不对"刚需，且色点不挤压 webview，Agnes 担心的"卡内塞太多"被规避；日志行空间充足，打完整文字供精确核对。这是"点(卡)+文(日志)"的分工，不是折中和稀泥——各放在各自能承载信息量的载体上。

② 前置门槛硬/软怎么统一成一条规则 —— 裁决：按"缺的是合法配置还是内容物"分级。
规则一句话：缺的是"能不能选出一个合法配置"→物理禁点开始；缺的是"内容是否填满"且引擎有等待/占位态→允许开始+挂 attention+引擎卡在门槛前不派发。 于是 chairman 无 API 席 = 主席角色无法被合法指派 = 物理禁点（Agnes/文心对）；iterate 缺草稿 = 内容物可后补、引擎有"等待草稿"占位 = 可先开但卡不派发（DeepSeek W3 对）。两边其实说的是不同东西，用这条二分一次收编，不必再辩。

③ 「人工咨询」入口形态 —— 裁决：独立按钮，不占 mode 下拉。
理由：第 3 轮建模三已定论——人工咨询不是"第 12 种会议模式"，是"全席 manual 的快捷预设"。塞进 mode 下拉会：(a) 误导用户以为它与 broadcast 同级；(b) 逼 ControlRegistry 给它编一个根本不存在的独立 modezone（它没有模式专属配置，只有 manual 通道）。独立按钮点它 = 把当前 mode 的席位临时切成全 manual 并旁路引擎，保留原 mode 值可一键回退——入口形态应忠实反映"预设"本质，而非伪装成模式。

④ debate "附带自身历史摘要" Toggle 进 v1？ —— 裁决：不进 v1，留 v1.1。
理由：debate 是单遍模式（无 loop），"自身历史摘要"要解决的长上下文溢出只在 loop/多轮才显著；单遍对辩里双方历史很短，默认全量注入即可。加一个 Toggle = 逼用户理解一个"当前没有痛点的开关"，违反"v1 只留真痛点的开关"。等真出现长辩论上下文溢出再进 v1.1，届时若证明高频可再议。
