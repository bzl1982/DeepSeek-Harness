# 多 AI 软件开发协作台
## 给 UI 设计师的流程灵感与功能规范

**版本：2026-09-26｜人工逐节点确认优先**

> 这是一份产品流程灵感简报，不是冻结的 PRD，也不是对现有界面的复刻要求。它只说明用户要完成什么、每步如何作决定、出错时往哪里退。**不提供现有 UI 布局、截图、控件形态或视觉规范**，请设计师自由探索信息架构和视觉表达。

## 一、产品想法

让用户依靠 **9 个网页 AI 与 3 个 API AI 组成的资源池**，从一个软件想法走到可验收的软件和安装包。用户不需要懂全部技术细节，但始终能看懂当前进度、选择方案、确认下一步，并知道哪里卡住。

这不是“12 个 AI 自动开会后替用户做决定”的系统，而是一个**用户掌舵、AI 分工、系统传递与留证**的半人工协作流程。并非每一步都要 12 个 AI 同时在线：按能力选人，没被选中的 AI 离线不应挡住工作。

### 最重要的设计原则

1. **默认人工逐节点确认。** 一个业务节点完成后，展示结果和证据，等用户选择继续、退回修改或暂停；用户确认的是“这个版本的结果”和“下一步要做的事”。
2. **备用自动模式由用户主动开启。** 只能预先选定可自动经过的节点、任务、权限和停止条件；遇到错误、不确定、材料缺失、版本变化、额度或权限问题就停下交还用户。
3. **确认不等于技术通过。** 用户可以确认“知道有风险、继续诊断”，但系统不能因此把失败测试标成通过。重要文件覆盖、危险命令、权限扩大、最终验收和 GitHub 同步始终单独由用户确认。
4. **项目阶段与单项任务分开。** 任务可按依赖并行；一项退回，只退这项及受影响部分，不要把无关任务全部打回。
5. **结果要有版本和来源。** 需求、方案、任务、代码、审查与测试都指向具体版本；材料准备好不等于已发送，AI 回复完不等于代码完整，构建成功也不等于用户验收。

自动保存、整理进度、收集回复等机械操作属于节点内部，不必每个小动作都打断用户；**开始一个新的重要业务节点时再确认**。

## 二、从想法到交付

### 1. 建立项目

用户说明软件想法、使用者、目标平台、已有代码或新项目、不能改动的范围和交付目标。系统整理项目背景、材料、权限与资源状态；只检查眼下需要的 AI 和工具，不为尚未发生的构建做多余操作。

**用户确认项目边界后，才开始整理需求。** 资源缺失时说明原因，只暂停受影响部分。

### 2. 整理需求并确认

AI 把零散想法整理成用户能阅读的功能说明：谁用、要做什么、输入和结果、正常与异常情况、什么不做、怎样验收。只追问会影响方案的关键空缺；未知项标清楚，不猜成定论。

**用户确认一个需求版本后才继续。** 不满意就修改；改动已确认内容时留住旧版，并指出哪些后续结果可能要重做。

### 3. 由功能流程推导界面方案

依据已确认需求，生成帮助用户理解产品的图文方案或可操作原型。重点是功能如何使用及成功、失败、等待、空内容、取消等情形；原型可用模拟数据，但要说明它尚非正式软件。

**用户体验通过后才进入技术方案。** 不满意就回这一步；如果发现需求本身不对，回需求确认。

### 4. 多 AI 独立提案，用户选技术方向

先让通常 3–5 个 AI 在看不到彼此答案的情况下，基于**同一版需求和约束**独立提出语言、架构、技术标准与规范。各自用通俗语言解释成本、优点、缺点、风险和取舍理由。

**第一轮完成后，用户先确认是否进入比较。**再把实际收到的答复匿名整理成方案 A/B/C，说明差异、适用情况和待查事实。匿名是为了减少先入为主，不承诺绝对认不出作者；未回复的 AI 明确标为未回复，不能当作同意。事实不能靠多数票决定。

**用户最后可选一案、组合多案或退回重问。** 组合方案需先核对是否兼容；若与用户已确认的体验冲突，回体验方案请用户重新决定。

### 5. 指定 AI 拆任务，用户确认计划

用户指定一个 AI，把**上一阶段完整定案材料**交给它，拆成任务索引和任务文件。每项说清负责人、前置依赖、输入、可读写范围、产出、接口、验收与回退方式。

检查任务是否漏负责人、互相循环等待、重叠写同一文件或没有验收方法；系统可请其他 AI 协助审计划。用户确认分工和本轮授权后，只启动已满足前置条件的任务；其他任务保持等待，不假装已发出。

### 6. 每个任务单独闭环

对每个已就绪任务分别执行：

**确认任务与对象 → 发给编码 AI → 收集代码和证据 → 用户发起审查 → 处理意见 → 用户确认任务通过**

- 编码 AI 给出实际文件／补丁、变更清单、做过的检查和未完成事项；不能只报“已完成”。网页 AI 的文件挂载不等于消息已发送，用户确认后才是已发送。
- 用户发起审查时选通常 2–3 个**未编写、未修正该任务**且可用的 AI；它们独立审同一版代码。未能凑足时如实说明，让用户选择等待或换人。
- 意见互相矛盾时先核对；用户决定修什么，修正后重新验证，必要时再审。无阻塞问题则无需为了流程而制造修正任务。
- 用户通过当前任务后，才解锁它的下游任务。一个任务的修改只让相关版本和依赖结论失效。
- 反复几轮仍未解决就暂停该任务，交用户选择换人、改方案或追加尝试；不能在第五轮自动放行。

### 7. 集成、测试与构建

必要任务都通过后，汇集本轮有效产物，解决文件和接口冲突，再分别运行全项目测试、构建、打包及必要的安装／启动验证。每步结束展示实际结果，等待用户确认进入下一步。

失败时把**真实日志**交回相关任务；工具链或环境故障先修环境，不让 AI 凭空猜。只有语法检查不等于构建完成；没有执行的验证明确标成未验证。必须核对安装包是本轮生成、真实存在且对应当前代码版本。

### 8. 用户验收与两个停止点

**停止点一：本地交付。** 用户拿到安装包的明确目录、版本、运行方法、测试结果和已知限制。用户验收不通过，退回相关任务修复；新增需求另开版本。验收通过后，停止自动 AI 调用，等待用户决定是否同步代码。

**停止点二：仓库同步。** 用户主动发起 GitHub 同步，确认仓库、分支和要上传的文件。排除密钥、登录态、私人材料及无关改动，记录提交和远端结果。同步失败时保留本地交付、核实远端后再处理；成功即结束本轮。合并主分支、公开发布或上线不属于默认流程。

## 三、异常时怎么走

| 发生什么 | 流程应如何处理 |
|---|---|
| 用户不同意当前结果 | 保留历史版本，回到对应节点修改；只让受影响的后续结果重新确认 |
| 任务依赖不满足或形成循环 | 显示卡在哪项和原因，等待前置结果或退回拆任务；不可假装正在执行 |
| AI／网络／额度／登录出错 | 保留已完成结果，暂停受影响任务；让用户选择重试、换人、稍后继续或放弃 |
| 消息发送结果不确定 | 标成待核实；检查原会话／远端状态后由用户决定，不盲目重发 |
| 文件缺失或附件未被确认 | 不把文件名或旧附件当内容，不让依赖该材料的任务假通过 |
| 用户暂停或重启 | 停止新派发，保留在途结果；重启后先核实，不自动重跑可能已执行的工作 |
| 构建或验收失败 | 回到对应任务或环境修复；不撤销已经有效的无关任务 |
| GitHub 同步失败 | 本地交付仍算完成；只处理同步状态，不重做开发 |

## 四、给设计师的灵感方向与边界

请自行探索如何让用户直观理解：

- 当前项目／任务／版本，以及系统、AI、用户各自正在等待谁。
- 刚发生的结果、证据、尚未完成的部分和明确的下一步。
- “确认继续”“退回修改”“暂停”各自会产生什么后果。
- 多 AI 意见如何比较、如何看到分歧，谁写代码、谁审查、结果来自哪个版本。
- 为什么被阻塞、如何解开，以及何时本地交付完成、何时仓库同步结束。

流程图里金色节点代表**必须体现用户决定的业务关口**，不是要求使用某种颜色或做成某种控件。页面数量、导航、布局、组件、动效和视觉风格完全由设计师决定；不要照搬任何现有测试台。

设计提案只需覆盖正常流程和最有代表性的退回／阻塞情形，并解释每个关键节点的触发、结果与下一步。无需把本文每句话逐项做成独立页面。

**最终目标：让用户感觉自己一直掌舵；AI 能并行帮忙，但绝不会在用户没看清结果时偷偷驶向下一步。**
