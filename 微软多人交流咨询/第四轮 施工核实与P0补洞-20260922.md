## 三、三个洞（汇报未提，我已补两个）

### 洞 1（安全性）：「三道安全校验」的第 ③ 道是空转 —— 已修

原代码（`main.js:627-631`）校验的是 **renderer 自报的 `size` 参数**：

```js
if (!Number.isInteger(size) || size <= 0 || size > MEETING_MAX_FILE_BYTES) { … }
```

但第 654 行真正写入的是 **`bytes`**：

```js
await fs.promises.writeFile(p, Buffer.isBuffer(bytes) ? bytes : Buffer.from(bytes));
```

**校验对象 ≠ 写入对象** → renderer 谎报 `size = 1` 再塞 500MB，上限形同虚设。

> 严重性评估：**中低**。renderer 是我们自己的 `meeting.html`，不是外部输入，所以不是可被远程利用的漏洞。
> 但既然代码注释明写"三道安全校验（缺一不可，否则 renderer 就能借主进程写任意文件）"，
> 这道就必须真生效——否则注释在骗未来的自己。

**已修**：以 `bytes` 自身长度为准（`ArrayBuffer.byteLength` / `TypedArray.length`），并让总量校验和返回值都用真实长度。

```js
const realSize = bytes && typeof bytes.byteLength === 'number'
  ? bytes.byteLength
  : (bytes && typeof bytes.length === 'number' ? bytes.length : -1);
```

### 洞 2（正确性）：「上传失败仍发『（见上传的文件）』」—— 已修

这就是我上一轮挖出的**根因 B**，本轮**依然没修**（`meeting.html` 原 L530-534）：

```js
const ok = await uploadFileToWebview(wv, filePath);   // ok 声明后从未被检查
await new Promise(r => setTimeout(r, 3000));          // 还是硬等 3000ms
broadcastToCell(cell, prefix + '（见上传的文件）');     // 无条件发
```

后果：长文本上传失败时，9 个 AI 全都收到一句「（见上传的文件）」，**而文件根本不存在**。
这是"9 个人收不到文件"里**最隐蔽的一种**——表面看起来发了，实际是空指路，且完全没有报错。

**已修**：`ok === false` 时改走降级——直发正文前 4000 字并显式标注「完整内容上传失败，以上为截断正文」。
**至少让 AI 拿到部分内容，而不是一句指向虚空的话。**

### 洞 3（资源）：「散会后可整个删除」只是注释，没有实现 —— 已修

## 四、必须点出的两个设计问题（未改，需你拍板）

### 4.1 角色数据现在有**三份**，而且客户端那份是**旧设计**

| 位置 | 内容 | 角色绑定方式 |

**问题不是"重复"，是"回退"**：你明确要的是"角色设定多种"，
而 `AGENT_ROLES` 把 deepseek 永久钉成红队 —— 同一批 AI **换不了角色组**，
这恰好是我上轮在 `roles.js` 里刻意改掉的结构性问题。

汇报自己把这笔债写成"Phase 2 统一删除内联段"。**但真正的风险不是漂移，是它已经在客户端固化了错误模型**——
Phase 2 接入时若只是"搬过去"，错误设计会跟着搬。

**建议**：Phase 2 不搬 `AGENT_ROLES`，直接以 `roles.js` 的席位模型为准，客户端只保留"从主进程取角色组"的接口。

### 4.2 `google-search` 的角色前缀会被拼进**搜索 URL**

```js
'google-search': '你是【事实核查员】。先搜后答，给出可验证的来源。',
```

它的发送方式是 URL 拼 `q=`（`agentCatalog.js` url 为 `https://www.google.com/search?q=`），
**不是对话 AI**。这句前缀会被当成搜索关键词：

> 搜索：`你是【事实核查员】。先搜后答，给出可验证的来源。\n\n请评审…`

**语义直接错乱**，且 `charLimit: 2000` 是按"拼进 `q=` 的字符量"配的——再叠加这段前缀会更容易撑爆 URL 上限。
**建议**：非对话型 provider（搜索结果页）**不注入角色前缀**，改用"把问题压缩成检索词"的专用前缀。

### 4.3 附注：`smartSend` 的 `charLimit` 参数目前是**死参数**

签名 `smartSend(cell, text, charLimit, batchPrefix)`，函数体只用全局 `INLINE_MAX`（4000）判断，`charLimit` 从未被使用。

## 八、真会实测：两个「假成功」缺陷（本轮最重要的产出）

用户在测试台（CDP 9223，独立 userData）里**登录了 DeepSeek / ChatGPT / Gemini 三个账号**，
我于是用 CDP 驱动真实鼠标事件跑了一轮真会 —— 结果**推翻了"成功 3/3"的表象**。

### 8.1 缺陷一：完成检测「假阳性」——页面原有内容被当成 AI 回复

**第一轮跑完显示「成功 3/3　会议记录 4 条」，但记录内容是：**

| # | 长度 | 内容 | 判定 |
|---|---|---|---|
| 1 | 25 | 用户原始问题 | ✅ 正常 |
| 2 | 10 | 「需要我为你做些什么？」 | ❌ **Gemini 的页面欢迎语** |
| 3 | 121 | 「你是【红队评审】…【本轮任务】…」 | ❌ **我们自己发出去的 prompt 回显** |
| 4 | 844 | 「结论：技术可行，但应直接以 MAF 为目标框架…」 | ✅ DeepSeek 真回复 |

**ChatGPT 的真实回复（页面上明明有一大段红队评审）根本没被采集到。**

耗时是第二重铁证：`gemini 932ms` / `chatgpt 1121ms` 就报 COMPLETED —— 真实网页 AI 不可能这么快。
webview URL 是第三重：Gemini 停在 `https://gemini.google.com/app`，**根本没进会话**。

**根因**（`adapters/web-adapter.js`）：

```js
let sawContent = false;
...
if (text !== lastText) {          // 首次探测：lastText=null，必然进入
  lastText = text;
  if (text.length > 0) sawContent = true;   // ← 语义是"看到 AI 回复"，实现是"页面有文本"
}
```

**只认「存在」，不认「增量」** —— 在已登录、页面本来就有内容的真实场景下**必然 1 秒内假完成**。
这不是偶发，是**设计缺陷**：用户的实际使用场景（登录 + 有历史对话）正是触发条件。

**修法**：
1. `sendText` 之后留 700ms 让"用户消息"先上屏，再抓 `baselineText` 基线快照
   （若在发送前抓，后续新增里会混进我们自己的 prompt 回显 —— ChatGPT 正是这样被误判的）
2. 新增 `hasNewContent()`：只有**相对基线确有新增**才算看到内容
3. 新增 `replyDelta()`：写进会议记录的是**增量**，不是整页文本

**修复后实测**：`deepseek 4422ms / chatgpt 34619ms / gemini 23809ms` —— 全部变成**真实等待时间**，
不再有任何 1 秒假完成。Gemini 的回复也变成了真实内容：「好的，请提供本轮各方…」（符合它的「主持助理」角色）。

同步更新了 `test/web-adapter.test.js` 的 fake driver，让它模拟"基线抓取时 AI 还没回复"的真实时序，
**保住了它原本要锁的 streamEnd 不跨轮闩锁行为** —— 测试仍是 126/126 全绿。

### 8.2 缺陷二：Gemini「文本卡在输入框发不出去」（用户先发现的）

用户原话：「Gemini 消息没发出去，在输入框里待着没动」—— 与我的实测完全一致（href 停在 `/app`）。

**根因**：Gemini 的输入框是 **Quill 富文本编辑器**（`div.ql-editor textarea new-input-ui`）。

```js
wv.insertText(text);                                   // ✅ 文本真写进去了（用户能看到）
wv.sendInputEvent({ type: 'keyDown', keyCode: 'Enter' });  // ❌ Quill 不响应
wv.sendInputEvent({ type: 'char',    keyCode: 'Enter' });
wv.sendInputEvent({ type: 'keyUp',   keyCode: 'Enter' });
} catch (e) { /* 兜底：点 button[aria-label*="发送"] */ }   // ← 永远到不了这里
```

**关键**：回车**不抛异常** → 永远走不到 `catch` 兜底。
而讽刺的是，**兜底里早就写好了** `aria-label*="发送"` 这个选择器（Gemini 的按钮恰好就是 `aria-label="发送"`），
只是根本执行不到。

**修法**（`shell/index.html`）：新增 `composerFilled()` / `clickComposerSend()`，
回车之后**校验输入框是否真的清空了**，没清空就点页面自己的发送按钮，并打 `[补发]` / `[补发失败]` 日志。

**修复后实测铁证**：

| 判据 | 修复前 | 修复后 |
|---|---|---|
| URL | `gemini.google.com/app` | **`/app/4970f8ae3bf763fd`**（进了会话）|
| Quill 内容 | 卡着 prompt 文本 | **`"\n"`**（清空了）|
| 页面回复 | 无 | **「好的，请提供本轮各方…」**（符合主持助理角色）|
