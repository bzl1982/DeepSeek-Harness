## 一、先纠错（草案 A/B 里我看到的 3 个真 bug）

> 咨询案 §7 第 2 条要求"若判断某缺口是错的，请直接反驳"。以下三处草案判断我认为是错的：

1. **草案 A·评标切片写 `ALL` 是 bug。**
   `ALL` 包含自己。评标人看到**自己出的那份方案**时会自我加分（锚定）。
   正确切片是 `OTHERS`（`messages.filter(m => m.senderId !== selfId)`）——恰好是"其它所有出标者的方案"。
   我实现的 `tournament` 评标阶段用的是 `OTHERS`，不是 `ALL`。

2. **草案 B·"冻结契约 seat: converge" 是 bug。**
   收敛类（chair-assistant）的互斥约束是"禁止引入新观点，只做归并"。
   让它写契约会**自相矛盾**——契约是设计产物，必须归建设类（architect）写。
   我实现的 `build` 模式"冻结契约"阶段 `seat: 'architect'`，并让架构师独占该阶段。

3. **Q4 草案候选①"得分增幅 < 阈值"做不到。**
   Q3 裁决用名次不用分数后，根本没有"得分"这个量，`delta` 无从谈起。
   我换成 `same-winner`（定标者不变）——它对齐"择优迭代"的语义：
   改进没让定标翻转 = 收敛；翻转会继续。

## 二、Q1/Q4：`tournament` 模式（已落地 + 测试）

### 字段级设计（进 `core/modes.js`）

```js
tournament: {
  id: 'tournament', label: '招标评审',
  needs: [],                  // 不需要 draft/material —— 从"问题"出发
  loop: true,
  maxIterations: 3,          // 比 iterate 的 5 轮狠：每轮 5 阶段更重
  phases: [
    { name: '出标',   seat: 'all',       speak: PARALLEL,   slice: TASK },
    { name: '评标',   seat: 'challenge', speak: PARALLEL,   slice: OTHERS }, // ★ 防锚定关键
    { name: '定标',   seat: 'converge',  speak: SEQUENTIAL, slice: ALL },
    { name: '改进',   seat: 'build',     speak: SEQUENTIAL, slice: CRITIQUES },
    { name: '复评',   seat: 'challenge', speak: PARALLEL,   slice: DRAFT },
  ],
  stopWhen: 'same-winner',   // ★ 连续两轮定标同一方案即收敛
}
```

### Q4 判据实现（`bordaMeans` + `tournamentStop`）

```js
// Q3：名次聚合（不用分数、不用 pairwise）
bordaMeans(ballots) → { winnerId, runnerUpId, means, ballots }
  // 每个方案在 M 个评审者处的名次取均值，均值最低者胜（经典 Borda 计数）

// Q4：收敛判据
shouldStop('tournament', { iteration, winnerId, prevWinnerId })
  → iteration ≤ 1：不收敛（无基线）
  → winnerId === prevWinnerId：收敛（"改进没让定标翻转"）
  → 否则：继续
  → iteration ≥ 3：强制停（兜底）
```

**成本**：单轮 = 出标 N 次 + 评标 C 次 + 定标 1 次 + 改进 1 次 + 复评 C 次。
C=质证席位数（通常 2–4）。比 iterate 的"挑错+修订"重 3 倍，所以 `maxIterations` 砍到 3。

**反例（什么时候不该用）**：
- 已有一份满意初稿 → 用 `iterate`（2 阶段比 5 阶段轻）
- 问题有唯一正确答案 → 用 `assist`（直接收敛，不需要选优）

## 三、Q5/Q6/Q9：`build` 模式 + `integrator` 角色（已落地 + 测试）

### Q9 环节清单 + 责任分配

| 环节 | 谁做 | 产出 |
|---|---|---|
| 架构冻结 | **architect**（建设类，不是收敛类） | 契约文件（签名级 TS interface） |
| 分头实现 | 全员（`CONTRACT` 切片） | 各模块文件（**产物 {path, content}**，不是聊天文本） |
| 集成验证 | ★ **新角色 `integrator`** | 编译/运行结果 + "哪里断了"清单 |
| 修复回路 | **原作者**（各模块负责人，不是集成者） | 修好"它自己那段" |

**为什么集成者不复用 chair-assistant**：主持助理互斥约束是"禁止引入新观点，只做归并"——它不碰代码。
集成者必须能读错误输出、判断"哪里断了"，是全新职能（第五类 group=`integrate`）。

**为什么修复归原作者**：集成者不知道原作者的意图，它改了就是猜。

### `build` 模式字段级设计

```js
build: {
  id: 'build', label: '工程交付',
  needs: [],
  loop: true,
  maxIterations: 4,
  modelFit: { channels: ['api'], requiresApi: true,  ... },  // ★ 必须走 API（webview 不能落盘/编译）
  phases: [
    { name: '需求澄清', seat: 'represent', speak: SEQUENTIAL, slice: OTHERS },
    { name: '架构设计', seat: 'architect', speak: SEQUENTIAL, slice: OTHERS },
    { name: '冻结契约', seat: 'architect', speak: SEQUENTIAL, slice: ALL },   // ★ Q5：架构师写
    { name: '分头实现', seat: 'all',       speak: PARALLEL,   slice: CONTRACT }, // ★ Q6
    { name: '集成验证', seat: 'integrator', speak: SEQUENTIAL, slice: ALL },    // ★ Q9 新角色
    { name: '修复',     seat: 'all',       speak: PARALLEL,   slice: CRITIQUES },
  ],
  stopWhen: 'build-pass',   // 集成通过即停；否则修复回路（4 轮兜底）
}
```

### Q6：`CONTRACT` 切片落地（`selectSlice` 新增分支）

```
执行者看到 = 契约全文 + 「你负责的模块」+ 「同伴模块（只看接口，不看实现）」
```

**关键：不给"别人的实现细节"，只给"别人的签名"** —— 这是"接口先行"的本意，
保证并行不互相等待，同时约束住所有人的函数签名/数据结构。

### Q5：契约形态（签名级，不是 OpenAPI）

**太细（函数体级）框死 AI，太粗（一句话"要模块化"）没约束力。** 分界线：
- **含**：函数名、参数类型、返回类型、错误约定、共享数据结构
- **不含**：函数体、内部实现

用 TS interface 而非 OpenAPI：同进程模块间调用，TS 更贴；且所有模型都熟 TS 类型。

**反例**：纯"讨论出一个方案"不需要冻结契约（用 `assist` 或 `review`），
只有"要分头写代码并集成"才需要 `build` 模式。

## 四、Q7：panel O(N²) 降本（已落地方案① + 排序）

### 排序（最有效 → 最笨）

| 排名 | 手段 | 效果 | 副作用 | 状态 |
|---|---|---|---|---|
| **①** | **分组合并**（panelGroupSize） | O(N²)→O(G·g+G)，9 人分 3 组注入量 36→12（1/3） | 组长要"代表组内发言"，丢一层信息 | ✅ **已落地** |
| **②** | 摘要压缩（每人发言即压） | O(N²)→O(N·摘要长) | 摘要质量决定会议深度，长会退化成"摘要传声筒" | 未做（`summarizer.js` 有基础） |
| **③** | 只在分歧点串行（场景限定） | 提前收敛 | 需判定"分歧点"，引入 chair API 成本 | 未做 |
| **④** | 硬限 N≤5 | 最直接 | 丧失"人多视角多"收益 | 未做（UI 兜底） |

**我的建议**：默认①分组 + ②组内摘要双管；③作可选；④作 UI 兜底（panel 人数滑块 >5 自动切分组）。

### ①落地细节（`planPhases` 新增 `panelGroupSize` 参数）

```
panelGroupSize=3 + 9 人：
  原"全员会诊"（第 k 人看前 k-1 份，注入 0+1+...+8=36）
  → 3 组组内会诊（每组 0+1+2=3，共 9）
  + 1 组长会诊（3 个组长看前 k-1 份组长摘要，0+1+2=3）
  = 总注入 12（降 1/3）
```

**组边界契约**：阶段对象新增 `groupSize` 字段（组内会诊）/ `groupLeaders` 标志（组长会诊），
编排层据此限定 `selectSlice(OTHERS)` 时只取本组的 messages —— 组间隔离靠编排层，不靠切片逻辑。

**反例**：人数 ≤ panelGroupSize 时不分组（无意义，保持原样）；`panelGroupSize=1` 退化为不分组。

## 五、Q8：人工中转席位（已落地 + 测试）

### 建模成真实 adapter，不是插一条 message

插一条 message 进不了选角/切片/审计（它是"幽灵席位"）。
所以它必须是 `channel:'human'` 的 adapter，实现同一套契约：

```
isReady()          → true（人随时在）
uploadFiles()      → { ok: true }（人粘贴时自己带文件，不需要"上传"）
sendText()         → 把"该你粘贴了"推给 UI（Electron 通知/弹窗）
waitForResponse()  → 阻塞在"等用户粘贴"的 IPC 事件上
                    ★ 超时不标 TIMEOUT，标 HUMAN_PENDING（人会迟到不是机器卡死）
cancel()           → 清空等待队列（散会用）
```

**能力画像**（`humanRelayModelEntry`）：
- `reasoning: 0`（它本身不生成，是"搬运工"）
- `stability: 5`（不会中途弹验证码）
- `structure: 5`（人粘贴前可整理成结构化）
- 它**不进正常选角**（推理 0 会被能力门槛一票否决），只在"需要接外部 AI 结论"时**手动挂**到某席。

**与普通席位的编排差异**（§8 要求"说清差异"）：
1. 无完成检测（人是事实源）
2. 可一次粘贴多个 AI 的回答（解析成 N 条 message）
3. 超时静默（不标记 TIMEOUT，会议其它席位照常）
4. 散会前必须 `cancel()`，否则等待队列残留（已加测试）

**成本**：0 调用（不花 token）。**反例**：无人值守的自动会议不能用（人会迟到 → 该席永不收口）。

## 八、给你下一步动手的 4 件事（按优先级）

1. **把 `tournament` 接到 orchestrator**：出标→评标（并行，OTHERS）→定标（读 `bordaMeans` 结果）→改进→复评。定标 prompt 里**必须喂 Borda 均值表**，不是"你觉得哪个好"。
2. **把 `build` 接到"产物 {path, content}"机制**：现在 orchestrator 的产出是文本，要支持"落盘成文件"。这是 Q9"生成可运行软件"的真正门槛。
3. **给 panel 加 UI 滑块**：`panelGroupSize` 1–3，超过 5 人默认切分组（Q7④兜底）。
4. **人工中转先手动挂**：不急着自动化——先让你"复制粘贴"时系统把它当成一个真实席位记录进 MeetingModel（可审计、可切片），自动化（自动检测外部 AI 完成并推送）是 Phase 4+ 的事。
