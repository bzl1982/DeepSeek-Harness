替换成下面这个版本：

### 裁决二：Phase 0/1 不引入 Microsoft Agent Framework，但原因不是“MAF 不支持 GroupChat”

这一点需要根据微软 2026 年最新官方资料修正。

**Microsoft Agent Framework 1.0 实际仍然原生支持 Group Chat。** 微软于 2026-04-03 发布 1.0 GA 时，明确将 Sequential、Concurrent、Handoff、Group Chat、Magentic-One 列为稳定的多智能体编排模式；2026-07-08 又进一步宣布这些编排模式在 Python 与 .NET 两端全部达到 1.0。当前官方 `GroupChatBuilder` 仍支持 Round-Robin、LLM/Prompt Speaker Selection、自定义选择逻辑以及自定义 Orchestrator。([Microsoft for Developers][1])

因此，本项目不能再以“MAF 已经取消 GroupChat、无法表达 9 人会议”作为不采用 MAF 的依据。

正确裁决是：

> **MAF 在能力层面能够表达通辽会议，但现阶段没有必要成为通辽会议的运行时依赖。**

原因如下：

1. **当前真正的技术瓶颈不在高级编排。**
   目前首先需要解决的是回复完成检测、附件上传 ACK、并发失败隔离、会议消息模型和 per-AI 状态机。这些问题与 MAF/AutoGen 无关。

2. **通辽会议已经拥有 Electron 浏览器运行时。**
   9 个 WebContents、9 个持久化 Partition、9 个登录状态、CDP 文件上传和 WebAI Adapter 都已经存在。重新引入 Python Playwright 浏览器池会重复建设浏览器层，并破坏当前 9 宫格可视化产品结构。

3. **项目当前架构纪律是纯 Node/Electron。**
   Microsoft Agent Framework 目前的一等 SDK 仍以 Python 和 .NET 为主，JavaScript/TypeScript 一等实现并不是当前主线，因此现在引入 MAF 会产生额外的 Python/.NET sidecar、IPC、打包、升级和故障处理成本。([GitHub][6])

4. **当前阶段引入框架会扩大问题面。**
   Phase 0/1 的目标是验证 WebAI Adapter 的三个核心不确定性，而不是验证第三方 Agent Runtime。

因此最终采用：

```text
Phase 0：
纯 Node Meeting Lab

Phase 1：
Node Meeting Core

Phase 2：
接入 Electron / WebAI Adapter

Phase 3：
实现 Broadcast → RoundRobin → Dynamic Speaker Selection

Phase 4：
根据实际需求评估 MAF sidecar
```

未来如果出现以下需求：

* 持久化 checkpoint；
* 长时间会议断点恢复；
* Human-in-the-loop 暂停/恢复；
* 复杂 Magentic 编排；
* 标准化 Workflow 暴露；
* 跨语言 Agent 协作；

则可以把现有 `SpeakerStrategy / Orchestrator` 替换或桥接到 Microsoft Agent Framework。

由于 Meeting Core、WebAI Adapter、Attachment Bus 与编排层已经通过协议隔离，这一升级不应影响 Electron 浏览器层、9 个登录 Partition、会议 UI 和附件系统。

因此：

> **现在不用 MAF，是工程阶段选择，而不是能力否定。**
>
> **MAF 是未来可插拔的编排后端，而不是当前产品必须依赖的基础设施。**
