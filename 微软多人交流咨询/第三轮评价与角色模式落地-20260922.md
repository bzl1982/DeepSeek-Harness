## 二、我核实的一条关键技术事实（直接决定 P0 怎么写）

**争议点**：拿到拖拽文件的真实路径，到底该用 `file.path` 还是别的？

- 谷歌搜索3 写的是：`const localPath = file.path || '';` —— 并说"Electron 中可直接拿到绝对路径"
- KIMI3 写的是：**新版 Electron 移除了 `File.path`，必须用 `webUtils.getPathForFile`**
- Hy4-3 也用了 `saveToDisk` + `localPath` 路线，未提 `file.path`

**我去 Electron 官方文档核实（原文引用）**：

> `webUtils.getPathForFile(file)`
> …Returns `string` - The file system path that this `File` object points to.
> **This method superseded the previous augmentation to the `File` object with the `path` property.**
> — https://www.electronjs.org/docs/latest/api/web-utils

**结论：KIMI3 对，谷歌搜索3 错。**

官方用词是 `superseded`（取代）。**并且官方明确要求**：开启 contextIsolation 时，这个调用必须放在 **preload 脚本**里，用 `contextBridge` 暴露给页面；官方还特别提示 *"It's best not to expose the full file path to the web content if possible."*

→ 这直接改写了 P0 的实现方式：**不是改 `meeting.html` 一处就完事，而是要同时改 preload**。这是本轮最重要的技术修正。

## 四、本轮落地：角色系统与会议模式

### 4.1 为什么"角色"要重做（原来那份有个结构性缺陷）

接手前的 `context-strategy.js` 里，角色是**按 providerId 硬绑**的：

```js
'deepseek-web': '你是【红队】…',
'chatgpt-web':  '你是【成本分析师】…',
```

这有三个问题，正好撞上你这次的需求：

1. **角色绑死在"某个 AI 是谁"上**，而不是"这场会需要什么职能"；
2. **同一批 AI 无法换角色组重跑**——而你要的正是"角色设定多种"；
3. 换 provider、加第 10 个 AI、调格子顺序，角色指派就全乱。

**改法：角色是「席位（seat）」的属性，不是 provider 的属性。**

> 开一场会 = 选一套角色组 + 把角色按顺序发给当前参会者。
> 谁坐哪把椅子由调用方决定，角色只管"这个席位该用什么视角说话"。

### 4.2 `core/roles.js` —— 14 个角色 / 6 套角色组

**角色按四大认知职能分类**（不是按"性格"）：

| 大类 | 角色 | 作用 |
|---|---|---|
| **质证**（挑错） | 红队、事实核查、合规审查、反方 | 防止会开成互相点赞 |
| **建设**（给方案） | 架构师、成本分析师、执行步骤、数据核算 | 防止只批不建 |
| **代表**（换立场） | 用户代言、产品经理、新人视角 | 补上专家盲区 |
| **收敛**（收结论） | 主持助理、书记员、基准与会者、检索员 | 防止开完没结论 |

**每个角色都必须有一条"互斥输出约束"和一条"格式约束"**——这是反趋同的真正机制，不是形容词。例如：

> 你是【红队评审】。职责：**只**找当前方案的漏洞、边界条件、隐藏风险和反例。**禁止**总结、**禁止**附和、**禁止**说"总体不错"。必须给出至少 2 个具体反例或失败场景，**用编号清单输出**。

**6 套预置角色组**（同一批 AI 换一套 = 另一场会）：

| 角色组 | 席位数 | 用途 |
|---|---|---|
| `trio` | 3 | 测试阶段默认（建设/质证/收敛） |
| `trio-review` | 3 | 针对一份材料的审阅 |
| `risk-audit-5` | 5 | 风险审查 |
| `tech-7` | 7 | 技术选型 |
| `product-9` | 9 | 产品评审（满员） |
| `diverge-9` | 9 | 早期发散找问题 |

**健康校验 `validateAssignment()`** 会拦下：角色重复（两人同职能 = 白占格子）、缺质证类（会开成点赞会）、缺收敛类（开完没结论）、收敛类排在第一位（它前面没有内容可收敛）。

### 4.3 `core/modes.js` —— 7 种会议模式

你说的三种都在，另外补了四种有实际价值的：

| 模式 | 阶段结构 | 你要的 |
|---|---|---|
| **广播** | 全员并行、各自回答 | （现状基线） |
| **共同审阅** | ① 各自**独立**审阅材料 → ② 交叉质证 → ③ 归并结论 | ✅ |
| **协助** | ① 建设类各出方案 → ② 质证类会诊挑错 → ③ 收敛成可执行结论 | ✅ |
| **反复修正** | ① 挑错（看草稿）→ ② 修订（看批评清单）→ 循环至**无新批评** | ✅ |
| **交叉辩论** | ① 立论 → ② 多轮对辩（只看别人） | |
| **专家会诊** | 串行接龙，后者能看到前者全部发言 | |
| **主席点名** | 主持人（走真实 API）动态点名追问 | |

三个设计要点，都有出处：

1. **上下文切片比"换角色"更能制造真实差异**（Hy4-3 结论）。给不同发言者喂**不同切片**：质证者只看别人的结论、修订者只看批评清单、归并者看全部。

2. **"先独立后交叉"是审阅类的关键顺序**（防锚定效应）。共同审阅的第一阶段**必须**是"并行 + 只看材料"——如果第一轮就让人看到彼此，后面的发言会全部向第一个发言者收敛，这正是"同质化坍塌"在流程层的成因。**这条被写成了硬测试。**

3. **反复修正必须有客观终止判据**，不能靠轮数硬切。判据 = 「本轮批评集合相对上一轮无新增」，且做**文本规范化**（去空白/标点、截前 60 字）。

   为什么必须规范化：**否则同一句批评换个标点就被算成新问题，反复修正会永远停不下来**—这是这类系统最典型的失控方式。演示实测：第 4 轮只换了标点，被规范化掉，正确判定收敛。

   同时保留迭代上限（默认 5 轮）兜底，防判据失效导致死循环。

### 4.4 已接到测试台（可直接体验）

`shell/index.html` 新增了**会议模式**与**角色组**两个下拉框 + 顶部流程预览条 + 每个格子的角色徽章：
