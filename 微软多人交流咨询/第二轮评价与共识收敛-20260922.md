## 零、TL;DR（先看这 6 条）

1. **我上一轮错了一个关键事实，而且污染了下游。** 我写过「MAF 1.0 刻意设计掉了 GroupChat / 微软放弃的正好是你要的」——**这是错的**。核实结果：**MAF 1.0 原生支持 Group Chat**，`GroupChatBuilder` 提供 round-robin / agent-based / custom 三种选择策略。真正被退役的是 **AutoGen 式涌现会话模型（`GroupChatManager`）**，不是 Group Chat 能力本身。**七家里有 3 家（GPT2 / Hy4-2 / KIMI2）在同一时间纠正了我，2 家（谷歌2 / 豆包2）继承了我的错误前提并据此写了代码。**

3. **共识已经形成：7 家在 8 条关键判断上完全收敛**（见 §五）。这是本轮最大的收获——比第一轮我"一家之言"的定案可信度高一个量级。

4. **分歧也有，而且是真的**：上下文重置激进度、完成检测信号阈值、以及**「到底要不要自研」**（元宝2 独树一帜说"可以直接用 MAF，无需自研"）——需要你拍板（见 §六）。

5. **我把「文件收不全」的根因链用代码实证钉死了**（见 §七），结论**比两份交付说得都更严重**：
   - **PDF / 图片 / 其他格式从来没上传过内容**——AI 收到的是 `[PDF文件: xxx]` 一行字。所谓"偶尔收不到"，对这几种格式而言是**永远收不到内容**。

   - 元宝2 的"根因是 sleep(3000) 时序"**覆盖面太窄**，只命中"txt 且总长 >4000 字"这一条窄路径。

6. **七家都没说的两个盲点**（见 §八）：**同质化坍塌**（9 个 AI 收到同样输入 → 回答趋同 → 会议退化成 9 个复读机）与**同一指纹下 9 账号本身就是最大风控特征**。

### 1.2 核实后的正确事实（一手来源）

来源：**Microsoft Learn** `agent-framework/user-guide/workflows/orchestrations/group-chat`（本轮直接拉取官方页面）

> "Group chat orchestration models a collaborative conversation among multiple agents, coordinated by an orchestrator that determines speaker selection and conversation flow."

- **Group Chat 是 MAF 的一等编排模式**，采用星型拓扑（orchestrator 居中），官方提供 C# / Python / Go 三种完整示例。
- `GroupChatBuilder` 支持**三种**发言者选择策略：

| 策略 | 参数 / 类 |
|---|---|
| Round-robin（轮询） | `round_robin_selector`（Python）/ `RoundRobinGroupChatManager` |
| Agent/LLM-based（智能选择） | `orchestrator_agent`（用一个完整 Agent 做选择器） |
| Custom logic（自定义） | `selection_func` / 自定义 `GroupChatManager` |

- 微软 2026-07-08 公告：Sequential / Concurrent / Group Chat / Handoff / Magentic 五种编排模式在 **Python 与 .NET 双双达到 1.0 稳定**。

### 1.3 正确的二分（这句话是关键）

| 被退役的 | 没被退役的 |
|---|---|
| **AutoGen 0.2 的涌现式 `GroupChatManager`**（谁说话、何时结束，全靠消息传递长出来；微软认为"在生产中难以推理"） | **Group Chat 这个能力本身** |

> **Group Chat 不是被删掉，而是被重建在图式 Workflow 引擎之上，变成「受控群聊」。**

### 1.4 裁决不变，理由更换

> **仍然 Phase 0–3 不引入 MAF 作运行时——但理由不能再是"它不能"，因为它能。**
> 正确理由 = **工程边界**：① 执行层已在 Electron/Node（9 webview + 9 partition + CDP 全在 Node 侧）；② MAF 无 JS/TS 一等实现（Discussions #6181），引入即 Python sidecar + 进程管理 + 打包运行时；③ 真正瓶颈（完成检测 / 附件握手 / 失败隔离）一个都不需要编排框架。

### 3.6 豆包2 —— 工程叙述最完整，但踩了 2 个硬技术错误

**优点**：架构图最清晰、分期路线图（Phase 0–4 含周期预估）、验收标准表、风险应对分 4 类（含"拟人输入：模拟打字速度逐字输入"）。

**硬错误 1：`session.fromPartition()` 的第二个参数是无效 API**
```js
const sess = session.fromPartition('persist:agent-deepseek', {
  cache: true,
  path: path.join(PARTITION_ROOT, 'agent-deepseek')   // ❌ 不存在这个字段
});
```
Electron 的 `fromPartition(partition, options)` 的 options **只支持 `cache`**；**partition 的存储位置由 `userData` 决定，不能自定义 path**。这段"复用登录态"的核心代码**不可用**。
→ 正确做法：设 `app.setPath('userData', <原 DeepSeek Harness 目录>)`（或用 `--user-data-dir`），partition 会自动落在其下。

**硬错误 2：`/deep/` 深度选择器早在 2018 年就被 Chrome 移除**
> "使用 CDP 的 `/deep/` 深度选择器"
→ `/deep/`（及 `>>>`）在 Shadow DOM v1 标准化时被废弃并从 Chrome 移除。正确做法是 Hy4 给的：**preload 注入 + 递归 `observe(shadowRoot)`**。

**硬错误 3（不算错但是减分）：关键实现全部省略**
```js
_pollSelector(check, cb) { /* 实现略 */ }
_observeStable(selector, ms, cb) { /* 实现略 */ }
_cleanup() { /* 清理轮询与观察者 */ }
```
→ 而 `_observeStable` **恰恰是"DOM 稳定"信号的核心**，也是我在 Phase 0 踩过的坑（起手即真是"页面本来就静止"）。省略它 = 把最容易错的地方留白。

### 3.7 谷歌搜索2 —— 最热闹，也最不严谨

**致命问题：它继承了我的错误前提**
> 开篇第一句：「收到这份深度评审和定案文件（彻底点破了微软 MAF 设计掉会话式 GroupChat 的核心痛点 [1]）」
→ 它把我的错误当成了正确结论，并以此作为"已定的地基"展开。**错误的源头是我，扩散是它的。**

**代码有 3 个实证问题**：

1. **混入了引用标记 → 直接语法错误**：
```js
resolve({ status: 'timeout', data: '【系统提示：…】' }); [1]
```
`[1]` 被写进了代码行尾 → **这个文件根本跑不起来**。这说明它给的代码**从未被执行过**。

2. **`cleanup` 的 TDZ 陷阱**：
```js
const timeoutTimer = setTimeout(() => { cleanup(); ... }, timeoutMs);   // cleanup 引用在前
const cleanup = () => { ... };                                          // 定义在后
```
（`timeoutMs` 足够长时侥幸不炸，但这是写法缺陷。）

3. **会复现我在 Phase 0 踩过的"抓空回复"坑**：
它的完成判据是 `score >= 3 || (!hasStop && hasSend && text.length > 0)`，其中"文本无增长"计 1 分 —— 而**"AI 还没开始生成时页面本来就不动"**，于是 `stopGone + sendReady + 静默` 三信号齐活 → 判定完成，`text` 是空串。
（这正是 `meeting-lab` 用 `requireContent` 堵掉的 Bug 2。）

**但它的三个"下一轮问题"是真的有价值**（我保留进 §九）：
1. 9 浏览器同开的**反指纹与风控对抗**（`setUserAgent` / blink-features / 时间阻尼）
2. **Shadow DOM / iframe 的穿透监听性能对比**（`DOM.attributeModified` + `Runtime.evaluate` vs 定时 `executeJavaScript`）
3. **超长会话的上下文修剪**（20 轮后页面极卡；监控 DOM 节点数超标 → 导出纪要 → 清空对话 → 以系统消息样式重注入）

## 六、真分歧（需你拍板）+ 我的裁决建议

### 分歧 1：网页端上下文的**重置激进度**（三家策略完全不同）

| 方案来源 | 策略 | 激进度 |
|---|---|---|
| **豆包2** | 每轮开始前都 `resetSession()` 清空网页端，再注入完整会议纪要 | 🔴 最激进 |
| **Hy4-2** | 滚动压缩：`最近N轮原文(N=2) + 更早摘要`，累计注入 >6k token 或 `round%3==0` 才 reset | 🟡 精细 |
| **KIMI2** | 默认不动；只在"纪要超 3 轮"或"该 AI 答题跑偏"时**单点重置** | 🟢 最温和 |
| **元宝2** | `transcript` 只喂上一条发言，不喂全量历史 | ⚪ 另一种思路 |

**我的建议：Hy4 的公式 + KIMI 的触发条件**。
- 采纳 Hy4 的**注入公式**（它是唯一可执行的）；
- 但触发阈值用 KIMI 的**"跑偏才重置"**，而不是固定 `round%3`——因为**重置本身有代价**：它会抹掉该 AI 的前文记忆，重置后需要重新"热身"，而网页 AI 的热身成本是 5–30 秒/轮。
- **豆包的"每轮都清"不可取**：它把网页 AI 降级成了"无状态单轮 API"，你会同时失去"网页端自带上下文"这个免费优势，而每轮重新注入全量纪要反而更慢、更容易触发长度限制。
- **元宝的"只喂上一条"太薄**：会议讨论需要"谁在回应谁"的关系，只给上一条会丢掉多轮论证的链条。

### 分歧 2：完成检测的**信号阈值**

| 来源 | 判据 |
|---|---|
| 谷歌2 | 4 信号评分，`score >= 3` |
| 豆包2 | `signals.size >= 2` |
| Hy4-2 | 5 信号，`>= 2` |
| KIMI2 | `stopGone && sendEnabled` 为最强组合 |

**我的建议：不投票，用手里的**真**证据定。**
`meeting-lab` 已经用**可运行代码**回答了这个问题，并实测抓出两个必然误判：
- **`domStable` 起手即真** → "AI 还没开始生成，页面本来就静止" → 误判完成、抓到空串。**修法：`requireContent`（必须先看到非空回答）**。
- **`streamEnd` 跨轮闩锁** → 第一轮的信号污染第二轮，第二轮 0ms 内被判完成。**修法：每轮 `arm()` 清零**。

> **所以阈值不是"≥2 还是 ≥3"的问题，而是"哪些信号在什么前提下才有资格置真"的问题。** 只调阈值不堵这两个洞，什么阈值都会误判。
> **建议以 `meeting-lab` 的 `requireContent` + 每轮 `arm()` 为基线**，阈值用 `minSignals=2` 但**必须配合**这两个前提。
> ⚠️ **这条建议有可复核性**：那两个 bug 都带回归测试，且做过**变异测试**（把修复退回去，测试立刻失败）。

### 分歧 3：**到底要不要自研编排层**（新出现的分歧）

- **元宝2**：「你可以完全可以直接用 MAF 的 GroupChat，**无需自研**。」

**我的建议：坚持自研，但把元宝的这句话当成"验证过的备选"记下来。**
理由：你真正的瓶颈是 **WebAI 运行时的不可靠性**（完成检测 / 附件 ACK / 风控），**这三件事 MAF 一件都帮不上**；而引入 MAF 你要先付 Python sidecar 的全套成本。等 Phase 3 之后，如果你发现自己开始重复实现 checkpoint / 断点续会，**那时再按 GPT2 的 `OrchestrationPort` 换一个 MAF Bridge 实现**——成本比现在引入低得多。

## 八、七家都没说的两个盲点（我的补充）

### 盲点 A（产品级，我认为最重要）：**同质化坍塌**

七家都在谈**"怎么把消息送进去"**（握手、门闩、完成检测、上下文注入）——
**没有一家问：9 个 AI 拿到同样的输入，凭什么给出不同的话？**

- 如果 9 个网页 AI 收到**同一份纪要 + 同一个问题**，它们的回答会**高度趋同**（同一批基座模型、同一个问题、近乎相同的提示）。
- 结果：会议不是"9 个人开会"，而是 **"9 个复读机"**——你能看到 9 个格子，但信息熵只有 1 份。
- **这会直接掏空"9 人同框"的产品价值。**

**我建议的解法（成本极低，收益极高）**：
1. **角色分化**：9 个 AI 各给一个**显式人格/立场前缀**——例如「你是红队，只找漏洞」「你负责算成本」「你只谈合规风险」「你扮演最挑剔的用户」。**同一份输入 + 不同角色 = 真正的多视角。**
2. **差异化上下文**：轮询制会议里，给不同 AI 喂**不同的前文切片**（A 看 B 的结论、C 看 A+B 的分歧点）。
3. **分歧可视化**：会议面板不只列 9 个回答，而是**抽取共识/分歧矩阵**（谁同意谁、分歧点在哪）。这才是"9 人会议"相对"1 个 AI"的真实增量。

> 这一条不改任何架构，**只改一条 prompt 构造逻辑**，但决定了你的产品是"9 宫格演示"还是"真的会开会的系统"。

### 盲点 B：**同一指纹下 9 个账号本身就是最大风控特征**

- Hy4 / 豆包谈的是"错峰、限速、削峰"——这些是**流量层**的缓解。
- 但没人指出：**9 个账号跑在同一个 Electron 宿主、同一个 IP、同一套浏览器指纹、同一个 `userData` 目录下**，这本身就是"账号农场"最典型的特征。
- 反爬系统看的不是你的请求间隔，而是**设备指纹相关性**。
- **建议**：把这条当作**明确的已知风险**接受下来（这是"9 宫格可视化"的产品代价），而不是假装靠错峰就能解决。至少要做到：① 绝不做账号轮换/指纹伪造（Hy4 也这么建议）；② 出现验证码立即闭麦、交人工，不自动重试风暴；③ **风控风险要在 UI 上显性提示用户**，而不是静默失败。

### 盲点 C：**"9 份回答 × N 轮"的纪要容量没人算过**

- 9 个 AI 各回答 500 字 = 一轮 ~4500 字；20 轮 = ~90000 字。
- 共识第 6 条说"用 API 压缩"，但**没人给压缩的容量上限与触发时机**（只有 Hy4 给了 6k token 阈值）。
- **建议**：把"每轮结束产出轮纪要（≤300 字/轮）+ 每 5 轮做一次全局压缩"定为基线，并在测试台里加一条**纯逻辑用例**（不依赖浏览器就能算）。
