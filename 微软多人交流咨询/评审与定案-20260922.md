## 零、先说结论（TL;DR）

1. **地基事实：6 份回答里有 5 份的前提已经过期。** 微软 AutoGen 已于 2025-10 进入**维护模式**，官方明确写「新项目请改用 Microsoft Agent Framework」。只有 **GPT 那份**抓对了这一点。
2. ~~**但"最新"不等于"最合适"。** Agent Framework (MAF) 1.0 恰恰**刻意设计掉了** GroupChat 这种"会话式涌现编排"——而"9 个 AI 开会自由讨论"正是这个场景。**微软放弃的，正好是你要的。**~~
   → **⚠️ 本条已于第二轮修正，原判断错误。** 事实：**MAF 1.0 原生支持 Group Chat**（五大稳定编排模式之一，`GroupChatBuilder` 提供 round-robin / agent-based / custom 三种选择策略）。被退役的是**AutoGen 式涌现会话模型（`GroupChatManager`）**，不是 Group Chat 能力。**"最新"依然不等于"最合适"，但理由换了**：MAF 能表达 9 人会议，不用它是因为**执行层已在 Electron/Node，没必要付 Python sidecar 成本**。详见 §1.3 修正框与 §4.2 修正后的裁决二。
3. **各家最大的共同盲点：都假设要另起 Playwright 在 Python 里重造浏览器。** 而你的架构里 **Electron 已经控制着 9 个浏览器**，`Partitions/` 里躺着 9 个已登录账号，CDP 文件上传都已跑通。按多数方案重造，等于**产品倒退**（失去 9 宫格可视化）+ **要重新登录 9 个 AI**。只有 **GPT** 明确反对这条路。
4. **真正的缺口从来不是"编排框架"，而是**：① 回复完成检测（现在没有）② 附件先上传齐再发送的握手（这就是你文件收不全的根因）③ 会议消息模型与 per-AI 状态机（现在只有"加载中……"）。
5. **定案**：**抄 AutoGen 的编排模型，不引入它的运行时**。用 Node 在 Electron 侧实现 Meeting Core（贴合你"纯 Node、无编译"的项目铁律），WebAI Adapter 沿用你已有的分层。Phase 0 先做**独立测试台**验证三个关键不确定性，**不碰客户端一行代码**。

### 1.3 最关键的架构变化（这条决定选型）

> ## ⚠️ 本节已于第二轮（2026-09-22 晚）**修正——原文有事实错误**
>
> **错误陈述**：原文断言「MAF 1.0 刻意设计掉了 GroupChat」，「微软放弃的，正好是你要的」。
>
> **核实后的事实**（来源：Microsoft Learn `agent-framework/user-guide/workflows/orchestrations/group-chat`，本轮直接拉取官方页面验证）：
>
> - **MAF 1.0 原生支持 Group Chat**，它是一等编排模式。官方原文：*"Group chat orchestration models a collaborative conversation among multiple agents, coordinated by an orchestrator that determines speaker selection and conversation flow."*
> - `GroupChatBuilder` 明确提供**三种**发言者选择策略：**round-robin**（`round_robin_selector`）、**agent-based orchestrator**（`orchestrator_agent`，用一个完整 Agent 做智能选择）、**custom logic**（`selection_func` / 自定义 manager）。
> - 微软 2026-07-08 公告进一步把 Sequential / Concurrent / Group Chat / Handoff / Magentic 五种编排模式在 Python 与 .NET 双双定为 1.0 稳定。
>
> **"retired it on purpose" 的真正所指**：那句原文说的是——**AutoGen 0.2 的「隐式会话模型」**（`ConversableAgent` + `GroupChatManager`，控制流从消息传递中**涌现**）被设计掉了，因为微软认为涌现式控制流在生产中「难以推理（hard to reason about）」。即：
>
> | 被退役的 | 没被退役的 |
> |---|---|
> | 涌现式 `GroupChatManager`（谁说话靠聊天长出来） | **Group Chat 这个能力本身** |
>
> Group Chat 不是被删掉，而是**被重建在图式 Workflow 引擎之上，变成「受控群聊」**（显式 orchestrator + 可配置 selection）。
>
> **对裁决的影响**：**结论不变，理由必须换。** 仍然 Phase 0–3 不引入 MAF 作运行时，但**不能再写"MAF 不能表达 9 人会议"——它能**。正确理由是工程边界（见 §4.2 修正后的裁决二）。
>
> **教训（写给我自己，也是本轮最该记住的一条）**：上一轮我引用了一篇二手架构分析文章里的句子 "It retired it on purpose"，**没有核到这句话的完整上下文**，就把它放大成了"MAF 放弃了 GroupChat"，还写进了 TL;DR 当成核心卖点。这违反了"争议问题必须去官方源头核实"的铁律。**下文所有涉及该判断的段落均已加注修正。**

### 2.2 逐家点评

#### ① KIMI —— 「把网页 AI 伪装成一个 Model」

**方案**：实现 `ChatCompletionClient` 协议（只需两个方法），把 9 个网页 AI 各写一个 Playwright adapter 伪装成模型，`SelectorGroupChat` 做调度，调度器用 API 不用网页。

**优点**
- **落地成本描述最精准**：Autogen 的 `ModelClient` 抽象确实是"缝"——只要实现 `create()` 就能骗过整个框架，这是最轻的接入路径。
- **`page.expect_response("**/conversation**")` 抓网络响应流**：比解析 DOM 稳得多、快得多。这个技巧很多人想不到，是本方案最有价值的技术点。
- 明确指出**调度器不要走网页版**（延迟 5–30 秒/轮，做高频调度会卡死）——正确且重要。

**缺点 / 风险**
- **前提过期**：基于 AutoGen v0.4 / MAF 混谈，没意识到 AutoGen 已冻结。
- **"伪装成 Model"这个方向的隐患**：AutoGen 会按模型语义给 model 喂**完整 messages 历史**，而网页版**自带上下文**。结果是双重上下文叠加 → 上下文窗口加速膨胀 + 你自己也不知道网页端实际看到了什么。**伪装成 Model 看着轻，其实是把状态控制权让出去了。**
- adapter 示例代码里 `send` 用 `asyncio.to_thread` 包同步 Playwright —— 这会吃掉线程池，9 个 AI 串起来会很惨。

#### ② 豆包2.1TUBO —— 「继承 BaseChatAgent」

**方案**：`WebAIChatAgent(BaseChatAgent)`，实现 `on_messages` / `produced_message_types`，Playwright 浏览器池 + `RoundRobinGroupChat(max_turns=1)`。

**优点**
- **比 KIMI 更干净的接入点**：`BaseChatAgent` 是"Agent 级"抽象，不是"Model 级"。Agent 能自己决定怎么消化 messages（比如只取最近几轮 + 会议纪要），**避免了 KIMI 方案的上下文双重叠加问题**。这是本方案最大的隐性优势。
- 代码示例完整可读，`_wait_for_reply` 的"轮询消息数变化"思路直观。
- 提到 `stealth` 插件反检测、`user_data_dir` 复用登录、单 AI 失败降级"自动降级为文本摘要发送"——工程细节考虑到位。

**缺点 / 风险**
- **前提过期**（同 KIMI）。
- `_wait_for_reply` 用"消息数增加"判断完成 → **不可靠**：流式输出时消息节点可能在生成中就出现，会抓到半截回答。这是它自己埋的坑，而"完成检测"恰恰是整个系统最要命的地方。
- **`RoundRobinGroupChat` + `max_turns=1` 其实只实现了你现在的"广播"**，没有升级到真正会议。方案里把它叫"实现一发多收"，等于用大炮打了只蚊子。
- **`await page.wait_for_selector` 之类同步等待混在 async 里**，示例代码有 `page.fill` 未 await 的笔误。

#### ③ 谷歌搜索 —— 「Web-to-API 网关」

**方案**：FastAPI 建一个 OpenAI 兼容网关（`/v1/chat/completions`），把 9 个网页 AI 暴露成 `tongliao-01..09`，Agent Framework 里用 `ChatAgent` + `GroupChat` 消费。

**优点**
- **最有价值的干货：文件分发握手协议。** 原文：
  > 统一拦截：文件先上传到网关 → 触发 9 个网页的 `upload_file()` → **确保 9 个网页全部上传成功且解析完毕后，网关再统一放行"发送"指令。**
  
  这**正是你"发文件 9 个人偶尔收不到"的根因解法** —— 你现在是"上传 + 固定 3 秒 sleep + 发送"，没有握手确认。**这一条建议单独拿出来就是本次最有价值的产出之一。**
- **`reset_session` 机制**：散会后驱动 9 个网页刷新/新建对话，清空网页端上下文。这是长会议不崩的关键，其他人没提。
- **优雅降级**：`asyncio.wait_for(timeout=30)`，超时返回「【系统提示：该AI由于网络原因暂时闭麦】」，保证会议继续。这个"闭麦"设计很贴合会议语义。
- **文件链路**：指出"等 DOM 加载完"才发，避免文件丢失。

**缺点 / 风险**
- **前提混乱**：把 AutoGen 和 Agent Framework 的 API 混着写（`from agent_framework.conversations import GroupChat` 这种导入在 MAF 里并不存在），**代码不可直接跑**。
- 引入 HTTP 网关这一层在**桌面单机场景是多余的**：多一层端口占用、token、localhost race、CORS。你有 Electron IPC，不需要绕 HTTP。
- 未处理"网页版自带上下文"与"网关无状态"的冲突。

#### ④ Gemini —— 「代理模拟器」

**方案**：Playwright driver + 自定义 `ConversableAgent`，重写 `receive`/`send`。

**优点**
- **提出了一个很关键的二分法**：
  - **方案 A：托管模式（Manager-Led）** —— Manager 决定谁说话，播给其他 8 个
  - **方案 B：广播模式（Broadcast-Led）** —— 你现在这样，9 个同时收
  
  这个区分**直接定义了你的升级路径**：你现在是 B，目标是 B→A 的混合。**是六份里对这一层抽象讲得最清楚的一份。**
- 技术栈对比表清晰；Roadmap 的"MVP 先做一个"务实。

**缺点 / 风险**
- **内容最泛、最短（78 行）**，代码都是片段，没有可直接落地的实现。
- 术语混用（一会儿 `ConversableAgent`，一会儿 `UserProxyAgent`，一会儿自定义 Agent），对 AutoGen 版本不敏感。
- 提到 `BeautifulSoup` 解析 DOM——**方向错了**，网页是动态渲染的，BS4 拿不到渲染后内容（应该是 Playwright 的 selector / CDP）。

#### ⑤ GPT —— 「MAF + Electron 拥有浏览器」★ 最优

**方案**：三层拆解（AutoGen 借思想 / MAF 做编排内核 / Magentic-UI 借浏览器操作思想），双进程架构（Electron 管浏览器 + Python 管编排），**IPC/JSON-RPC 而非 HTTP**，Meeting Core 状态机 + Attachment Manager + SpeakerStrategy。

**优点（这一份明显高出一个层级）**
- ✅ **唯一前提正确**（*第一轮*时）：明确指出 AutoGen 已维护模式、新项目应用 MAF，并给出迁移指南引用。**第一轮里事实层面唯一站得住的。**
  - → **第二轮更新**：7 家中已有 6 家主动纠正前提（GPT / KIMI / Hy4 / 元宝 / 谷歌 / 豆包），"唯一"已不成立。
  - ★ **更有意思的是：第二轮反过来是 GPT 帮我纠正了一个我自己搞错的事实**（MAF GroupChat，见 §1.3）。这说明多轮咨询是有价值的——**它不只修正被问者的错误，也修正提问者的错误。**
- ✅ **唯一抓住架构本质**：
  > 不要让 Python Agent Framework 直接操作网页。应该让 **Electron Main Process** 管理所有 Web AI 页面。
  > Electron = 「手和眼睛」；Microsoft Agent Framework = 「思想和会议调度」
  
  这是**唯一与你现有架构（Electron + webview + partition）对齐的判断**。其他五家都默认要另起 Playwright 重造，等于把你的产品退化成一个无界面的 Python 脚本。
- ✅ **唯一发现你已有的资产**：指出 `@deepseek-ai/dsh-client-file-upload` 已存在，不要另造"超级文件上传系统"。
- ✅ **文件方案最专业**：
  - 建立 **Meeting Attachment Manager**，一个文件 = 一个 `attachmentId`
  - **CDP `DOM.setFileInputFiles`** 直接塞文件，不模拟"点上传→文件选择器→输路径→确定" —— 而你的代码里**已经这么干了**，他识别出来了
  - 拖拽**只在会议层接受一次**（Meeting Drop Controller），不让 9 个 webview 各自抢 DropEvent —— **这条精准命中你"偶尔收不到"的结构性病因**
- ✅ **"完成检测器"多信号联合**（Stop 按钮消失 + Send 恢复 + DOM 稳定 N ms + 网络流结束），明确指出不能 `sleep(5秒)`。
- ✅ **明确的技术裁决清单**：不引入旧 AutoGen（因已转向）、不把 MagenticLite 当底座（因官方 limitations 明确列了"浏览器内上传本地文件"不支持）、第一阶段不上 A2A（都在本机，没必要加网络协议层）、第一阶段不上 AG-UI（DSH 自己已有通信基础）。
- ✅ 每个论断都带官方链接引用（24 条参考文献），可核查。
- ✅ 指出 **Magentic-UI 的 `limitations.md` 明确把"浏览器内上传本地文件"列为当前限制** —— 直接判了"拿 MagenticLite 当底座"这条路死刑。这是个很有价值的反证。

**缺点 / 风险**
- **方案最重**：双进程 + IPC + 9 个 Phase，第一版就要引入 Python sidecar。对"先单独测试"来说门槛偏高。
- 对 **MAF 的编排抽象是否适合"9 人会话式会议"没有质疑** —— 他正确地指出"该用 MAF"，但没深挖"MAF 已经把 GroupChat 设计掉了"这个反向风险（这正是本报告要补的一刀）。
- Phase 划分偏宏观，缺少"哪三个不确定性必须先验证"的收敛。

#### ⑥ Hy4 Preview —— 「Web2API 网关 + 里程碑」

**方案**：`web2api.py`（FastAPI）把 9 个网页包成 `tongliao-01..09`，`AssistantAgent` + `GroupChat`，`round_robin` → `auto` 两阶段，M1–M5 里程碑。

**优点**
- **里程碑划分最清晰**（M1 打通 1 个 → M2 广播 → M3 稳定性 → M4 真开会 → M5 产品化），可直接当排期模板。
- 明确指出 **`cache_seed=None` 必须关缓存** —— 这是个很实际的坑：AutoGen 默认会缓存 LLM 响应，导致同样的 prompt 返回旧答案、根本不会真的去请求网页。**这条是只有踩过的人才知道的坑。**
- 提出"网页 AI 不知道别人说了什么，必须在 prompt 里手动喂会议记录"，并给了 prompt 模板 —— 切中要害。
- 立场正确：**"你的 9 个网页 AI 是执行层；AutoGen 是会议大脑，你不需要把网页 AI 改成 API"**。
- 提到浏览器扩展桥（MV3 + `all_frames: true`）作为备选路径，视野较全。

**缺点 / 风险**
- **前提过期**（基于 AutoGen 0.2.x/0.4）。
- **`page.send_and_wait()` 是同步阻塞**（`time.sleep(1)` 轮询），却在 `@app.post` 的 async 端点里直接调 —— **会阻塞整个 FastAPI 事件循环**，9 个 AI 并发时直接卡死。这是个会真实爆炸的 bug。
- 用的完成检测是"连续 3 次文本相同" —— 比豆包的"消息数增加"好，但流式输出时段落可能短暂稳定，仍会误判。
- 示例模型名用了 `deepseek-chat`（官方 API 模型名）去连本地网关，混淆了"网页版"和"API 版"两条路。

## 四、最终定案

### 4.1 一句话方案

> **Electron 管"手和眼睛"（9 个网页 + 附件 + CDP），Node Meeting Core 管"会议规则"（谁发言、何时停、状态机、完成检测），Adapter 管"翻译"（DOM ↔ 统一消息）。编排模型抄 AutoGen，运行时不引 AutoGen，也不引 MAF。**

### 4.2 三个关键裁决 + 理由

#### 裁决一：**不引入 AutoGen 作为依赖**

理由：
1. 已进入维护模式，官方明确"新项目不要用"
2. **2026 Q3 主要 API 提供商会弃用 AutoGen 依赖的 legacy callback patterns** —— 现在开工就是接一个已知有期限的雷
3. 它是"实验性遗产"，你的项目是长期维护的产品

#### 裁决二：**Phase 0/1 也不引入 MAF（但保留升级路径）**

这是本次最需要解释的裁决，因为**反直觉**（GPT 说要上 MAF，而 MAF 是最新的）。

理由有三层：

**（1）场景错配（⚠️ 本条已于第二轮重写，立足点换掉、结论不变）**

> **原表述已废止**：~~"MAF 1.0 刻意把 GroupChat 换成确定性 graph workflow，官方原话 retired it on purpose"~~ → 事实错误（见 §1.3）。
>
> **修正后的错配论证**：
> - MAF 的 Group Chat 是**受控群聊**：跑在图式 workflow 引擎上，带 checkpoint、类型边、显式 orchestrator 与 selection 函数。
> - 它的设计假设是**参与者可靠** —— 可重试、可重放、可恢复。这套假设对 **API 模型**完全成立。
> - 而你的参与者是 **9 个网页版 AI**：5–30 秒/轮、随时弹验证码、随时静默失败，**且网页端对话状态无法快照与回滚**（这是致命的一条：checkpoint 对你的参与者无意义）。
> - **框架替你解决的（重试 / checkpoint / 恢复）恰好是你这里最难标准化的部分** → 收益落不到实处，Python sidecar 的成本却要实付。
> - **一句话**：不是"MAF 不能开会"，而是 **"MAF 的可靠性假设与网页端现实不符"**。

**（2）工程成本**
- MAF 是 Python/.NET；你的项目铁律是 **"纯 Node.js CommonJS，无编译步骤，npm install && npm start 即可运行"**（`PROTOCOL.md` 明文）
- 引入 Python sidecar = 进程管理 + IPC 协议 + **打包分发 Python 运行时**（你的原则是"所有依赖打包进软件，不做运行时下载"）

**（3）Phase 0 要验证的根本不是编排**
- 三个待验证的不确定性（完成检测 / 附件握手 / 并发失败隔离）**没有一个需要框架**
- 先引框架 = 在流沙上盖楼

**保留的升级路径**：Meeting Core 与编排层之间用**标准协议**（§4.4）隔离。将来若需要 MAF 的 **checkpointing / durable execution / 复杂 human-in-the-loop**（比如"某 AI 出验证码，整场会议暂停等你点一下再续"——GPT 方案第四十节讲的那个），**换掉编排层即可，不动 Adapter、不动 Electron、不动 UI**。

#### 裁决三：**抄 AutoGen 的编排模型（不抄实现）**

具体"抄"什么：

| 抄什么 | AutoGen 概念 | 你的 Node 实现 |
|---|---|---|
| 发言策略 | `RoundRobin` / `Selector` / `Manual` | `SpeakerStrategy` 策略模式（round_robin / broadcast / llm_selector / chairman） |
| 终止条件 | `TextMentionTermination` / `MaxMessageTermination`（可 AND/OR 组合） | `TerminationPolicy` 组合器 |
| 轮次抽象 | `Turn` / `Round` | `MeetingMessage{turn, round}` |
| 并发扇出/扇入 | `Concurrent`（fan-out/fan-in） | `Promise.allSettled` + 单点隔离 |
| 主持人 | `GroupChatManager` | `SpeakerManager`（用 API，不用网页版） |

**核心价值不在框架代码（那不过几百行），在于它踩过的坑变成的抽象。**

### 4.4 三个必须先立起来的东西

#### （1）会议消息模型（取代"各 webview 自己管状态"）

```typescript
interface MeetingMessage {
  id: string;              // msg_xxx
  meetingId: string;
  senderType: 'user' | 'agent' | 'system';
  senderId: string;        // 'human' | 'deepseek-web' | ...
  content: string;
  attachments?: AttachmentRef[];
  round: number;           // 第几轮
  turn: number;            // 轮内第几位
  timestamp: number;
  status: 'pending' | 'streaming' | 'completed' | 'failed' | 'timeout';
}

interface AttachmentRef {
  attachmentId: string;    // att_xxx（一个文件一个 id，9 个 AI 共用）
  name: string; size: number; mime: string;
  sha256: string; localPath: string;
}
```

**意义**：会议状态**独立于网页**。刷新、崩溃、重启、掉线、加第 10 个 AI —— 会议记录都还在。

#### （2）附件握手协议（解决"文件收不全"的根因）

**现在（错的）**：
```
用户拖文件 → 各自处理 → upload → sleep(3000) → 发送
                                    ↑ 猜的，没确认
```

**改成（对的）**：
```
用户拖文件
   ↓
【会议层统一接管】Meeting Drop Controller（宿主 document 只接一次）
   ↓
AttachmentBus 登记 → attachmentId + 落盘 + sha256
   ↓
fan-out 到 9 个 Adapter，每个执行 uploadFiles(att)
   ↓
★ 每个 AI 回报 ACK（DOM 出现附件卡片 / 上传进度 100%，带超时+重试）
   ↓
【门闩】waitForAllUploadACK(timeout)
   ↓  全部 ACK（或超时降级为"文本摘要走"）
才统一放行 sendText()
   ↓
9 个 AI 同时开始回答
```

**这一条直接解决你"9 个人偶尔收不到"的问题** —— 从"猜 3 秒"改成"等到 ACK"。

#### （3）完成检测器（多信号联合，不能固定 sleep）

```
信号 A：Stop generating 按钮消失
信号 B：Send 按钮恢复可用
信号 C：assistant 消息节点内容连续 N ms 无变化（MutationObserver）
信号 D：流式网络请求结束（靠 CDP Network 域）
信号 E：页面生成中标志位消失

判定：满足 ≥ 2 个信号 → COMPLETED
      超过 timeoutMs → TIMEOUT（标记"闭麦"，会议继续）
```

**这是全系统稳定性的命门**，也是 6 份方案里讲得最浅、而实际上最要命的地方。

## 六、给外部 AI 的下一轮咨询问题

拿到本方案后，建议带这几个问题出去问（这些是真正还没共识的）：

1. **9 个网页 AI 的"上下文边界"该怎么定？** 网页端自己记历史，你又要喂会议记录，两套上下文怎么分工？什么时候该 `new_conversation()` 重置？有没有成熟做法（而不是靠"摘要注入"这种土办法）？
2. **完成检测在 9 个 AI 上都用"多信号联合"，各家的信号该怎么取？** 特别是那些用 iframe / Shadow DOM 的站点（豆包、通义），MutationObserver 能穿透吗？有没有比 DOM 更稳的方案（比如 CDP Network 域抓流结束）？
3. **会议记录注入的压缩策略**：9 个 AI × 多轮，会议记录会指数膨胀。用哪个模型做会议纪要压缩最划算？压缩时机（每轮结束？超阈值？）怎么定？
4. **MAF 的 graph Workflow 能不能表达"动态点名发言"**（由主持人 LLM 决定下一个谁说话）？如果能，Schema 长什么样？如果不能，是不是该等 AutoGen 的社区 fork（AG2）？
5. **反爬与限速的工程实践**：9 个账号同 IP、同时段高频调用，实际封号概率和缓解手段（指纹、错峰间隔、账号轮换）怎么做才不越线？
