# 咨询案（第五轮）· 多 AI 会议系统：模式与角色体系的场景定义

> 这份稿子是给**外部 AI** 读的，自包含，不需要任何前置上下文。
> 提问者是一位中文技术负责人，正在做一个「多个 AI 网页版/API 同场开会」的系统（代号**通辽会议**）。
> 本轮他要解决的核心疑问是：**哪些真实工作流该对应哪些"会议模式"，以及现有模式设计哪里不合理。**

## §1 一句话现状

系统目前有 **8 个会议模式** + **15 个角色** + **6 个角色组**。
- **模式** = 阶段序列 + 每阶段"看什么上下文" + 终止判据。
- **角色** = 注入给某个 AI 的「认知职能 + 互斥输出约束 + 格式约束」。
- **选角** = 先按能力门槛一票否决，再在够格的人里按适配分加权随机（同一个随机种子 = 同一套编制）。

已经跑通：3 个网页版 AI（DeepSeek/ChatGPT/Gemini，走 Electron webview 自动收发）+ 2 个 API 席位（deepseek-chat / gemini-3.6-flash），5 席可同场开会。
已实测：两轮真实对辩 8/8 项通过（第二轮里每个 AI 的 prompt 确实含对方立论、不含自己的）。

## §2 现有 8 个模式（逐条）

**读法**：`切片` 是这个阶段的 AI 会被注入什么上下文。切片是本系统最核心的机制 ——
**给不同的发言者喂不同的前文，比"换角色口吻"更能制造真实差异。**

切片取值：`TASK` 只看本轮任务 / `MATERIAL` 只看待审材料 / `OTHERS` **只看别人的发言（不含自己的）** / `ALL` 看全部发言 / `CRITIQUES` 只看上一阶段批评清单 / `DRAFT` 只看当前草稿。

---

### 1. 广播 `broadcast`
- **什么时候用**：你只想听同一件事的多个不同角度，不需要 AI 之间对话。
- **例子**：「这个方案有什么问题？」——想看 9 个 AI 各给一份独立意见。
- **别用**：需要 AI 互相反驳、需要自动收敛出结论时。
- **产出**：N 份并行的独立意见（互不影响，适合当第一轮素材）。
- **阶段**：`回答`（全员 / 并行 / TASK）—— 就一个阶段。
- **终止**：单趟，跑完即止。
- **成本**：**N 次调用，每次只注入任务。最低档。**
- **模型要求**：推理 ≥ 3。

### 2. 共同审阅 `review`
- **什么时候用**：你手上有一份**具体材料**（文档/代码/方案/合同），要它被多角度把关。
- **例子**：丢一份需求文档进去，事实核查员查数据漏洞、用户代言者挑看不懂的地方、书记员抓遗漏。
- **别用**：开放性问题（没有具体材料可审）。
- **产出**：审阅结论 + 分歧点清单 + 被忽略的遗漏项。
- **阶段**：`独立审阅`（全员 / **并行** / MATERIAL）→ `交叉质证`（质证类席 / 顺序 / OTHERS）→ `归并结论`（收敛类席 / 顺序 / ALL）
- **终止**：单趟。
- **成本**：**中高**。第一阶段 N 次（各注入材料）；第二阶段每人注入**其他所有人的审阅意见**；第三阶段注入全部。
- **模型要求**：推理 ≥ 4、结构化 ≥ 4。
- **关键设计**：**第一阶段必须并行**——若让 AI 先看到别人的意见，后面会全部向第一个发言者收敛（锚定效应），最终 N 份回答互相抄。

### 3. 协助 `assist`
- **什么时候用**：你自己是执行者，需要的是「能直接照做的方案」，不是讨论。
- **例子**：「我要把系统接入某框架，具体怎么落地？」——要步骤，不要综述。
- **别用**：纯粹想了解一个概念（那是普通对话，不用开会）。
- **产出**：可执行步骤 + 每步前置条件 + 失败了怎么回退。
- **阶段**：`各出方案`（建设类席 / 并行 / TASK）→ `会诊挑错`（质证类席 / 顺序 / OTHERS）→ `收敛执行`（收敛类席 / 顺序 / ALL）
- **终止**：单趟。
- **成本**：**中**（约 3~N 次）。
- **模型要求**：推理 ≥ 4、结构化 ≥ 5。

### 4. 反复修正 `iterate`
- **什么时候用**：你**已经有了一版产出物**（文案/方案/代码），要反复挑错改到挑不出新问题。
- **例子**：一份给客户的方案：红队挑错 → 修订 → 再挑 → 再改，直到某轮挑不出新东西自动停。
- **别用**：还没有第一版的时候（先跑「协助」拿到初稿）。
- **产出**：收敛后的终版 + 完整的批评清单。
- **阶段**：`挑错`（质证类席 / 并行 / DRAFT）→ `修订`（建设类席 / 顺序 / CRITIQUES）→ **回环**
- **终止**：`no-new-critique` —— **「本轮批评集合相对上一轮无新增」**（纯集合运算，可单测），上限 5 轮。
- **成本**：**中，且自带省钱机制**（判停是自动的，不会空转）。
- **模型要求**：推理 ≥ 5。
- **关键设计**：判据必须做**文本规范化**（去空白标点 + 截前 60 字），否则"换个标点"就算新问题 → **永不停机**。

### 5. 交叉辩论 `debate`
- **什么时候用**：有两个（或几个）方案**难分高下**，你要看它们正面对撞的结果。
- **例子**：「用框架 A 还是自研？」「上云还是自建？」
- **别用**：问题只有一个正确答案时（那是浪费，直接用「协助」）。
- **产出**：各方的最强论证 + 各自的致命弱点（**不是**折中意见）。
- **阶段**：`立论`（全员 / 并行 / TASK）→ `对辩`（全员 / 顺序 / OTHERS）
- **终止**：单趟。
- **成本**：**中高**（2N 次，对辩阶段每人注入 N-1 份）。
- **模型要求**：推理 ≥ 4、中文 ≥ 4。
- **关键设计**：对辩阶段每人**只看别人的、不看自己的**——防止 AI 复述自己上一轮的话。

### 6. 专家会诊 `panel`
- **什么时候用**：问题复杂，需要每个专家**看到前面所有人的发言**再往下深挖。
- **例子**：疑难故障排查、复杂架构决策 —— 第一个人开头，后面的人接着往深里挖。
- **别用**：**人多的时候**（串行会让总时长线性增长，9 人很慢）。
- **产出**：逐层加深的分析链 + 最后汇总结论。
- **阶段**：`会诊`（全员 / **顺序** / OTHERS）→ `归并结论`（收敛类席 / 顺序 / ALL）
- **终止**：单趟。
- **成本**：**最高档，O(N²)**。第 k 个发言者要注入前 k-1 份发言，总上下文 ≈ N²L/2。
- **模型要求**：推理 ≥ 4、长文 ≥ 4。
- **关键设计**：越到后面上下文越长，**挑"长文承载"强的模型坐后排**。

### 7. 主席点名 `chairman`
- **什么时候用**：你希望有个**主持人**像真人开会那样，抓住分歧点追问到底，而不是平均分配发言。
- **例子**：评审会、复盘会：主持人看到 A 和 B 意见相反，就点他们俩各自说清理由。
- **别用**：没有明确分歧点的开放性咨询。
- **产出**：被追问到底的分歧结论 + 谁在哪个点上无法自圆其说。
- **阶段**：`点名发言`（**由主持人动态点名** / 顺序 / OTHERS）→ 回环
- **终止**：`no-new-question`（本轮没有新分歧点就停）。
- **成本**：**不确定（这是问题，见 §5.3）**。每轮 = 1 次 API 判停 + 1~2 次被点名者发言，轮数没有硬上限。
- **模型要求**：推理 ≥ 5、稳定性 ≥ 5。
- **关键设计**：**主席必须走 API 通道**——它每轮都要即时判断，网页版的渲染延迟会把一轮拖到分钟级。

### 8. 分头攻克 `divide`
- **什么时候用**：任务**能被拆开**，且拆开后各块互不依赖（这是前提）。
- **例子**：「把这 9 个模块的接口文档各写一份」——每人一个模块，最后汇总。
- **别用**：任务不可拆分时（拆了会各说各话、拼不起来）。
- **产出**：N 份子任务成果 + 一份拼装好的完整产出。
- **阶段**：`拆分任务`（收敛类席 / 顺序 / TASK）→ `分头攻克`（全员 / **并行** / **TASK**）→ `汇总拼装`（收敛类席 / 顺序 / ALL）
- **终止**：单趟。
- **成本**：**中**（1 + N + 1 次）。
- **模型要求**：结构化 ≥ 4。
- **关键设计（我的怀疑，见 §5.2）**：★ 前提是任务真的可拆。拆不开硬拆 = 9 份互不相干的半成品，拼装时全废。

## §3 现有 15 个角色（逐条）

**设计三原则**（写在代码注释里的）：

- **A. 给「认知职能」，不给「人格腔调」。** ✅「只找漏洞，必须列编号清单」 ❌「你是一个脾气火爆的评审」。前者制造真实视角差异，后者只制造语气噪音。
- **B. 每个角色必须有一条互斥输出约束**（只看 X / 只做 Y / 禁止 Z）。角色不是形容词，是**输出内容的边界**。
- **C. 每个角色带一条轻量格式约束。** 格式差异本身就是反趋同手段：即使两个 AI 观点撞了，一个出编号清单、一个出成本表，读起来也不像复读机。

**分四类：**

### 质证类（挑错、找风险、核事实）
| 角色 | 职责与硬约束 |
|---|---|
| **红队** | 只找漏洞、边界条件、隐藏风险和反例。禁止总结、禁止附和、禁止说"总体不错"。必须给 ≥2 个具体反例或失败场景，编号清单输出。 |
| **事实核查** | 逐条检查事实性断言，指出哪些无依据、哪些是推测被当成结论。**禁止发表自己的方案**。格式：每条一行「断言 → 有据/无据/存疑 → 理由」。 |
| **合规审查** | 只谈数据安全、隐私、法务、平台政策与账号风险。**禁止讨论技术实现优劣**。无风险就直接说"此项无合规风险"，不要展开。 |
| **反方** | 无论主流意见是什么，只论证它可能错在哪，站对立面。**禁止附和任何已有结论**；但不为反对而反对——必须给出"最可能错在哪个假设"的具体推理。 |

### 建设类（给方案、算账、落地）
| 角色 | 职责与硬约束 |
|---|---|
| **架构师** | 只谈技术可行性、可扩展性、可维护性、演进路径与耦合边界。**禁止谈成本、禁止谈排期、禁止给市场判断**。格式：先一句结论，再列 2–4 条技术依据。 |
| **成本分析师** | 把每个主张折算成钱/时间/人力，指出谁是主要成本项。**禁止评价方案好坏、禁止给技术建议**。能用数字的一律用数字。格式：极简表格（项目/估算/假设）。 |
| **执行步骤** | 把结论翻译成可照做的步骤，标出每步前置条件与失败回退。**禁止讨论战略与理念**。格式：有序列表「动作 → 前置条件 → 失败怎么办」。 |
| **数据核算** | 只给能量化、能验证的结论。无法量化的主张直接标注"不可量化，需补充数据"。**禁止写段落**，只输出条目 + 数字 + 口径。 |

### 代表类（替不同立场的人说话）
| 角色 | 职责与硬约束 |
|---|---|
| **用户代言** | 站在使用者角度挑体验毛病，指出哪里看不懂、哪里会让人放弃。**禁止用技术术语**，全程大白话。确实没问题就说"这次没问题"，不要硬凑。 |
| **产品经理** | 只谈优先级与取舍——做什么、不做什么、先做什么。**禁止写代码、禁止谈技术细节**。格式：必做/可做/不做三栏清单，每项一句理由。 |
| **新人视角** | 提最朴素、最基础、最容易被专家忽略的疑问，指出讨论中**默认成立但从未被验证的前提**。**禁止展现专业深度、禁止给方案**。只提问，每问一行。 |

### 收敛类（把发散的观点收成结论）
| 角色 | 职责与硬约束 |
|---|---|
| **主持助理** | 把本轮观点收敛成「已达成共识 / 仍有分歧 / 待决问题 / 下一步动作」四块。**禁止引入任何新观点，只做归并**。有分歧必须点名是哪两方在哪个点。 |
| **书记员** | 抓细节与遗漏——谁说了但没被回应、哪些结论缺依据。每条发言结尾必须附「我注意到的一点：…」。**禁止复述已有结论**。 |
| **基准与会者** | 只给主流、稳妥、可被多数人接受的判断，作为全场观点基准线。**禁止提出激进方案**。必须明确说出你不同意谁、为什么。 |
| **检索员** | 只返回与议题最相关的 3 条事实或资料线索，每条一句话。**禁止长篇论述、禁止给建议、禁止承接前文闲聊**。凑不满 3 条就给 2 条，不编造。 |

### 角色组（6 套，决定这场会有几把椅子、每把是什么职能）
| 角色组 | 席位数 | 组成 |
|---|---|---|
| 三人组（建设/质证/收敛） | 3 | 架构师、红队、主持助理 |
| 三人审阅（事实/体验/归并） | 3 | 事实核查、用户代言、书记员 |
| 风险审查五人组 | 5 | 红队、合规审查、事实核查、执行步骤、主持助理 |
| 技术选型七人组 | 7 | 架构师、成本分析师、执行步骤、红队、数据核算、产品经理、主持助理 |
| 产品评审九人组 | 9 | 架构师、成本分析师、执行步骤、红队、合规审查、事实核查、用户代言、产品经理、主持助理 |
| 发散九人组 | 9 | 红队、反方、事实核查、合规审查、新人视角、用户代言、数据核算、架构师、书记员 |

每个角色都带一份**能力要求画像**（权重 + 硬门槛）。举例：

```
红队       权重{推理5, 稳定性3, 结构化3, 长文3}   门槛{推理≥4}
书记员     权重{速度5, 结构化4, 中文4}            门槛{速度≥4}
主持助理   权重{结构化5, 推理4, 稳定性5, 速度3}   门槛{结构化≥4, 稳定性≥4}
检索员     权重{检索5, 速度4, 中文3}              门槛{检索≥4}
```

**门槛的取值哲学**：宁可让位子空着降级，也不要让不适配的模型硬坐。
例：主持助理稳定性门槛 4 分——它的产出是"全场结论"，一个会中途弹验证码的模型当收敛者，等于整场会白开。

**选角公式**：`fitScore = Σ(能力×权重) / Σ(5×权重) × 100`，任一门槛不满足即否决。

## §4 用户提出的两个真实工作流（他的原话）

### §4.1 工作流 A：「写不出想要的效果时，出去问一圈再回来挑」

**用户原话**：

> 我现在经常的办法就是：程序写到某个功能写不出想要的效果，或者想调整的调整不过来，此时我就会让 AI 写一个咨询案，那一份咨询案问所有 AI，他们回答后，我复制回来给我的 AI 助手，最终选择优秀的尝试，还不行就再进行一轮，直到满意为止。这样的功能是什么模式？

**我把它拆成 7 步**：

| 步 | 动作 | 现有模式能接吗 |
|---|---|---|
| 1 | 遇到卡点（改不出想要的效果） | — |
| 2 | 先写一份「咨询案」（问题描述 + 相关代码 + 期望效果） | ✘ 无此能力 |
| 3 | **把咨询案同时问所有外部 AI**（他的习惯是一次问 3~4 家：元宝 / 谷歌 / 千问 / DeepSeek） | ✅ 近似 `broadcast` |
| 4 | **人工复制**各家回答，带回给主 AI 助手 | ✘ 无此概念（他是手工中转！） |
| 5 | **从 N 个答案里"选择优秀的"** | ✘ **无此阶段（最大缺口）** |
| 6 | 试；不成功 | — |
| 7 | **再来一轮**，直到满意 | △ `iterate` 只改一份草稿，无法"重新出 N 份再选" |

**我的判断**：现有 8 个模式**接不住**这个流程。缺的不是一个阶段，而是**一整类模式**：
「产生 N 个候选 → 评判 → 选优 → 改进 → 复评」的闭环。我暂称 **招标评审 / 择优迭代**。

而第 4 步暴露了一个更基础的缺口：**用户的 AI 并不全在同系统内**，他是**人肉当消息总线**的（§5.4）。

### §4.2 工作流 B：「我提一个想法，让他们商量出架构，然后分头写，最后汇总成软件」

**用户原话**：

> 如果我提一个想法想把它变成真的，例如开发一个什么样的软件，我提出想法，让他们商量出功能和架构后就开始一个 AI 写一部分，最后有一个 AI 接受他们的产物汇总后生成软件。这样的功能用什么模式？

**我把它拆成 5 步**：

| 步 | 动作 | 现有模式能接吗 |
|---|---|---|
| 1 | 提想法 | — |
| 2 | 商量出**功能**（需求/范围） | △ `assist` 能做方案，但不专门做需求澄清 |
| 3 | 商量出**架构**（模块划分） | △ `panel` / `assist` 能做，但**没人负责"冻结接口"** |
| 4 | **一个 AI 写一部分** | ✅ `divide` 的「分头攻克」阶段 |
| 5 | **最后一个 AI 汇总生成软件** | △ `divide` 有「汇总拼装」，但它只拼**文本**，不落盘、不验证 |

**我的判断**：`divide` 能接一半，但有**两个致命缺口**：

- **缺口 A（接口契约）**：现有 `divide` 的「分头攻克」阶段切片是 `TASK` —— 也就是说，**每个 AI 只看得到原始任务，看不到"别人负责什么"、也看不到"接口怎么约定"**。9 个 AI 各写各的模块，函数签名/数据结构/命名全不一致，**汇总时必然拼不起来**。这在软件工程上是常识（接口先行），但当前设计里没有这个阶段。
- **缺口 B（产物形态）**：最终要的是**可运行的软件**，而现在所有模式的产出都是**聊天文本**。没有落盘、没有编译/运行、没有失败回滚。

## §5 我识别出的 5 个设计缺口（供你证伪或确认）

### §5.1 缺口一：没有"候选择优"这一类模式
`broadcast` 只产出 N 份意见，**没有评判与选择**。
`iterate` 的 `needs: ['draft']` —— 它只能改进**给定的一份**草稿，无法"从 N 份里选一份再改进"。
**这两者的组合也补不上**：因为缺的是"评判 → 选择"这个动作本身。

### §5.2 缺口二：`divide` 分头时看不到接口契约（代码级证据）
```js
// core/modes.js 第 259-263 行，原样摘录
phases: [
  { name: '拆分任务', seat: 'converge', speak: SPEAK.SEQUENTIAL, slice: SLICE.TASK },
  { name: '分头攻克', seat: 'all',      speak: SPEAK.PARALLEL,   slice: SLICE.TASK },   // ← 只看原始任务
  { name: '汇总拼装', seat: 'converge', speak: SPEAK.SEQUENTIAL, slice: SLICE.ALL },
],
```
「分头攻克」用的是 `SLICE.TASK`。**每个执行者看不到拆分结果、看不到同伴的分工、看不到任何接口约定。**
对"写文档"类任务这还勉强能用；对"写代码"类任务这是必坏。

### §5.3 缺口三：模式定义里**完全没有成本维度**
用户的抱怨是"瞎聊浪费 TOKEN"。但现有 8 个模式的 `modelFit` 字段里只有
`need`（能力门槛）/ `recommendSet` / `channels` / `tips` —— **没有任何一个字段表达"这个模式要花多少"**。

我按现有阶段定义手工推算的成本（N = 参会人数，L = 单次发言长度）：

| 模式 | 调用次数 | 上下文增长 | 档位 |
|---|---|---|---|
| broadcast | N | N·L | 低 |
| review | N + n_质证 + 1 | 第二阶段每人注入 ≈ N·L | 中高 |
| assist | ≈3~N | 中等 | 中 |
| iterate | R × 2（R = 实际轮数） | 每轮注入固定大小 | 中（**自带判停，省钱**） |
| debate | 2N | 对辩每人 ≈ (N-1)·L | 中高 |
| **panel** | N | **第 k 人注入 (k-1)·L → 总计 O(N²L)** | **极高** |
| **chairman** | R × (1+1~2)，**R 无硬上限** | 不确定 | **不可预测** |
| divide | 1 + N + 1 | 汇总阶段注入 N·L | 中 |

**两个具体问题**：
1. `panel` 在 9 人时是 O(N²)，**最贵的模式没有任何告警或限制**。
2. `chairman` 的轮数没有硬上限（`maxIterations` 只配在 `iterate` 上），**成本不可预测** —— 这对"怕浪费 token"的用户是最危险的。

### §5.4 缺口四：外部 AI 的意见进不来（人肉中转不是一等公民）
系统的设计假设是"**所有参会者都在本系统内**"（9 个 webview 自动收发）。
但用户的实际工作流是**跨环境**的：他自己在浏览器里问元宝/千问，然后**复制粘贴**回来。
当前架构里没有"外部意见"这个入口 —— 它不是一条 message，进不了 `messages`，也就**不参与任何切片**。

这不只是功能缺失，还关乎**可用性**：让用户为 9 个网站逐个登录是最大的摩擦；而"粘贴一下就能参与"是零摩擦入口。

### §5.5 缺口五：产物只到文本，不到可运行文件
所有模式的 output 都是文本。用户要的是"**生成软件**"。
中间至少差：结构性产物定义（哪些文件、什么内容）→ 落盘 → 编译/运行验证 → 失败回滚/修复回路。

## §6 问题清单（展开版）

**Q1** 工作流 A 该新建 `tournament` 模式，还是 `broadcast + iterate` 组合？
> 我倾向新建，因为"评标 + 选优"是既有模式都没有的动作。但我不确定是否过度设计 —— 如果组合能成，编排器要多做什么？

**Q2** 评标阶段怎么防锚定？
> 现有 `review` 用「第一阶段并行 + 只看材料」解决审阅锚定。评标是否同理（评标人也应该**先独立打分，再看别人的评审**）？还是说评标天然需要看到所有方案，锚定不可避免，只能靠"打分而不是排序"来缓解？

**Q3** 打分 vs 淘汰？跨模型分数怎么校准？
> 不同 AI 给分尺度不同（有的给 3 分有的给 8 分）。是归一化（每个评审者的分数减去自己的均值）？还是强制排序（只给名次不给分）？还是两两对决（pairwise，像 Elo）？

**Q4** 工作流 A 的可计算终止判据是什么？
> `iterate` 用的是「本轮批评相对上轮无新增」（集合运算）。择优迭代能不能用类似的东西？
> 我的候选想法：①「本轮最优方案的得分相对上轮增幅 < 阈值」；②「没有评审者提出新的反对意见」；③ 强制人工确认。
> 请判断哪个可计算且不会空转。

**Q5** 接口契约由谁写、写成什么形态？
> 是让"架构师"角色写一份伪代码式契约？还是 OpenAPI / TypeScript interface？契约太细会把实现框死（AI 变抄写员），太粗约束不住（还是拼不起来）。**分界线在哪？**

**Q6** 分头实现时每个 AI 该看到什么？
> 我的草案：契约全文 + 自己负责的模块 + 其他模块的一句话摘要（不展开）。是否够？需要新增一个 `CONTRACT` 切片类型吗？

**Q7** 降成本：9 人 panel 的 O(N²) 怎么破？
> 候选手段：①摘要压缩（把前面的发言压成摘要再注入）；②分组合并（9 人分 3 组，组内先归并再上会）；③硬性限制 N ≤ 5；④只在"分歧点"上串行。
> **请按有效性排序，并说明各自的副作用。**

**Q8** 人工中转席位怎么建模？
> 它和普通席位的关键差异：①不能 `waitForResponse`（要等人工粘贴），②没有"完成检测"（人说了算），③可能一次粘贴多个 AI 的回答。
> 它应该是一个特殊 provider 类型？还是干脆建模成"用户手动插入的 message"？

**Q9** 从文本到可运行软件，最少几个环节？谁当集成者？
> 我猜是：架构冻结 → 分头实现 → 集成（编译/运行）→ 修复回路 → 交付。
> 「集成者」应该是一个独立的角色（比如"集成工程师"），还是复用现有的"主持助理"？集成失败时谁来修 —— 原作者还是集成者？

## §6.5 我的初步草案（**请当作靶子批判，不要只做增量修补**）

我给两个缺口各起草了一个模式。**如果你认为方向就错了，请直接推翻**，并给出你的方案 —— 我不需要"你这样挺好，建议微调"。

### 草案 A：招标评审 `tournament`（对应工作流 A）

| 阶段 | 席位 | 发言方式 | 切片 | 产出 |
|---|---|---|---|---|
| 1 出标 | 全员 | 并行 | `TASK` | N 份候选方案 |
| 2 评标 | 全员 | 并行 | `ALL` | 每份方案一张评分表 |
| 3 定标 | 收敛类 | 顺序 | `ALL` | 选出 1 个胜出者（+1 个备选） |
| 4 改进 | 建设类 | 顺序 | `CRITIQUES` | 对胜出者定向改进 |
| 5 复评 | 质证类 | 并行 | `DRAFT` | 挑错清单 |

- **关键设计**：第 2 步评标时，评审者**能看到所有方案，但看不到别人的评分**（防止"跟票"）。
- **终止**：复用 `iterate` 的 `no-new-critique`（第 5 步无新错 → 停）。
- **成本**：`N + N + 1 + 2 × R`（R = 改进轮数）。
- **我的疑问**：① 评标用打分还是排名？② 评标要全员还是只让质证类评？③ 第 3 步"定标"由单个 AI 决定全场，会不会成为脆弱瓶颈？

### 草案 B：工程交付 `build`（对应工作流 B）

| 阶段 | 席位 | 发言方式 | 切片 | 产出 |
|---|---|---|---|---|
| 1 需求澄清 | 代表类 | 顺序 | `OTHERS` | 功能清单 + 明确的"**不做什么**" |
| 2 架构设计 | 建设类 | 顺序 | `OTHERS` | 模块划分 + 依赖关系 |
| 3 **冻结契约** | 收敛类 | 顺序 | `ALL` | 接口契约（签名/数据结构/错误约定） |
| 4 分头实现 | 全员 | 并行 | **`CONTRACT`（新）** | 各自负责的文件 |
| 5 集成验证 | 收敛类 | 顺序 | `ALL` | 拼装 + 编译/运行结果 |
| 6 修复 | 建设类 | 顺序 | `CRITIQUES` | 只修编译/运行错误 |

- **需要新增切片** `CONTRACT` = 接口契约全文 + 自己负责的模块 + 其他模块的一句话摘要。
- **需要新增概念「产物」**：每个阶段的输出应该是 `{ path, content }` 而不是自由文本 —— 否则"生成软件"永远停在聊天层面。
- **终止**：集成通过；或达到修复轮数上限。
- **我的疑问**：① 契约由架构师写还是收敛类写？② "集成者"该是独立新角色吗？③ 第 6 步谁修 —— 原作者，还是集成者？

### 附：本系统的技术栈（供参考，不影响你的设计建议）

- 编排内核：纯 Node.js，**零外部依赖**，可单测（当前 170 个用例全绿）。

- 会议状态：`MeetingModel` 是唯一事实源（messages / rounds / 压缩摘要）。
