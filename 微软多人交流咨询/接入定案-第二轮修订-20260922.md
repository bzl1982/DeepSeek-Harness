## 零、本轮做了什么（TL;DR）

上一轮定案的**架构判断是对的**（抄 AutoGen 模型、不引运行时、Electron 管手和眼睛）。本轮不改架构，只做三件事：

1. **抓着并修掉了两个真 bug**（都不是"理论风险"，是必然误判）：
   - `streamEnd` 信号是个**永久闩锁** → 第二轮回复会被瞬间误判完成
   - `domStable` 起手即真 → **空回复被判完成**（抓空气）
2. **兑现了文档承诺但不存在的 CDP 接入**：`streamEnd` 从"白占信号位"变成真实可用的第 5 信号。
3. **校正了上一轮对客户端现状的 3 处误判**（见 §3），并给出精确到行号的客户端补丁点。

**用例数：45 → 68**。且两个修复都用**变异测试**验证过——把修复退回去，测试立刻失败（不是假保险）。

## 一、修掉的两个真 bug（本轮最高价值产出）

### Bug 1：`streamEnd` 永久闩锁 → 跨轮污染

**位置**：`meeting-lab/adapters/web-adapter.js`（v1 第 101、190 行）

```js
// ❌ v1：模块级布尔量，一旦为真永不复位
let streamEnded = false;
driver.onStreamEnd(() => { streamEnded = true; });
...
if (streamEnded) detector.feed(SIGNALS.STREAM_END, true);
```

**为什么必然出错**：
`createWebAdapter()` 在会议开始时**只调用一次**，返回的 adapter 对象被 9 个 AI **复用整场会议**。
于是第一轮回复结束后 `streamEnded` 永久为 `true`，第二轮一开始就白送一个信号。
而 `CompletionDetector` 默认 `minSignals: 2` —— 只要 `sendReady` 再为真，**第二个 AI 的回复会在 0ms 内被判"已完成"**，抓到的是空字符串。

**修法**：把布尔闩锁换成**每轮 `arm()` 的 `StreamTracker`**：
- `sendText()` 时 `tracker.arm()` → 清零上一轮
- 判定要求"**见过流 + 全部结束 + 静默够久**"三者同时成立

**回归测试**：`test/web-adapter.test.js` → `★★ 修复回归：streamEnd 不得跨轮闩锁`

---

### Bug 2：`domStable` 起手即真 → 空回复被判完成

**位置**：`meeting-lab/adapters/web-adapter.js`（v1 第 166 行）

```js
// ❌ v1：循环开始前就声明"DOM 稳定"
detector.feed(SIGNALS.DOM_STABLE, true);
```

**为什么必然出错**：
`StreamTracker`/探针在"AI 还没开始生成"时，页面本来就处于静止状态 ——
`stopGone=true`、`sendReady=true`、`domStable=true` → **三个信号同时满足**。
`minSignals=2` 被轻松越过，判定 `COMPLETED`，而 `text` 是空串。

症状：**偶发性的"AI 没说话但会议认为它说完了"**，且只在网络慢/首字节延迟高时出现 —— 典型的偶发难查 bug。

**修法**：引入 `requireContent`（默认 `true`）——
1. 必须**先看到非空回答文本**，`domStable` 才有资格置真；
2. 网络还在流（`st.state === 'streaming'`）时，**主动抽掉 `domStable`**，防止长回答中途"长时间无新字"被腰斩。

**回归测试**：`test/web-adapter.test.js` → `★ 修复回归：DOM 全部空闲但回答为空 → 绝不能判 COMPLETED`

> 保留 `requireContent: false` 逃生门：极少数站点（如纯搜索引擎页）确实需要允许空回复完成。

## 二、兑现 `streamEnd`：从"信号位摆设"到真实第 5 信号

上一轮文档把 `streamEnd` 列为信号 D，但 v1 代码里它**永远是 false**（README 自认"暂未接入"）。
一个恒定不变的信号位，在 `minSignals` 计数里等于**让人**——`minSignals=2` 实际只有 3 个候选信号，抗误判能力被悄悄削弱。

### 新增 `core/stream-tracker.js`

**设计要点：不猜"哪个请求才是回答"，而是看"网络还有没有在流"。**

```
send() → arm()
   ↓ Network.requestWillBeSent          pending+1
   ↓ Network.responseReceived（像流）    active+1 / pending-1，记 URL
   ↓ Network.dataReceived               刷新 lastDataAt（"还在吐字"）
   ↓ Network.loadingFinished / Failed   active-1
   ↓
判定：见过流 && pending==0 && active==0 && 静默 ≥ idleMs（默认 900ms）
     → streamEnd = true
```

**为什么这个模型比"URL 精确匹配"更耐用**：
网站把 `/api/v0/chat/completion` 改成 `/api/v1/message/stream` 时，
URL 正则失配 → `active` 不增 → 退化为 `idle`（不谎报结束），
**DOM 信号照常工作，会议不崩**。若改成精确匹配，则会是"静默误判"。

**为什么它比 DOM 信号更可靠**：
DOM 静默可能只是"还没开始渲染"；**网络静默才是"服务器真的不吐字了"**。

### 新增 `shell/cdp-driver.js`（Phase 1 可直接搬进客户端）

关键：**不需要任何新权限**。客户端 `meeting.html` 已经在用 `wv.debugger`（文件上传），
同一个 debugger 会话再开 `Network` 域即可。

源码里标注了 4 个照抄时必须注意的坑：
1. **必须先 `attach` 再 `enable Network`**，顺序反了拿不到事件
2. `Network.enable` 要给 `maxTotalBufferSize`，否则长回答撑爆 CDP 缓冲
3. `detach` 必须 `removeListener`，否则 9 个 webview 长会累积泄漏
4. **`isAttached()` 判断必不可少，且不要把 debugger 本身 detach 掉** ——
   文件上传还要用同一个会话。两处各自 detach 会互相踩，
   **典型症状是"上传突然开始随机失败"**（这会是个极难查的 bug，提前埋好注释）

## 三、上一轮对客户端现状的 3 处误判（本轮校正）

> 用户铁律：争议问题去源头核实。本轮读了 `meeting.html` / `agentCatalog.js` 实际代码，
> 有 3 处上一轮说错了，这里明确纠正。

| # | 上一轮的说法 | 核实结果 | 影响 |
|---|---|---|---|
| 1 | `meeting.html:672` 引用 `model.charLimit` → 恒为 `undefined` → "超长分批"死代码 | ❌ **错误**。实际代码是 `model ? model.charLimit : 10000`，最坏也只是回落到 `10000`，**不是 `undefined`，分批分支能触发** | 死代码判断不成立，**但**真正的坑是另一个：`charLimit` 在 `agentCatalog.js`（唯一配置源）里**根本没定义** → 9 个 AI 的字符上限**全被硬编码成 10000**，无法按模型差异化。这仍该修，只是性质不同 |
| 2 | "9 个 webview 各自抢 DropEvent"是"偶尔收不到"的**结构性病因** | ⚠️ **不准确**。核实 `meeting.html:602-608`：drop 是**宿主 document 统一接的**（`e.preventDefault()` + 只 `handleFiles` 一次），拖拽期间还配了 `setIgnoreMouseEvents` + `pointer-events:none` 双保险。**不存在抢 DropEvent** | 病因要重新定位，见 #3 |
| 3 | "上传后固定 `sleep(3000ms)` 就发送"是偶尔收不到的**根因** | ✅ **这条是对的**，但**不是全部**，而且有个更前置的问题被漏掉了 —— 见下 | 见 §3.1 |

### 3.1 真正的根因链（按优先级）

```
症状：9 个 AI 偶尔有人收不到文件

├─ 根因 A（最关键，上一轮漏掉）：附件压根没真上传
│    meeting.html:578-598  handleFiles()
│      → txt/md:  读出文本塞进 attachedFiles[].text
│      → pdf:     只存 '[PDF文件: xxx]' 一行字
│      → 图片:    存 base64 dataUrl，但发送时只取 .text 字段
│    meeting.html:659-664  发送时把 attachedFiles[].text 拼成字符串
│      → 也就是说 PDF/图片 根本没上传，AI 收到的是「一个文件名占位符」
│    ★ 结论：对 PDF/图片而言，「偶尔收不到」其实是「永远收不到内容」，
│      只是占了位所以看起来像"有时成功"
│
├─ 根因 B：确实是 sleep(3000) 无握手
│    meeting.html:527-531  uploadFileToWebview() → sleep(3000) → 发说明文字
│      → 大文件/慢网络下 3 秒不够 → 文件还在解析就发了 → AI 读不到
│
└─ 根因 C：attachedFiles 从不保留真实文件路径
     meeting.html:535  // {name, text, isImage, dataUrl}   ← 没有 localPath
     ★ 这直接阻塞了 AttachmentBus 的接入：它就认 localPath
```

**所以正确的修法是"先补路径、再上握手"，顺序不能反。**
