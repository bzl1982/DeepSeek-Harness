我把微软这一套重新查了一遍，也把它和你现在的 **DeepSeek Harness + 通辽会议 + 9 个网页版 AI** 的实际形态对照过了。

我的结论很明确：

> **你真正应该接入的不是某一个微软项目，而是把微软现在这条技术链拆开利用：**
>
> **AutoGen 的 GroupChat 思想 → Microsoft Agent Framework 作为编排内核 → Magentic-UI/MagenticLite 借鉴浏览器操作思想 → 你自己的 Electron WebAI Adapter 负责控制 9 个网页版 AI。**
>
> **不要试图把 9 个网页版 AI“改造成 API”，而是把每一个网页 AI 包装成一个“Agent”。**

这样才真正符合你现在这个“通辽会议”的形态。

下面这份方案，我是按“以后真要让 AI 助理照着代码落地”的标准来设计的。

# 一、先把微软这个项目认准

你听说的“微软多人 AI 对话交流项目”，核心上就是 **Microsoft AutoGen**。

AutoGen 最早就是微软研究团队做的多智能体协作框架，核心思想不是“调用 9 个 API”，而是：

> 建立多个 Agent，让它们按照一定的会话拓扑互相发送消息，共同完成一个任务。

微软官方论文明确描述了 AutoGen 的核心能力就是“让多个 Agent 相互对话”，并可以组合 LLM、人工输入和工具。([微软][1])

但是这里有一个非常重要的时间点：

## 2026 年不要直接以旧 AutoGen 作为新项目基础

微软现在官方 AutoGen 仓库已经明确写着：

> **Starting a new project? Head to Microsoft Agent Framework for the latest multi-agent capabilities with long-term support.**

也就是说：

**AutoGen = 前身 / 思想来源**

**Microsoft Agent Framework = 微软现在主推的新一代基础**

([GitHub][2])

目前 Microsoft Agent Framework 的 Python 项目版本已经是 **1.19.0**，Python 包标记为 Production/Stable，许可证为 MIT。([GitHub][3])

所以你的项目应该采用：

> **Microsoft Agent Framework，而不是从旧 AutoGen 代码开始。**

> “9 个 API → 9 个 AI → 互相聊天”

它们在 **会议引擎看来全部都是 Agent**。

# 三、微软现在实际上有三层东西，对你都很有价值

可以把微软这套东西理解成三件工具。

| 微软项目                       | 本质                        | 对通辽会议的用途              |
| -------------------------- | ------------------------- | --------------------- |
| AutoGen                    | 多 Agent 对话思想              | 借鉴 GroupChat          |
| Microsoft Agent Framework  | 新一代 Agent / Workflow 编排内核 | **真正接入**              |
| Magentic-UI / MagenticLite | AI 控制浏览器、文件、工具            | **借鉴 Web Agent 实现方式** |

其中 Magentic-UI 是微软研究团队公开的开源研究原型，专门研究“人 + Agent + 浏览器”的交互。它可以浏览网页、执行代码、处理文件，并通过 MCP 扩展工具。([微软][4])

而现在仓库里的 MagenticLite 已进一步采用：

```text
MagenticBrain
      ↓
负责计划 / 编排

Fara
      ↓
负责浏览器操作

Quicksand
      ↓
浏览器沙箱
```

它能够跨浏览器和本地文件系统执行任务。([GitHub][5])

但是：

## 千万别直接把 MagenticLite 当作你的通辽会议核心

原因非常关键。

它当前文档明确把：

> **浏览器内上传本地文件**

列为当前限制。

也就是说，微软自己的浏览器 Agent 当前甚至不适合直接承担你“一个文件发给 9 个 AI”这个核心任务。([GitHub][6])

所以正确做法是：

> **抄它的架构思想，不抄它的完整实现。**

# 六、最关键设计：把“网页版 AI”包装成 Agent

这是整个项目能否成功的核心。

我们不能要求：

```text
Microsoft Agent Framework
        ↓
调用 ChatGPT API
```

因为你的 ChatGPT 是网页版。

所以我们自己做：

```text
WebUIAgent
```

它在 Agent Framework 看起来仍然是一个普通 Agent。

但是：

```text
WebUIAgent.run()
```

内部不是：

```python
client.chat.completions.create()
```

而是：

```text
打开对应 AI Web 页面
        ↓
找到输入框
        ↓
输入会议消息
        ↓
必要时上传附件
        ↓
点击发送
        ↓
等待 AI 输出
        ↓
检测回答完成
        ↓
提取最终回答
        ↓
返回给 Agent Framework
```

这一步微软 Agent Framework 本身其实已经给我们留出了正式扩展接口。

官方现在明确支持：

> 自定义 Agent，只需要实现统一的 Agent Run 接口。

甚至可以直接实现协议，而不一定继承微软的基类。([GitHub][10])

所以我们可以做：

```python
class WebAIAgent(BaseAgent):
    ...
```

或者直接实现：

```python
SupportsAgentRun
```

# 九、为什么这比“让 AI 自己看网页乱点”更适合通辽会议

微软 Magentic-UI 的浏览器 Agent 走的是：

```text
LLM
 ↓
理解页面
 ↓
决定动作
 ↓
浏览器
```

这很强，但并不适合你的“9 个固定聊天网站”。

你的任务其实非常固定：

```text
输入框在哪里
上传按钮在哪里
发送按钮在哪里
回答在哪里
什么时候结束
```

所以不应该每次都让视觉模型猜。

应该：

## 第一层：确定性 DOM Driver

比如：

```text
textarea
contenteditable
input[type=file]
Send Button
Stop Button
Assistant Message
```

直接定位。

速度快。

稳定。

成本几乎为零。

# 十、第二层才用浏览器视觉 Agent 做“故障恢复”

例如某一天 Gemini 改版：

```text
原来的 textarea
↓
换成 div[contenteditable=true]
```

此时：

```text
CSS Selector 失效
```

系统不要直接报错。

应该进入：

```text
WebAI Repair Mode
```

然后：

```text
DOM
 +
Accessibility Tree
 +
Screenshot
```

交给视觉/浏览器 Agent：

```text
“找出当前页面的输入框、发送按钮、文件上传控件、最后一条 AI 消息。”
```

得到：

```json
{
  "composer": "...",
  "sendButton": "...",
  "fileInput": "...",
  "assistantMessage": "..."
}
```

再更新 Adapter 的临时运行状态。

这其实正好借鉴 AutoGen/Magentic-UI 对网页浏览的设计。

微软 AutoGen 的 WebSurfer 后来已经发展到使用 Playwright，并探索 Accessibility Tree、截图、网页控件定位等机制。([GitHub][11])

所以这里可以形成：

```text
确定性 DOM
    ↓
失败
    ↓

    ↓
仍失败
    ↓
视觉 Browser Agent
```

而不是反过来。

之后：

```text
ChatGPT Adapter → att_01
Gemini Adapter   → att_01
Claude Adapter   → att_01
...
```

# 十五、你目前“拖拽文件失败”的架构性解决办法

我尤其建议注意这一点。

现在错误设计很可能类似：

```text
Chat Input A
   ↓
drop

Chat Input B
   ↓
drop

Chat Input C
   ↓
drop
```

这在“9 个输入框”情况下非常容易乱。

应该修改成：

```text
document
  ↓
Meeting Drop Controller
  ↓
Attachment Manager
  ↓
Meeting Core
```

也就是：

> **拖拽只在会议层接受一次。**

然后会议层决定：

```text
发送给哪几个 AI
```

而不是让 9 个 AI 自己抢这个 DropEvent。

这对你目前“9 个网页版 AI 都能收到文件，但是偶尔接不到”的问题，实际上是最重要的结构性改进之一。

# 十六、会议消息也必须建立自己的标准格式

不要让不同 AI 网页自己管理会议状态。

建立：

```typescript
interface MeetingMessage {
    id: string
    meetingId: string

    senderType: "user" | "agent" | "system"
    senderId: string

    content: string

    attachments?: AttachmentRef[]

    round: number
    turn: number

    timestamp: number
}
```

例如：

```json
{
  "id": "msg_1024",
  "meetingId": "meeting_001",
  "senderType": "user",
  "senderId": "human",

  "content": "请审查这份软件架构方案",

  "attachments": [
    {
      "attachmentId": "att_01"
    }
  ],

  "round": 1,
  "turn": 0
}
```

这样以后无论：

```text
刷新页面
AI 崩掉
Electron 重启
某个 AI 掉线
加入第 10 个 AI
```

会议状态仍然是独立存在的。

# 二十四、Python 侧最核心代码可以非常简单

概念上：

```python
from agent_framework import BaseAgent

class WebAIAgent(BaseAgent):

    def __init__(self, bridge, agent_id, name):
        super().__init__(
            name=name,
            description=f"Web AI: {name}"
        )

        self.bridge = bridge
        self.agent_id = agent_id

    async def run(self, messages=None, **kwargs):

        result = await self.bridge.request({
            "type": "web_ai.send",
            "agentId": self.agent_id,
            "messages": messages
        })

        return result
```

重点是：

> **Agent Framework 只负责“调用 Agent”。**

真正的：

```text
网页
输入框
文件
点击
等待
抓回答
```

全部由：

```text
bridge
```

完成。

这正符合微软目前 Custom Agent 的设计方式。([GitHub][10])

# 三十五、尤其要做“完成检测器”

### 不应该采用

**直接把旧 AutoGen 嵌进去**

因为微软已经把新的发展方向转向 Agent Framework。([Microsoft Learn][23])

### 不应该采用

**直接把 MagenticLite 当通辽会议底座**

因为其当前浏览器文件上传存在明确限制。([GitHub][6])

### 第一阶段不应该采用

**A2A**

因为所有 Agent 都在本机，没有必要增加网络协议层。

### 第一阶段也不应该采用

**AG-UI**

因为 DSH 自己已有成熟的 Web/Electron 通信基础；AG-UI 更适合作为以后独立 Web 客户端的标准接口。微软目前将 AG-UI 定位为 Agent ↔ Web Client 的标准化流式/状态协议，而且当前仍处于 Preview。([Microsoft Learn][17])

---

# 四十九、最重要的一句话

**不要把“9 个网页版 AI”强行变成 9 个 API。**

应该反过来：

> **把 9 个网页版 AI 包装成 9 个 Agent，让 Microsoft Agent Framework 负责“思想和会议调度”，让 Electron 负责“手和眼睛”。**

这样你的：

```text
通辽会议
```

就会从现在的：

```text
9 个网页 AI 同框
```

真正升级成：

```text
9 个 Web Agent
        +
多 Agent Orchestrator
        +
统一文件总线
        +
会议状态机
        +
动态 Speaker Selection
        +
Human-in-the-loop
```

而且这个架构和 DeepSeek Harness 当前“Everything is a Plugin”的方向并不冲突；DSH 官方本身就采用插件化 Web Client、Host、RPC 和文件上传等分层。([GitHub][24])
