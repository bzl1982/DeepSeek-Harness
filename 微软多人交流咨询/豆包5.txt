# 通辽会议模式与角色体系完善方案（针对第五轮9问）
基于现有8模式+15角色体系，结合两个真实工作流与5个设计缺口，给出**字段级、可计算、带成本与反例**的落地方案。所有设计100%兼容现有纯Node编排内核，零外部依赖，可直接单测覆盖。

---

## 核心结论总览
1. **新增2个模式**：`tournament`（招标评审，对应工作流A）、`build`（工程交付，对应工作流B），不采用「现有模式组合」方案，避免破坏模式封装性与状态边界。
2. **新增1类切片**：`CONTRACT`（接口契约切片），解决分头实现的接口对齐问题。
3. **新增1类席位**：`manual_provider`（人工中转席位），标准化外部AI意见入口，复用完整消息总线。
4. **补全成本维度**：所有模式新增`costModel`字段，显性化调用次数与上下文量级。
5. **补全产物体系**：新增`FileArtifact`结构化产物，从纯文本升级到可落盘文件。

## 一、9个核心问题逐项解答
### Q1：工作流A该新建模式，还是用现有模式组合？
**结论：必须新建`tournament`模式，不推荐`broadcast + iterate`组合。**

#### 为什么组合不行
`broadcast`只能产出N份独立方案，`iterate`只能迭代单份草稿，两者之间缺了**「评标→选优→定向改进」**的核心动作。如果硬做组合，编排器需要跨模式维护状态、做数据格式转换，会破坏模式的封装性，状态边界模糊，单测无法覆盖，长期维护成本远高于新建一个模式。

#### 新建模式的合理性
工作流A是典型的「多方案竞标→选优迭代」场景，和`review`（单材料多视角）、`iterate`（单草稿迭代）、`broadcast`（多意见并行）是完全独立的场景类，有自己固定的阶段序列、切片规则、终止判据，符合现有模式的抽象粒度。

#### 成本
- 开发成本：新增1个模式定义，约200行代码，复用现有`phase`/`slice`/`termination`抽象，复用率≥80%。
- 运行成本：`N + N + 1 + 2×R`（N=方案数，R=改进轮数），和同复杂度模式持平。

#### 反例（什么时候不该新建）
- 一次性场景、方案数≤3：直接用`broadcast`+人工选优即可，无需模式化。
- 只有一份草稿需要迭代：用现有`iterate`模式，不要用tournament。

#### 字段级设计
```javascript
// 新增模式枚举
MODE.TOURNAMENT = 'tournament';
// 模式元数据新增字段
{
  id: 'tournament',
  name: '招标评审',
  costModel: {
    callCount: 'N + N + 1 + 2*R',
    contextScale: 'O(N)',
    grade: 'medium'
  },
  phases: [ /* 见下文优化版草案 */ ]
}
```

### Q2：评标环节如何防止评审者被第一份方案锚定？
**结论：两阶段盲评法 + 方案匿名化，从机制上彻底规避锚定效应。**

#### 具体机制
1. **第一阶段：独立盲评（并行）**
   - 所有方案隐去来源AI标识，只标`scheme_01`/`scheme_02`…编号
   - 每个评审者**只能看到所有方案的内容，看不到任何其他人的评分、评语**
   - 并行输出各自的排名+理由，互不干扰
2. **第二阶段：交叉质证（串行）**
   - 公开所有评分与排名，只针对「得分差异≥阈值」的分歧点展开讨论
   - 评审者可以调整自己的排名，但必须说明调整理由

#### 和review模式的差异
review防锚定靠「只看材料、不看别人意见」；评标防锚定靠「看所有方案、但不看别人评价」——因为评标天然需要横向对比所有方案，不能只看单个。

#### 成本
- 第一阶段：N次并行调用，和普通评审成本一致
- 第二阶段：增加1轮交叉讨论，成本+N次调用
- 匿名化处理：纯文本替换，零额外成本

#### 反例
- 方案数≤2：锚定效应可忽略，直接评审即可
- 定性评审、不打分排名：匿名化收益很低，可省略

#### 字段级设计
```javascript
// 评标阶段配置
{
  name: '独立盲评',
  type: 'independent_eval',
  blind: true, // 开启匿名化，自动剥离senderId
  speak: SPEAK.PARALLEL,
  slice: SLICE.ALL_SCHEMES // 只看方案内容，不看评审历史
},
{
  name: '交叉质证',
  type: 'cross_discuss',
  speak: SPEAK.SEQUENTIAL,
  slice: SLICE.ALL_EVALUATIONS // 看所有评审结果
}
```

### Q3：打分排序还是淘汰制？跨模型分数怎么校准？
**结论：强制排序 + 分位校准，不使用绝对分；海选场景叠加淘汰制。**

#### 为什么不用绝对分
不同AI的打分尺度天然不一致（有的0-3，有的0-10，有的习惯给中间分，有的习惯给极端分），归一化、均值校准都会被极端值带偏，无法真正横向可比。

#### 具体方案
1. **基础规则：强制排名**
   - 每个评审者必须对N个方案给出**严格的1~N名次**，不允许并列
   - 输出`rankings: number[]`（索引对应方案，值对应名次），不输出原始分数
2. **校准方式：分位标准分**
   - 第1名统一换算为100分，最后1名统一换算为0分，中间线性插值
   - 公式：`standard_score = (N - rank) / (N - 1) * 100`
   - 最后汇总所有评审者的标准分取平均值，得到最终排名
3. **海选叠加淘汰制（N>5时推荐）**
   - 第一轮：所有评审并行排名，淘汰后50%的方案
   - 第二轮：对剩余方案再做详细评审+交叉质证

#### 成本
- 排序与校准：纯集合运算，零额外调用，单测可完全覆盖
- 淘汰制：减少第二轮评审的方案数，运行成本降低约40%

#### 反例
- 方案有明确可量化指标（如响应时间、成本金额）：直接用客观数据排序，无需AI排序
- 方案数≤3：排序和打分差异不大，可简化

#### 字段级设计
```javascript
// 评审输出结构
interface Evaluation {
  schemeId: string;
  rank: number; // 1~N，强制不重复
  reasons: string[];
  standardScore?: number; // 汇总层计算，0-100
}
// 终止条件新增
{
  type: 'elimination',
  remainCount: number // 淘汰后剩余方案数
}
```

### Q4：工作流A的可计算终止判据是什么？
**结论：双条件终止（得分收敛 + 无新增致命问题），满足其一即终止，强制轮数兜底。**

#### 两个可计算判据（按优先级）
1. **得分收敛判据（优先，最客观）**
   - 逻辑：本轮最优方案的标准分，相对上一轮最优方案的标准分，增幅 ≤ 阈值
   - 公式：`(currentBest - lastBest) / lastBest ≤ threshold`，默认阈值`2%`
   - 原理：选优迭代的核心是最优解不再提升，就说明已经收敛
2. **无新增致命问题判据（兜底）**
   - 复用`iterate`的集合比对逻辑，但**只统计blocker级批评**，major/minor级优化建议不算
   - 对批评做分级：`blocker`（走不通）/`major`（严重缺陷）/`minor`（优化建议）
   - 本轮没有新增blocker级批评，即可终止
3. **强制兜底**：`maxRounds = 5`，避免无限空转

#### 为什么不用“没有新批评”
批评可以靠换说法、换角度“新增”，很容易文字游戏式空转；得分是相对排序，无法靠文字游戏提升，更稳定。

#### 成本
- 纯数值/集合运算，零额外调用开销
- 批评分级只需要在prompt里加约束，不增加调用次数

#### 反例
- 创意类、审美类方案：没有明确优劣标准，得分收敛不适用，只能人工确认
- 安全合规类场景：必须用“无新增致命问题”作为核心判据，得分只是参考

#### 字段级设计
```javascript
// 终止条件类型
TERMINATION.SCORE_CONVERGENCE = 'score_convergence';
TERMINATION.NO_NEW_BLOCKER = 'no_new_blocker';
// 配置
{
  termination: [
    { type: 'score_convergence', threshold: 0.02 },
    { type: 'no_new_blocker' },
    { type: 'max_rounds', value: 5 }
  ],
  // 批评新增字段
  critique: {
    severity: 'blocker' | 'major' | 'minor',
    content: string
  }
}
```

### Q5：接口契约由谁写、写成什么形态？
**结论：架构师起草 → 全员确认 → 收敛者冻结；形态是「接口级伪代码契约」，只定边界不定实现。**

#### 责任分工
1. **起草者：架构师角色**
   - 输出：模块划分、每个模块的输入输出结构体、依赖关系、错误约定
   - 不写具体实现逻辑，不规定内部函数名、算法
2. **确认者：所有分头实现的AI**
   - 并行审阅契约，只提「接口无法实现、缺少必要字段、边界模糊」类意见
   - 禁止讨论实现细节、禁止修改接口以外的内容
3. **冻结者：主持助理（收敛类）**
   - 汇总意见，修订后发布「冻结版契约」
   - 冻结后任何人不得修改接口，只能调整内部实现

#### 契约的粗细分界线
✅ **契约必须定**：模块职责边界、输入输出数据结构、字段类型、错误码约定、调用时序
❌ **契约不能定**：内部变量命名、具体实现算法、代码风格、优化方式

#### 成本
- 1次起草 + N次审阅 + 1次冻结，共`N+2`次调用
- 契约一次性生成，后续迭代复用，边际成本递减

#### 反例
- 单文件脚本、单人开发：不用写契约，直接实现即可
- 一次性原型验证：可以先写代码后补契约，不要反过来

#### 字段级设计
```javascript
// 新增契约结构体
interface Contract {
  version: string;
  modules: ModuleDef[];
  globalTypes: TypeDef[];
  errorCodes: ErrorDef[];
}
interface ModuleDef {
  name: string;
  responsibility: string;
  inputs: FieldDef[];
  outputs: FieldDef[];
  dependencies: string[]; // 依赖的其他模块名
}
// 新增阶段类型
PHASE.FREEZE_CONTRACT = 'freeze_contract';
```

### Q6：分头实现时每个AI该看到什么上下文？
**结论：契约全文 + 自己模块的详细需求 + 其他模块的接口摘要，必须新增`CONTRACT`切片类型。**

#### 最小切片内容（三层）
1. **全局层（全量）**：完整的冻结版接口契约（所有模块的接口定义）
2. **专属层（全量）**：分配给当前AI的模块的详细需求、设计约束、验收标准
3. **外部层（摘要）**：其他每个模块的一句话功能描述 + 输入输出列表（不展开实现细节）

#### 为什么不能用现有切片
- 用`TASK`：看不到契约，各写各的接口，最后拼不起来
- 用`ALL`：信息冗余，容易被别人的实现思路带偏，上下文成本O(N²)

#### 成本
- 切片大小 = 契约长度 + 单模块需求长度，约为`ALL`切片的1/N
- 上下文成本从O(N²)降到O(N)

#### 反例
- 写文档、文案类任务：各部分完全独立，不需要接口对齐，用`TASK`即可
- 模块间强耦合、需要频繁联调：不适合分头实现，应该用串行迭代

#### 字段级设计
```javascript
// 新增切片枚举
SLICE.CONTRACT = 'contract';
// 切片配置
{
  slice: SLICE.CONTRACT,
  contractDetail: 'full', // 自己的模块：full
  othersDetail: 'summary' // 其他模块：summary
}
```

### Q7：9人panel的O(N²)怎么降成本？按有效性排序
**排序：摘要压缩注入 > 分组合议制 > 分歧点串行；硬性限员是兜底手段，不是降成本手段。**

#### 1. 摘要压缩注入（有效性第一，降本60%-70%）
- **做法**：每3人发言后，自动调用API生成一段≤300字的中立摘要，后面的人只看「累计摘要 + 最近2人原文」，不看全部历史。
- **效果**：9人串行panel，总上下文量从36份·长度降到约10份·长度，减少约70%。
- **副作用**：信息有损，细节可能丢失；每3人多1次摘要调用（但节省的成本远大于1次调用）。
- **反例**：故障排查、法律评审、安全审计这类极度依赖细节的场景，禁用摘要压缩。

#### 2. 分组合议制（有效性第二，降本40%-50%）
- **做法**：9人分3组，每组3人，组内先开小panel，每组输出1份结论；然后3组代表开大会。
- **效果**：上下文总量从36份降到12份，减少约67%；组内还可以并行，总时长缩短。
- **副作用**：组间信息隔离，容易出现「组内共识、组间互斥」，跨领域视角丢失。
- **反例**：问题本身有明确领域划分，适合分组；完全交叉融合的问题不适合。

#### 3. 分歧点串行（有效性第三，降本30%左右）
- **做法**：前3人并行发言打底，后面的人只针对前面的分歧点发言，不对全部内容重复表态。
- **效果**：单轮发言长度缩短30%左右，减少重复论述。
- **副作用**：容易漏掉新角度，后面的人跟着分歧走，不开拓新话题。
- **反例**：第一轮发散阶段不能用，必须全员完整发言。

#### 补充说明
- 硬性限制`N≤5`是成本上限控制，不是降成本手段；9人场景优先用前三种手段，而不是直接减人。
- 三种手段可以叠加：分组 + 组内摘要压缩 + 分歧点串行，最高降本80%以上。

### Q8：人工中转席位怎么建模？
**结论：建模为`manual_provider`（异步人工席位），符合标准Agent接口，不是纯消息插入。**

#### 和普通席位的核心差异
| 维度 | 普通Agent席位 | 人工中转席位 |
|---|---|---|
| 回复等待 | `waitForResponse()`，自动检测完成 | `waitForManualInput()`，等待用户提交 |
| 完成检测 | 多信号联合自动判定 | 用户手动触发完成信号 |
| 消息数量 | 一次一条 | 支持一次提交多条（对应多个外部AI） |
| 超时时间 | 30-60秒 | 可配置长超时（如24小时） |
| 选角参与 | 自动选角匹配 | 固定角色，不参与自动选角 |

#### 编排上的处理
- 完全复用现有消息总线，人工提交的消息自动拆分为标准`MeetingMessage`，正常参与切片、历史、所有模式逻辑
- 状态机新增`WAITING_MANUAL`状态，UI上显示「等待人工输入」
- 支持批量导入：粘贴多个外部AI的回答，系统自动按来源拆分、打标签

#### 成本
- 开发成本：新增1个provider类型，约100行代码，完全兼容现有接口
- 运行成本：零额外调用，纯人工操作

#### 反例
- 偶尔使用一次：直接手动插入消息即可，无需专门建模
- 所有AI都在系统内：不需要这个类型

#### 字段级设计
```javascript
// 新增provider类型
PROVIDER_TYPE.MANUAL = 'manual';
// Agent状态新增
AGENT_STATE.WAITING_MANUAL = 'waiting_manual';
// 消息新增字段
{
  source: 'external_manual',
  externalSource: string // 标注来自哪个外部AI
}
```

### Q9：从文本到可运行软件，最少几个环节？谁当集成者？
**结论：最少5个环节；集成者必须是独立的「集成工程师」角色，不能复用主持助理。**

#### 最少5个环节与责任分配
| 环节 | 负责角色 | 输出产物 | 核心动作 |
|---|---|---|---|
| 1. 需求冻结 | 产品经理 + 用户代言 | 需求清单（含「不做什么」） | 明确范围，划清边界 |
| 2. 架构与契约冻结 | 架构师 + 主持助理 | 模块划分 + 接口契约 | 定边界、定接口 |
| 3. 分头实现 | 各建设类AI | 各模块代码文件 | 按契约实现各自模块 |
| 4. 集成验证 | 集成工程师（新角色） | 完整代码 + 运行结果 + 错误清单 | 拼装、编译、运行、报错 |
| 5. 修复迭代 | 对应模块的原作者 | 修复后的代码 | 按错误清单修改 |

#### 为什么集成者必须独立
- 主持助理的能力是「文本归并、总结分歧」，不需要懂代码、编译、排错
- 集成工程师的核心约束：**只做集成验证，不修改业务代码**，只输出错误清单，打回原作者修复
- 既当裁判又当运动员会导致责任不清，修复质量不可控

#### 修复责任原则
谁的模块出问题谁修，集成者只定位问题、不解决问题；集成失败时，错误清单精确到模块、行号、错误类型，返回对应作者修复，修复完重新进入集成环节。

#### 成本
- 比普通`divide`模式多2次核心调用（集成+首轮修复），总调用`1+1+N+1+R`（R=修复轮数）
- 新增1个角色定义，约30行代码

#### 反例
- 单文件简单脚本：一个AI从头到尾写完即可，不需要分头+集成
- 原型验证、不要求可运行：跳过集成验证环节，输出文本代码即可

#### 字段级设计
```javascript
// 新增角色
ROLE.INTEGRATION_ENGINEER = 'integration_engineer';
// 角色约束：只做集成编译运行，不修改业务代码，只输出错误清单
// 新增产物类型
interface FileArtifact {
  path: string;
  content: string;
  language: string;
  isRunnable: boolean;
  runResult?: { success: boolean; output: string; error: string };
}
```

## 二、两个模式优化版草案（修正原草案问题）
### 草案A优化：招标评审 `tournament`
| 阶段 | 席位 | 发言方式 | 切片 | 核心产出 | 关键设计 |
|---|---|---|---|---|---|
| 1. 出标 | 建设类 | 并行 | TASK | N份候选方案 | 方案自动编号匿名 |
| 2. 盲评 | 质证类 | 并行 | ALL_SCHEMES | 每份方案的排名+理由 | 看不到他人评分 |
| 3. 定标 | 收敛类 | 顺序 | ALL_EVALUATIONS | 胜出方案+备选方案 | 分位校准后排序 |

| 5. 复评 | 质证类 | 并行 | DRAFT | blocker级批评清单 | 只统计致命问题 |

- **终止**：得分收敛 或 无新增blocker 或 满5轮
- **成本**：中，`N + N + 1 + 2×R`
- **修复原草案问题**：去掉了全员评标，只让质证类评；定标不是单AI决定，是算法校准+收敛者确认；改进只针对胜出者，不全面开花。
