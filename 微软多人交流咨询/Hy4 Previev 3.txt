## 二、文件根因链的施工化（P0→P3，顺序不可颠倒）

第二轮已实证：PDF/图片**不是“偶尔收不到”，而是“永远收不到内容”**（只发了一行 `[PDF文件: xxx]`）；且 `uploadFileToWebview` 的 `ok` 声明后从未被检查 → **上传失败静默继续**。施工顺序：

### P0：给 `attachedFiles` 补真实路径 `localPath`（唯一地基）
评审证据 5 已确认 `attachedFiles` 只有 `{name, text, isImage, dataUrl}`，**没有 `localPath`**，这直接阻塞 AttachmentBus。**用户的文件必须先落盘**：

```js
// desktop/agent/meeting.html —— handleFiles() 内，伪代码
async function handleFiles(fileList) {
  for (const f of fileList) {
    const ext = getExt(f.name);
    const localPath = await saveToDisk(f);      // ★ 落盘到 attachments/ 目录，返回绝对路径
    if (['txt','md','csv','json','log'].includes(ext)) {
      attachedFiles.push({ name: f.name, text: await readText(f), localPath });
    } else {
      // PDF / 图片 / docx：text 仍是占位符，但 ★ 现在有 localPath 了
      attachedFiles.push({ name: f.name, text: `[${ext}: ${f.name}]`, localPath, isBinary: true });
    }
  }
}
```
> 不补 `localPath`，后面所有 ACK 门闩、CDP `setFileInputFiles`、AttachmentBus **全部空转**。

### P1：AttachmentBus + ACK 门闩
- ACK 判据 = **DOM 出现附件卡片 / 上传进度 100%**，**不是** CDP 调用返回（共识 4）。
- 门闩 `Promise.allSettled`；单 AI 超时 → 最多 1 次重试 → 仍失败则**降级**为“文件名+文本摘要”并标 `degraded`，会议继续。
- **根因 B 修复**：`uploadFileToWebview` 的返回值必须检查：
  ```js
  const ok = await uploadFileToWebview(wv, filePath);
  if (!ok) { markDegraded(cell); /* 不再发“（见上传的文件）” */ }
  ```

### P2：CDP 流结束信号接入
把评审验证过的 `stream-tracker.js` + `cdp-driver.js` 搬进客户端；`streamEnd` 作为完成检测的主信号之一，且每轮 `arm()`。

### P3：状态灯 + `charLimit`
- 每个 cell 显示 per-AI 状态机（pending/streaming/completed/failed/timeout）。
- `agentCatalog.js` 给 9 个 provider 补 `charLimit` 字段（修 `fullText.length > undefined` 死代码），默认对齐现有“>4000 字转 .md”逻辑，不再全硬编码 10000。

## 三、补齐第二轮两个盲点（我的完善增量）

### 盲点 A：同质化坍塌 → `RoleDifferentiation` 模块（成本极低，决定产品价值）
**做法**：在 `agentCatalog.js` 给 9 个 AI 各增一个 `persona` 字段；构造 prompt 时加**角色前缀**，并在后续轮做**差异化上下文切片**。

Prompt 模板：
```
[角色] 你是本次会议的红队评审：只找逻辑漏洞与证据缺口，不重复他人结论，必须指出至少 2 个反例。
[本轮任务] 请点评 Kimi 网页关于“成本风险”的结论。
[差异化上下文] B（Kimi）的结论是：{...}；请只针对该结论发言。
[最近 2 轮原文] ...
[更早纪要摘要] ...
```
**9 视角示例**（避免人格噪音，只赋“认知职能”）：
DeepSeek=综合推理 / ChatGPT=红队找漏洞 / Kimi=长文归纳与成本 / 豆包=合规与风险 / 通义=反方唱反调 / 元宝=用户视角与体验 / Gemini=数据核算 / 谷歌搜索=事实核查与引用 / 文心=落地执行步骤。

**UI 增量**：会议面板不只列 9 个回答，而是出**共识/分歧矩阵**（谁同意谁、分歧点在哪）。  
**可测性**：加一条纯逻辑用例——计算 9 个回答的关键词重合度/嵌入相似度，若“分歧度”低于阈值则自动增强角色分化或换切片（不依赖浏览器即可测）。

### 盲点 B：同指纹 9 账号 = 最大风控特征（接受，不假装能解决）
- **不伪造指纹、不轮换账号、不绕过验证码**（与 Hy4-2 一致）。
- 风控系统看的是**设备指纹相关性**，不是请求间隔；错峰/限速只是流量层缓解，**不能消除根因**。
- 缓解：① 主席/选择器/压缩**全部走真实 API**（共识 6）；② 对提供官方 API 的厂商（如 DeepSeek 有 API），其“后台调度”早已是 API，若某天愿意，可把该格子的网页版换成 API 驱动**以彻底规避该账号的设备指纹风险**（但会失去同框网页，需你权衡）；③ 出现验证码 → 立即 `闭麦` + UI 显性提示用户人工处理，**不自动重试风暴**；④ 把“同设备 9 账号”在 UI 上作为**已知风险显性告知**。

### 盲点 C：上下文容量基线（纯逻辑可算）
- **每轮结束**产轮纪要：**≤300 字/轮**。
- **每 5 轮**做一次全局压缩（保留最近 1 轮原文 + 历史摘要）。
- 注入阈值：**累计注入 >6k token 触发单点 reset**（沿用）。
- 新增**纯逻辑容量用例**（不依赖浏览器）：`9 AI × 500字 × 20轮 ≈ 9万字`，测试台直接算纪要膨胀并检查压缩是否把总量压回阈值内。

## 四、回答第二轮留下的 3 个外部问题（这是“继续完善”的核心增量）

### Q1｜角色分化 prompt 工程：怎么最大化“视角差异”而不是“人格噪音”？
1. **正交认知职能优先**：不要给“性格”（如“你是一个愤怒的批评家”→ 噪音），要给**互斥的输出约束**（只看成本 / 只找漏洞 / 只谈合规 / 只做事实核查 / 只做执行步骤）。
2. **差异化上下文 > 相同输入**：轮询制里给不同 AI **不同的前文切片**（A 看 B 的结论、C 看 A+B 的分歧点），比只换角色前缀更能制造真实差异。
3. **主席合成**：用 API 模型做“分歧检测+总结”，把 9 份输出压成共识/分歧矩阵，而不是让网页 AI 互相读全部原文（省 token、降延迟）。
4. **用分歧度闭环**：简单做法=计算 9 个回答的关键词重合度；重合度过高 → 下一轮自动换更互斥的切片或加强角色约束。**这一条可纯逻辑单测**。

### Q2｜同指纹 9 账号的风控阈值：有没有实测数据？
- **没有公开权威阈值**，且各厂商（Google/OpenAI/字节/月之暗面/百度/腾讯）策略不公开；风控模型看的是**同设备多账号的指纹相关性 + 行为聚集**，而非单纯 QPS。
- **不建议你用“小流量灰度到封号”去实测阈值**——成本是丢掉已养了几个月的 `Partitions/` 登录态。
- 正确姿势：**当已知风险接受**；优先把有 API 的能力（主席、压缩、甚至某个 AI 的格子）迁到 API 以**减少同设备上的网页账号数**；错峰/限速/削峰作为缓解；验证码闭麦交人工。

### Q3｜9 家网页 AI 的 context 容量上限与降级行为？（已检索核实）
**模型卡 ≠ 网页端实际可用**，这是关键：

| AI | 官方/主流标称上下文 | 网页端实际注意 |
|---|---|---|
| **DeepSeek 网页版** | **128K tokens**（约 9–10 万汉字，官方 deepseek.com / API Docs 多源确认） | 稳定 128K；超长仍建议分段 |
| **Kimi 网页版** | **200 万字级**（月之暗面长文本领跑；K2 约 2M tokens/140 万汉字量级） | 长文本最强，但网页 UI 另有轮次/文件限制 |
| **豆包** | Pro **256K**（约 16–20 万汉字） | 接近上限时对最早信息记忆模糊 |
| **通义千问** | Max 常 128K；`qwen-long` 可达 1000 万字级 | 网页端通常以 128K 为主 |
| **文心一言** | 约 128K（部分资料称 5.0 更高，以实测为准） | 常规够用 |
| **腾讯元宝（混元）** | 通常 32K–128K（官方未统一明确） | 需实测 |
| **Gemini / 谷歌搜索** | **百万级 token** | 强，但网页 UI 会裁剪 |
| **ChatGPT（GPT-4o/5）** | 128K–320K | OpenAI 坚持 128K 标准，中间段召回率低 |

**超限后的降级行为（最危险）**：
- 多数网页 UI 不是报错，而是**“静默截断前文”（滑动窗口）**——AI 看起来在回答，其实已忘了最早的共识；这就是长会议“越聊越跑偏”的隐形杀手。
- 少数会报 `context_length_exceeded` 或提示“对话过长请新建会话”。
- **“大海捞针 / Lost in Middle”**：信息放开头/结尾召回率高，**放中段明显下降**；工程建议是**只用到标称值的 80%**，关键约束放开头或结尾重述。

> **结论**：容量不能只看模型卡，必须在 `meeting-lab` 里做**拐点实测**——递增注入长度，直到某 AI 的回答开始丢失前文，记录每个 AI 的“可用轮次/字数”并写进 adapter 的 `ctxLimit` 配置。

## 五、完善后的 Phase 0 验收基线（在原来三条上新增）

1. 完成检测：短/长/流式回答都不误判（**带 `requireContent` + `arm()` 回归用例**：退掉修复则测试失败）。
2. 附件：**非文本格式（PDF/图片）在 P0 后能拿到 `localPath` 并上传成功**（根因 A 闭环）；上传失败不再静默发“（见上传的文件）”（根因 B 闭环）。
3. 并发：1 个 AI 卡死/掉线，其余 8 个照常完成（单点隔离）。
4. **新增**：`domStable` 在“AI 尚未生成”时不置真（堵起手即真）。
5. **新增**：`streamEnd` 不跨轮污染（第 2 轮 0ms 内不被误判完成）。
6. **新增**：角色分化后 9 个回答有**可测量的视角差异**（纯逻辑分歧度用例，不依赖浏览器）。
