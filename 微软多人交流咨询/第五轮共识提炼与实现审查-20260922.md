## §2 五家分歧（需你拍板，附我的判断）

### 分歧 1：人工中转该建模成什么？★ 影响 Q8 落地方式

| 家 | 主张 |
|---|---|
| GPT5 | **不要**建模成 Seat。应是 `External Message Import` / `Human Gate`，方法是 `awaitHumanInput()` 而非 `waitForResponse()` |
| 混元 | **两者结合**：message 层加 `senderType:'external'` + `relayBatchId`；席位层加 `providerType:'human-relay'` |
| 豆包 | 建模为 `manual_provider` 席位（复用消息总线） |
| 谷歌 | 必须是**一等公民 provider**（`HumanRelayProvider` 类，`waitForResponse` 返回由 UI 按钮 resolve 的 Promise） |

**我的判断：两家其实不矛盾，可以合并（混元方案 + GPT5 的语义纠正）。**
- GPT5 反对的是"**假装成一个普通 AI 席位**"（会导致编排层对它调 `waitForResponse` 等 CDP 信号）；它并不反对"UI 上有个位子"。
- 落地：**message 层**用 `senderType:'external'` + `relayBatchId` + `sourceName`（这样外部回答**能进 `messages`、能参与切片**，成为一等公民）；**seat 层**用 `providerType:'human-relay'`，但完成信号必须是 `awaitHumanInput()`（UI 按钮 resolve），**明确不走超时/CDP 完成检测**。
- 理由：只有 message 层改造 → UI 上没有"等待人工输入"的可见位子，用户不知道轮到谁了；只有 seat 层改造 → 外部回答进不了消息总线。**两边都要。**

### 分歧 2：终止判据的逻辑关系

| 家 | 主张 |
|---|---|
| 混元 | `winner_stability` **AND** `critique_convergence`，两条件同时满足才停（防提前停） |
| 豆包 | 得分收敛 **OR** 无新增 blocker（满足其一即停，省 token） |
| GPT5 | 五条件：maxRounds / maxCalls / acceptance / critiqueSaturation / winnerStability / minImprovementDelta |
| 谷歌 | `rankDelta < 0.1`（平均名次变化小于阈值） |

**我的判断：用混元的 AND + 硬上限。**
- 你怕浪费 token，但更怕"没收敛就停"（那才是真浪费——错误的结论会带你走错路）。
- 硬上限（`maxIterations`）已经保证不会无限烧，所以 AND 不会导致成本失控。
- 谷歌的 `rankDelta` 是 `winner 稳定性` 的细粒度版（实现用的是粗粒度"同一 winner"），**够用**，不必上 delta。
- ⚠️ **但实现的 AND 只做了一半**：`same-winner` 判据没接 `winnerId`（见 §4.2），且没有 `critique_convergence` 那一半。

### 分歧 3：O(N²) 降本手段的优先级排序

| 家 | 第一名 | 第二名 | 第三名 |
|---|---|---|---|
| GPT5 | **分歧驱动**（只在分歧处形成边） | 分组归并 | 摘要压缩 |
| 混元 | **摘要压缩** | 分组归并 | 硬限人数 |
| 豆包 | **摘要压缩** | 分组合议 | 分歧点串行 |
| 谷歌 | **动态单链剪枝**（O(N)） | 分组并行归并 | 异步非阻塞评注 |

**我的判断：按"摘要压缩"为主（3:1），分歧驱动作为 panel 的可选策略。**
- 摘要压缩：实现最简单（一句话就能接进 `selectSlice`）、收益稳定（GPT5 算 36L→12L，混元算 8.5x）。
- 但有损：四家都警告**法律条款 / 代码 / 精确引用 / 错误日志** 不能压（一个字符都有意义）→ 必须做成 `compressionPolicy.except`。
- 分歧驱动（GPT5）：**省得最多但有坑**，GPT5 自己给了反例 ——"探索阶段找不到分歧 → 误以为没问题"。所以只能用在**收敛阶段**。
- ⚠️ **谷歌的第一名（动态单链）有副作用**：它自己说"中间某个 AI 跑偏且未被识别 → 错误基因被滚动轴继承 → 后排选择性失明"。**这个风险对"疑难排查"场景是致命的。**

### 分歧 4：产物形态

| 家 | 主张 |
|---|---|
| GPT5 | **反对**纯 `{path, content}`，主张 `{artifactId, kind:'patch', path, baseRevision, contractVersion, owner, patch, tests}` —— 防整文件重写覆盖别人改动 |
| 混元 | `{path, content, language, producedBy, round, verified}` |
| 豆包 | `FileArtifact {path, content, language, isRunnable, runResult}` |
| 谷歌 | `{path, content}` + **路径穿越安全校验**（拒绝 `../../etc/passwd`） |

**我的判断：先 `path + content + ownedPaths`，暂不上 patch。**
- GPT5 的担忧是真实的（9 个 AI 同时改 `meeting.js` 会互相覆盖），但**"文件所有权"已经能解决这个问题**，成本远低于 patch 机制。
- 所以：**取 GPT5 的所有权字段（`owner` + `ownedPaths`），不上它的 patch 机制。** 等真出现"多人必须改同一文件"时再上。
- ⚠️ **谷歌的路径穿越校验必须采纳**（零成本，纯安全）：AI 返回的 `path` 是不可信输入，`path.resolve` 后必须校验在沙箱根内。这是**真实的本地安全风险**，不是理论问题。

### 分歧 5：架构层面 —— 要不要抽"原语层" ★ 最根本的分歧

| 家 | 主张 |
|---|---|
| GPT5 | **模式之下应抽出原语**：`CandidatePool / Evaluation / Selection / Validation / Retry / Contract / Artifact / HumanGate / Workspace / TestReport`。模式 = 原语组合。警告"不要越做越乱" |
| 其余四家 | 都不提原语层，直接"新增 2 模式 + 切片 + 角色"（增量） |

**我的判断：方向认同 GPT5，但现在不重构；只做一件低成本的事。**
- GPT5 说得对：**"每种业务再造一个新模式"最终会失控**（10 个模式已经到边际了）。
- 但现在重构会拖死进度，且那个会话正在写代码（撞车）。
- **可立即做、零冲突的一件事**：GPT5 的原话是"**先冻结 `CandidatePool / SelectionPolicy / AcceptanceGate / Artifact / Contract` 这 5 个数据结构和 JSON Schema，再去改 `modes.js`**"。所以：**只写这 5 个数据结构的定义文档 + 对现有实现的映射表**，不动代码。这样将来原语化不用返工。

### 分歧 6：评标矩阵

| 家 | 主张 |
|---|---|
| 谷歌 | **N×N 笛卡尔积**：3 候选 × 3 评审 = 9 次独立调用，每个评审单看一个方案（最彻底隔离） |
| 其余 | 一次把所有候选给评审（成本 N×1） |

**我的判断：不采纳谷歌方案。**
- 成本高 3 倍（N×M vs N）。
- **谷歌自己的反例就否定了它**："候选之间存在强依赖或互补关系时，严禁盲审，否则 AI 会把互补方案判为不完整。" 你的场景（多方案竞争同一问题）常有互补性。
- 保留价值：**它的"单方案孤立评估"思路可以用在"给每份候选单独打分"的轻量版**（即一次调用评一份，但 N 次并行，M=1）。


### §4.1 缺口一：评标切片语义不对 —— 两个已知漏洞都没堵

**现状**（`core/modes.js:296`）：
```js
{ name: '评标', seat: 'challenge', speak: SPEAK.PARALLEL, slice: SLICE.OTHERS },
```
`SLICE.OTHERS` = `messages.filter(m => m.senderId !== selfId)`（`core/modes.js:478-481`）。

**问题 A：评审者看不到自己那份候选。**
- 出标阶段是 `seat:'all'`（全员出标），所以每个评审者**也是出标者**。
- `OTHERS` 把"自己的发言"过滤掉了 → 评审者只能给 N-1 份候选排名 → **每个评审者排的集合都不一样**。
- `bordaMeans` 用"被几个评审者排过"当分母（`core/modes.js:614`），所以不会崩，但**各候选人被排名的次数不同 → 名次均值不可比**。
- 注释里的理由（"ALL 含自己，评标人看到自己的方案会自我加分"）**方向对，但解法错了**：正解是**匿名化**（评审者认不出哪份是自己的），而不是**抽掉**自己那份。

**问题 B：没有过滤"别人的评分"→ 第 2 轮起会跟票。**
- 四家共识（§1 第 7 条）：评标者**不能看到别人的评分**。
- `OTHERS` 会把评标阶段别人写出的名次表也一起注入（它们也是 `messages`）。
- 第 1 轮因 `SPEAK.PARALLEL` 并发发起，确实看不到；但 **`tournament` 是 `loop:true`** → 第 2 轮的评标者能看到第 1 轮所有人的名次表 → **跟票**。
- 混元给了精确的字段名：`otherScores:'NONE'`；GPT5 给的是 `hidePeerScoresUntilLocked:true`。

**解决方向（三家共识一致）**：新增切片 `CANDIDATES`（混元叫 `CANDIDATES`，豆包叫 `ALL_SCHEMES`，谷歌叫 `PROPOSAL_ONLY`），语义 = **注入全部候选方案原文，但过滤掉所有评分/评审类消息**。同时加 `blind`（剥掉 senderId，候选编号为"候选 A/B/C"）。

### §4.2 缺口二：`bordaMeans` / `tournamentStop` 是孤儿代码 ★ 最要紧

**核实结果**（全仓 grep）：
```
bordaMeans / tournamentStop 的调用方 → 只有 test/modes.test.js，生产代码零调用
ballots / ranks 的解析器            → 不存在（只在测试里手写 mock 数据）
shell/index.html:679 →
  const verdict = shouldStop(currentMode, { iteration, critiques, prevCritiques });
  //                              ↑ 没传 winnerId / prevWinnerId / buildPass
```

**后果（三条连锁）**：

| # | 后果 | 证据 |
|---|---|---|
| 1 | `tournament` 的 `same-winner` 判据拿不到 `winnerId` → `tournamentStop` 恒返回 `{stop:false, reason:'尚无定标结果'}` → **智能判停不生效**，只能跑满 `maxIter=3` | `modes.js:638-644` + `shell:679` |
| 2 | `build` 的 `build-pass` 拿不到 `buildPass`（恒 false）→ 恒返回"集成未通过" → 跑满 `maxIter=4` | `modes.js:568-572` + `shell:679` |
| 3 | **定标实际仍是"收敛类 AI 顺序发言拍板"**（`seat:'converge', speak:SEQUENTIAL`）→ 正是混元明确推翻的"脆弱瓶颈且不可复现" | `modes.js:298` |

**这条缺口的本质**（也是本文档最重要的一句）：
> **AI 输出的是自然语言，`bordaMeans` 要的是 `[{reviewer, ranks:[{proposal, rank}]}]`。**
> **这中间的解析器没人写 —— 于是 Borda 链路整条是断的。**

**同类问题会连锁出现在 `CONTRACT` 切片上**（见 §4.4）：`selectSlice` 的 `CONTRACT` 分支需要
`contract.modules:[{owner, module, signature}]`，但契约是架构师用自然语言写的，**同样没有解析器**。

→ **这是贯穿性的系统缺口，不是两个孤立 bug。**

### §4.5 顺带抓到一个真 bug：`chairman` 的多轮追问能力失效

**核实**：
```js
// core/modes.js:223-245  chairman 的定义
chairman: {
  desc: '主持人在每一轮根据分歧点动态点名追问。',   // ← 宣称"每一轮"
  phases: [{ name: '点名发言', seat: 'picker', ... }],
  stopWhen: 'no-new-question',                      // ← 宣称"直到没有新分歧才停"
  // ★ 但没有 loop: true
}
```
而 `shell/index.html:624`：
```js
const maxIter = mode.loop ? (mode.maxIterations || 5) : 1;
// chairman 没有 loop → maxIter = 1 → 只跑一轮
```

**后果**：
- `stopWhen:'no-new-question'` 成了**死代码** —— 第 1 轮 `shouldStop` 恒返回 `{stop:false, reason:'第 1 轮尚无对比基线'}`，紧接着被 `iteration >= maxIter (1>=1)` break 掉。
- **"每轮追问"这个核心卖点从没生效过**，实际退化成"点名一次就散会"。

**顺带修正混元的一个判断**：混元说"`chairman` 缺 `maxIterations` 是成本黑洞"。
- 实测：因为 `loop` 缺失 → `maxIter=1` → chairman 反而**只跑一轮、成本最小**（不是黑洞）。
- 所以"给 chairman 加 `maxIterations`"这个药**对不上症** —— 加了也不会被读（`loop` 为假时 `maxIter` 恒为 1）。
- **真正的修法是先给它 `loop: true`，再加 `maxIterations` 上限**（届时才需要上限）。

> 这个例子说明一件事：**外部 AI 看不到代码，它的判断基于"模式定义应该怎样"；而真 bug 藏在"定义与执行层不一致"的缝里。** 所以五家意见必须过一遍代码核对，不能直接照做。
