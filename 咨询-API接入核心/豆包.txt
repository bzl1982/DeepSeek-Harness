问题：内置哪些适配器覆盖主流；中转站全部按 openai‑chat 兼容是否足够；字段级接口、差异清单。

Q2 模型列表自动拉取，缓存降级，元数据来源
一句话结论：优先调用协议原生 listModels；拉取失败使用本地缓存；元数据（contextWindow/multimodal/support_reasoning）不要完全依赖 API 返回；采用「接口返回优先 + 内置静态兜底字典」；过期缓存 TTL=24h。
成本：代码≈350 行；维护负担：静态元数据字典需要跟随新模型迭代更新；性能开销：单次网络请求；缓存落盘 JSON。
反例：不要完全信任中转返回/v1/models，部分中转返回空数组、返回重复模型 id；不要每次打开设置页面都重拉模型列表。
伪代码流程：
plaintext
listModelsFlow(provider):
  1. 读取provider.modelCache，判断updatedAt是否在24h以内 && cache不为空
      → 缓存有效，直接返回缓存

Q3 密钥本地存储选型：safeStorage vs keytar vs yaml 明文
一句话结论：单机 Electron 单用户场景优先选择 safeStorage；但必须做可用性判断；当isEncryptionAvailable()===false直接禁止保存密钥，绝不降级明文存储；不推荐 keytar，不允许明文 yaml。
成本：代码≈120 行，零 npm 依赖（safeStorage 是 Electron 内置模块）；维护负担低。
反例：绝对不能在 safeStorage 不可用的时候自动 fallback 明文写磁盘；不要用 keytar：keytar 需要额外 npm 包；Windows 部分企业策略禁用系统凭据服务，keytar 也会失效，且打包 electron‑builder 处理 keytar 容易踩坑。
可运行最小代码片段（主进程！safeStorage 仅主进程调用，renderer 不能直接访问）
javascript
运行
// main process
const { safeStorage } = require("electron");

function encryptSecret(plaintext) {
  if (!safeStorage.isEncryptionAvailable()) {
    throw new Error("ENCRYPTION_UNAVAILABLE：当前系统不支持加密，禁止保存密钥");
  }
  const buf = safeStorage.encryptString(plaintext);
  return buf.toString("base64");
}

function decryptSecret(base64Enc) {
  if (!safeStorage.isEncryptionAvailable()) {
    throw new Error("ENCRYPTION_UNAVAILABLE");
  }
  const buf = Buffer.from(base64Enc, "base64");
  return safeStorage.decryptString(buf);
}

业务规则：UI 层面，如果加密不可用：弹窗警告；只允许临时内存使用密钥，拒绝持久化存储密钥。
你的草案薄弱点修正：你原先没有处理isEncryptionAvailable失败分支，会出现静默明文漏洞。
Q4 50 席位并发流式输出，信号量限流，DOM 渲染节流
一句话结论：两层限流：全局 HTTP 信号量（默认 6） + 每个 provider 独立二级信号量；渲染层采用「每个席位独立消息队列 + requestAnimationFrame 合并批量 DOM 刷写」；50 席位不需要立刻上完整虚拟列表，但要强制队列节流；DOM 不做每 delta 直接 appendChild。
成本：代码≈400 行；内存开销：每个席位维护 delta 队列；50 席位同时全流式极端场景，内存峰值会升高；延迟：信号量排队会带来请求排队延迟。
反例：不要无限制同时开启 50 个 fetch SSE 流；不要每收到一个 delta 就操作 DOM；不要全局单一信号量忽略服务商独立 rate‑limit。
字段级数据结构
javascript
运行
/** 全局并发信号量状态 core/concurrency‑semaphore.js */
const ConcurrencyState = {
  global: { max:6, running:0, queue:[] },
  perProvider: new Map(), // providerId → {max: number, running:0, queue:[]}
};

/** 每个席位渲染队列对象（renderer进程） */
class SeatRenderQueue {
  constructor(seatId) {
    this.seatId = seatId;
    this.pendingContent = "";
    this.pendingReasoning = "";
    this.flushScheduled = false;
  }
  appendContent(text){ this.pendingContent += text; }
  appendReasoning(text){ this.pendingReasoning += text; }
  // rAF批量刷DOM，合并多次delta
  flush() {
    if(this.flushScheduled) return;
    this.flushScheduled = true;
    requestAnimationFrame(()=>{
      // 一次性把pendingContent/pendingReasoning更新到DOM，而不是逐字符插入
      this._writeDom();
      this.pendingContent = "";
      this.pendingReasoning = "";
      this.flushScheduled = false;
    })
  }
  _writeDom() { /* DOM更新逻辑 */ }
}

关键参数建议：全局信号量默认max=6；每一个 provider 可配置独立 max 并发，默认 4。
实测坑：Electron renderer 页面 50 个 SSE ReadableStream 同时存活不会直接崩溃，但大量并发网络会触发操作系统 TCP 端口耗尽、服务商 429 限流，必须信号量排队。
是否虚拟化？：50 席位同时可见 N 宫格，如果开启 50 格同时显示 DOM 节点数量巨大；建议 UI 支持分组折叠，不活动的席位格子设置display:none释放 DOM；如果用户同时打开全部 50 个可见，后期迭代再加虚拟滚动，第一版不必做。
Q5 会话上下文管理，存储、截断、usage 统计
一句话结论：会话元数据 + messages 历史：内存常驻当前激活席位；非激活席位按需从 JSON 文件懒加载，不要全部 50 席位完整消息常驻内存；第一版不引入 SQLite，JSON 文件足够；提供三种上下文策略：自动截断、摘要（可选高级功能）、用户手动裁剪；统一聚合 usage，兼容各协议 SSE 不一定返回 usage 块。
成本：≈450 行；反例：不要把全部 50 席位完整 messages 全部放在内存，长会话 50 份大上下文会内存爆炸；不要假设 SSE 流一定返回 usage 字段。

Q3 密钥本地存储选型：safeStorage vs keytar vs yaml 明文
一句话结论：单机 Electron 单用户场景优先选择 safeStorage；但必须做可用性判断；当isEncryptionAvailable()===false直接禁止保存密钥，绝不降级明文存储；不推荐 keytar，不允许明文 yaml。
成本：代码≈120 行，零 npm 依赖（safeStorage 是 Electron 内置模块）；维护负担低。
反例：绝对不能在 safeStorage 不可用的时候自动 fallback 明文写磁盘；不要用 keytar：keytar 需要额外 npm 包；Windows 部分企业策略禁用系统凭据服务，keytar 也会失效，且打包 electron‑builder 处理 keytar 容易踩坑。
可运行最小代码片段（主进程！safeStorage 仅主进程调用，renderer 不能直接访问）

运行
// main process
const { safeStorage } = require("electron");

function encryptSecret(plaintext) {
  if (!safeStorage.isEncryptionAvailable()) {
    throw new Error("ENCRYPTION_UNAVAILABLE：当前系统不支持加密，禁止保存密钥");
  }
  const buf = safeStorage.encryptString(plaintext);
  return buf.toString("base64");
}

function decryptSecret(base64Enc) {
  if (!safeStorage.isEncryptionAvailable()) {
    throw new Error("ENCRYPTION_UNAVAILABLE");
  }
  const buf = Buffer.from(base64Enc, "base64");
  return safeStorage.decryptString(buf);
}

业务规则：UI 层面，如果加密不可用：弹窗警告；只允许临时内存使用密钥，拒绝持久化存储密钥。
你的草案薄弱点修正：你原先没有处理isEncryptionAvailable失败分支，会出现静默明文漏洞。
Q4 50 席位并发流式输出，信号量限流，DOM 渲染节流
一句话结论：两层限流：全局 HTTP 信号量（默认 6） + 每个 provider 独立二级信号量；渲染层采用「每个席位独立消息队列 + requestAnimationFrame 合并批量 DOM 刷写」；50 席位不需要立刻上完整虚拟列表，但要强制队列节流；DOM 不做每 delta 直接 appendChild。
成本：代码≈400 行；内存开销：每个席位维护 delta 队列；50 席位同时全流式极端场景，内存峰值会升高；延迟：信号量排队会带来请求排队延迟。
反例：不要无限制同时开启 50 个 fetch SSE 流；不要每收到一个 delta 就操作 DOM；不要全局单一信号量忽略服务商独立 rate‑limit。

  global: { max:6, running:0, queue:[] },
  perProvider: new Map(), // providerId → {max: number, running:0, queue:[]}

/** 每个席位渲染队列对象（renderer进程） */
class SeatRenderQueue {
  constructor(seatId) {
    this.seatId = seatId;
    this.pendingContent = "";
    this.pendingReasoning = "";
    this.flushScheduled = false;
  }
  appendContent(text){ this.pendingContent += text; }
  appendReasoning(text){ this.pendingReasoning += text; }
  // rAF批量刷DOM，合并多次delta
  flush() {
    if(this.flushScheduled) return;
    this.flushScheduled = true;
    requestAnimationFrame(()=>{
      // 一次性把pendingContent/pendingReasoning更新到DOM，而不是逐字符插入
      this._writeDom();
      this.pendingContent = "";
      this.pendingReasoning = "";
      this.flushScheduled = false;
    })
  }
  _writeDom() { /* DOM更新逻辑 */ }
}

关键参数建议：全局信号量默认max=6；每一个 provider 可配置独立 max 并发，默认 4。

是否虚拟化？：50 席位同时可见 N 宫格，如果开启 50 格同时显示 DOM 节点数量巨大；建议 UI 支持分组折叠，不活动的席位格子设置display:none释放 DOM；如果用户同时打开全部 50 个可见，后期迭代再加虚拟滚动，第一版不必做。

Q7 单机单用户最小权限模型；区分哪些是过度设计

Q8 对话界面布局；ASCII 示意图；和现有 N 宫格 webview 共存方案
一句话结论：复用现有 N 宫格格子；格子两种模式互斥：webview 网页 AI / API 对话面板；点击格子切换模式；参数面板内嵌格子右侧固定 240px；50 席位依靠滚动 + 分组折叠；不新开独立浏览器窗口，不使用全局 Tab。
成本：CSS+DOM 代码≈600 行；反例：不要为 API 席位搞一套完全独立窗口体系，会割裂现有的人工分发甲板群发通路。

Q9 附件统一抽象；图片 / PDF / 文本文件跨协议映射
一句话结论：定义统一 Attachment 抽象层；附件分为文本、图片、二进制 PDF；适配器内部把统一 Attachment 翻译成各厂商请求体格式；PDF 绝大多数模型原生不支持，第一版默认做文本提取，把 PDF 文字内容注入 prompt，二进制 PDF 只传给明确支持的模型。
成本≈300 行；反例：不要直接把原始 PDF 二进制 base64 无脑传给所有模型；大量 base64 图片会显著增大请求体，占用内存。

  extractedText: string|null, //pdf提取出的文本；如果图片OCR后续可扩展
  sizeBytes: number
}
