## §一 实测裁决（本轮新做，终结 3 个各家互怼的点）

| 裁决点 | 各家说法 | **实测结果** | 定案 |
|---|---|---|---|
| renderer 能否直调 safeStorage | 千问"可以"；豆包/元宝"仅主进程" | **`require('electron').safeStorage` 在本机 renderer = undefined**（加密解密均不可用） | **豆包/元宝对，千问错**。SecretStore 必须放主进程，renderer 走 `ipcRenderer.invoke`（与现有 `cdp-set-files` 同模式） |
| agne 中转 /v1/models 靠不靠谱 | 元宝"中转常返回伪 id"；谷歌"中转列表常含废弃模型" | HTTP 200、标准 `data[]`、12 模型，字段只有 `id/object/created/owned_by/supported_endpoint_types` | **可用但无任何元数据**——"模型 id 从远端拉、能力从本地表"双层结构证实 |
| Gemini 原生 /models 元数据 | 元宝"inputTokenLimit 可推断"；谷歌"id 带 models/ 前缀要洗" | 61 模型，**自带 inputTokenLimit(1M)/outputTokenLimit(64K)/thinking 字段**；id 确实带 `models/` 前缀 | **Gemini 是唯一元数据自足的协议**；`gemini-3.6-flash` 属 3.x 系 → 思考映射走 `thinkingLevel` 分支（谷歌硬货证实） |

## §二 Q1-Q9 共识与裁断（★=已定案，◐=待你拍板）

### Q1 协议适配器
- 共识 6/6：**内置 3 原生适配器** `openai-chat / anthropic-messages / gemini-native`；**中转站一律 openai-chat 兼容，绝不为中转单写适配器**；统一接口 `listModels() + chatStream(onEvent)`；system prompt 位置差异三家三处（messages 首位 / 顶层 system / systemInstruction）；零依赖 fetch 不引官方 SDK。
- 分歧 openai-responses：3 做 vs 3 不做。**★裁断：暂不做**——交集是"不做默认、不阻塞主线"，且我们现有端点（agne/google/deepseek）无一路需要它；等真接 o 系/gpt-5 官方再加。
- 独占硬货（采纳）：元宝"中转只需覆盖 /models、auth 头、reasoning 三处 override"；豆包"`reasoning_content` 别名兼容（thinking_content/reasoning）+ baseURL 尾斜杠 normalize"；千问"Gemini 流是 NDJSON 非 SSE，或用 `?alt=sse` 转标准 SSE"。

### Q2 模型列表
- 共识 6/6：**远端拉 id + 本地静态表补元数据 + 缓存 TTL 24h + 失败逐层降级**（缓存→静态→手动填）。
- **实测补强**：agne 实测无元数据字段 → 静态表不是"兜底"而是**必需品**；Gemini 实测自足 → 它的静态表可以最薄。
- 独占硬货（采纳）：Gemini 家"直接抓 **LiteLLM 的 model_prices_and_context_window.json** 当本地基准表，免自建"；ChatGPT"200 + 空数组**不覆盖旧缓存**，标记 suspicious"；ChatGPT"模型状态机 AVAILABLE/STALE/UNAVAILABLE/MANUAL，远端消失不删席位"。

### Q3 密钥存储
- 共识 6/6：**safeStorage 加密 + 本地 JSON + keytar 不用**。
- 分歧（不可用时降级）：3 家"禁止保存弹窗" vs 元宝"口令派生 AES-GCM" vs Gemini"base64 混淆（被全场孤立）"。**★裁断：禁止明文，不可用即弹窗禁止保存**——本机 Win11 实测 safeStorage 可用的概率极高，降级路径是死代码不如不做；真要做选元宝的口令方案，绝不 base64。
- **实测定案**：SecretStore 放**主进程**，暴露 IPC：`secret:save / secret:load / secret:test`。
- 独占硬货：谷歌"跨机器拷贝配置必炸（SID 不同解密抛异常）——想多机同步就别用 safeStorage"；豆包"失效场景不止 DPAPI 坏：Windows 设备加密关闭、WSL 远程也会失效"。

### Q4 50 席并发与渲染
- 共识 6/6：**delta 入缓冲 + rAF 合帧刷 DOM，严禁每 token 直改 DOM**；第一版不上虚拟列表；流式期 textContent 纯文本、结束后才 Markdown 渲染。
- 分歧（限流）：限流派 4 家（全局 8-12 + provider 二级） vs 谷歌系 2 家"不限流、429 反馈即可"。**★裁断：采纳限流派，但限流维度必须是 provider 而非席位**（元宝硬货："50 席可能 30 席同属一个中转"——本机 3 家提供方，全局 8 + 每提供方 3 起步）；同时采纳 ChatGPT 的 **429 Retry-After 自适应降档**（连续成功 N 次恢复）作为不限流派的诉求补偿。
- 独占硬货（采纳）：ChatGPT"**流式请求禁自动重试**——3000 token 后断线重试=两份回答；partial + interrupted + 用户点继续"；豆包"50 流不崩 renderer 但会 TCP 端口耗尽"；ChatGPT"请求生命周期状态机 + requestId 防串线"；豆包"SSE 中断必须清残留 delta 缓冲"。

### Q5 会话上下文
- 共识 6/6：**V1 不上 SQLite**（JSON/JSONL + 内存）；**滑窗截断保留 system prompt 从最旧丢**；usage 缺失时本地估算补"虚拟 usage 事件"。
- 分歧（自动摘要）：ChatGPT/元宝要 vs 豆包/谷歌强烈反对（"摘要损坏推理逻辑与角色设定"）。**★裁断：V1 不做**——先滑窗 + UI 红色预警，真出现长会话痛点再上。
- 独占硬货（★★★ 必须采纳）：ChatGPT"**上下文用量 ≠ 各轮 prompt_tokens 累加**（每轮都带全量历史）——UI 显示 `contextTokensAtSend`（最近一次请求的输入量），累计值只做花钱统计另列"；元宝"截断判断公式要把 reasoning token 预算算进去：`projected = history + newInput + maxTokens + reasonBudget > contextWindow × 0.8`"；豆包"非激活席位历史懒加载，不常驻内存"。

### Q6 思考等级映射
- 共识 5/6：**DeepSeek 是模型路由不是参数**（chat⇄reasoner）；映射在适配器层做、统一参数绝不透传；Claude 开思考需 budget≥1024 且 < max_tokens 并同步调大 max_tokens。
- 分歧（档位）：三档派 4 家 vs 五档派 2 家（ChatGPT"三档必返工"）。**★裁断：五档 `off/low/medium/high/auto` + `budgetTokensOverride` 高级数字框**——豆包自己给的 Claude 映射（standard→1024/max→8192）就超出三档能表达的粒度，五档成本与三档相同（都是映射表查表）。
- 分歧（UI）：置灰派 3 家 vs 隐藏派 2 家。**★裁断：置灰 + Tooltip**（宫格对齐不闪烁）。
- 独占硬货（★★★）：元宝"**Anthropic 新模型已改 adaptive thinking**（`thinking:{type:'adaptive'}` + `output_config.effort`，部分新模型不吃 temperature/top_p）——映射函数按模型正则分新旧两套"；谷歌"不要对老模型注入 `<think>` prompt 假装思考：SSE 无独立 reasoning 通道，渲染器分不开"。
- **实测补强**：本机 gemini-3.6-flash 有 `thinking` 字段 → 走 `thinkingLevel` 分支；Gemini 2.5 走 `thinkingBudget`。

### Q7 权限管理
- 共识 5/5：**坚决不做 RBAC/角色/用户表**；能力开关三件套（图片/文件/系统提示词编辑）+ 每席位 token 上限；"Dollar 预算不可行、max_tokens 才是防死循环的物理手段"。
- **★裁断**：采纳谷歌 `maxTokensPerRequest`（默认 4096，**UI 上不锁死**——谷歌自己的反例：长篇协同/大工程分析时 4096 会拦腰掐断）+ ChatGPT 的 **capability/policy 分离**（"模型支持联网"是元数据，"本席位允许联网"是席位配置，别混）+ 谷歌"开关联动 UI：关掉 allowImages 就隐藏 + 号里的图片入口，而不是提交时报错"。
- 本地收编：现有"自动上传白名单"逻辑收编为 perms 字段，不再旁路。

### Q8 对话界面
- 共识：**绝不新开子窗口**（5/5）、**绝不 50 Tab**（3/5）、**输入框[+] + 右侧 240px 参数栏**（上下文用量/思考等级/模型选择器，3/5 数字一致）、50 席分组折叠。
- 分歧：原地切换派 4 家 vs ChatGPT 独立 Focus 面板派 1 家（反对理由：格子内互换的 webview 生命周期/焦点管理更复杂）。**★裁断：第一版原地切换**（4 家共识 + 侵入最小），但**吸收两条反对派约束**——豆包"**切走时必须销毁 webview DOM 节点，display:none 不释放内存**"；ChatGPT"焦点与滚动位置要显式管理"。真到 50 席卡了再升级 Focus 面板。
- **实测补强**：本机 gemini-3-flash 上下文 1M——右侧用量条按模型元数据动态取分母。

### Q9 附件
- 共识 5/5：统一 Attachment 抽象 + 三协议图片映射表（三家给的字段一字不差）；文本文件拼进 prompt；**PDF 默认本地提取文本**（补上现有 `UNSUPPORTED_FORMAT_FOR_API` 的洞）。
- 独占硬货（采纳）：ChatGPT"**50 席群发同一附件别复制 50 份 base64——独立附件实体 + per-provider 上传一次拿 file_id 复用；Gemini Files API 只存 48 小时，remoteId 必须带 expiresAt**"；谷歌"表格/图纸/扫描件 PDF 提取纯文本=乱码，强制引导走 gemini-native"。
- 本地注意：agne 中转大概率不透传 file 上传接口——file_id 方案在纯中转下退化为内联 base64，设计时留 `transport: 'inline'|'remote'` 字段。

### 6.3 DP 新增的其余要点

- **Q2 元数据源升级**：DP 给了完整实现——**LiteLLM 表（定价+窗口）+ models.dev api.json（能力标记更全，4000+ 模型）两级查找**，比单用 LiteLLM 更全；注意 LiteLLM 表约 2MB、models.dev 约 5MB，首次加载 1-3 秒后走缓存；**离线环境必须打包 bundled snapshot**。
- **OpenRouter 特殊性**：它的 /v1/models 返回 rich metadata（context_length/pricing/supported_parameters）——若 provider 是 OpenRouter 直接用自家元数据，跳过两级查找。
- **Q7 修正**："编辑系统提示词"不是权限是基本配置（推翻豆包/谷歌/元宝的三件套之一）——采纳，三件套改为：图片开关 / 文件开关 / maxTokensPerRequest；另加 DP 的 `maxConcurrentRequests: 1`（席位级防手滑双发）。
- **对"上 OpenRouter 统一网关"的否定论证**（回答了 ChatGPT 埋的问题）：多一跳费用（约 5%）+ 单点故障 + 延迟；正确用法是把 OpenRouter 当一个普通 openai-chat provider。
- **总量口径**：DP 估 4000 行 / 10 步——与其他家一致；其 Step8/9（并发+渲染节流）放最后的"先跑通再优化"与我们的顺序冲突，**不采纳**（50 席场景渲染防火墙必须先进，谷歌 80 行成本极低）。

### 6.4 修订后的最终共识快照

- 协议：3 适配器 V1（responses 缓做）——7/7 不变
- 密钥：safeStorage **主进程** + secrets.json/providers.json 分离 + 原子写入；不可用→base64 混淆+显式警告（DP/Gemini 派 2:3，仍以禁止派为原则但 DP 的"警告式混淆"比静默安全，作为代码路径保留）——微调
