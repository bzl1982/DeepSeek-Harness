## Q3 密钥本地存储

### 【共识】
- **Electron safeStorage 加密 + 本地 JSON 文件（userData 目录）** —— 6/6，无异议。千问："Electron 官方推荐的标准做法"；文心对照组缺失。
- **keytar 不推荐**（native 编译坑 / 项目 2022 年已归档 / electron-builder 打包踩坑）—— 5/6（谷歌以对比表形式同样给出低分）。
- **密文与配置分离存储、文件损坏 try-catch 容错**：豆包、ChatGPT（credentialId 关联）、元宝（providers.json / credentials.json 分离）—— 3/6 明确。

### 【分歧】★ 本题最大冲突：safeStorage 不可用时怎么办
- ChatGPT：**禁止明文降级**。已有密钥可临时内存使用；新密钥禁止持久化，提示"安全存储不可用"。
- 豆包：同上，`isEncryptionAvailable()===false` 直接抛错禁止保存，UI 弹窗。
- 千问：直接 throw error。
- 元宝：**用户口令派生密钥的 AES-GCM（Web Crypto / node:crypto scrypt）** 作为替代加密方案，而不是明文。
- **Gemini：静默降级为 base64 混淆存储**，自评"防君子不防小人，单机够用"——与全場对立，且直接违背 ChatGPT"不要自动降级到明文"的红线。
- 谷歌：未给降级方案。
- → 3 家"禁止保存" vs 1 家"口令加密" vs 1 家"base64 混淆"。

### 【独占硬货】
- ★★★（豆包 + 元宝）**safeStorage 只能在主进程调用，renderer 不能直接访问**——豆包代码注释明确"main process"；千问代码注释却说"可在主进程或拥有 Node 集成的渲染进程运行"，两家矛盾，需实测（关系到本项目 renderer 有 Node 集成的架构能否直接用）。
- ★★★（豆包）safeStorage 失效的具体触发场景清单：Windows 设备加密关闭、WSL 远程、mac 无钥匙串——不止"DPAPI 坏了"一种。
- ★★（谷歌）**跨机器拷贝配置必炸**：机器 A 加密的 blob 拷到机器 B，因用户 SID/硬件凭证不同 decryptString 直接抛异常——反例："未来想多台电脑同步 API key"就不能用 safeStorage。
- ★★（元宝）DPAPI 保护边界：防"别的 Windows 用户"，**不防同用户下的恶意进程/木马**；renderer 绝不持有明文，解密只放主进程。
- ★（ChatGPT）node-keytar 已 2022 年归档；建议包一层 SecretStore 抽象，Electron 升级 API 变化时不动业务层。

### 【本地核对提示】
- **renderer 有 Node 集成能否直接 require('electron').safeStorage**——本项目主窗口是 renderer 侧代码，若 safeStorage 仅主进程可用，需要走 IPC 或把 SecretStore 放主进程（千问与豆包/元宝说法冲突，实测 5 分钟可定）。
- 现状蹭读 `~/.dsh/.credentials.yaml` 明文——迁移到 safeStorage 后旧文件是否保留只读兼容。
- 本机 Windows 11 的 `isEncryptionAvailable()` 实际返回值（设备加密是否开启）。

## Q4 50 席位并发与渲染

### 【共识】
- **每席位 delta 先入缓冲，requestAnimationFrame 合帧批量刷 DOM，严禁每 delta 直接改 DOM** —— 6/6，且人人给了可运行实现。谷歌量化反例："50 流 × 每秒 10 chunk = 每秒 500 次 DOM 重绘，UI 线程完全锁死"。
- **第一版不上虚拟列表**（50 个轻量卡片 DOM 完全扛得住，真杀手是消息历史列表/Markdown 重排）—— 5/6。
- **流式阶段纯文本 textContent / TextNode 追加，结束后再整体 Markdown 渲染** —— 4/6（ChatGPT、Gemini、谷歌、千问）。
- **AbortController 必须贯穿，提供单席位/全局停止按钮** —— Gemini、谷歌、ChatGPT（分层 stop）—— 3/6。

### 【分歧】★ 用户点名的直接冲突：本地信号量限流
- **限流派（4 家）**：
  - ChatGPT：全局 8 + provider 2 + credential 2 + seat 1（四级信号量）；
  - 元宝：全局 8-12 + 按 provider 二级，provider 并发可从 rpm/20 经验折算，Ollama 本地降到 1-4；
  - 豆包：全局 6 + 每 provider 默认 4；
  - 千问：全局 10。
- **不限流派（2 家，均为谷歌系）**：Gemini"无需全局限制，瓶颈在网络响应而非本地 CPU"；谷歌"强烈建议不限流，低信号量会让第 7 个席位人为卡顿；429 应由适配器捕获返回 UI 提示，而不是本地自我设限"。
- → 双方理由：限流派怕 TCP/文件句柄/中转限流被打爆；不限流派怕人工编排延迟。不可和稀泥，需实测。

### 【独占硬货】
- ★★★（元宝）**"按席位数限流"是错误抽象：50 席可能 30 席同属一个中转，会瞬间把中转限流打满**——必须按 provider（甚至 credential）维度限流，不是按 seat。
- ★★★（ChatGPT）**流式请求禁止自动重试**：输出 3000 token 后断线自动重试会生成两份回答；正确做法是 partial answer + status=interrupted + 用户点"继续"（继续 = 新 turn）。
- ★★（ChatGPT）429 自适应降档：读 Retry-After → provider cooldown → maxConcurrent 2→1 → 连续成功 N 次恢复——比手工猜各家限流强。
- ★★（豆包）实测坑：50 个 SSE 流不会崩 renderer，但会触发 **操作系统 TCP 端口耗尽** 和服务商 429。
- ★★（豆包）50 席分组折叠，不活动格子 `display:none` 释放 DOM；后期才考虑虚拟滚动。
- ★（ChatGPT）请求生命周期状态机 QUEUED/RUNNING/CANCELLING/COMPLETED/FAILED/CANCELLED/TIMEOUT + requestId/sessionId/turnId——50 路并发没有 ID 会串线。
- ★（豆包）SSE 中断后残留 delta 缓冲区必须清空，否则"脏消息乱入其他对话窗口"（与 ChatGPT 的 requestId 方案互为补充）。
- ★（元宝）合帧间隔 16-33ms；flush 里追加 TextNode 而非重建消息 DOM；全局 scheduler 单帧预算 10ms 防卡死。

### 【本地核对提示】
- 现有 api-adapter.js 已有单请求 AbortController 超时——扩展为"每席位可中断 + 全局停止"时的复用方式。
- 灯箱点亮入会机制（当前 3 席）与信号量排队状态 QUEUED 的 UI 呈现如何共存。
- replies 归档是追加式——流式中断（partial）时归档文件写不写、何时写，需定规则。

## Q5 会话上下文管理

### 【共识】
- **V1 不上 SQLite**（原生模块编译噩梦/读写频率低不值得），JSON/JSONL 落盘 + 内存即可 —— 6/6。谷歌："Electron + SQLite 经常版本冲突"；千问："历史超 1000 条再考虑"。
- **滑动窗口截断：始终保留 system prompt，从最旧的非 system 轮开始丢** —— 6/6。
- **内存为主 + 异步落盘** —— 6/6；形态分歧小：JSONL 追加（ChatGPT/元宝/Gemini/谷歌）vs 每席位一个 JSON 文件（豆包/千问/谷歌 history/<seatId>.json）。
- **usage 缺失时本地估算兜底**（适配器补发"虚拟 usage 事件"/打"估算"标记）：豆包、谷歌、千问 —— 3/6。

### 【分歧】
- **自动摘要（compact）要不要**：ChatGPT 要（70% 提醒 / 85% 自动 compact / 92% 强制，compact = system + 摘要 + 最近 N 轮"而非机械砍头"）；元宝要（截断后再摘要作为第二层）；**豆包明确反对**（"摘要第一版不要实现，增加大量复杂度"）；**谷歌最强烈反对**（"禁止自动摘要，摘要会损坏模型的推理逻辑和角色设定"）；Gemini/千问只做滑窗。→ 2 vs 2 明确对立。
- **触发阈值各家不一**：ChatGPT 70/85/92%；豆包 95% 弹窗三选；元宝 warnRatio 0.8；谷歌/千问到上限才截。无共识值。
- **50 席全量历史内存估算差 10 倍**：Gemini"50 席 × 100K token ≈ 20MB，V8 完全可控" vs 千问"每席 1-5MB，50 席约 250MB"。→ 豆包居中：只把激活席位历史放内存，其余懒加载。

### 【独占硬货】
- ★★★（ChatGPT）**上下文用量不能把各轮 prompt_tokens 累加**：第 1 轮 2k + 第 2 轮 4k + 第 3 轮 8k ≠ 当前 14k（每轮请求都带全量历史）；应分列记录 lastRequestInputTokens / contextTokensAtSend / sessionCumulative（累计仅用于花钱统计）——这是右侧"上下文用量"UI 的正确数据基础。
- ★★★（元宝）发送前截断判断公式：`projected = estimatedTokens(history) + newInput + maxTokens + reasonBudget > contextWindow × 0.8`——**reasoning token 也要预留**；NormalizedUsage 应含 cacheRead/cacheWrite 字段（Claude 新模型有）。
- ★★（豆包）50 席历史懒加载：只有当前激活席位完整 messages 驻内存，切换席位再从磁盘读。
- ★★（谷歌）中文 ≈1 字 × 2 token、英文 ≈1 词 × 1.3 的估算系数（豆包版：中文 1 字 ≈1.3 token——两家系数不一致，均为粗估用途）。
- ★（千问）两段式 UI：实时估算显示"预估用量"，onDone 收到精确 usage 后校准。
- ★（谷歌）JSONL 落盘按"完整交互回合"一行，不是按单条 message。

### 【本地核对提示】
- 现有 replies/<席位名>.md 归档（追加式）与新 session-store 的关系：是共存（归档给人看、JSONL 给程序用）还是合并——各家未讨论，需自定。
- 本地事实"usage 解析了但只透传"（G7）——按 ChatGPT 的"分列记录"方案重构累计逻辑时注意别把累计 prompt 当上下文占用。

### 【共识】

- **Anthropic 开思考时 budget_tokens 必须 ≥1024 且 < max_tokens，需同时调大 max_tokens** —— 元宝、谷歌、千问（代码里同时设 max_tokens 16384）—— 3/6。

### 【分歧】★ 档位数与 UI 降级

  - 五档派（2 家）：ChatGPT minimal/low/medium/high/max + auto（"你的 off/standard/max 太粗，各家 thinking 已明显分叉，简单 reasoning:'high' 以后一定返工"）；元宝 off/low/medium/high/auto。
- **不支持思考时 UI 隐藏还是置灰**：

### 【独占硬货】
- ★★★（元宝）**Anthropic 新模型已改 adaptive thinking：`thinking:{type:'adaptive'}` + `output_config.effort=low/medium/high/xhigh/max`，且部分新模型不再接受 temperature/top_p**——老式 `thinking:{type:'enabled',budget_tokens}` 只适用旧模型；映射函数要按模型正则分两套。
- ★★★（谷歌）**不要对不支持思考的老模型强行注入 `<think>` prompt 假装思考**：推理开销暴增，且 SSE 流里没有独立 reasoning_content 通道，流渲染器无法分离思考区——这是"伪装思考"反例的完整机理。
- ★★（ChatGPT）OpenAI 档位已超出 low/medium/high（有 xhigh/max/minimal/none）；Gemini 3.x 用 `thinkingLevel=MINIMAL/LOW/MEDIUM/HIGH` 且**部分型号不能彻底 off**，2.5 用 `thinkingBudget`（0 关 / -1 自动 / N 数字）——两代 Gemini 参数不同；Ollama `/api/show` 返回 `thinking.values` 让模型自己声明档位。
- ★★（豆包）Claude 具体映射值：standard→1024 / max→8192（谷歌版 standard→2048/max→8192，元宝按 maxTokens 比例 0.1/0.3/0.6——三家给的数字互相矛盾，均为经验值）。
- ★（元宝）Gemini 映射：off→budget 0（Flash 可关、Pro 不一定）、auto→-1。

### 【本地核对提示】
- DeepSeek reasoner 映射（自家端点表有 deepseek chat/reasoner）按"模型路由"实现无争议；但 agne 中转的 deepseek-reasoner 是否接受 reasoning_effort 参数需实测。
- 本地 google 端点是 gemini-3.6-flash——属 3.x 系（thinkingLevel）还是 2.5 系（thinkingBudget），决定映射表分支。
- 现有代码已收 reasoning_content——发侧参数（effort/thinkingBudget）当前完全没发，Q6 是纯新增。

## Q7 权限管理（分母 5：元宝缺失）

### 【共识】
- **单机单用户坚决不做 RBAC / 角色 / 管理员 / 用户表** —— 5/5。千问："只有你一个用户"；谷歌："RBAC 在单机版中均属于彻底的过度设计"。
- **能力开关三件套：允许传图片 / 允许传文件 / 允许编辑系统提示词** —— 5/5。
- **每席位 token 配额（数字上限）** —— 5/5。
- **过度设计共识**：多账号登录、角色表、ACL（5/5）；谷歌另判" Dollar Budget（按美元限额）不可行——各中转费率不同且动态变更，限制单次 max_tokens 才是防死循环烧 token 的物理手段"；豆包另判"文件系统沙箱过度（Electron 已有安全边界）"；千问另判"网络隔离过度"。

### 【分歧】
- **token 上限的粒度**（四家四个样）：
  - 谷歌：`maxTokensPerRequest` 单次请求上限（默认 4096，防模型死循环胡言乱语）；
  - 豆包：`maxSessionTotalTokens` 会话累计硬上限（null=不限）；
  - Gemini：`maxContextTokens` 软限制（触发截断策略，默认 8000）；
  - ChatGPT：三层都要——perTurn input/output + perSession 500k。
- **默认值反例分歧**：谷歌明确警告"50 席协同写长篇/超大工程分析时严禁锁死 4096 默认值，会拦腰掐断生产力"。

### 【独占硬货】
- ★★★（ChatGPT）**capability 与 policy 是两回事**："模型支持联网"是 capability（模型元数据），"这个席位允许调用联网工具"是 policy（席位配置）——混成一件事是常见设计错误；另加 allowModelSwitch（主持人席不许随便切模型）和 tools.mode: none/readonly/ask 三态。
- ★★（谷歌）"权限"的真实定位：不是安全而是**资源防火墙 + 行为边界**——防的是模型死循环烧 token，不是防人。
- ★（谷歌）开关要联动 UI：关掉 allowImages 就直接隐藏输入框"+"里的图片入口，而不是提交时报错。

### 【本地核对提示】
- 本地白名单外"设计性禁自动上传"已是权限雏形——新 perms 对象应把"自动上传白名单"收编为字段而不是旁路逻辑。
- 现状 API 格子只读无输入框，开关的 UI 联动（隐藏"+"入口）依赖 Q8 的输入框落地，注意实施顺序。

## Q8 对话界面布局（分母 5）

### 【共识】
- **绝不新开 Electron 独立子窗口**（50 个 BrowserWindow 卡死系统）—— 5/5。
- **绝不 50 个 Tab**（切换丧失"多 AI 齐头并进"的宏观掌控感；50 Tab 不可维护）—— ChatGPT、Gemini、豆包 —— 3/5。
- **输入框带 [+] 附件按钮 + 右侧固定 240px 参数栏**（上下文用量条/思考等级/模型选择器）—— 豆包、谷歌、ChatGPT（inspector 栏）—— 3/5，宽度数字一致。
- **50 席宫格靠滚动 + 分组折叠管理** —— 豆包、Gemini、千问 —— 3/5。

### 【分歧】★ 本题核心分裂：格子内切换 vs 独立对话面板
- **原地切换派（4 家）**：豆包（格子 webview⇄API 对话面板互斥，"不搞独立窗口体系，否则割裂分发甲板群发通路"）；Gemini（点击原地翻转扩展，反例是独立窗口和 Tab）；谷歌（原地无缝切换，左 75% 对话 + 右 25% 参数抽屉）；千问（卡片内部从只读摘要切到完整对话界面，CSS Grid）。
- **独立 Focus 面板派（1 家）**：ChatGPT 明确推翻原地切换——"格子高度变化/滚动位置/输入框抢焦点/webview 生命周期/chat state 最后 CSS 比独立 overlay 更复杂"；主张保留席位轻卡片总览 + 打开统一三栏 Focus Surface（左席位列表带搜索/分组/状态 + 中对话 + 右 inspector），且 9 个 webview 的 partition/登录态不动。
- **混合派（元宝，Q8 缺失但其总评有表态）**："宫格缩略 + 聚焦展开 + 右侧 inspect 混合，比纯原地互换更扛性能"。
- → 4 vs 1(+1)，但 ChatGPT 的反对理由（webview 生命周期、焦点管理）恰是原地派需要回答的。

### 【独占硬货】
- ★★★（豆包）**切换模式时必须销毁/移除 webview DOM 节点，不能只 `display:none`**——webview 极吃内存，隐藏不释放。
- ★★（ChatGPT）Focus Surface 与 9 个 webview 并存方案：Focus Overlay 是独立 DOM 层，原 grid 不销毁，webview 登录状态/partition 不受影响。
- ★★（谷歌）CSS Grid 过渡动画实现"原地放大"，DOM 结构复用度高。
- ★（千问）每格一个 Custom Element/组件，状态独立保持，切换视图不丢上下文。
- ★（ChatGPT）席位列表要有搜索 + 分组 + 最近使用 + 运行状态（50 席的导航不是 Tab 而是列表）。

### 【本地核对提示】

## Q9 附件协议差异（分母 5）

### 【共识】
- **统一 Attachment 抽象（type/mime/name/data），适配器层翻译成各协议格式** —— 5/5。
- **图片映射表三家完全一致**：OpenAI `image_url{url:data:base64}` / Anthropic `image{source:{type:'base64',media_type,data}}` / Gemini `inlineData{mimeType,data}` —— 5/5。
- **文本文件三协议统一做法：读取内容直接拼进 user message 文本** —— 5/5。
- **PDF 默认本地提取纯文本注入 prompt，不走二进制**（规避各家支持差异）—— 5/5。Gemini 用 pdf.js、谷歌用 pdf-parse；豆包给出条件开关：模型元数据标 supportPdfBinary=true 才传二进制。

### 【分歧】
- **PDF 二进制何时可直传**：
  - ChatGPT 最激进：OpenAI Responses `input_file` 已支持 PDF/DOCX/PPTX/XLSX；Anthropic 有 document block + Files API；Gemini inlineData 或 Files API（单文件 50MB/1000 页）；应按 capability 分流。
  - 豆包：元数据开关制（supportPdfBinary）。
  - 谷歌：一律不二进制；极端场景（扫描件/图纸）强制引导走 gemini-native 官方通道。
  - 千问：前端 pdf.js 提取文本或截图，不建议二进制。
- **抽象字段**：ChatGPT 主张附件为**独立实体**（attachmentId 引用，message 只存 id），其余四家为内联 data 字段。

### 【独占硬货】
- ★★★（ChatGPT）**50 席群发同一附件时不要每席复制一份 base64**：独立 Attachment 实体 + per-provider 上传一次拿 file_id 复用（OpenAI/Anthropic file_id、Gemini Files API）；**Gemini Files API 文件只保存 48 小时**，remoteId 必须带 expiresAt，不能当永久 ID。
- ★★★（谷歌）**表格密集/工程图纸/扫描件 PDF 提取纯文本=乱码**：表格错位、图片信息全丢——必须禁止低端席位盲目读取，引导投喂原生多模态通道（gemini-native）。
- ★★（豆包）大附件用完释放 Uint8Array 引用帮 GC；50 席同时加载 base64 会 OOM。
- ★（ChatGPT）附件实体带 sha256 + localPath，便于去重与缓存。

### 【本地核对提示】
- 现有 api-adapter.js 明确报 `UNSUPPORTED_FORMAT_FOR_API` 拒绝 PDF——Q9 共识（本地提取文本）正好补这个洞；4MB 上限各家均沿用，无冲突。
- 本地有 agne 中转——其是否透传 OpenAI file 上传接口存疑；file_id 复用方案在纯中转场景可能退化为每请求内联 base64。
- Claude/Gemini PDF 二进制支持需按实际接入模型实测（各家说法基于 2026 文档，版本敏感）。
