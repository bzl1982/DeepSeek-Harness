你提到的这个思路，本质上是在解决一个核心矛盾：**如何让运行在浏览器沙箱里的网页版 AI，安全地触达本地系统资源**。结合你提到的 DeepSeek Harness，这确实是一个很有价值的架构方向。Harness 的核心设计哲学是“一切皆插件”，其模型、工具、会话、沙箱等能力均由 Cordis 插件系统组合而成。这为“网页端调用本地工具”提供了天然的架构基础。下面我梳理几条可行的技术路线。

---

## 路线一：浏览器扩展 + 本地 MCP 网桥（推荐优先考虑）

这是目前与 Harness 插件生态契合度最高的方案。

**核心思路**：在浏览器侧安装一个轻量扩展，监听网页版 AI 的对话流（SSE），当检测到工具调用意图时，通过 **WebSocket** 转发给本地运行的 MCP 网桥服务，由网桥调用实际的本地工具（文件读写、Shell 执行、浏览器控制等），再将结果回传。

**关键组件**：

- **浏览器扩展**（Tampermonkey/ScriptCat 脚本或完整扩展）：负责解析 AI 回复中的工具调用标记，并通过 WebSocket 与本地服务通信。
- **本地 MCP 网桥**：一个常驻的本地进程（Node.js/Python 均可），对外暴露 WebSocket 接口，对内以 stdio 方式启动并管理多个 MCP Server 子进程。
- **MCP Server 池**：每个本地工具（或工具组）封装为一个独立的 MCP Server，通过 `mcp.json` 统一配置管理。

**与 Harness 的对接点**：Harness 本身就是一个 MCP 客户端，你可以将本地 MCP 网桥注册为 Harness 的一个 **MCP 工具提供者插件**。Harness 的工具系统本身就是插件化的，通过工具注册表暴露能力，因此新增一个指向本地网桥的 MCP 连接器即可让那 200+ 插件直接可用。

**优势**：改动最小，复用 Harness 现有的 MCP 生态；网桥进程可以复用同一套 `mcp.json` 配置。

**需注意**：需要处理异步时序问题——工具调用结果返回前，Agent 可能已经继续生成，导致“幻觉”。`fusion-mcp-proxy` 的做法是在代理层运行 Agent 本身，确保工具同步执行完毕后再让 Agent 继续。你也可以选择在浏览器侧做“等待工具结果后再继续”的流程控制。


## 路线二：WebAssembly 沙箱化本地工具（更彻底的方案）

如果希望网页端**不依赖常驻本地进程**，或者对安全性有更高要求，可以将工具编译为 WASM 模块，直接在浏览器内运行。

**核心思路**：将本地工具用 Rust/C++ 编写，通过 Emscripten 或 wasm-pack 编译为 WASM，利用浏览器原生 WASM 引擎执行。Mozilla 的 `wasm-agents-blueprint` 已经验证了这条路线：通过 Pyodide 在 WASM 中运行 Python Agent SDK，配合 Web Worker 中的 WASM 沙箱提供 Shell、Python 和文件系统能力。

**与 Harness 的对接点**：Harness 的插件系统支持将任意能力封装为插件。你可以创建一个 **WASM 工具运行时插件**，在 Harness 的沙箱插件层中注册一个 WASM 实例管理器和工具调度器。当 Agent 需要调用某个本地工具时，插件将请求路由到对应的 WASM 模块。

**安全机制**：WASM 天然提供沙箱隔离，但需要额外实现**能力白名单 API**——只允许 WASM 模块访问明确授权的系统能力（如特定目录的文件读写、特定端口的网络访问），并支持授权撤销。

**优势**：零本地安装依赖；沙箱安全性可形式化验证；适合多用户/多租户场景。

**局限**：工具需要重新编译为 WASM；对系统级操作（如进程管理、硬件访问）的支持有限；Harness 的 200+ 插件若原生是 Python/Node 实现，迁移成本较高。


## 路线三：本地反向代理 + Harness Headless 模式

如果 Harness 的 200+ 插件已经以原生进程形式存在，最直接的方案是让 Harness 本身以 **Headless 模式**运行在本地，网页版 AI 通过反向代理调用 Harness 的 API。

**核心思路**：在本地启动 Harness 的 Headless 实例（Harness 本身就提供了 Headless Bundle 用于一次性任务运行器），对外暴露一个受鉴权保护的 HTTP/WebSocket 接口。网页版 AI 的浏览器扩展将工具调用请求转发到这个接口，由 Harness 在本地调度其全部插件完成执行。

**与 Harness 的对接点**：这几乎是“零改动”方案——Harness 已有的插件体系、工具注册表、Agent Loop 全部在本地运行。你只需要在网页侧增加一个**适配器**，将网页 AI 的工具调用意图翻译为 Harness 的 API 调用。

**参考实现**：`Chat-Plus` + `MCP-Gateway` 的组合就是这个思路的简化版——MCP-Gateway 在本地汇聚工具，Chat-Plus 浏览器扩展把工具能力“注入”到网页 AI 对话中。你可以把这个模式升级为 Harness Headless + 自定义适配器。


## 建议的落地路线

如果让我给一个优先级建议：

1. **先走路线一**，用 `fusion-mcp-proxy` 或自建 WebSocket 网桥快速验证“网页端触发本地工具”的闭环。这一步的产出是一个可工作的 Demo，能明确异步时序、鉴权、结果回传等关键问题的解决方案。

2. **同步推进 Harness 的 MCP 工具提供者插件开发**，把网桥注册进 Harness 的工具系统。Harness 的工具注册表是插件化的，新增一个 MCP 连接器插件不需要改动核心循环。

3. **对安全敏感的工具考虑 WASM 化**，特别是那些涉及文件系统或网络访问的工具。WASM 的沙箱隔离 + 能力白名单 API 可以作为 Harness 沙箱插件的一个执行后端。

4. **最终形态**：浏览器扩展负责“网页 AI ↔ 本地”的通信桥接，Harness Headless 负责“本地工具调度与插件管理”，WASM 沙箱负责高风险工具的隔离执行。三层各司其职，Harness 的 200+ 插件通过统一的 MCP 接口暴露给网页端。

你目前接入 Harness 客户端后，网页版这边是计划用浏览器扩展来桥接，还是打算在 Harness 侧写一个 Web 入口插件？这会影响路线一和路线三的具体取舍。
